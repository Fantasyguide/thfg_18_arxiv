## 1. th128 妖精大战争 —— 冻结机制

- **正身**：`ChargeAttack::on_tick` `th128:0x40eaa0`。每帧扫弹池（`BULLET_MANAGER+0x64`，2000 项 × `0x11b8`），
  按 `th128:0x9d8`/`+0x9dc` 推出的**冰格坐标**做八邻域探测（`th128:0x40fc60`，格子表 `charge+0x65a20`、
  每格 12 字节、8×10），命中就在**这发弹的位置**造冰节点（`th128:0x410590`）并把弹**改造/吃掉**
  （`th128:0x407fb0`）；档位 1–5 由冰强度 `charge+0xa00` 与四个 float 阈值决定，各档跑不同的**原生 anm 脚本**
  （`0x15/0x19/0x21/0x31/0x41`，脚本指针 `th128:0x4b1ef8` 等）。激光池同样处理。
- **不是**：全局时间停止、也不是把弹速写 0。（曾经的最大嫌疑 `GameThread+0x60` bit 10 已被证否：
  **全镜像没有产生者**，见 §7。）
- **能否搬**：🟡。可搬的是**配方**（每帧池扫描 + 邻域/半径判定 + 生成节点 + 消费弹 + 档位选脚本）。
  TH18 侧需要的是：弹池遍历（已有反汇编基础）、"把弹换成别的实体"的入口、按脚本号起 anm（`get_vm_with_id` ✔）。
- 详情：[`photo-and-freeze-mechanics-recon.md`](photo-and-freeze-mechanics-recon.md) §11–§18。

## 2/3. 拍照机制（两作）

- **th095**：`PhotoManager::on_tick` 真身 `th095:0x42ad60` 双循环（11 项 × `0x2214`、6 记录 × `0x2cc`，第二段 `+0x10c8`）；
  记录处理器 `th095:0x43a600` 是**解释器**（指令 = `{int16 操作码, …, int16 帧}`，操作码上界 88、
  表 `th095:0x43e87a`；计时器 `[rec+0x58]`、指令流 `[rec+0x240]`、状态位 `[rec+0x228]`）；
  全局 `th095:0x4bded8` 是**每记录可覆盖的时间倍率**。
- **th165**：`PhotoManager::on_tick` `th165:0x440a30` 是薄壳 → 真身 `th165:0x43ec10`；
  **35 状态号**经 `th165:0x43f47c`（35 字节）重映射到 **5 项**跳转表 `th165:0x43f468` 的处理器；
  公共处理器 `th165:0x43f153` 只做"状态号 ++"，收尾处理器 `th165:0x43f0f4` 收 VM 并关掉照片标志。
- **★ 判定/评分不在 tick 里**（负结果）：两作的 tick 都只做**演出**；th165 侧 15 个 call 目标里没有一处数敌人/算分。
  ⇒ 卡要做"拍照得分"**必须自己写评分**，只能照搬演出外壳。
- **能否搬**：🟡 配方三件套 —— ① 记录级脚本 VM + 帧驱动 + 可覆盖倍率；② 状态号→处理器分派（"35→5"很省）；
  ③ 薄壳 tick + 位闸的挂法。**都不能整块搬**（TH18 无 `zPhotoManager`、无全局时间倍率）。
- 详情：同上一份 recon 文档 §9–§21。

## 4. th185 全卡搬入

**输入侧已经齐了**（这是本轮最大的收获：**不用逆向就有清单**）：

| 需要的东西 | 出处 |
| --- | --- |
| 卡名 / 说明 | `th185.dat` 内的 **纯文本 `ability.txt`**（86 段 = **85 张** + NULL） |
| id / 内部名 / 类别 / 购买上限 / 出现规则组 | **卡表 `th185:0x4ca374`，87 行 × `0x44`**（全表已抽成素材） |
| 商店版面 | `cardpos.txt`（`x, y, 倾角`，5 个一组） |
| 卡图 | `abcard.anm`（**185 entry** 装 85 张卡） |

**三项前置**（缺一不可）：

1. **卡图 entry 容量**（🟢 已有解）：TH18 侧现有 `164/256`，剩 46 张；若按"每卡 2 格"搬 85 张需 170 格 ⇒ 放不下。
   解法 **①**：把每卡的大图/小图**并进一个 entry**（一 entry 两 sprite，**原生合法且是构建器预告过的退路**）
   ⇒ `164+85 = 249 ≤ 256` ✅，卡数上限从 69 抬到 138；工作量为 `cards.js` 卡图索引格式改造。
   解法 ②：另开 anm 槽（贴图键 `(槽号<<8)|entry`，槽号上限 33）；代价是分发侧要能往 `th18.dat` 加文件（未证）。
2. **号段**：见 §6（>128 已可安全打通）。
3. **逐卡效果**：85 张里 **51 张与 th18 同名**（可对 th18 现成实现移植）、**34 张独有**（要从零读 th185 卡类代码）。
   ⇒ 这是**唯一还没做完**的大块（"每张卡的数值/贴图/动效/脚本号"）。

- 详情：[`../card/th185/README.md`](../card/th185/README.md) §1–§14。

> **落地**：th185 的搬迁实施计划（分族配方 + 号段/容量 + 顺序 + 风险）见 [`../card/th185/PORT-PLAN.md`](../card/th185/PORT-PLAN.md)。

## 5. th185 货币（弹货）

- 钱：`th185:0x4d1074`（收 `th185:0x40a9eb` / `th185:0x412c2e`，支 `th185:0x41ee2d`，清零 `th185:0x40ed69`）。
- **渐进定价**：`price = T(n+1)·(base − w·k) + w·k`，`T(n+1) = ((n+1)n)/2 + 1`（`n=0` 时 `price = base` 自洽 ✅）；
  `n` = 已购计数 `AM+0xec8+id*4`，`w` = 类别权重（`th185:0x4b59c0`：1–9→5、10–14→10），`k = AM+0x2c`。
- 货架：`shop+0xa44` 存 **`row − 4`**，价格数组 `shop+0xe44`（`0` = 无货），货架由 RNG 从候选里挑。
- 上架三闸：已购计数 < `row+0x18`、解锁字节 `[th185:0x4d7c48 + id + 0x26570] ≠ 0`、出现规则组 `row+0x14`（11 条规则）。
- **能否搬**：🟢。结构与收/支/判定都有确切出处。⚠ **别复用 TH18 的 `MONEY`（`th18:0x4ccd34`）** ——
  它**同时是计分乘数**，而 th185 这只只服务市场。
- 仍缺：**基准价的具体数值**（`row+0x3c` 镜像里全 0，运行期才填；下轮取法见 th185 文档 §13.3）。

## 6. 卡表 id > 128（TH18 侧）

- 引擎侧 **id 是 32 位、无位域**：`allocate_new_card` `th18:0x411460` 用 `jmp dword [ebx*4 + th18:0x412dac]`；
  图鉴 id 数组是 dword（`th18:0x414970` 的 `lea esi,[esi+4]`）。
- **真断点**：图鉴条目数 `num_total_cards = 56 + N` 有 **两处 `cmp r, imm8`**（`th18:0x4145e2` `83 f8 38`、
  `th18:0x4157cb` `83 fa 38`）—— `imm8` 符号扩展 ⇒ **N ≥ 72 就整表空**（不是少几项）。
- **修法**：把 `cmp`+其后的 `jl` 当整体换 `e9 rel32`（9 字节 / 5 字节两种现场）进 cave，
  cave 里用 imm32 比后跳回。逐字节方案见
  [`../card/th18/10-extensibility-limits.md`](../card/th18/10-extensibility-limits.md) §8.6。
- ⚠ 另一条**必须先加**的东西：`th18:0x411479` 的守卫被改成 `83 fb fe`（`cmp r,imm8`，符号扩展）后
  **已经不是上界了** ⇒ id ≥ 255 时引擎不拦、会写坏内存（`owned[255]` 越对象、
  `[jt + 255*4]` 越 cave）⇒ **运行期护栏必须由 mod 自己加**。

## 7. 明确**证否/排除**的东西（省得后人再走一遍）

| 曾经的假设 | 结论 | 证据 |
| --- | --- | --- |
| th128 的冻结 = `GameThread+0x60` bit 10 | ❌ **全镜像没有产生者**（字面 or/and × 三种宽度、`bts` 位号、寄存器掩码、别名 `lea` 五条路全 0） | recon §15–§17 |

### 9.2 两条订正（记录在案，避免后人沿用旧说）

1. **"引擎按卡 id 判定"要收窄**：`th185:0x4ce400` 一类**不是卡 id 位图**，而是某全局对象
   （基址 `th185:0x4ce3f0`）的**位域字段**（§40）；真正按 id 特判的是**商店区的 5 张卡**（§42，9 处真命中）。
2. **"引擎侧消费点"改判为"卡与卡协作"**：`th185:0x40ae70` / `th185:0x40aee0` 是 **`MAINSHOT_SP` 这张卡自己的两个槽方法**，
   不是引擎代码 ⇒ "存量/次数"类效果在 TH18 侧要**成对移植（发布方 + 消费方两张卡）**（§70/§13.2）。

### 9.3 方法与工具上的沉淀（可复用到其它 exe）
