## 6. 工具配方（本轮踩过的坑，下一轮直接用）

**金矿 `type-structs-own.json` 的形状**（三作同形）：顶层是 **`dict`：结构体名 → 成员表**，
成员表是 **`[[offset, 成员名, C 类型], …]`**（`offset` 是 `'0x..'` 字符串，最后一条常是 `['0x..','__end',None]`）。
⇒ 读字段表要**按这个形状遍历**（别按 `{name, addr, members}` 那套猜，本轮猜错过一次）：

```python
d = json.load(open("local/vendor/th-re-data/data/<ver>/type-structs-own.json", encoding="utf-8"))
for off, name, typ in d["zBullet"]:            # ← 结构体名做键
    print(off, name, typ)
```

**已确认存在的结构体（可作下一轮起点）**：TH12.8 有 `zBullet` / `zBulletManager` / `zPlayer`（冻结要在这三个里找）；
TH09.5 有 `zPhotoManager` / `zPhotoManagerArrayItem`；TH16.5 有 `zCamera` / `zCameraSky` / `zPhotoManager`。
最后一条常是 `['0x..','__end',None]` ⇒ 它就是对象大小（别当字段读）。

**汉化 exe 与本作的关系**：`th095c.exe`（700416 B）/ `th128_CN.exe`（752640 B，与日文同尺寸）是**另一版**

## 10. 轮 4：文花帖照片记录的**布局算术自证**（一手）

继续读 `th095:0x42ad60` 的内层循环体（一手反汇编）：

```
42ada1  edx = i * 0x2214                      ; 项步长（= zPhotoManagerArrayItem 大小）
42adb0  ecx = mgr + 0x44 + i*0x2214           ; +0x44 = __array 基址（与金矿字段表一致）
42adb7  edx = j * 0x2cc                       ; 子记录步长
42adbf  call th095:0x43a600                   ; ← 第一段（项内 +0）
42add3  edx = mgr + 0x44 + i*0x2214
42ade0  ecx = edx + j*0x2cc + 0x10c8          ; ← 第二段（项内 +0x10c8）
42ade7  call th095:0x43a600                   ;   同一个函数
```

**算术自证（三条，全部相等 ⇒ 布局成立）**：`0x2cc × 6 = 0x10c8`（一段 6 条记录）；
两段 = `0x2190`；项大小 `0x2214 − 0x2190 = 0x84`（项内的头/尾）。

⇒ **`zPhotoManagerArrayItem` = `0x84` 头/尾 + 两段 × 6 条 `0x2cc` 记录**，`zPhotoManager.__array` 有 **11 项**。
🟡 解释候选（待下一轮证伪）：11 项 = 11 个关卡/场景；每项两段 = 「本次照片 / 最佳照片」（或「照片 / 快照」）；
每段 6 条 = 每关可拍的 6 次机会（文花帖的"每关多拍"）。**不猜定**，要靠内层函数读出来。

**每条记录的被调函数 `th095:0x43a600`（金矿未命名）一手**：`sub esp,0x400` 大栈帧；

## 17. 轮 11：bit 10 的两条路**都断了**，`GameThread+0x60` 的写入端全镜像封口（一手）

§16 留了两条路：① 别名指针（`lea`）；② 动态置位（`th128:0x4274e5` 的 `ecx`）。本轮把两条都走完，
**结论是负结果 + 一个封口**：`th128.v1.00a` 里**没有任何代码产生 bit 10**。

### 17.1 路 ①（别名）：全镜像 **0 命中**

发现：用 capstone 5.0.7 线性反汇编全部可执行节，检索 `lea reg,[imm32]` 且 `imm32 == th128:0x4b8954`
（`GAME_THREAD_PTR`）—— **0 命中**。
结论：**这个全局从不取地址**。代码一律 `mov eax,[th128:0x4b8954]` 后直接用 `[eax+0x60]`，
不存在 `lea reg,[gamethread+0x60]` 这条别名路（可信度 🟢，方法：全节线性扫描）。

### 17.2 路 ②（动态）：`th128:0x4274e5` 的 `ecx` = **1**，不是位掩码

发现（一手反汇编）：

```asm
th128:0x4274e0  mov  ecx, 1
th128:0x4274e5  add  dword ptr [eax+0x60], ecx
th128:0x4274e8  add  dword ptr [eax+0x64], ecx
th128:0x4274eb  ret
```

结论：这是 **帧计数器对**（`+0x60`/`+0x64` 同步自增 1），不是置位器。要凑出 bit 10 得自增 1024 次，
说不通 ⇒ **动态置位路也不成立**（可信度 🟢）。

### 17.3 封口：全镜像立即数普查（这张表建议长期留着）

发现：全节扫描「任何操作数里出现立即数 `0x400`」—— **全镜像只有 7 处**，逐处归属如下：

| 地址 | 形态 | 归属 |
| --- | --- | --- |
| `th128:0x4060f2` | `cmp dword [ebx+0x28], 0x400` | 比较，非位操作 |
| `th128:0x408db6` | `test dword [eax+0x60], 0x400` | **§12 的读端**（弹更新闸） |
| `th128:0x409e05` | `cmp ecx, 0x400` | 比较 |
| `th128:0x415a45` | `test edx, 0x400` | **§17.4 的第二读端** |
| `th128:0x41af4a` / `th128:0x41af76` / `th128:0x41c11a` | `add edx, 0x400` 后 `imul`/`sar 0xb` | 定点乘法凑整（除 2048），与位无关 |

另外两条独立普查：
- `mov r32, 0x400`（把掩码装进寄存器再 `or [reg+0x60]` 的形态）：**0 命中**；
- 对 `[reg+0x60]` / `[reg+0x61]` 的**任何写点**：**6 处**，逐处都不是 GameThread
  （`th128:0x40585f` / `th128:0x405c89` 是把栈参数批量填进某个 `+0x50..+0x98` 的结构体，
  `th128:0x4061cb` / `th128:0x4061cf` / `th128:0x4061d3` / `th128:0x410585` 基址是 `ebp`/`esi`/`edi`，与 §16 的访问点无一重合）。

**★ 结论（本轮的封口）**：bit 10 **在镜像里没有产生者**（字面 `or`/`and`、字节/字/双字三种宽度、
`bts/btr` 位号、寄存器掩码、别名指针五条路全 0）。⇒ 只有两种解释：
1. **数据驱动**（掩码来自内存表，立即数扫描看不见）；
2. **本 build 里是死位**（读端留着，写端被裁掉/从未接线）。

两种解释都不利于「把 bit 10 当冰冻结的挂钩点」这一设想 ⇒ **§12/§16 的 bit 10 假设到此降级为 🔴 不可用**，
冻结必须去玩家射击路径找（下一轮的既定转向，不再回头纠缠这个位）。

### 17.4 顺手确认的两个一手事实

- **第二读端** `th128:0x415a34`：`mov eax,[edx+0x60]` → 依次 `test cl,1`、`test dl,2`、`test edx,0x400`，
  三者都走同一条「不满足就 `call th128:0x4158f0`」的短路链。⇒ 这个位域是**真的被 ≥2 个子系统消费**的
  通用更新门（不是冰专用），与 §16 末尾的 ⚠ 预警一致。
- **bit 10 到底跳过了什么**（§12 只说到 `call th128:0x408640`，本轮读进函数体）：`th128:0x408640` 是
  **单发子弹的更新步**——先累加 `[ebx+0x1198/0x119c/0x11a0/0x11a4]` 这组浮点累加器（含 `call th128:0x48fac0`），
  再 `test byte [ebx], 8` → `call th128:0x407fb0`。⇒ bit 10 置位 = **整批子弹的更新步被跳过**（全局全停），
  这更像暂停/演出用的总闸，**不是**「被我冻住的那颗弹不动」的逐弹语义。

### 17.5 陈旧负结果的第二次确认

和 `__end`）。⇒ 逐弹冻结标志**拿不到社区名**，只能从反汇编认。

宿主是 ECL 运行上下文而不是子弹 —— 别误用。）

## 18. 轮 12：★ **冻結的正身找到了** —— `ChargeAttack::on_tick` 的「冰格 flood fill」（一手）

转向生效：不再纠缠 §12/§17 的全局位，直接顺着**冰本身**（`CHARGE_ATTACK_PTR` = `th128:0x4b8938`，类型
`zChargeAttack*`，大小 `0x6b21c`）走，一轮就落到实现上。冻结**不是**"把弹停住"，而是**把弹吃掉换成冰格节点**。

### 18.1 定位过程（可复用）

`th128:0x4b8938` 的 19 处引用里，落在「每帧更新」区间的只有 `th128:0x40eaa0`（金矿名 `ChargeAttack::on_tick`）。
它同时引用 `BULLET_MANAGER_PTR`（`th128:0x40eae3`）和 `LASER_MANAGER_PTR`（`th128:0x40eeee`、`th128:0x40f416`）
⇒ **弹池和激光池都归它管**，这就是冻结的施加端。

### 18.2 主循环（一手反汇编，步长与池算术完全对上）

- 外循环头 `th128:0x40eac8`：沿 `charge+0x10` 走 **2 项、步长 `0x54`** 的槽位数组，每项 `call th128:0x4103d0`；
  2 个槽都空就继续往下（这一段是"冰种/弹壳"两槽）。
- **弹池扫描** `th128:0x40eaf7`：`ecx = [BULLET_MANAGER]+0x64`（弹数组基址）、计数 `0x7d0` = 2000、
  尾部 `th128:0x40eed3` 的 `add …, 0x11b8` ⇒ 与 §11 的池算术（2001 项 × `0x11b8`）**同源对上** ✓
- 逐弹活性筛选 `test byte [ecx], 1`（byte0 bit0）；再经 `[bullet+0x11ac]→+0x118` 分类
  （`==1` 直接跳过后处理，`==2` 要求 `[bullet+0x119c] >= 0x3c`）。
- **冰的格坐标**：`fld [charge+0x9d8]` / `fdiv [th128:0x4a6ba8]` → `call th128:0x48fac0`（浮点转整）
  得第一个坐标（`cmp …,7` 上限 7）；`fld [charge+0x9dc]` / `fdiv [th128:0x4a6ba0]` 同理得第二个（上限 9）。
  ⇒ **冰在一张 8×10 的格子上推进**。
- **八邻域探测**：对上下左右+四个斜角的 8 组坐标各 `call th128:0x40fc60`（参数：`edx` = 冰对象、
  两个格坐标、`[charge+0x9f8]` 这个 float），任一命中或"释放位"置位 ⇒ 进施加分支。

### 18.3 格子表与邻域探测（两个辅助函数的算术自证）

- `th128:0x65a20` = **格子表基址**（相对冰对象），cell 索引 = `3*(10x + y)` 个 dword ⇒ **每格 12 字节**、
  8×10 = 80 格 = `0x3c0` 字节。`th128:0x40fc60` 里 `cmp eax,7 / cmp ecx,9` 的越界判断与之一致 ✓
  探测内容：`[edx + 索引*4 + 0x65a20]` 非 0 才算"这里有冰"（`test ecx,ecx; je 失败返回`）。
- 结论：**这是一个显式格子数据结构**，不是"遍历弹表找相邻弹"。80 格 × 12B 的规模说明它是**短生命期的
  冰面/波纹**（每次蓄力释放铺一张），而不是长期全局态。

### 18.4 施加分支 `th128:0x40ece8`（这就是"冻住一发弹"的全部动作）

1. `fld [charge+0xa00]` —— **冰强度**（后面用来选档）。
2. `push 0 / push 0xc8 / push float / push edi`（`edi` = **当前这发弹**）→ `call th128:0x410590`
   ⇒ **在弹的位置上创建冰节点**（返回值 `esi` = 节点）。`th128:0x410590` 内部是"从 `charge+0x65a0c`
   起按 `0x68` 步长找空槽"，与 `charge+0x10c` 基址一起构成节点池。
3. `call th128:0x467ef0`（`charge+8` 处的一次查询）→ 把结果写进 `node+0x50`。
4. **吃掉这发弹**：`mov eax, [esp+0x10]`（弹指针）→ `call th128:0x407fb0`。该函数把
   `word [bullet+0xa2a] = 0` 并重建 `+0x1184/+0x1188/+0x118c/+0x1190/+0x1194` 这组**浮点累加器**
   （`+0x1190` 写入 `GAME_SPEED` 的地址 `th128:0x4b6f58`，`+0x1184 = 0xfff0bdc1` 是 ZUN 的
   quiet-NaN 哨兵值），`+0x1194` 置 bit0。
   ⇒ 这是"**把弹改造成另一种实体**"而不是单纯删除（对比 §17.4：弹更新里 `test byte [ebx],8` 后走的
   也是这个函数）。
5. **按强度选档**：`[charge+0xa00]` 依次与四个 float 常量比较 —— `th128:0x4a6b9c`、`th128:0x4a6b98`、
   `th128:0x4a6b94`、`th128:0x4a6b90` —— 得到 `node+0x58` = **1/2/3/4/5**；每档配套不同的
   **anm 脚本号与脚本指针**：`0x15`/`th128:0x4b1ef8`、`0x19`/`th128:0x4b1f50`、`0x21`/`th128:0x4b1fb8`、
   `0x31`/`th128:0x4b2040`、`0x41`/`th128:0x4b21c8`，经 `call th128:0x4106e0` 与
   `th128:0x407ec0`（取 anm VM，传入 `[charge+0x65ddc]`）落地 ⇒ **冰的视觉是原生 anm 脚本驱动**。
6. 收尾 `th128:0x40eee5`：`and dword [charge+0x6b1fc], 0xfffffffb`（清 bit 2 = 释放位，一次性）
   → 接着同一函数里再扫**激光池**（`[LASER_MANAGER+0x18]` 与计数 `+0x5fc`）⇒ **激光同样会被冻**。

### 18.5 ★ 结论：GFW 的「冻结」= 格子 flood fill + 弹被替换成冰节点

- **机制**：释放瞬间在弹/激光的位置上铺一张 8×10 的冰格，随后每帧对**整个弹池**（2000 项）逐发探测
  八邻域，**与已有冰格相邻的弹就被"吃掉"并原地生成一个冰节点**（档位 1–5 由冰强度 `charge+0xa00`
  与四个阈值常量决定，档位决定 anm 脚本）。
- **不是**：全局时间停止（§17 的 bit 10 因此本来就无关）、也不是给弹写速度 0。这也解释了为什么在
  弹更新/`GameThread` 里怎么找都找不到"冰"的写入端 —— **写入端根本不写全局，它写的是弹自己**。
- 可信度：🟢 结构层（弹池步长/计数与 §11 独立对上、格子表算术自证、档位与脚本号一手）；
  🟡 细节层（"八邻域命中"与"释放位"两条进入施加分支的条件谁主谁辅、`charge+0x9f8` 半径比较的确切语义、
  节点槽池 `0x68` 步长的容量上限，均未读全）。

### 18.6 对「能不能做进 TH18」的直接含义

- 可移植的是**配方**而不是字节：每帧遍历弹池 → 八邻域/半径判定 → 在弹的位置生成节点 → 消费该弹 →
  节点按档位跑原生 anm。TH18 侧要确认的三件事（下一轮）：① 弹池基址/容量/步长（TH18 的
  `zBullet` 池）② 有没有"把弹换成别的实体"的原生入口（对应 `th128:0x407fb0`）③ 我方卡里能否按脚本号
  起 anm VM（TH18 有 `AnmManager::get_vm_with_id` 一线，§7 已登记）。
- 另注：冰的**档位阈值是 float 常量**（`th128:0x4a6b9x` 四个），若要复刻手感必须先读出这四个数与
  `charge+0xa00` 的量纲关系 —— 这是纯数据、下轮一读即得。

## 19. 轮 16：★ 文花帖的"照片"= **每条记录一个 88 操作码的脚本 VM**（一手）

§10 只证明了**布局**（11 项 × 2 段 × 6 记录 × `0x2cc`）。本轮把**语义**读出来了 —— 而且它不是硬编码
C++，是一台**小虚拟机**。

### 19.1 双层循环（`PhotoManager::on_tick` 真身 `th095:0x42ad60`，一手）

```asm
th095:0x42ad83  cmp  [ebp-4], 0xb          ; 外层 i: 0..10  (11 项)
th095:0x42ada4  imul edx, edx, 0x2214      ; 项步长 0x2214
th095:0x42adb0  lea  ecx, [eax+edx+0x44]   ; 基址 = zPhotoManager + 0x44
th095:0x42ad9b  cmp  [ebp-8], 6            ; 内层 j: 0..5   (6 条记录)
th095:0x42adb7  imul edx, edx, 0x2cc       ; 记录步长 0x2cc
th095:0x42adbf  call th095:0x43a600        ; ← 第一条记录段
th095:0x42ade0  lea  ecx, [edx+eax+0x10c8] ; ← 第二条记录段（偏移 = 6×0x2cc）
th095:0x42ade7  call th095:0x43a600
```

⇒ §10 的布局算术**在代码里逐字复核通过**（11 × `0x2214`、6 × `0x2cc`、第二段 `+0x10c8`）✅

### 19.2 记录处理器 `th095:0x43a600` = **88 操作码的解释器**（一手）

```asm
th095:0x43a617  cmp  dword [eax + 0x240], 0   ; +0x240 = 指令流指针；0 ⇒ 直接返回 1（未启用）
th095:0x43a630  mov  edx, [ecx + 0x228]       ; +0x228 = 状态位域
th095:0x43a636  shr  edx, 0x11 / and 1        ; bit 17 置位 ⇒ 返回 0（本条记录**不跑**）
th095:0x43a659  shr  edx, 0x1d / and 1        ; bit 29 置位 ⇒ 把全局 th095:0x4bded8 写成 float 位型 3F800000h (=1.0f)
th095:0x43a671  movsx ecx, word [eax + 0x22e] ; +0x22e 是 int16 计数器；非 0 ⇒ 走 th095:0x43b377
th095:0x43a69f  movsx ecx, word [ptr + 4]     ; 指令的**帧字段**
th095:0x43a6a3  cmp  ecx, [rec + 0x58]        ; 与记录计时器 [rec+0x58] 比 ⇒ 未到帧就跳走（时间驱动）
th095:0x43a6af  movsx eax, word [ptr]         ; **操作码**（int16）
th095:0x43a6c7  cmp  eax, 0x58 / ja …         ; 操作码上界 **0x58 = 88**
th095:0x43a6da  jmp  dword [edx*4 + 0x43e87a] ; ★ 88 项跳转表
```

⇒ **照片记录是一条按帧推进的脚本**：指令 = `{int16 操作码, …, int16 帧}`，操作码表在 `th095:0x43e87a`
（88 项），记录计时器 `[rec+0x58]`，指令流指针 `[rec+0x240]`，状态位域 `[rec+0x228]`（已知 bit 0 会被清、
bit 17 = 禁用、bit 29 = 时间倍率覆盖）。

### 19.3 ★ 顺带找到"拍照时的顿帧"开关：全局 `th095:0x4bded8`（float）

进入处理器时先把 `th095:0x4bded8` 存进栈 (`[ebp-8]`)，若状态位 bit 29 置位就把它写成 **float 位型 3F800000h = 1.0f**，
函数出口再**还原**（`th095:0x43a70c`）。
⇒ 这是一个**每记录可覆盖的"时间倍率/速度"全局**（借用 §18 的词汇：和 GFW 的冰不是一回事，
但它就是文花帖里"拍下去的瞬间世界慢下来"那类效果的正身）。🟡 默认值由谁改成非 1.0、以及它被哪些子系统读，
**未读** —— 这是下一轮的第一件事。

### 19.4 对「能不能做进 TH18」的含义（本轮更新）

- **可移植的不是"拍照"这个玩法，而是这套"记录级脚本 VM"的配方**：
  每条记录 = `{指令流指针, 帧驱动器, 状态位域, 时间倍率}`，操作码表独立。
  TH18 的卡要复刻"文花帖"式的弹幕照片，最贴近原生做法的实现就是
  **在卡里建一个自己的小 VM（或直接用 TH18 的 anm/ECL 里现成的定时器机制）+ 一个可覆盖的速度全局**，
  而不是硬编码若干发弹。
- **TH18 侧的前置条件**（§7 已登记的遗留件）：`AnmManager::get_vm_with_id` 一线可用 ✔；
  但 TH18 **没有** `th095:0x4bded8` 这种"全局时间倍率"（§7 盘点：全局 `slowdown` 缺失）⇒
  若要做"拍照顿帧"，得自己加一个每帧生效的倍率并在弹/敌机更新里乘进去 ——
  这正好是 §18 里 GFW 冰格那条路的同型工作。
- **VD（th165）还没读**：`zPhotoManager` 在 th165 侧是 `0xd664`（不透明），本轮未动 ⇒ 下一轮读
  `th165` 的 photo tick，**核对它是不是同一台"88 操作码 VM"**（是 ⇒ 两作共用一套配方，移植成本减半；
  不是 ⇒ 分开处理）。这是判"拍照机制能不能搬"的最后一块拼图。
