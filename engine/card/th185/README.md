# th185（100th Black Market）的卡牌 / 货币系统 —— 侦察起点

> **结论总表**：本文的结论已收进 [`../../_shared/porting-verdicts.md`](../../_shared/porting-verdicts.md)（一页速查 + 实现路径）。


> **版本**：跨版本（本文主写 TH18.5 = th185 v1.00a，兼与 TH18 对照）。跨版本文档：**每个地址都带版本前缀**
> （`th185:` / `th18:`）。

**背景**：用户 2026-09-18 把 TH18.5 的 Steam 安装目录指过来，提出三件事：
① 能不能把 th185 的**全部卡**加进本仓的 TH18 卡牌 mod（`mods/th18.v1.00a/card-expand/`）；
② **货币（弹货）系统**能不能一并复刻；③ 为承载这些卡，卡表要扩到 **id > 128**（用户实测 >128 有问题）。
本文只做**第一手清点**：先把这个游戏里"卡/货币"相关的系统、全局和结构大小钉死，作为后续深入的路标。

## 1. 样本与一手来源（🟢）

- 样本：`local/th185.v1.00a/th185.exe`，md5 `234b1e6eb1cc1b8b0c6e490487cf191c`
  （原始位置 `D:\SteamLibrary\steamapps\common\th185`，只复制了 exe；`th185.dat` 等留在原处）。
- 版本：`readme.txt` 标 2022/08/14；exe 内含字符串 `1.00a` ⇒ 目录名按 `th185.v1.00a` 登记。
- 命名来源：`local/vendor/th-re-data/data/th185.v1.00a/`（ExpHP 金矿）。
  **金矿在这个版本上明显变薄**：`funcs.json` 58 条、`statics.json` 41 条、
  `type-structs-own.json` 36 个类型、`type-structs-ext.json` 89 个类型，
  且**没有** `zTableCardData` / `zCardBaseClass` / `zVTableCard` / `zAbilityMenu` 这些
  th18 侧已有的卡系统类型名 ⇒ **th185 的卡层没有被社区命名**，要自己认。

## 4. 三个待解问题（**下一轮直接从这三条切**）

1. **th185 有多少张能力卡？卡定义表在哪？**
   th18 侧是 `zTableCardData[]`，每项 `0x34` 字节、共 58 项（见
   [`../th18/07-registry.md`](../th18/07-registry.md)）。th185 侧对应结构**没有被命名**，
   要从 `AbilityManager` 的 tick/initialize 里反推表基址与项大小，**先拿到张数** —— 这个数直接决定
   "全部卡搬进来"的规模，也决定第 5 节那个问题的答案。
2. **货币字段在哪？**
   `zPermanentCardShop`（`0xe4c`）与 `zBlackMarket`（`0x1254`）的成员表在金矿里是**空白的**，
   只能反汇编认：钱是哪个偏移、什么类型（int32？）、扣款/加款的唯一入口是哪个函数、
   **跨局持久化**写进哪个存档结构（这是"复刻货币"的真正难点，不是画个 UI 就完）。
3. **卡 id > 128 的坏点**（与 TH18 mod 共通的题目）：
   若 th185 自己的卡数 **>127 且引擎跑得动**，那就**直接证明限制出在 mod 侧而不是引擎侧**；
   反之若 th185 的卡 id 也被压进 ≤7 位，就要找到那个位域的确切位置。**这一条是第 1 条的直接副产品**，
   所以顺序是：先数卡 → 再看 id 位宽。

## 5. 与 TH18 卡牌 mod 的关系（先记判断，别当结论）

- 同源是**事实**（同名 `AbilityManager`、同名 `zAnmVm`/`zGui`/`zUpdateFuncRegistry` 一族）。
- 但 `zAbilityManager` 大小不同 ⇒ **卡基类/虚表槽位必须逐字段核对**后才能谈移植（🟡）。
- "把卡搬过来"的实际工作量取决于**卡的效果是数据驱动还是代码驱动**：th18 侧已经证明是
  「`zTableCardData` 静态表 + 每卡一个 C++ 子类（21 槽虚表）」（见 [`../th18/01-object-model.md`](../th18/01-object-model.md)），
  若 th185 同构，则"加卡"= **搬数据 + 搬行为代码**，不是改几个数字。这条在下一轮用 th185 的
  `AbilityManager::on_tick`（`th185:0x408a40`）确认。

## 5. ★ 样本是 **SteamStub 包装版**，已脱壳（一手，**做 th185 任何反汇编前必须先做这一步**）

**发现**：`local/th185.v1.00a/th185.exe` 的入口点 `th185:0x57d310` **落在 `.bind` 节**（该节 `0x29900` 字节、
带 `CODE|EXECUTE` 标志），`.text` 字节熵 ≈ 8.0，**任何地址都反汇编不出合法指令** ⇒ 这是被
**SteamStub 包装**过的镜像（本仓另外 14 份样本的 EP 全部落在 `.text` 里，只有它一个例外）。

**处置**：用**本仓已有的** [`tooling/steamless`](../../../tooling/steamless/README.md)（Linux 上跑 Steamless）：

```bash
~/.dotnet/dotnet tooling/steamless/bin/Release/net8.0/steamless-linux.dll local/th185.v1.00a/th185.exe
# → local/th185.v1.00a/th185.exe.unpacked.exe（local/ 是 gitignored）
```

**判据（全部通过，逐条实测）**：

| 判据 | 包装版 | 脱壳后 |
| --- | --- | --- |
| 文件大小 | `1,053,440` | `883,200`（正好差 `0x29900` = `.bind`） |
| 入口点 | `th185:0x57d310`（`.bind` 内） | `th185:0x49003b`（`.text` 内）—— **与金矿 `_start` = `th185:0x49003b` 完全一致** |
| `.text` 熵 | ≈ 8.0 | `6.53` |
| 节表 | 含 `.bind` | `.text` / `.rdata` / `.data` / `.rsrc` |
| 符号对账 | — | 6 个金矿函数地址**逐个对上合法序言**（见下） |

符号对账明细（金矿地址 → 脱壳镜像里的序言）：`AbilityManager::operator new` `th185:0x408690`、
`AbilityManager::on_tick` `th185:0x408a40`、`BlackMarket::on_tick` `th185:0x41e150`、
`PermanentCardShop::on_tick` `th185:0x420150`、`AnmManager::get_vm_with_id` `th185:0x48a4a0`、
`WinMain` `th185:0x473950` —— 全部是 `push ebp / mov ebp,esp` 或 `push ebx / mov ebx,esp` 一类的
正常序言，**没有一处是垃圾字节** ⇒ **金矿的 th185 地址与脱壳镜像同源**，可以放心拿金矿当地图。

⚠ **不要用 md5 判等**：Steamless 会重建 PE 容器（零化 DOS stub、重排节头），代码段字节才是原生的。

## 6. ★ 卡表结构：**th185 有 87 个卡槽**，虚表步长 `0x5c`（一手，独立双证）

**手法**（可复用）：卡类构造器都会把自己的**虚表地址**写进对象首字段（`mov dword ptr [对象], imm32`），
所以**把"这类 immediate 的取值集合"统计出来**，就得到卡类虚表的地址集合，进而得到张数与步长。

| 版本 | 虚表地址集合 | 个数 | 步长 | 整除性 |
| --- | --- | --- | --- | --- |
| th18（对照） | `[th18:0x4b4c78, th18:0x4b6010]` | **58** | `0x58` | ✅ 整除 |
| th185 | `[th185:0x4b6ab0, th185:0x4b8998]` | **87** | **`0x5c`** | ✅ 整除 |

- **th18 侧自校准成立**：算法给出 58 个、基址 `th18:0x4b4c78`、步长 `0x58`，与本文 §1 已登记的
  「金矿 `VTABLE_CARD_*` 共 58 项、`VTABLE_CARD_NULL` 在 `th18:0x4b4c78`」**逐项吻合** ⇒ 方法可信。
- **th185 的第二条独立证据**：`.rdata` 里从 `th185:0x4b6ab0` 起，有 **87 行**「22 个 dword 全是 `.text`
  代码指针」的段，**行距正好 `0x5c`**，末行正好是 `th185:0x4b8998`
  （= th18 侧「基类虚表放在数组最后」的那条约定，`VTABLE_CARD_BASE_CLASS` 同形）✓
- **推论一**：th185 的卡槽是 **0–86**，比 TH18 的 0–57 多 **29** 个。
- **推论二**：卡基类虚表**多了 1 个槽**（`0x58 → 0x5c` = 22 → 23 slot）⇒ 想把 th185 的卡**行为**搬过来，
  必须按 th185 的槽位表重核（🟡 多出来的那一槽是什么，未读）。
- ★ **对 §4 问题 3 的直接含义**：**th185 自己的卡 id 只到 86，根本没碰到 127/128 边界**
  ⇒ 它**证明不了** >128 可行，>128 的断点仍然只能在 mod 侧（或 TH18 引擎侧）找。这条把问题 3 的
  调查范围**钉死在 mod 侧**，省掉一整条弯路。

## 7. ★ **货币（弹货）找到了**：`MONEY` = `th185:0x4d1074`（一手，🟢）

**手法**（可复用）：先扫三个商店函数的**绝对全局引用**（`BlackMarket::on_tick` `th185:0x41e150`、
`PermanentCardShop::initialize` `th185:0x41fb50`、`PermanentCardShop::on_tick` `th185:0x420150`），
再只在"**被加减、且和某个返回值比较**"的候选里挑 —— 钱一定同时有收、支、判定三种用法。

**判定链（三条互相独立，都指向同一个地址）**：

1. **收**：`th185:0x40a9eb`（`add dword [0x4d1074], edx`）、`th185:0x412c2e`（`add …, eax`）；
   另有 `th185:0x40ed69`（`mov dword [0x4d1074], 0`）一次性清零。
2. **支**：`th185:0x41ee2d`（**`sub dword [0x4d1074], eax`**）—— 在 `BlackMarket::on_tick` 的购买分支里。
3. **判定**：`th185:0x41e298` / `th185:0x41e316` 都是 `cmp dword [0x4d1074], eax` 后接
   `jge`（买得起才走购买/换货分支）。这个 `eax` 来自 **`th185:0x41f860`** —— 见下。
4. 另有两处阈值比较 `cmp dword [0x4d1074], 0x12c`（=300）：`th185:0x40aea5`、`th185:0x40ee20`。

### 7.1 **价格表**：`[shop + 0xe44]` 起的 dword 数组，项数 `[shop + 0xa40]`

`th185:0x41f860` = **算价函数**（一手反汇编）：

```asm
th185:0x41f860  mov  edi, ecx            ; edi = 商店对象（this）
th185:0x41f864  call th185:0x41f8a0     ; 先把货架刷新一遍
th185:0x41f869  mov  esi, [edi + 0xa40]  ; 项数
th185:0x41f86f  mov  eax, 0x1869f        ; 99999 = 哨兵初值
th185:0x41f878  lea  ecx, [edi + 0xe44]  ; 价格表基址
th185:0x41f880  mov  edx, [ecx]          ; 逐项取价
th185:0x41f882  cmp  eax, edx / jle …    ; 取最小值
th185:0x41f886  test edx, edx / cmovne eax, edx   ; **0 = 该槽无货，跳过**
```

⇒ 价格表 = **`[shop+0xe44]` 起、`[shop+0xa40]` 个 dword**，**0 表示该槽没货**（`test edx,edx; cmovne`
是"零价不算候选"的写法），函数返回**当前最便宜的非零价**（初值 `0x1869f` = 99999 哨兵）。
⇒ 所以"**买不起**"的判定 = `MONEY < 最便宜价`，这就是 §7 判定链第 3 条那个比较。

### 7.2 顺带排除的两个候选（🟡 未定，**不是钱**）

| 地址 | 引用 | 关键用法 | 判断 |
| --- | --- | --- | --- |
| `th185:0x4d1078` | 16 处 | `cmp dword [0x4d1078], 0x64`（=100）`th185:0x4126e6` | 疑为"已持有/进度计数"，与 `th185:0x4d107c` 成对比较 |
| `th185:0x4d107c` | 7 处 | 与 `th185:0x4d1078` 成对（`th185:0x41e3ef`、`th185:0x41d950`） | 疑为该计数的上限 |

两者都**没有**"被价格减"的用法 ⇒ 不是货币。0x100 的差值（100）与"100th"这个标题呼应，
但这是**推测**，未证。

### 7.3 对「复刻弹货货币」的含义

- 结构**极简**：一个 `.data` 全局（钱）+ 一张 dword 价目表（含"0=无货"约定）+ 一个扣款点。
  TH18 侧本来就有 `MONEY`（`th18:0x4ccd34`）与整套商店/金钱系统（见
  [`../th18/05-shop-and-money.md`](../th18/05-shop-and-money.md)）⇒ **复刻货币不是新机制**，
  而是"换一套价目表与入口"。
- **但语义不同，必须分开**：TH18 的 `MONEY` **同时是计分乘数**（`../th18/05 §2`），
  而 th185 这只 `MONEY` 只服务于市场（与价格比较、扣款），**没有看到计分/火力换算**。
  若两者共用同一个全局就会互相污染 ⇒ 实现上应当**另开一个货币字段**，不要复用 `th18:0x4ccd34`。
- 未做：**跨局持久化**（钱/已买断的永久卡是否写进存档、写在哪）—— 这是下一步第一件事。

## 8. ★★ 卡表正身：`th185.dat` 里有一份**纯文本卡表** `ability.txt`（一手，本轮最大收获）

**发现**：把资源档解开（`tooling/thtk/build/thdat/thdat -x d th185.dat`，**284 个文件**）后，里面有
**`ability.txt`**（23125 字节，cp932/CRLF）—— **ZUN 随游戏发行的纯文本卡表**：
每张卡一段，段首是 `@内部名`，下一非空行是卡面显示名，其余是该卡说明文。

⇒ **"th185 有哪些卡"这个问题不需要任何反汇编**：`ability.txt` 里 **86 段**，末段是 `@NULL`
⇒ **85 张实体卡**（内部名 + 显示名 + 说明文全在）。全表索引（源码素材）见
[`_sources/ability-txt-index.md`](_sources/ability-txt-index.md)；说明文正文属版权文本，留在 `local/` 不入库。

### 8.1 与 §6 的虚表算术**闭合**（两条独立证据互相印证）

| 版本 | `ability.txt` 段数 | 虚表条目（§6 实测） | 闭合式 |
| --- | --- | --- | --- |
| th18 | **56**（首 `EXTEND`，末 `MAGATAMA2`，**无 NULL 段**） | **58** | 56 实体卡 + id 56 NULL + id 57 BASE = 58 ✅ |
| th185 | **86**（首 `EXTEND`，**末段 `NULL`**） | **87** | 85 实体卡 + id 85 NULL（有段）+ id 86 BASE = 87 ✅ |

⇒ 两作都是"**实体卡 + NULL + BASE = 虚表条目**"，且 **th185 比 th18 正好多 29 张**（85 − 56）
—— 与 §6 里"虚表条目 87 − 58 = 29"**完全对上**（🟢 双证）。

### 8.2 对「把 th185 的全部卡搬进来」的直接含义

- **卡的内容（名称/说明/内部名）已经到手**，无需解密、无需逆向：直接读 `ability.txt`。
- **还缺的是"每张卡的效果怎么实现"** —— 那在代码里（th185 的卡类），而 th185 金矿**没有**卡类命名
  （§1），所以"效果语义"仍要逐张反汇编；但**卡的"清单与归属"这一层已经不用猜了**。
- 内部名与 th18 侧高度同形（都从 `EXTEND` / `WARP` / `ITEM_CATCH` / `MAINSHOT_PU` 这一族起），
  说明两作卡表**同一套命名约定** ⇒ 做"逐张对照表"（th18 id ↔ th185 内部名）是纯文本工作，成本很低。
- **价格**不在这份文本里（`ability.txt` 只有名与说明）；th18 的价格表是 `th18:0x4b35c4` 的 15 档
  （见 [`../th18/08-catalog.md`](../th18/08-catalog.md) 抬头），th185 侧的价格要另找（§7 已知运行期价目表在
  `[shop+0xe44]`，但**填表来源**未定位）—— 这是下一轮的价格线。

### 8.3 顺带确认的两件事

- **`abcard.anm` 在 th185 里也在**（与 th18 同名）⇒ 复刻"卡图"时两作可以照同一条路走；
  但 §8.8（[`../th18/10-extensibility-limits.md`](../th18/10-extensibility-limits.md)）那条
  "entry 号 8 位"的容量墙仍在，**85 张卡要多少 entry 必须先算**。
- th185 的 anm 查表惯用法（本轮一手）：`movzx eax, dl / imul r, 0x5c / sar esi,8 / [base + esi*4 + 0xe0]`
  —— **低字节 = entry 索引（步长 `0x5c`）、高字节 = 槽/文件索引**，与 th18 的 `th18:0x486d38` 一族同形

### 9.1 逐指令还原（一手）

```asm
th185:0x41f8be  lea  ebx, [eax + 0xe44]      ; ebx → 价格数组
loop i < [shop+0xa40]:
th185:0x41f8d0  mov  edi, [ebx - 0x400]      ; ★ 货架数组在 shop+0xa44，与价格数组相距 0x400
th185:0x41f8d9  mov  edx, [th185:0x4d7ab8]   ; edx = AbilityManager
th185:0x41f8df  mov  eax, [edi + 4]          ; 卡的 id
th185:0x41f8e2  mov  ecx, [edx + eax*4 + 0xec8]   ; n = 该 id 的**已购/持有计数**
th185:0x41f8e9  mov  eax, [edi + 0x10]       ; 卡的**类别**
th185:0x41f8ec  mov  esi, [eax*4 + th185:0x4b59c0] ; w = 类别权重（静态表）
th185:0x41f8f6  imul esi, [edx + 0x2c]       ; w *= k（AbilityManager+0x2c 的全局倍率）
th185:0x41f8fd  mov  ecx, [edi + 0x40]       ; base = 卡的基准价
th185:0x41f900  sub  ecx, esi                ; base - w·k
th185:0x41f8f3  lea  eax, [ecx+1] / imul eax,ecx / sar eax,1 / inc eax
th185:0x41f908  imul eax, ecx                ; T · (base - w·k)
th185:0x41f912  add  eax, esi                ; + w·k
th185:0x41f914  mov  [ebx - 4], eax          ; ⇒ 写回价格数组
```

⇒ **定价公式**（`n` = 该卡的已购计数，`w` = 类别权重，`k` = `[AbilityManager+0x2c]`，`base` = 卡自带基准价）：

```
T(n+1) = ((n+1)·n)/2 + 1        （n = 0,1,2,3… ⇒ 1, 2, 4, 7, 11, …）
price  = T(n+1) · (base − w·k) + w·k
```

★ **自洽校验（这条最有力）**：`n = 0` 时 `price = base` —— **第一次买正好是基准价**，
与"基准价"这个名字完全吻合 ⇒ 公式读对了（🟢）。买第二张同卡就翻倍（`2·base − w·k`），
第三张 ≈ 4 倍 …**这就是 th185 的"渐进定价"**，也是它和 TH18 商店（固定几档价、`th18:0x4b35c4`）
**最本质的区别**。

## 11. 卡表的**上架规则**与字段精修（一手，轮 20）

### 11.1 上架要过三道闸（一手）

`th185:0x41cdb0` 是"**逐 id 试上架**"的函数（`edi` = id 循环变量），它按顺序查三样：

```asm
th185:0x41cdf7  mov edx, [AM + edi*4 + 0xec8]   ; n = 该 id 的已购计数
th185:0x41ce03  cmp [row], edi ...（查表取行）    ; 行基址 th185:0x4ca374，步长 0x44
th185:0x41ce27  cmp edx, [row + 0x18] / jge 跳过  ; ★ 闸 1：n < 购买上限（row+0x18）
th185:0x41ce5e  cmp byte [th185:0x4d7c48 + edi + 0x26570], 0 / je 跳过
                                                  ; ★ 闸 2：该 id 的「已解锁」字节非 0
th185:0x41cec4  call th185:0x41cce0               ; ★ 闸 3：出现规则组
```

**闸 3 的正身** `th185:0x41cce0`（一手）：它按 `[ecx + 0x18]`（= **`row + 0x14`**，因为传进来的是 `row − 4`）
做 **0..0xa（11 个分支）的跳转表**，分支里读全局 `th185:0x4d1024`（关卡/进度号）并与常量比，
其中一支还 `call th185:0x402800` 后 `div 5` 取余 ⇒ **RNG**；最后一支 `call th185:0x417f10([ecx+4])`
（参数 = `row + 0x00`，即 **id**）。
⇒ `row + 0x14` = **出现规则组（0–10 共 11 条规则）**，这就是 th18 那句
"`CardData__is_available_at_stage` 返回 0/1/2"（[`../th18/05-shop-and-money.md`](../th18/05-shop-and-money.md) §5）
在 th185 侧的对应物 —— **形状不同**（th18 是一个函数按关卡判，th185 是一张"规则组→判定"的跳转表）。

### 11.2 字段表精修（覆盖 §10.2 的两格）

| --- | --- | --- |
| `+0x14` | **出现规则组** 0–10（11 条） | `th185:0x41cce0` 的 `cmp eax,0xa / ja` + 跳转表 `th185:0x41cd84` |

### 11.3 顺带解开的"默认行"算术（一手，可复用）

查表失败时那几处回退地址（`th185:0x4cba04` / `th185:0x4cba14` / `th185:0x4cba18` / `th185:0x4cba20` / `th185:0x4cba28`）看着零散，

## 14. ★ 卡图容量：**th185 自己就是"一个文件装 85 张卡"的活证据**（一手，轮 22）

这是"全卡搬进来"的**真门槛**（比价格更要紧）：本 mod 的台账
[`CAPACITY.md` §0](../../../mods/th18.v1.00a/card-expand/CAPACITY.md) 已经写明
"下一次加卡会先撞 **`abcard.anm` 的 256 entry**（还能进 46 张）"。本轮把**两作的 entry 数实测出来**做对照。

### 14.1 两作 `abcard.anm` 的 entry 数（一手，`thanm -l <版本> <文件>`）

| 版本 | 文件大小 | **entry 数** | 实体卡数 | 每卡 entry |
| --- | ---: | ---: | ---: | ---: |
| th18 | 20,969,464 | **118** | 56 | 2.11 |
| th185 | 32,961,848 | **185** | **85** | 2.18 |

⇒ ★ **th185 用一份 `abcard.anm`（185 entry）就放下了 85 张卡的卡图**，而且留在 256 以内 ✅
⇒ 于是"每卡约 2 格"这个成本是**原生同款**，不是我们这边用法特殊。

### 14.2 于是 TH18 mod 侧的算术变清楚了

- 现状：native **118** + 我们已加 **46** = **164 / 256**（余 **92** entry）。
- 若照"每卡 2 格"搬 85 张 ⇒ 需 **170** 格 ⇒ `164 + 170 = 334 > 256` ❌ **放不下**（差 78）。
- 三条出路（按"离原生多近"排）：

| 路线 | 算术 | 依据 | 代价 |
| --- | --- | --- | --- |
| **① 一 entry 多 sprite**（每卡只吃 1 格） | `164 + 85 = 249 ≤ 256` ✅ | [`engine/anm/th18/06`](../../anm/th18/06-entry-limit-and-multi-sprite.md) §0-Q2：一 entry 多 sprite **合法且是原生常态** | **这本来就是构建器自己写下的退路**：`assets/build_abcard.py:106` 明写"把大图/小图并进一个 entry ⇒ 可容纳卡数翻倍" |
| **② 另开一个 anm 槽**（th185 那样"自己的文件"） | 新文件 185 entry ≤ 256 ✅ | 贴图键 = `(槽号 << 8) \| entry`，**槽号最多 33**（`th18:0x4867fe`，`engine/anm/th18/06` §1.1） ⇒ 多文件是原生支持的 | 分发侧要能**往 `th18.dat` 里加一个文件**（本 mod 现在是"整文件替换"路线）⇒ 要查 thcrap 能不能加档 |
| ③ repack 原生 118 entry | 腾出若干格 | — | 动原生卡图，风险最高，**不建议** |

### 14.3 结论（对目标 (2)）

- "把 th185 的 85 张卡连卡图一起搬进来"**不是不可行，是当前构建方式下的余量不够**；
  **①（一 entry 多 sprite）是最近的解**，因为它是**原生做法**（th185 自己每卡 2.18 entry 说明它没有省，
  但 TH18 的引擎**允许**省），② 则是 th185 的活样板（自成一档）。
- **"每卡 2 entry"的原因已经查清**（一手，构建器注释）：`assets/build_abcard.py:29-33` 写着
  "abcard 每张新卡吃 **2** 条 entry"，而 `:114-115` 两条就是 **`<卡名>_max.png`（大图）+ `<卡名>_min.png`（小图）**
  ⇒ **两 sprite 的语义 = 大图/小图**，与"卡面/卡背"无关；
  同一文件 `:106` 早就把退路写在报错信息里：「把大图/小图并进**一个 entry**（一个 entry 两个 sprite）⇒ 可容纳的卡数翻倍」。
  ⇒ 所以 ① 不是"新发明"，是**构建器预告过的改法**：entry 从 `118 + 2N` 变成 `118 + N`，
  卡数上限从 **69** 张抬到 **138** 张 —— 85 张**够放下**（249/256）。
- **① 的真实工作量**在 `cards.js` 的**卡图索引**一侧：现在每卡存一对 sprite（`check_cards_js` 里的 `pair`），
  合并后两个 sprite 落在**同一 entry** 内 ⇒ 索引格式与读端要一起改（引擎侧没问题：sprite 号是 dword、
  一 entry 多 sprite 原生支持）。这一步的具体改法属于 mod 侧施工，不在本文范围。
- 本节只做了**容量账**；**一张 th185 卡图怎么变成 entry/sprite**（贴图从 th185.dat 的哪个文件取、
  卡面尺寸/坐标）是下一步的素材工作。

## 17. 槽语义表：**"盲扫"这条路走不通**（一手 + 方法论结论，轮 26）

§16.4 的第 ① 步（定位 th185 的槽语义表）本轮试了一次，结论是**方法要换** —— 这条负结果值得单独记。

### 17.1 目标词汇已经有了（th18 侧的权威槽名，一手）

金矿 th18 的 `zVTableCard` **逐槽命名**（`__end` = `0x54` ⇒ **21 槽**）：

`+0x00 constructor` / `+0x04 destructor` / `+0x08 c_press` / `+0x0c on_player_death_after_deathbomb` /
`+0x10 on_player_before_deathbomb` / `+0x14 …_frame_2` / `+0x18 on_power_level_change` / `+0x1c on_tick_shooters` /
`+0x20 on_load` / `+0x24 on_tick` / `+0x28 on_bullet_created` / `+0x2c __on_tick_2` / `+0x30 recharge` /
`+0x34 __on_load__2` / `+0x38 method_38` / `+0x3c get_bomb_timer` / `+0x40 method_40` /
`+0x44 on_anm_id_assigned_to_hud` / `+0x48 on_draw` / `+0x4c method_4C` / `+0x50 operator delete`。

同表 `zCardBaseClass` 的**字段**（注意与虚表槽号不是一回事）：`+0x4 card_id`、`+0x8 array_index`、

⇒ th185 是 **22 槽**（§16.1），比它**多一槽**。词汇可以借用，但**槽号必须重定位**。

### 17.2 盲扫的实测结果：**不能把 call 点直接归给卡虚表**

做法：全 `.text` 扫 `call dword ptr [reg+disp]`，按 disp 分桶（disp ∈ 0..`0x54` 且 4 的倍数）。
结果与应有的"每槽一个调用点"（th18 那张表的样子）**对不上**：

| slot | 有 call 点？ | slot | 有 call 点？ |
| --- | --- | --- | --- |
| `+0x00` `+0x04` `+0x18` | 各 1 处 | `+0x2c` `+0x38` `+0x3c` `+0x40` `+0x44` `+0x48` `+0x4c` | 各 1 处 |
| `+0x1c` 4 处、`+0x20` 2 处、`+0x24` 5 处、`+0x50` **27 处**、`+0x54` 4 处 | | **`+0x08` `+0x0c` `+0x10` `+0x14` `+0x30` `+0x34`** | **0 处** |

- 附带确认：**th185 里没有任何"索引式"间接调用**（`call [reg+reg*n]` = **0 处**）⇒ 虚调用一律常数位移，
  这一点和 th18 一样（好消息：理论上能穷举）。
- 但**为什么盲扫不行**：`+0x50` 那 27 处全是同一个**析构惯用法**——
  `push esi / mov esi,ecx / mov eax,[esi] / call [eax+0x50] / mov dword [esi+0x58],0`——
  散布在**许多不相干的小函数**里 ⇒ 这条 `call [+0x50]` 属于"某个带 `+0x58` 字段的类"的通用清理，
  **无法证明基址寄存器装的是卡对象**。同理，6 个槽之所以"0 处"，也不是它们不存在，而是
  调用它们的地方基址寄存器**带了偏移**（扫描里确实出现了负位移 `disp = -0x2c` ×4 这类）。
  ⇒ **常数位移扫描 + 数据流归属**缺一不可。

### 17.3 顺带得到的一条跨版本对应（🟡 单点推断）

th185 `[card + 0x54]` ≈ th18 `[card + 0x50] flags`：证据是 §16.3 的 EXTEND 槽 `+0x08`
（`th185:0x413800`）写的是 `or dword [edi + 0x54], 0x20`，而 th18 侧 **bit `0x20` of `flags` = `is_firing`**
（mod 的一手表 [`../th18/03-hooks.md §1`](../th18/03-hooks.md)：`+0x40 method_40` 就是 `flags & 0x20`）。
⇒ th185 的卡对象在这些字段上**整体后移 4 字节**（与"多一槽"呼应）。只有一个数据点，标 🟡。

### 17.4 于是 ① 的正确打法（下一轮照这个做）

**别扫，读宿主函数** —— th18 那份表当年就是这么来的（在 `Player__on_tick__body` / `AbilityManager__*`
里逐个确认"这个 `[reg+disp]` 的 reg 是卡对象"）。th185 侧的宿主起点（金矿有名）：

| 宿主 | 地址 | 为什么从它开始 |
| --- | --- | --- |
| `AbilityManager::on_tick` | `th185:0x408a40` | 卡的管理器侧每帧钩子（`.c` 里对应 `+0x2c`/`+0x4c` 一类） |
| `AbilityManager::on_draw` | `th185:0x408fc0` | HUD 侧（`+0x44`/`+0x48`/`+0x50` 一族） |

## 20. 逐卡方法实证（一）：WARP / AUTOBOMB 的方法读到了，且**"整体平移"读法被否掉**（一手，轮 29）

### 20.1 WARP（id 28，虚表 `th185:0x4b77fc`）：一张**会花火力**的卡


### 20.2 AUTOBOMB（id 52，虚表 `th185:0x4b8268`）：方法在做**演出对象的创建**

### 20.3 ★ 结论：**"整体 +4 平移"（§18.3 读法 B）被否掉**

  但这两个槽分别只有 23/… 张卡覆盖 ⇒ **平移读法不成立** ✘

## 21. ★ 广播点全找出来了：**中高段槽与 th18 同号同义**（一手，轮 30）

§17.2 说"盲扫不能归因"。本轮用**结构特征**代替归因：卡对象在引擎里是**链表节点**（`[node]` = 卡对象、
`[node+4]` = next），所以"引擎向所有卡广播某个事件"的循环长得一模一样：

```asm
mov ecx, [edi]        ; node -> 卡对象
mov eax, [ecx]        ; 卡对象的虚表
call dword ptr [eax + <槽>]
mov edi, [edi + 4]    ; next
```

按这个四指令特征全镜像筛，得到 **6 个广播点**（这就是"引擎会主动通知卡"的全部事件）：

| 广播点 | 槽 | 宿主函数 | 与 th18 对照 |
| --- | --- | --- | --- |
| `th185:0x408aa4` | `+0x2c` | `AbilityManager::on_tick`（`th185:0x408a40`） | th18 `+0x2c __on_tick_2`（由 `th18:0x408640` 调）✅ **同号同义** |
| `th185:0x408fcc` | `+0x48` | `AbilityManager::on_draw`（`th185:0x408fc0`） | th18 `+0x48 on_draw`（`th18:0x408ABC` 调）✅ |
| `th185:0x408ff5` | `+0x20` | 同上函数内（第二遍） | th18 `+0x20 on_load`（OR 累加）🟡 |
| `th185:0x41d464` | `+0x4c` | `BlackMarket::initialize`（`th185:0x41d430`） | th18 `+0x4c method_4C`（局末重置卡内状态）🟡 |
| `th185:0x41dd76` | `+0x38` | 商店区（`th185:0x41d430` 之后） | th18 `+0x38` = `set_recharge_timer(n)` 🟡 |
| `th185:0x41dda4` | `+0x20` | 同上区 | 同 `+0x20`（第二次出现）|

### 21.1 结论（更新 §18.3 / §20.3）

- **中高段槽与 th18 同号同义**：`+0x20` `+0x2c` `+0x38` `+0x40` `+0x48` `+0x4c` 全部对得上
  （其中 `+0x2c`/`+0x48` 两条是**宿主函数级**的铁证：管理器每帧 / 管理器绘制）。
- **低位槽（`+0x00`–`+0x1c`）仍未定**：它们不是"广播"型（不在这个四指令特征里），
  只在玩家动作/死亡/开火等**具体事件**里被调 ⇒ 需要另找宿主（§20.4 的判定集）。
- **ctor/dtor 区确实不同构**（§20.3 的构造函数槽判据）：th185 构造不分槽、销毁落在 `+0x50`/`+0x54`。
- ⇒ 于是"槽表"可以**分两半交付**：中高段（6 个槽）已可当成 th18 语义直接用（🟢）；
  低位段（约 8 个槽）继续按判定集实证。

## 22. ★ 基类默认实现把槽的"性质"定死了：`+0x50` 不是 delete、`+0x54` 才是析构（一手，轮 31）

上一轮靠"覆盖卡数"猜结构，这轮直接**读基类虚表里每个槽的默认实现** —— 这一步是决定性的（默认实现长什么样，
就说明这个槽是什么性质）：

| 槽 | 基类默认实现（`th185:0x417680` 一族） | 性质（一手判定） |
| --- | --- | --- |
| `+0x00` | `xor eax,eax / ret` | **返回 0 的事件钩子**（不是构造函数：构造不可能只返回 0） |
| `+0x04` | `xor eax,eax / ret` | 同上（第二个返回 0 的钩子） |
| `+0x50` | **`ret 0`** | **每张卡必须实现的主行为方法**（基类留空）—— 86 张卡全部覆盖 ✅ 吻合 |
| `+0x54` | `push esi / mov esi,ecx / mov dword [esi], 0x4b8998（写回基类虚表）/ mov edx,[esi+0x10] / test…` | **析构函数**（写回基类虚表 + 清理成员）—— 86 张卡全部覆盖 ✅ 吻合 |

### 22.1 于是三条结论要更新

1. ❌ **§20.3 的"`+0x00`/`+0x04` 是构造/析构对"读法作废**：它们默认实现是 `ret 0`，是**钩子**。
   （顺带纠正一个旧印象：th18 侧的 `+0x00 constructor` 默认实现**也是** `ret`，而 `allocate_new_card`
   是**按返回值决定删不删卡**的 ⇒ 两作的这两个槽本来都更像"钩子"而非 ctor/dtor。）
2. ❌ **§21 里"`+0x50` 与 th18 的 `operator delete` 同义"要收回**：th185 的 `+0x50` 是**每卡必实现的
   主行为方法**（基类 `ret 0`），不是销毁 —— 尽管 §17.2 盲扫时那 27 处 `call [+0x50]` 长得像析构惯用法，
   那些调用**确实不是卡对象**（又一次印证"盲扫不可归因"）。
3. ⚠ **th18 的槽名表不能直接套到 th185**：连"每卡必实现"的槽号都不一样
   （th18：`+0x00`/`+0x04`/`+0x50`；th185：`+0x50`（行为）/`+0x54`（析构））。

### 22.2 当前槽表的"可信度分层"（截至本轮）

### 22.3 对 mod 侧移植的直接含义

想照 th18 的"槽表"去写 TH18 侧的卡行为时，**不能假设 th185 的槽号等价**；尤其
**`+0x50` 在两作语义完全相反**（th18 = operator delete / th185 = 主行为）。
正确做法是按本节的"可信度分层"逐槽实证后再映射，或者干脆**只搬行为，不搬槽号**
（把 th185 的卡效果重写成 TH18 侧自己的卡实现——§16.4 的 ②③ 本来就是这么计划的）。

## 23. 第四个锚点：`+0x20` = **on_load 型 OR 累加广播**；卡链表头是 `AM+0x1c`（一手，轮 32）

### 23.1 `th185:0x408fe0` = 一个**专门做 OR 累加广播**的函数（与 th18 的 `on_load` 同义）

```asm
th185:0x408fe1  mov  esi, [th185:0x4d7ab8]   ; AbilityManager
th185:0x408fea  mov  esi, [esi + 0x1c]       ; ★ 卡**链表头**（不是数组）
th185:0x408ff1  mov  ecx, [esi]              ; node -> 卡对象
th185:0x408ff3  mov  edx, [ecx]              ; 虚表
th185:0x408ff5  call dword ptr [edx + 0x20]  ; ★ 槽 +0x20
th185:0x408ff8  mov  esi, [esi + 4]          ; next
th185:0x408ffb  or   edi, eax                ; ★★ **返回值 OR 累加**
th185:0x409001  mov  eax, edi / ret
```

th18 侧的一手表：[`../th18/03-hooks.md §1`](../th18/03-hooks.md) 里 `+0x20 on_load` 的语义正是
"**OR 累加返回值**"（调用点 `AbilityManager__notify_cards_on_load`）⇒ **同槽同义，且连"OR 累加"这个细节都对上** 🟢
⇒ 这是第 **4** 个铁锚（前三个：`+0x2c` 管理器每帧、`+0x48` 每帧绘制、`+0x40` bool 判定）。

### 23.2 顺带钉死两个结构/两个工具函数

- **`AbilityManager + 0x1c` = 卡链表头**（一手，§23.1 与 §21 的广播循环都用它走链表）
  ⇒ 与 §9 的"持有卡链表 `AM+0x1c`"是同一个东西 ✅（那次是从 `th185:0x41f930` 的列卡函数看出来的）。
- `th185:0x409040` = **按 (参数, 当前卡) 找卡对象**（`push arg; push [AM+0x7c]; call`），返回新卡或 0；
  它的调用者都是"切换当前卡"的语义（`th185:0x409010`、`th185:0x41dd3b` 商店）。
- `th185:0x409180` = **当前卡的 HUD/ANM 刷新**（内部 `call th185:0x48a4a0` = `get_vm_with_id`、
  清 `AnmVm+0x534` 位、遍历 VM 链表）⇒ 属于**演出/HUD 侧**，**不是"使用卡"**。

### 23.3 于是"使用卡"（c_press）**不在 AbilityManager 里**（负结果）

`AM+0x7c`（当前卡）在 AbilityManager 内的所有用法都看过了：重置（`th185:0x408036` / `th185:0x408609`）、
设置（`th185:0x408665`）、**HUD 高亮与绘制**（`th185:0x408bb9`–`th185:0x408d05`：`get_vm_with_id` + `AnmVm`
的 `+0x4e4/+0x4ec/+0x524` 写入）、商店（`th185:0x41dd41`）—— **没有一处是"按键触发的使用"**。
⇒ `c_press` 的派发在**玩家/USER 侧**（th18 是 `Player__on_tick__body` `th18:0x45C048`）；
th185 的玩家代码区还没定位（金矿无 `Player::on_tick` 名），这就是**下一轮的第一件事**：
在 0x45xxxx 一带找"读输入 → 调卡槽"的函数，钉下 `c_press` 的槽号后低位段即可对齐。

## 24. WARP 的语义读通了 + **订正 §17.2 的一次统计错误**（一手，轮 33）

### 24.1 ★ `th185:0x4d7af4` = **玩家对象**（本轮最有用的一条）

WARP 的三个槽方法（一手，逐条读）：

```asm
; 槽 +0x2c（= 管理器每帧，§18.1 已锚定）
th185:0x40e860  mov  eax, [th185:0x4d7af4]   ; ★ 玩家对象
th185:0x40e867  je   出口
th185:0x40e869  mov  dword [eax + 0x164], 1  ; ★ 给玩家置"请求传送"标志
; 槽 +0x0c / +0x14 = 火力开销（§20.1：−50、下限 100）
; 槽 +0x50 = and dword [ecx+0x54], 0xfffffffd  ; 清卡自己 flags 的 bit1
; 槽 +0x34 = mov eax,[ecx] / jmp [eax+0x50]    ; ★ 只是 +0x50 的转发壳（同一段代码）
```

⇒ **WARP 的实现方式**：每帧给**玩家对象**置一个标志位 `player+0x164 = 1`，传送本体在玩家代码里做。
⇒ `th185:0x4d7af4` **就是玩家对象指针**（旁证：EXTEND 的 `+0x2c` 也读它，并查 `[player+0x4f44]`）。
这条对后续所有"玩家侧"的追查都省事 —— §23.3 要找的"使用卡/输入"就在这个对象的方法圈里。

### 24.2 ⚠ 订正：§17.2 的"`+0x08` 等槽 0 个调用点"是**我的扫描器出错**（原始字节扫描更可信）

用**原始字节**扫 `ff <modrm> <disp>`（`call dword ptr [reg+disp]`），真实数量远超我上一轮的统计：

| disp | 我上轮（capstone 过滤） | 原始字节扫描 | 例 |
| --- | ---: | ---: | --- |
| `+0x08` | 0 ❌ | **71** | `th185:0x428a39`、`th185:0x45a1c4`… |
| `+0x0c` | 0 ❌ | **116** | `th185:0x44e4aa`、`th185:0x462176`… |
| `+0x14` | 0 ❌ | **24** | `th185:0x4294b3`、`th185:0x44e0d1`… |
| `+0x1c` | 4 | 11 | … |
| `+0x24` | 5 | 27 | … |
| `+0x34` | 0 ❌ | **17** | … |

⇒ §17.2 里"6 个槽 0 个调用点"的结论**作废**（那是过滤器的 bug，不是事实）。

**但数量多并不等于能归因**：抽查 `+0x08` 的密集区（`th185:0x45a1xx`–`0x45a2xx`）发现那是
**统一的"停掉+释放"套路**：`mov eax,[obj]; push obj; call [eax+0x20]`（停机）紧接着
`... call [eax+8]`（**COM `Release`**）然后把指针清零 ⇒ 这些 `call [reg+8]` 是 **DirectX 接口的 Release**，
不是卡槽 ⇒ **位移相同的调用分属不同对象族，归因只能靠"这个寄存器里装的是不是卡"**（§17.2 的结论仍然成立，
只是理由从"扫不到"变成"扫到了但不能归因"）。

## 25. `+0x50` 的真身 = **"置启用状态"**，`card+0x54` bit1 = 启用位（一手，轮 34）

### 25.1 三张卡的 `+0x50` 方法逐条读出（一手）

| 卡 | `+0x50` 方法 | 代码 |
| --- | --- | --- |
| `NITORI`(0) | `th185:0x40a5d0` | `or dword ptr [ecx + 0x54], 2` / `ret` |
| `LARVA`(84) | `th185:0x412b30` | `or dword ptr [ecx + 0x54], 2` / `ret` |
| `TAKANE`(5) | `th185:0x40b540` | `and dword ptr [ecx + 0x54], 0xfffffffd` / `ret` |
| `WARP`(28) | `th185:0x40e850` | `and dword ptr [ecx + 0x54], 0xfffffffd` / `ret` |

⇒ 全都是**对卡自己 `+0x54` 的 bit1 做置位/清位**（有的是纯一行，有的后面还跟着收尾，如
`LARVA` 的邻居方法 `th185:0x412b60`：`test byte [ecx+0x54],2` → 真则 `mov dword [th185:0x4d1038], 0`
再清位）。⇒
**`card+0x54` bit1 = "本卡已启用"，`+0x50` = "置启用状态（开/关）"**，
这与"86 张卡全部覆盖 `+0x50`"完全吻合（每张卡都必须声明自己开/关时做什么）🟢

> ⇒ §22 里我写的"`+0x50` = 每卡必实现的主行为"要再收窄一格：**它具体是"启用/停用"这个主行为**。

### 25.2 ★ 大量槽是**转发壳**（thunk）——读覆盖集时必须穿透

同一片代码里反复出现这种 4 字节小函数：

```asm
th185:0x40a5e0  mov eax, dword ptr [ecx]   ; 取自己虚表
th185:0x40a5e2  jmp dword ptr [eax + 0x2c] ; ★ 转发给 +0x2c
```

`WARP` 的 `+0x34` 也是壳：`mov eax,[ecx] / jmp [eax+0x50]`（§24.1）。
⇒ **"某张卡覆盖了 N 个槽"这句话会高估真实代码量**：其中一部分槽只是**转发到别的槽**。
读卡行为时应当**先穿透转发壳**，再看真正干活的槽（多数落在 `+0x2c` 每帧 / `+0x50` 启用）。
