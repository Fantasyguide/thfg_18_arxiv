# TH18 新增卡牌的硬边界 —— 每一处被原生卡集合写死的地方

> **版本**：TH18 v1.00a（`th18.exe`，imagebase `0x400000`）。本文裸地址默认属该版本；引用其他版本须写成 `th16:0x…`。
> **性质**：**前期调研**，不含改造方案的实施。回答一个问题——
> 「想加一张能进商店池、能在菜单里显示的新卡，会撞上什么？」
> **可信度**：标 ✅ 的是本次一手反汇编读出的；标 🟡 的来自 ExpHP 结构体尺寸，**未逐个一手复核**。

## 0. 结论先行

**原生卡集合的规模以 `56 / 57 / 58` 三个数字散落在至少 12 处**，其中 4 处是代码里的
立即数、8 处是结构体尺寸。**没有任何一处是「读表算出来的」**——全部写死。

更关键的是：**按 card_id 索引的数组几乎没有余量**。`zAbilityManager` 里那个「本局是否
拥有」的数组占到 `+0xd64`，而对象在 `+0xd70` 结束——**只剩 12 字节**。

所以「往 `zTableCardData[]` 后面追加一项」这条路**不成立**，不是因为表在 `.rdata`
不可写（thcrap 写得了），而是因为**表长只是十几处硬编码之一**。

## 1. 先把三个数字分清

| 数字 | 含义 | 出处 |
| --- | --- | --- |
| **58** | `zTableCardData[]` 的条目数（`0x4c53c0`，stride `0x34`） | [`07-registry.md`](07-registry.md) |
| **57** | 可分配的 card_id 数（0–56）；跳转表项数；解锁位数组长度 | 本文 §2 #1 #2 #10 |
| **56** | 真正的「卡」——58 减去 `NULL`/`BACK` 两个菜单哨兵。商店池、菜单数组、全收集成就都按它 | §2 #7 #9 #12 |

**id 56/57 是哨兵，不是卡**（`07-registry.md` 表末两行）。`TableCardData__get` 查不到
时正是返回 56 号那个 `NULL` 条目当安全值。

## 3. 未知 id 的实际行为（不是「default 分配」）

ROADMAP 里问的是「`allocate_new_card` 的完整 switch/default：未知 ID 当前如何处理」。
答案是：**根本走不到 switch**。

```asm
0x411460  cmp dword [edi+0x28], 0x100    ; 已持有 >= 256 张?
          jge  失败
          mov  ebx, [ebp+8]              ; card_id
          cmp  ebx, 0x38                 ; > 56 ?
          ja   失败                      ; ← 无符号比较,新 id 在这里就被挡掉
          jmp  dword [ebx*4 + 0x412dac]  ; 57 项跳转表
...
失败:     or   eax, -1                   ; return -1
成功:     inc  dword [edi+0x28]          ; num_total_cards++
          mov  eax, [edi+0x28]           ; 返回新的持有数
```

所以**二进制里没有一个可单独接管的 default 标签**——编译器把 `default: return -1`
和「持有数 ≥ 256」的失败路径合并成了同一个出口（`0x412da0`），`ja` 就是跳转表的范围检查。
⚠️ 别据此以为源码里也没有 default，源码里有，见
[`11-sentinels-56-57.md`](11-sentinels-56-57.md) §4.6.2。

要接自定义分配，只有两个位置：在 `ja` 之前 hook（改判定 + 自己分派），或者整体重指跳转表。

好消息是它**失败得很干净**：返回 -1、不崩、不留半个对象。

## 4. 好消息：文案是文本文件

`FUN_004160b0` `0x4160b0`（由 `AbilityManager__operator_new` `0x408439` 调一次）解析
**`ability.txt`**：

- 按 `@<internal_name>` 分块，用**内部名字符串**在注册表里线性查该卡；
- 每卡读最多 **7 行**，逐行写进 `(card_id * 7 + 行号) * 0x40 + 缓冲区`。

即**卡牌名称/说明来自游戏归档里的一个文本文件**，不是硬编码字符串。
这正是 thcrap 最擅长的东西（文件替换是它的本职），所以**文案侧几乎没有障碍**——
前提是 #5 的循环边界和 #6 的缓冲区尺寸放得进去。

内部名是查表键，也意味着新卡必须先在注册表里有一项、且 `internal_name` 指针有效。

## 6. 三条可能的路线（判据，不是方案）

| 路线 | 做法 | 代价 |
| --- | --- | --- |
| **A. 换皮** | 不加新 id，改写某张原生卡的效果/文案/图标 | 边界一个都不撞。ROADMAP 阶段 1 就是它 |
| **B. 吃掉哨兵** | 拿 id 56/57 两个菜单哨兵当新卡用 | ❌ **已判死**，见 [`11-sentinels-56-57.md`](11-sentinels-56-57.md) |
| **C. 整体搬迁** | 把注册表 + 所有按 id 索引的数组搬进 codecave，binhack 掉 §2 全部立即数 | 12 处边界、其中 8 处是**结构体内部的数组**——意味着 `zAbilityManager` / `zAbilityMenu` / `zScoreFile` 都要扩容或重指，牵连**存档格式** |

**C 的真正难点不是表，是存档。** `unlocked_cards` 和 `initial_cards_per_shottype` 都在
`zScoreFile` 里，而 `zScoreFileSuper` 还有一份 `backup` 副本（`+0x5f888`）。动它就动存档
兼容性——老存档、以及别人的存档。

**B 的可行性已调查完毕（2026-09-01）：不可行。**id 56 是全部内联查表的「查不到」回退行、
兼卡组编成里的「空槽」伪卡；id 57 是图鉴里未解锁卡的卡背图，而且 `allocate_new_card`
根本不放行它。全部证据见 [`11-sentinels-56-57.md`](11-sentinels-56-57.md)。

于是只剩 A 和 C。C 的机械工价现在算得出来了（全二进制线性反汇编穷举，同篇 §4.5）：
**只搬表 99 处 / 9 个函数，全部改完 132 处 / 15 个函数**。

更根本的解释也在那一篇：**56 不只是「数量」，还是一个写进存档的「值」**——
初始卡组数组被 `memset(…, 56, 48)` 填成空槽，所以每一份现有存档里都写着 56。

## 8. ★ 新题目：卡 id **> 128** 到底断在哪（调查中，2026-09-18 起）

**缘起**：用户要把 TH18.5 的卡（[`../th185/README.md`](../th185/README.md) §6：**87 个卡槽**）搬进本 mod，
需要 id 号段越过 127，而**用户实测过 >128 会出问题**。本节先钉**已有一手事实**，未证的写清是未证。

### 8.1 mod 侧：**数据结构早就按 254 设计**（一手，代码在案）

| 事实 | 出处（mod 源码，行号为写此节时的快照） |
| --- | --- |
| `CE_SDK_CARD_ID_MAX` = **254** | `mods/th18.v1.00a/card-expand/native/sdk_core.h:11` |
| 行为表 / 伤害 permille / 无敌表都开 `[CE_SDK_CARD_ID_MAX + 1]` = 255 项 | `native/sdk_core.c:7`、`:167`、`:209` |
| 有专门清 128+ 的码路：`for (id = 128; id <= CE_SDK_CARD_ID_MAX; ++id)`、`cid > 127u` 分支、核对 `owned[128..254]` | `native/sdk.c:1915`、`:1928`、`:1893`、`:1941` |
| 菜单顺序表搬进 codecave（255 项）、`__card_ids` 从 `+0x304` 搬到对象尾部 `+0x13fc`（255 项）、编成前的清理循环抬到 255 | `native/menu.c` 文件头注释 |

⇒ **mod 自己这层不构成 >128 的障碍**（它明确预留到 254）。

### 8.2 ★ 已经写在代码注释里的那条硬限制：**图鉴条目数 ≤ 127**（一手，`native/menu.c:11`）

> 「把**图鉴条目数**的 7 处立即数写成 `56 + N`。**两处是 `cmp r,imm8`（符号扩展）→ 条目数 ≤ 127**。」

`imm8` 符号扩展到 `-128..127`，所以条目数一旦 ≥128，那两处比较就再也走不通。
**这是目前唯一一条被指到实处的 >128 断点**（🟢 有代码注释与 site 表为证；🔴 尚未实测复现）。
⇒ 推论：**「全部 th185 卡 + 图鉴全展开」这条路线，在条目数上先撞 127**；
要么把这两处 `imm8` 换成长编码（codecave 重写），要么**图鉴只展开前 N 张**、其余走别的入口。
这条与 §6 的「卡表口径」一起，构成 >128 路线的**第一道闸**。

> ★ **2026-09-19 已修**：这两处**没有**改用 codecave，而是**原地换成「无符号字节比较 + `jb`」**
> （只改 2 字节、立即数位置不变），上界 **127 → 255** ⇒ 新卡上界 71 → 197（= id 空间）。
> 落地清单、等价性的一手反汇编、回读护栏与未做的实跑验证见 **§8.11 / §8.12**。
> 本节以下关于「≤127」的记述保留为**当时的发现过程**，不再代表现状。

### 8.4 ★ 引擎侧的 id **是 32 位、无位域**（一手反汇编，本轮新钉）

`allocate_new_card` 的守卫（`th18:0x411460` 起，逐指令读）：

```asm
th18:0x411469  cmp  dword ptr [edi + 0x28], 0x100   ; 同时存在的卡数上限 = 0x100 (256)
th18:0x411470  jge  th18:0x412da0                   ; 到顶就拒绝
th18:0x411476  mov  ebx, [ebp + 8]                  ; ebx = 请求的 card id
th18:0x411479  cmp  ebx, 0x38                       ; 原生上界 56   ← mod 改成 0xfe
th18:0x41147c  ja   th18:0x412da0                   ; ★ ja = **无符号**比较
th18:0x411482  jmp  dword ptr [ebx*4 + 0x412dac]    ; id 直接当 dword 索引跳转表
```

- ★ **`ja` 是无符号比较** ⇒ mod 把 `0x38` 改成 `0xfe` 是**对的**：`0xfe` 不会被符号扩展成 −2
  （若是 `jg` 就会变成"一切 id 都放行/都拒绝"的灾难）。这条写清楚，免得后人误判成 bug 又改回去。
- **id 的使用方式是 `[ebx*4 + 表]`**，即 **32 位整数索引**，没有任何 `& 0x7f` / 位域打包
  ⇒ **位宽不是 >128 的断点**。（同一结论在别处复现：图鉴清空循环 `th18:0x414970` 是
  `edi = 0x38` 项、`lea esi,[esi+4]` 步长 4 ⇒ **id 数组是 dword**；
  `sites.py` 的 `MENU_CLEAR` 注释也写着"数组本来就是 `[0x100]`"，patch 把 `mov edi,0x38 → 0xff`。）
- **卡数据表的一手坐标**（本轮一并钉死，此前只有金矿推断）：`zTableCardData` = **`th18:0x4c53c4`**，
  **58 行 × `0x34`**，区间止于 `th18:0x4c5f8c`（`(0x4c5f8c − 0x4c53c4) / 0x34 = 58` ✅）。
  查找循环 `th18:0x4149c0` 就是 `cmp dword ptr [eax], esi` —— **逐 dword 比 id**，同样无位域。
- 引擎里"本局是否拥有"是 **`int[56]`**（`sites.py:55` 的 `OWNED_OLD = 0xc84`，止于 `0xd64`）——
  也是 dword 数组；mod 已把它搬到对象尾部（`OWNED_NEW = 0xd70`）。

### 8.5 于是 >128 的断点排序（更新 §8.2；**按证据强度**）

| # | 断点 | 算术 | 证据 | 可信度 |
| --- | --- | --- | --- | --- |
| 1 | **图鉴条目数 ≤ 127** | `条目数 = 56 + N`（N = 新卡数）⇒ **N ≥ 72 就撞线** | `native/menu.c:11`（7 处立即数、其中 2 处 `cmp r,imm8`） | 🟢 代码在案 / 🔴 未实测复现 |
| 2 | **跳转表 cave 只有 `rows*4` 字节** | 运行期要求 `id < rows`；`sites.py` 只在**生成期** `assert 59 <= rows <= 255` | `native/sites.py:46-52,465,492,502` | 🟡 |
| 3 | 分配器「同时在场卡数 < 0x100」 | 255 张卡全在场时是否撞 256，需算 | `th18:0x411469`（一手） | 🟡 待算 |
| 4 | 存档 / replay 的 card-id 数组、HUD、商店 offer 表 | 未查 | — | ❓ |

⇒ **给用户的直接答复**：>128 坏掉**最可能不是"id 位宽"**（引擎侧是 32 位、无掩码，见 §8.4），
而是 **#1 的"条目数 = 56 + N ≤ 127"**：**能加的新卡数 N 上限是 71**，
想搬 th185 的 87 张（或更少但加上现有 10 张仍越线）就会先断在图鉴条目数上。
⇒ **安全的扩展方案（按顺序）**：① 把 #1 那两处 `cmp r,imm8` 改成长编码（codecave 重写，
和 `MENU_CLEAR` 同一手法）；② 给 #2 的跳转表加**运行期**护栏（`id < rows` 否则回落到 NULL 行，
别让高 id 跳到表外）；③ 再谈存档/replay。

### 8.6 ★ 那 7 处「条目数」站点**逐处列出来了**，两处罪魁是 `cmp r,imm8`（一手字节 + 修法）

来源：`mods/th18.v1.00a/card-expand/native/sites.py:203-210` 的 `MENU_COUNT_SITES`（patch 不动它们，
**DLL 在门里按「`56 + 已注册新卡数`」现写**）。七处如下（原字节 → 立即数偏移/宽度）：

| 站点 | 原字节 | 形态 | 立即数宽度 |
| --- | --- | --- | --- |
| `th18:0x4137bb` | `c787c401000038000000` | `mov dword [edi+0x1c4], 0x38` | 4 |
| `th18:0x414394` | `c7870003000038000000` | `mov dword [edi+0x300], 0x38` | 4 |
| `th18:0x41439e` | `c787c401000038000000` | `mov dword [edi+0x1c4], 0x38` | 4 |
| **`th18:0x4145e2`** | `83f838` | **`cmp eax, 0x38`** | **1** ⚠ |
| `th18:0x41570d` | `b838000000` | `mov eax, 0x38`（行数/列数） | 4 |
| **`th18:0x4157cb`** | `83fa38` | **`cmp edx, 0x38`** | **1** ⚠ |
| `th18:0x415817` | `bf38000000` | `mov edi, 0x38`（退出遍历 vm） | 4 |

两处 ⚠ 就是 §8.2 那条「≤127」的出处：`83 f8 38` / `83 fa 38` 是 `cmp r, imm8`，**符号扩展**，
立即数只能 −128..127 ⇒ **条目数 ≥128 时这两条循环判定再也走不通**。

**逐字节看清了现场（一手读原始字节）**：

```
th18:0x4145e2  83 f8 38             cmp  eax, 0x38        ; 3 字节
th18:0x4145e5  0f 8c d5 fd ff ff    jl   th18:0x4143c0   ; 6 字节  ⇒ 合计 9 字节
th18:0x4157cb  83 fa 38             cmp  edx, 0x38        ; 3 字节
th18:0x4157ce  7c 80                jl   th18:0x415750   ; 2 字节  ⇒ 合计 5 字节
```

**修法（2026-09-19 已落地，与这里最初那版不同）**：最初写的是「把 `cmp`+`jl` 当**一个整体**替换成
`e9 rel32` 跳进 codecave、cave 里用 imm32 比较后跳回」——**这版作废**（thcrap 的 `code` 串只替换
绝对地址、算不出 rel32，cave 地址生成期也不知道）。实际采用**原地换编码**：

- `th18:0x4145e2`：`83 f8 38 0f 8c …` → `80 f8 38 0f 82 …`（`cmp al,imm8` + `jb`，9 字节不变）
- `th18:0x4157cb`：`83 fa 38 7c 80` → `80 fa 38 72 80`（`cmp dl,imm8` + `jb`，5 字节不变）

理由、等价性一手与落地清单见 **§8.11**；旧 cave 方案的要点已无操作意义，保留在此仅作过程记录：
① count ≤ 32767 时 `jl`（有符号）在 imm32 下安全；② `e9 rel32` 可达 ±2GB、cave 须同镜像；
③ 原 `jl` 目标是向后跳的循环头（`th18:0x4143c0` / `th18:0x415750`），语义要原样保留。

### 8.11 ★ 实施（2026-09-19 已落地）：**原地换编码**，不是搬 cave

**先记一条作废**：下面 §8.6 结尾那版方案（把 `cmp`+`jl` 当整体换成 `e9 rel32` 跳进 codecave、
cave 里用 imm32 比较再跳回）**没有采用**，原因是硬约束：thcrap 的 `binhack.code` 串只支持把
`<codecave:名字>` 替换成**绝对地址**，算不出 `rel32`；而 cave 地址要到 patch 应用时才知道
⇒ `e9 <cave>` 在生成期写不出来。（同一原因，跳转表搬迁用的是 `ff 24 9d <绝对地址>` 而不是 `e9`。）

**实际做法**：这两处的比较**根本不需要 32 位立即数** —— 计数器 8 位就够，缺的只是「无符号」。
把「有符号 dword 比较 + `jl`」换成「**无符号字节比较 + `jb`**」：逐字节同长、立即数位置与宽度不变。

| 站点 | 原字节 | 改后字节 | 改后语义 |
| --- | --- | --- | --- |
| `th18:0x4145e2` | `83 f8 38 0f 8c d5 fd ff ff` | `80 f8 38 0f 82 d5 fd ff ff` | `cmp al,0x38` + `jb th18:0x4143c0` |
| `th18:0x4157cb` | `83 fa 38 7c 80` | `80 fa 38 72 80` | `cmp dl,0x38` + `jb th18:0x415750` |

每条**只改 2 个字节**（比较指令首字节 `83`→`80`；jcc 第二字节 `8c`→`82` / `7c`→`72`），
**立即数字节（偏移 2）一字不动** ⇒ DLL 那 7 处写入点（偏移 / 宽度）一个都不用改。
条目数上界 **127 → 255**（正好等于表行上限 `CE_MAX_ROWS`）。

**为什么等价（一手：`AbilityMenu__on_tick` = `th18:0x413af0`，本节反汇编自 `th18.exe`）**：

1. 两处比的都是**同一个循环计数器** `[ebp-0xc]`：`th18:0x414377` / `th18:0x415737` 都是
   `mov dword ptr [ebp-0xc],0`（该函数里这两处循环之前没有别的写点）；
2. 循环体里 `th18:0x4145de` / `th18:0x4157c7` 各 `inc` 一次、写回同一格后**立刻**比较
   ⇒ 到这两处时计数器恒在 `0..255`；
3. 于是 `al` / `dl` 就是计数器本身，「无符号字节比较」与原来的「有符号 dword 比较」**逐值同真值**；
4. jcc 只换**条件码**：`0f 8c`→`0f 82`（rel32 6 字节）、`7c`→`72`（rel8 2 字节），**位移照抄**
   ⇒ 循环头地址与跳转目标一字不动，窗内其它指令边界也没变。
