# TH19 能力卡（アビリティ）— 枚举表 / 基类接口 / 装配链 / 生效点

> **版本**：TH19 v1.10c（`th19.exe`，imagebase `0x400000`）。本文裸地址默认属该版本；引用其他版本须写成 `th20:0x…`。
> **样本**：`local/th19.v1.10c/th19.exe`（已脱 SteamStub，md5 `dd0e1ff8c02327bf6408f763b8beedc9`）。
> **方法**：`local/th19.v1.10c/decomp`（4740 函数语料库，`th20_show.py` 读）+ `th19-rtti.json`（448 vftable）
> + `ability.txt`（一手文本）+ **capstone 直接反汇编 th19.exe**（补语料库没建函数的地址；全程未开 Ghidra 库）。
> **可信度**：文中每条结论都带地址；`🟡` = 单源/负面结果，`❓` = 未解（见 §7）。
> **前置**：TH18 同源系统见 [`../th18/01-object-model.md`](../th18/01-object-model.md)、[`../th18/03-hooks.md`](../th18/03-hooks.md)。

## 0. 一句话结论

TH19 的能力系统 = **一个 40 项的静态表**（`0x5c5640`，stride `0x20`，键=字符串、id 显式存）
+ **id→类 40 路 switch**（`FUN_004deba0` `0x4deba0`）+ **每角色 2 张选 1 张**（19 角色 × 2 = id 1–38）
+ **23 槽虚表**（TH18 的 21 槽 + 2 个新槽）+ 效果几乎全部落在
**「能力参数结构体」`[ctx+0x2c]` 的少量 int/byte 字段**上（不是 TH18 那种「每帧查询广播」模型）。

## 1. 能力卡的枚举与表

### 1.1 静态表（TH18 `zTableCardData[]` 的直系后继）

- **表地址**：`0x5c5640`（Ghidra 名 `PTR_s_POWERUP_005c5640`，`.data`，**40 项 × `0x20`**，在文件映像内、可直读）。
  项 0 的 `+0x00` 指向字符串 `0x59728c` = `"POWERUP"`；字符串表连续排到 `0x5973e4` 的 `"BACK"`。
- 项 39 是 `"BACK"`（**id = 40**），项 40 起是全 0 的哨兵（`0x5c5b20`，查表失败的返回值）。

| 偏移 | 类型 | 语义 | 一手证据 |
| --- | --- | --- | --- |
| `+0x00` | `char*` | 键字符串（`POWERUP`…`ZANMU2`/`BACK`） | 表 dump；字符串表 `0x59728c` |
| `+0x04` | int | **ability id**（0–38；`BACK` 是 40） | `FUN_004de830` 按此线性查 |
| `+0x08` | int | 全项 = 1（用途未定） | 表 dump（40 项均为 1） |
| `+0x0c` | int | 全项 = **999**（`0x3e7`，用途未定） | 表 dump |
| `+0x10` | byte | 类别码：全部 = 1，`BACK` = 0 | `FUN_004de860` 读此字节比 1/2 |
| `+0x14` | int | 图标/名字脚本号 A（0 起连续偶数：5,7,9…） | 表 dump（项 n→`5+2n`） |
| `+0x18` | int | 图标/名字脚本号 B（= A+1） | 表 dump |
| `+0x1c` | int | 全项 = 1（`BACK` = 0） | 表 dump |

> 与 TH18 差异：**没有价格 / 出现关卡 / 权重档**（TH19 取消金钱与商店抽卡，改「解锁」见 §5），
> 取而代之是「键字符串 + 图标脚本号」。

这解释了「键查表函数没人调」这个假象。

**三个必须记住的坑**（都是一手）：

1. **`AbilityCardNitoriInf` 就是 `@MARISA2`** = 蒐集家の教訓。RTTI 名字我用原始 RTTI 结构独立复核过
   （vtable `0x5a80bc` 的 COL → type descriptor = `.?AVAbilityCardNitoriInf@@`），
   行为也对得上：它的 slot `+0x20` `0x408550` 把玩家的アイテム回収半径改成 10/30/110/110（见 §4）。
   ⇒ **类名是 ZUN 侧的遗留/别名，不是别的角色**。
2. **没有 `AbilityCardReimu1Inf` / `Marisa1Inf` / `Marisa2Inf`**：Reimu/Marisa 的「1」卡沿用 TH18 的
   `*Op` 命名（TH18 的 `REIMU_OP`/`MARISA_OP` 也是自机射击卡），Marisa 的「2」卡就是上面的 `Nitori`。
3. `ability.txt` 里 `@SEIRAN1` **出现两次**（第 118、145 行）= 原文件笔误（第二次应为 `@SEIRAN2`），
   解析器按表查键所以不影响运行；表里没有 `@NITORI` 键。

### 1.4 id 的构成、角色索引、文本库

- **id 线性**：`0` = POWERUP、`1..38` = 19 角色 × 2、「1」= 奇数、「2」= 偶数。
  一手生成点：`FUN_005539c0` `0x5539c0`（case 2）`id = (rand&1) + 2*chara + 1`，
  `chara` 被夹到 `[0, 0x13]`（0–19）——这正好是「每角色 2 张、随机/按选择取 1 张」的算式。
- **`ability.txt` 解析**：`FUN_004e3e60` `0x4e3e60`（在 `AbilityInf` 构造时惰性调用，见 §3.3）
  逐行找 `@KEY` → **内联的键查表** → 取 `entry+0x04` = id → `if (id < 0x28)`（**id ≥ 40 直接丢弃**，
  即 `BACK` 不是能力）→ 之后最多 8 行、每行 0x40 字节写入 `DAT_005d1a30 + id*0x240 + i*0x40`。
- **文本库（= assert 串里的 `AbilityCardTxtInf`）**：全局 `DAT_005d1a30`，大小 **`0x5a28` = `0x28` 头 + 40 × `0x240`**
  （`0x240*40 = 0x5a00`，加头正好 0x5a28 ✅）。字段 0 = 名前，字段 1 = 効果名，字段 2 = 説明。
  读取例：`FUN_004e5280` `0x4e5280` 用 `DAT_005d1a30 + id*0x240` 组 `"『%s』"`。

### 2.2 与 TH18 的 21 槽逐槽对齐（★ 关键结论）

TH18 的槽序（[`../th18/03-hooks.md`](../th18/03-hooks.md)）与 TH19 实测**前 18 槽同构**，
但 TH19 在**两处各插了一个新槽**：

| TH18 槽 | TH18 名 | TH19 槽 | 判定 |
| --- | --- | --- | --- |
| `+0x00`…`+0x34` | ctor/dtor/c_press/死亡三连/装备/射击/on_load/on_tick… | 同槽号 | ✅ 语义可比（死亡 `+0x0c`、`+0x14` 调用点一手对上） |
| — | — | **`+0x38`（新）** | 释放/退出钩子（默认 no-op）：`0x4de0b0` 遍历全卡调它，同时 `manager+0xea0`=1.0 |
| `+0x38` | `set_recharge_timer` | `+0x3c` | ✅ 字段写入模式逐字节相同（`+0x38/+0x34/+0x3c`） |
| `+0x3c` | `get_recharge_remaining` | `+0x40` | ✅ 都返回计时器 `current` |
| `+0x40` | `is_firing` | `+0x44` | ✅ 都是 `(flags>>5)&1` |
| `+0x44` | `on_anm_id_assigned_to_hud` | `+0x48` | ✅ 都是 `ret 4`（1 参） |
| `+0x48` / `+0x4c` | `on_draw` / `method_4C` | `+0x4c` / `+0x50` | 🟡 槽序对齐、默认实现都是 `return 0` |
| — | — | **`+0x54`（新）** | 「武装/解除」钩子；由 `+0x38` 与局末重置调用 |
| `+0x50` | `operator_delete` | `+0x58` | ✅ 都是 deleting destructor（TH19 传 `0x60`/`0x64`） |

> 即：**TH18 21 槽 = TH19 23 槽去掉 `+0x38` 与 `+0x54`**。`flags` 从 TH18 的 `+0x50` 移到 `+0x54`
> （`+0x44` 的 `flags>>5&1` 两条实现可互证），对象从 `0x54` 涨到 `0x60`（1 型卡 `0x64`，多一个 `+0x60` 指针）。
> **🟡 订正过的两处语义差异**：TH18 `+0x30` = 「敌人掉道具后」，TH19 `+0x30` = **每帧 tick**
> （`FUN_004dd6b0` `0x4dd6b0` 每帧对全卡调它）；TH18 `+0x2c` = 管理器每帧钩子，TH19 里 `+0x2c` 被
> Narumi 用作「数值修正」。⇒ **中段槽位被重新指派，别按 TH18 的名字读 TH19。**

### 2.3 覆写模式：三类卡

| 家族 | 覆写槽 | 代表 | 语义 |
| --- | --- | --- | --- |
| 「1」型（追加攻击） | `+0x18 +0x1c +0x38 +0x54 +0x58` | `ReimuOp`/`MarisaOp`/`Ran1`/`Sanae1`/`Suika1`/`Zanmu1`… | slot `+0x18` 调 `FUN_004dea70` 建对象存 `card+0x60`；`+0x1c` 调 `FUN_004de910` 发射 |
| 「2」型（一次性参数） | `+0x20 +0x38 +0x54` | `Saki1/2`、`Biten2`、`Mamizou2`、`Suika2`… | slot `+0x20` 往 `[ctx+0x2c]` 写一个 flag/数值，然后什么都不做 |
| 「被动一次」 | `+0x00 +0x04 +0x30 +0x54` | `Reimu2`、`Aun1/2`、`Nazrin1/2`、`Narumi`(`+0x2c`) | slot `+0x30` 每帧检查 flags bit1 → 生效 → 清 bit1（自解除） |

## 3. 装配链（选择 → 装载 → 每帧驱动）

### 3.1 玩家选择存在哪

- 选择界面 task = `FUN_004e0f60` `0x4e0f60`（**10119 字节**，全仓最大函数之一，就是 assert 串
  `ability.cpp` 那一族）。它同时引用静态表 `0x5c5640`（候选列表）与文本库 `DAT_005d1a30`。
- 它管的字段（一手，均在同一函数内）：

| 偏移 | 语义 |
| --- | --- |
| `+0xe8` | **正在编辑哪个玩家**（0/1） |
| `+0x1c0` / `+0x1c4` | 光标 / 上一个光标（候选列表索引） |
| `+0x304` / `+0x308` | 候选 ability id 的**个数 / 数组** |
| `+0xfb8` (`+0x3ee` dword) | 256 项：两名玩家当前卡的镜像（读 `card+0x04` 取 id） |
| `+0x13b8` (`+0x4ee` dword) | 256 项：**确认的选择 id 数组，按玩家号索引** |

- **确认动作**（`0x4e2b51` + `0x4e2c08`）：
  `*(menu + 0x13b8 + menu[0xe8]*4) = *(menu + 0x308 + menu[0x1c0]*4)`，
  然后 `FUN_004de2f0(1, menu+0x13b8)`（`ecx` = `DAT_005d1a80` = **P0 的 AbilityInf**）。
- **对战规则（一手）**：若光标所指 id 与**对手已选的卡 id 相同且 ≠ `0x27`**，播错误音 `FUN_004bb8d0(0x10,0)`
  并拒绝 ⇒ **两名玩家不能选同一张能力**（`0x27` = Null 例外）。

### 3.2 装载：`FUN_004de2f0` → `FUN_004deba0`

`FUN_004de2f0` `0x4de2f0`（thiscall `ecx` = AbilityInf，`param_2` = 是否重建，`param_3` = id 数组）：

1. 遍历卡链表逐张走 `+0x58`（deleting dtor）摘链、`thunk_FUN_0047a4db` 释放；
2. 清 `manager+0x1c/0x24/0x28/0x2c(计数)/0x34/0x38/0x3c/0x40`、`+0x80`(当前卡)、`+0x88[64]`、
   `+0x188[64]`、`+0x2a0[256]`、`+0xebc[0x27]`（**按 id 的使用计数**）；
3. `if (param_2 && param_3)` → 装配循环（`0x4de4e0`–`0x4de517`）：
   `call FUN_004deba0(ids[edi])`，`edi` 只取 **0**（`cmp edi,1; jge` 退出）⇒ **每玩家 1 张**；
   循环内还做一次「配置字节比对」（不一致则置 `DAT_0062cdf8 = 0xfffffffe`，调试码）。

调用点（全 `.text` 直接调用扫描）：`0x4e2c08`（菜单确认，P0）、`0x532df0`/`0x532e09`/`0x532e7c`/`0x532e95`
（开战/清空，`ecx = [0x5d1a80]` = P0、`[0x5d1abc]` = **P1**）、`0x51680a`（遍历两名玩家的 manager 清空）、

## 6. 与 TH18 的差异清单（一句话版）

1. **卡数/选法**：TH18 = 商店买、卡组装 N 张；TH19 = **每角色 2 张选 1 张、每玩家 1 张**
   （`FUN_004de2f0` 的装配循环只取 `ids[0]`），且**两玩家不能选同一张**（`0x4e2b51`）。
2. **静态表**：TH18 `zTableCardData[]` 58 项 × `0x34`（价格/关卡/权重）；TH19 `0x5c5640` 40 项 × `0x20`
   （键字符串 + id + 图标脚本号 A/B），**无价格字段**（TH18 的 price/关卡档在此不存在；本作取消金钱的说法见 [`games/th19.v1.10c/INDEX.md`](../../../games/th19.v1.10c/INDEX.md) 🟡）。
3. **增表键**：TH18 只有数字 id；TH19 每张卡有 `@KEY` 字符串，`ability.txt` 靠它反查 id（`FUN_004e3e60`）。
4. **对象**：`0x54`→**`0x60`**（1 型 `0x64`），flags `+0x50`→**`+0x54`**，虚表 `21`→**`23`** 槽
   （新增 `+0x38` 释放钩子、`+0x54` 武装钩子）。
5. **管理 API**：TH18 的「查询广播」7 个派发器在 TH19 **仍存在但已无人调用**（§3.4 🟡），
   改成玩家侧内联调用 + 效果直接写 `[ctx+0x2c]` 的参数字段。
6. **计时器/充能语义不变**：`set_timer`/`get_recharge_remaining`/`is_firing` 三个槽的实现
   与 TH18 逐字节同构，只是整体后移一个槽（§2.2）。
7. **新增系统**：`AbilityMenuInf`（选择界面，`0x17e0` 对象）+ `AbilityUnlockInf`（解锁弹窗，`0x5c`）
   = TH18 的商店/卡组菜单在 TH19 的对位物。
8. **文本库**：TH18 的卡名/说明在 `zTableCardData`；TH19 独立成 `AbilityCardTxtInf`
   （全局 `DAT_005d1a30`，`0x28 + 40*0x240`），由 `ability.txt` 填。
