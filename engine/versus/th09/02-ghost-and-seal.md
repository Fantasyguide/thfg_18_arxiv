## 2. 谁生成幽灵／「击破妖精 → 送幽灵」的精确条件（✅）

生成器是引擎的 `FUN_0040f1d0`（`0x40f1d0`）：池 = `manager+0x5758` 起 **129 槽 × `0x5430`**，内容拷自模板 `manager+0x328`；
参数 `param_3 → 敌机+0x2e48`（**HP**）、`param_4 → +0x335c`（type）、`param_5 → +0x2e54`、`param_6 → flags bit15`。

**送攻击 A 链**（详见 [`01-versus-loop.md`](01-versus-loop.md) §2.3）改的就是它的 `sub` 与 charge 等级：

* 触发（`FUN_004102b0` `0x4102b0`，敌机被击破时）：`((enemy+0x3380 >> 6) & 7) ∈ {1,2}`（**charge 等级 1/2**）
  ∧ `param_1 < 2`（**由自机弹击破**）∧ **对手** `EM+0x2ac3b8 < 0x19`(25)；
* 载体 effect 的 type = `side+3`（表 `0x4a0b48`，落地函数 = effect `+0xbc` = `FUN_0040d9e0` `0x40d9e0`）；
* `FUN_004102b0` 填：`+0xa4 = min(等级, 2)`（= **要生成的 `enemy.ecl` sub 序号**）、`+0xa6 = min(等级+1, 3)`、`+0xa8 = 本侧`、`+0xa0` = HP 加成；
* 落地（`FUN_0040d9e0`）：闸门 **对手 `EM+0x2ac3b8 < 10**，然后 `FUN_0040f1d0(对手EM, 载体+0xa4, 位置, 0x14, -2, 1000, …)`，
  并把 `载体+0xa6` 写进新敌机 `+0x3380` 的 bit6–8（charge 等级）⇒ **链会层层加码：等级 1 → 2 → 3（终点）**。

### 2.1 ★ 更正与补充：charge 等级是**敌机自己的**档位，不是玩家的气槽

`(enemy+0x3380 >> 6) & 7`（bits 6–8）记在**敌机**身上，语义是「**这只敌机是被第几级蓄力攻击产出的**」（社区名 `charge_attack_enemy_count` 数的就是带 `&0x1c0` 的敌机数）。
⇒ 玩家气槽到没到 1/2 级**无关**；开局用普通攻击打死的妖精是**等级 0**，它走的是**另一条分支**（同一函数 `FUN_004102b0` 内）：

| 分支 | 条件（一手）| 落地 |
| --- | --- | --- |
| **等级 0 / 非自机弹击杀 / 已平静化** | `((flags & 0x1c0) == 0) \|\| (param_1 == 0) \|\| (flags & 0x1000)` | `FUN_0040cc00(本侧载体, enemy[+0x3368] + 0x14, pos, 1, -1)`（**载体**，type = 20 + 死亡特效号）+ `FUN_0041d110(...)`（充能/分数）|
| **等级 1/2 且自机弹击杀且未平静化** | 否分支 | 本文件上面那条 **敌机连锁**（载体 type `side+3` → `FUN_0040d9e0` 在对手场地生成敌机）|

* `enemy+0x3368/+0x3369/+0x336a` = **ECL 的 `anm_death_effects(a,b,c)` 写下的死亡特效号**（写点 `0x40a290` 一带 = 解释器 `case 138__anm_death_effects` ✓；重置在 `FUN_0040fa70` 清 0 ✓）。
  幽灵 `Sub0/1/2` 分别 `anm_death_effects(0/1/2)` ⇒ 等级 0 死亡时发出的载体 type = `0x14/0x15/0x16`（20/21/22）✓ —— **三色幽灵的“死法”各自对应一种载体**。
* ⇒ 所以：**开局普通攻击打死的妖精不会“连锁送敌机”，它送的是攻击载体**；玩家在该作里看到的「开局就有幽灵」来自**关卡波次**（`FUN_0040fcc0` 的 timeline 数据）与**角色 ECL 的 `enemy_create_*`**，不是这条连锁。

⇒ **「一队妖精 = 一只幽灵」不成立**：**每次「带 charge 等级 1/2 的敌机被自机弹击破」各送 1 只**（1 次击破 = 1 个载体 = 1 只对方场上的敌机）；
等级 0（普通/妖精本体）**不连锁**。因为 `+0xa4 = min(等级,2)`，A 链落到的是 **`Sub1`（黄）/ `Sub2`（红）**这两个幽灵档。

### 2.2 开局那批敌人从哪来：**波次表**（✅ 一手）

* 取波次数据：**`FUN_0040f170(this, id)`（`0x40f170`，16 B）= `*(*(int*)this + 8 + id*4)`** —— 从**指针表**里取「第 id 个波次」的数据块。
* 推进逻辑（`0x411ec0` 一带，`esi` = per-side `EnemyManager`）：

```
al = *(manager + 0x2ac3d4)            ; ★ 波次序号（byte 计数器）
ecx = *(byte*)(0x4a7c88 + al) & 0x7f  ; ★ 从运行期表 0x4a7c88 取「本局第 al 个波次 id」
*(manager + 0x2ac3fc) = manager       ; 自指（回调上下文）
al++  → *(manager+0x2ac3d4) = al
eax = FUN_0040f170(manager, ecx)      ; 取该波次的数据块
*(manager + 0x2ac400) = eax           ; ★ 设为当前 timeline 条目指针（FUN_0040fcc0 就遍历它）
call 0x401500(manager+0x2ac3ec, 200)  ; 计时器复位（200）
```

* 🟡 **未核**：波次**条目数据**里到底点了哪些 `enemy.ecl` sub（即「关卡会不会刷 `Sub0/1/2` 的幽灵」）。
  本轮追加证据：**没有任何 ECL 调用 `Sub0/1/2`**（三个 sub 名只作为定义出现，跨 sub 调用只有 `SubN_xxx` 这种**函数内标签**）⇒ 幽灵进场的路径**只有**「引擎按序号生成（波次数据 / 载体 `+0xa4`）」两条 ✓；
  而 `*(int*)manager` 指向的**波次数据表在 exe 里全 0**（`0x4a7c88` 一带运行期填充 ✓），填充代码还没定位（`FUN_00412090`→`FUN_0040fca0` 只初始化容器；各侧初始化循环 `0x41b1xx` 建管理器但没看到写波次表）⇒ 要 100% 回答，需实跑时 dump 内存。已知：条目的 sub 就是 `FUN_0040f1d0` 的第二参 ✓；
  但指针表的**填充源**还没找到（`FUN_00412090`→`FUN_0040fca0` 只初始化容器；`0x4a7c88` 是运行期表）。**已确定的是 level 恒为 0 ⇒ 不会连锁** ✓。
* `0x4a7c88` 在 exe 里**全 0**（运行期填充的 byte 表）= 本局的**波次序列**；每个波次的数据块被 `FUN_0040fcc0`（见 [`01-versus-loop.md`](01-versus-loop.md) §2.3 的生成链）按计时逐条生成，**1 条 = 1 只**。
* ⇒ **开局看到的妖精/幽灵是波次表给的**（与「击破连锁」无关）；击破连锁只在打死 **level 1/2** 的敌机时才继续（§2.1）。

### 2.3 ★「怎么才会有 level 1/2 的敌机」——种子与链（✅ 一手）

**全 exe 只有一条指令会写敌机的 charge 等级**（bits 6–8）：`0x40dafe` 的 `and $0x1c0,%ecx`（= `FUN_0040d9e0` 里 `newEnemy[0xce0] = (new & ~0x1c0) | (载体+0xa6 << 6)`）。
⇒ 所以「带 level 的敌机」**只能**由这条 A 链载体诞生，而且 `载体+0xa6` 的值决定了新敌机的 level：

| 载体 level 源 | 写点（一手）| `+0xa4`（新敌机 sub）| `+0xa6`（新敌机 level）|
| --- | --- | --- | --- |
| **玩家自己的「送」**（拾取霊图标 kind 3 那一档 ⇒ `FUN_0041dc20` 的 `0x41dee2` 调用、参数含 `0x11170`=70000）| `0x41d4af` | **`0`**（`enemy.ecl` `Sub0`＝绿幽灵）| **`1`**（**这就是种子**）|
| 同族另一条（`FUN_0041dff0` 的 `0x41e2fd` 调用，参数 `(…,2,…)`）| `0x41d61e` / `0x41ddee` | `+0xa4 = 3`（妖精族 sub）| `4`（终端，不再连锁）|
| **连锁**（打死 level 1/2 的敌机，见上表 §2 的两分支）| `0x4106f5`（`FUN_004102b0`）| `min(level,2)` ⇒ 1/2（黄/红）| `min(level+1,3)` ⇒ 2/3 |

* 种子那条的**HP 加成**：`载体+0xa0 = f(rand, 全局等级 0x4a7e44)`（`0x41d4c3`–`0x41d4d1`：`fildl 0x4a7e44; fmuls …; faddp`）⇒ 越到后期送出去的越硬。
* ⚠ **更正（owner 2026-10-05 实测）**：4 槽拾取物的外观我切图核了——`etama.anm` sprite 172–175 是 **4 个小光球**（白/红/红/紫），**不是**「G/弾/Ex/点 图标」（此前我照文档写、未切图 ✗）；owner 表示**实战里从未见过**这类拾取物 ⇒ **拾取路径很可能不是实战中「送」的入口**。
* ★ **实战入口更可能是子弹驱动**（一手，本轮新）：`BulletManager__on_tick`（`0x4146f0`）里 `0x414a56 call 0x41e350`（内部也调 `FUN_0041dff0`）→ 返回 1 时 `mov %al,0xdc3(%esi)`（给该对象打标记）→ `0x414a7b call 0x41dff0` → `FUN_0041dff0` 再调 `FUN_0041d150`（`0x41e2fd`）。

## 3. 固灵／活化灵（✅，一手）

判定与转化在 **`FUN_00408180` 的 `0x40849f`–`0x408503`**（每帧敌机更新里跑）：

| # | 指令（`0x4084xx`，`esi` = 敌机）| 含义 |
| :-: | --- | --- |
| 1 | `mov $0x1000,%edi; test %eax,%edi; jne 0x408526` | 已转化的跳过 |
| 2 | `mov (%esi),%ecx; mov 0x320(%ecx),%edx; mov 0x4(%edx),%ecx` | 取该敌机所属侧的**玩家** |
| 3 | `mov 0x364(%ecx),%eax; test; je 0x408526` | **`player+0x364` ≠ 0 ＝ 领域展开中** |
| 4 | `lea 0x2d74(%esi),%eax; push; call 0x406820` | 领域形状判定：`0x406820` 内 `call *0x30404(%ecx)` = **按角色虚函数**，形状随角色变 |
| 5 | `mov 0x3380(%esi),%edx; or %edi,%edx` | **flags \|= `0x1000`** |
| 6 | `shr $6,%eax; and $7; add $0x16` | **脚本号 := 22 + (flags>>6 & 7)** ⇒ `23/24/25` |
| 7 | `push %eax; lea 0x8(%esi),%ecx; …; call 0x403e00` | 换 `enemy+0x8` VM 的主脚本 ⇒ **换 sprite** |
| 8 | `movw $0xffff,0x3390(%esi)` | 复位 pose 槽 |
| 9 | `push ±500; push $0x2f; …; call 0x43e2f0` | SE `0x2f` |
| 10 | `test %edi,0x3380(%esi); …; call *0x30408(%ecx)` | 带 bit12 的敌机每帧再走**按角色的第二个虚函数** |

* 两张按角色表 = `player+0x30404`（表 `0x4a1a50`）/ `player+0x30408`（表 `0x4a1a90`）⇒ **领域形状/持续作用按角色分**（与 TH19 的 per-character aura 同构）。
