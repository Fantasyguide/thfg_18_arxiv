# 03 — 動物霊の「送り込み」と対戦骨格（TH19）

> **版本**：TH19 v1.10c（`th19.exe`，imagebase `0x400000`）。本文裸地址默认属该版本；引用其他版本须写成 `th20:0x…`。

本文只挖**对战骨架**与**動物霊送り込み**（119 号合成卡「TH09 + TH19」需要的那一半）。
所有结论走五段链：发现 → 推测 → 验证 → 结论（✅/🟡/❓）→ 证据（地址）。
函数名一律用语料库里的 `FUN_00xxxxxx`，**没有地址支撑的一律标 ❓ 并进 §7**。

工具口径：反编译语料 `local/th19.v1.10c/decomp`（`tooling/ghidra/th20_show.py`）、
常量/表用 `tooling/pe_read.py` + 只读的 pefile/capstone 扫描（**未开 Ghidra 库**）。

## 1. 场地模型：TH19 里「两个玩家的场地」怎么表示

### 1.1 承载对象：静态 per-side 记录表 `DAT_005d1a60`（✅）

**发现**：`0x5478f0`（PlayerInf 初始化）里有两行写得极清楚：

```c
(&DAT_005d1a64)[param_2 * 0xf] = param_1;                          // 记录 +0x04 = PlayerInf*
*(undefined4 **)(param_1 + 0x14c44) = &DAT_005d1a60 + param_2 * 0xf; // PlayerInf+0x14C44 = 记录指针
```

**推测**：`&DAT_005d1a60 + side*0xf` 是一张「每侧一份」的静态记录表（`0xf` dwords = `0x3c` 字节）。

**验证**（多路独立）：

- 同一形态出现在全 exe 的 100+ 处（自机、子弹、敌、灵、能力卡、CPU 全都拿它当入口）：
  `0x4f6470`、`0x50bbd0`、`0x50e150`、`0x51d4e0`、`0x548df0`、`0x4fb6f0`、`0x51ffa0`、`0x5217f0`…
- 两个 side 的地址差正好是 `0x3c`：`DAT_005d1a64`（side0+4）/`DAT_005d1aa0`（side1+4）在 `0x51b6c0` 里被当作「对手的 PlayerInf」用。
- `0x50bbd0` 明确写 `*(int *)(param_1 + 0x4c80) = param_2;`（side）→ `0x50d410` 再用它算记录的地址。

**结论** ✅：TH19 的「场地」= **一个 2 项静态数组，每项一套完整子系统**；没有「自己 + CPU 对端」这种不对称结构，
CPU 只是某个 slot 上挂的一个 AI 对象（§2.4）。

| 记录偏移 | 内容 | 建立者（地址） |
| --- | --- | --- |
| `+0x00` | 该侧 **BulletCtrl**（载 `bullet.anm`；自身 `+0x81571c`=side、`+0x815720`=记录） | `0x4f6470` |
| `+0x04` | 该侧 **PlayerInf\*** | `0x5478f0` |
| `+0x08` | 该侧 **EnemyCtrlInf\***（自有敌列表 `+0x4b50`，计数 `+0x4b78`；`+0x4c80`=side） | `0x50bbd0` |
| `+0x0c` | 一个 `~0xFF908` 字节的侧对象（3 个子 task：`0x520b30`/`0x520b00`/`0x520ad0`）❓类名待补 | `0x5217f0` |
| `+0x18` | 该侧 **AuraCtrlInf**（载 `aura.anm`，task `0x1e`/`0x1f`；`+0xC8`=side、`+0xCC`=记录） | `0x548df0` |
| `+0x20` | 一个 task 容器（`+0x2c`=计数，`+0x6a0` 起 task 表）❓类名待补 | ❓ |
| `+0x2c` | **每侧「参数/状态」对象**：`+0x08`=操作模式、`+0x0c`=角色 id、`+0x1c`/`+0x18`=血条值、`+0xa8…+0xb0`=能力旗标 | ❓（读取见 §6） |
| `+0x30` | 每侧对象（`+0x6410` 起 205 项 × `0xC8`；task `0x1b`）❓ | `0x51ffa0` |
| `+0x34` | 该侧 **CPU AI**（`0x4fb6f0`，分配 `0x36eecc`，vft `CPUHit*Inf`） | `0x4fb6f0` |
| `+0x38` | 该侧 **ExtraAttackInf\***（额外攻击管理器） | `0x50e150` |

> `+0x04` 的 PlayerInf 大小 = `0x14c48`（`0x548df0` 里 `FUN_004d6b50(0x14c48,4)` + vft `PlayerInf__vftable`）；
> 它在 `+0x14C40` 存自己的 side、`+0x14C44` 存记录指针、`+0x68C/0x690` 存坐标、`+0x2238` 存 `pl%02d.sht`。

### 1.2 两个实例怎么建出来（✅ 的关键一步）

**发现**：一段没进语料库（Ghidra 未建函数）的代码里，连着两次调用同一个「建一侧」函数：

```
0x00518612  xor  ecx, ecx
0x00518614  call 0x548df0        ; side 0
0x00518626  mov  ecx, 1
0x00518626  call 0x548df0        ; side 1
0x0051889d  call 0x4f6470        ; BulletCtrl
0x00518a0c  call 0x50bbd0        ; EnemyCtrlInf
0x00518ad1  call 0x51d200        ; GhostCtrlInf（全局单例）
```

`0x548df0(side)` 内部：`FUN_004d6b50(0x14c48)`→`0x42f440`（PlayerInf ctor）→`0x5478f0`（注册进记录）
→ AuraCtrl → `0x51ffa0`（`+0x30`）→ `0x50e150`（ExtraAttackInf，`+0x38`）→ **若 `[record+0x2c]+8 == 1` 则建 CPU AI**（`0x4fb6f0`）。

**结论** ✅：一场比赛 = 「跑两遍 `0x548df0(0/1)`」+ 建两个 BulletCtrl/EnemyCtrl + 一个 GhostCtrl 单例。
`0x548df0` 在语料库里**没有调用者**，正是因为它的调用点落在 `0x518xxx` 这段未反编译的洞里（§7）。

### 1.3 「送り込み」的底层开关：当前生成侧 `DAT_005d19bc+0x710`（✅）

**发现**：

```c
// 0x40a6e0 —— 单行 setter
void FUN_0040a6e0(undefined4 param_1) { *(undefined4 *)(DAT_005d19bc + 0x710) = param_1; }

// 0x4f6470（BulletCtrl ctor）建自己那一侧的子弹管理器时
*(int *)(iVar2 + 0x710) = param_2;

// 0x50df40（ExtraAttackInf 每帧）每帧把生成侧复位成「自己」
*(undefined4 *)(DAT_005d19bc + 0x710) = *(undefined4 *)(param_1 + 500);

// 0x423d30 / 0x421dd0 / 0x420140（Extra 弹体发射时）改成「对手」
*(int *)(DAT_005d19bc + 0x710) = 1 - *(int *)(param_1 + 0x774);
```

`0x51afe0`（GhostCtrl 每帧）结尾再把它复位成 `0`。

**结论** ✅：`DAT_005d19bc+0x710` = **「这一帧新建的东西落在哪一侧的场地」**。
「送り込み」= 生成前把它设成 `1 - 自己`。

### 1.4 送过去落在**谁**的子系统里（✅ 最强证据）

`0x50d410`（建 EnemyInf）内部用第一个参数（EnemyCtrl）的 `+0x4C80` 决定 side。
而发射点的实参是**算出来的对手 EnemyCtrl**：

```
0x00423dd1  mov  edx, <owner*0xf>          ; owner = 自己的 side
0x00423dcd  mov  ecx, 0x5d1aa4             ; = &DAT_005d1a60 + 0x44 = side1 记录 +0x08
0x00423dca  shl  edx, 2                    ; *4 → 0x3c 步长
0x00423dd2  sub  ecx, edx                  ; side0 时 = side1 的 EnemyCtrl；side1 时 = side0 的
0x00423de1  mov  ecx, dword ptr [ecx]
0x00423de3  call 0x50d410                   ; 把敌人建到「对手」的 EnemyCtrl 里
```

`0x51b480`（灵寿命到期 → 放敌人）用同一套算法（`0x51b58c` 起）。

**结论** ✅：**「送进对手场地」= 用 `*(0x5d1aa4 - owner*0x3c)` 取对手 EnemyCtrl 建敌人 + 同时把
`DAT_005d19bc+0x710` 设成 `1-owner`**。两条独立机制互相印证（同源常量 `0x5d1aa4` 与 `1-owner`）。

## 2. 胜负与流程

### 2.1 `GameRuleTaskInf` 的真相：它是**对战规则＆让子设定菜单**，不是比赛引擎（✅）

**发现**：类名容易误导。`0x51a740`（ctor）分配 `0x314` dwords = `0xC50`，写 vft `GameRuleTaskInf__vftable`，
存全局单例 `DAT_005d1a5c`；它注册的两个 task 是 `FUN_00519760`（id 10）与 `LAB_00519750`（id `0x5c`）。
`FUN_00519760` → `0x519a60`：一个**光标/文字菜单**，7 行设定，
用 `PTR_s_…` 串表（`0x59aacc`/`0x59aac0`/`0x59aab0`/`0x59aa9c`/`0x59aa8c`，标题串在 `0x59aaf0`）。

**验证**：`0x59aaf0` 的串解出来是 **「対戦ルール＆ハンディキャップ設定」**；各行取值：
`無し/3min/5min/7min/10min/15min/20min`（`0x59aacc`）、`１本勝負/２本先取/３本先取`（`0x59aac0`）、
`無し/ランダム/自分のカードのみ/全てのカードから選択`（`0x59aab0`）、`1..5`（`0x59aa9c`）、
`常にバリア無し/手動回復のみ/時間長め/時間早め`（`0x59aa8c`）。

**结论** ✅：`GameRuleTaskInf` = **vs 模式专用的「对战规则 + 让子」设定画面 task**；
7 行设定写进 3 个结构（见 §2.2）。真正的比赛循环在 §2.3 的另一个对象上。

### 2.2 槽与每帧入口（✅）

| 槽 | 地址 | 干什么 |
| --- | --- | --- |
| `+0x00` | `0x413b20` | 析构（先写回 vft，再逐个释放 `+0x220` 起 60 个菜单 task） |
| `+0x04` | `0x409d50` | 启动：把两个子 task（`+0x08`/`+0x0c`）状态位 `\|= 2` |
| `+0x08` | `0x402460` | 空（`return 0`） |

- 每帧入口：全局 task id **10** → `FUN_00519760` → `0x519a60`；另一个 task id `0x5c` = `LAB_00519750`（绘制）。
- 阶段字段 `+0x310`：setter = `0x413ab0`（顺带清零 `+0x1cc/+0x1d0/+0x1c8` 计时）；
  `0x519a60` 只在三处调用它：`→1`、`→2`（×2）⇒ 现知阶段值只有 0/1/2 🟡（可能还有别处写，见 §7）。
- 当前选中行 `+0x14`（0…6）；行显示刷新 `0x519770`（7 个文本 task 在 `+0x248`…`+0x260`）。

设定项写入的**位域**（`0x519a60` 里按 `+0x14` 分支 XOR 翻转，指针读自 `+0x214`/`+0x218`/`+0x21c`）：

| --- | --- | --- | --- |
| `+0x214` | bit0-3 | 時間制限 | `0x59aacc`（無し/3/5/7/10/15/20 min） |
| `+0x214` | bit4-5 | 本数（rounds） | `0x59aac0`（1/2/3 本先取） |
| `+0x214` | bit6-7 | 能力卡规则 | `0x59aab0`（無し/ランダム/自分のみ/全部） |
| `+0x218` | bit0-2 / bit3-5 | **side0** 让子等级 / バリア模式 | `0x59aa9c` / `0x59aa8c` |
| `+0x21c` | bit0-2 / bit3-5 | **side1** 让子等级 / バリア模式 | 同上 |

> ✅ 顺带一手核到「vs 模式有让子、且**逐侧**」——这是 TH09 时代没有的骨架变化。

### 2.3 比赛骨架（match object）：`0x518xxx`（🟡，部分在洞外）

`0x5185c0` 一带的 `this`（暂称 match object，`[ebp-0x24]`）在建两侧之后注册两个 task：

| 项 | 地址/偏移 | 内容 |
| --- | --- | --- |
| task id `0x13` 入口 | `0x516400` → `0x516450` | 比赛每帧（见下） |
| task id `2` | `0x5163c0`（未反编译） | ❓ 绘制/前处理 |
| 倒计时/计时 | `+0x14` | 与 `0x1e`(30)、`0xdd4`(3540=59s)、`0xe10`(3600=60s) 比较 |
| 状态旗标 | `+0x140` | bit1/bit4/bit7/0x10/0x4000/0x10000/0x40000/0x8000000… |
| 结束/结算计数 | `+0x144`、`+0x148`、`+0x14c` | `+0x144` 递减到 0 时清 `0x40000` 位并清两侧 Extra 的 `+0xb8` |

`0x516450` 每帧做三件与「送り込み」直接相关的事（✅ 部分）：

1. `DAT_005d19bc+0x710` 由 `0x50df40` 复位；随后**遍历两侧** `DAT_005d1a98`（`+0x38`，步长 `0xf`）
   调 `[[record+0x38]+0x18]` 的槽 `+0x48`（= `ExtraAttackCharaBaseInf` 槽 18 = `0x50d980`）。
2. 血条同步：`PlayerInf+0x2274 = *(PlayerInf+0x2238)+0x28`（两侧都做，`0x516450` L214775/L214780）。
3. `+0x140 & 0x10000` 置位时走结算路径：`FUN_005346b0()`（随机数 `<0x2b` 时）与
   `FUN_005349e0(1, *DAT_005d1c04)`（往存档/profile 写），并 `FUN_00413660()`。⇒ **🟡 这段就是「分出胜负后的结算」**，
   但**判定条件本身**（比较谁的血条、谁先过线）尚未定位 —— 见 §7。

### 2.4 story / vs 的差异（🟡）

- 画面/模式分派在 `0x558680`，读 `*(int *)(param_1 + 0x2c)`（0/1/2…）。**只有部分分支**才
  `FUN_0051a740(...)` 建 `GameRuleTaskInf`（例如 `case 3 / case 2` 里 `0x51a740(&DAT_0062be08,&DAT_0062be0c)`，
  以及 `case 9` 里 `0x51a740(FUN_00563160(0), FUN_00563160(1))`）。⇒ **规则/让子画面只在有对端的模式里出现**。
- 每侧是不是 CPU：`0x548df0` 读 `[[record]+0x2c] + 8`，`== 1` 才建 CPU AI（`0x4fb6f0`）。
  ⇒ 同一份骨架，story 模式只是把某一侧的模式位设成「CPU」。

## 3. 動物霊「送り込み」

### 3.1 三种灵的类型码（✅，两路独立互证）

**发现**：`0x509980`（敌人受击判定）里有一串「免疫」检查，读**被攻击方**记录的 `+0x2c` 对象：

```c
iVar2 = *(int *)(*(int *)(param_1 + 0x563c) + 0x2c);          // param_1 = EnemyInf+0x1230 的子对象
... (*(char *)(iVar2 + 0xae) == 0 || ((uVar6 & 0x700000) != 0x200000))   // kind==2
... (*(char *)(iVar2 + 0xaf) == 0 || ((uVar6 & 0x700000) != 0x300000))   // kind==3
... (*(char *)(iVar2 + 0xb0) == 0 || ((uVar6 & 0x700000) != 0x400000))   // kind==4
```

**验证**（交叉对名，两路独立）：

1. 三张「無効化」能力卡写的正是这三个字节：`0x409410`（Enoko2=オオカミ霊無効化）→`+0xae`、
   `0x409300`（Biten2=カワウソ霊無効化）→`+0xaf`、`0x409520`（Chiyari2=オオワシ霊無効化）→`+0xb0`；
   而 Enoko 属 Saki 的勁牙組（狼）、Biten 属 Yachie 的鬼傑組（獺）、Chiyari 从属饕餮（鷲）。
2. `0x51b480` 的 switch 把 kind 直接映射成 anm 脚本名：`1→GhostPure`、`2→GhostWolf`、
   `3→GhostOtterR/L`、`4→GhostEagle`（串在 `0x59ade8`/`0x59adf4`/`0x59ae00`/`0x59ae0c`）。

**结论** ✅：**kind 2 = オオカミ、3 = カワウソ、4 = オオワシ**（1 = 普通霊 GhostPure）。
存在敌人身上的 flag 字是 **`EnemyInf+0x63A0` 的 bit20-22**（`0x700000`）。

> ⚠ 反编译陷阱（本文档最值钱的一条）：语料库里读作 `param_1 + 0x5170` / `+0x563c` 的那些函数，
> 其 `param_1` 其实是 **`EnemyInf+0x1230` 处的内嵌子对象**（`0x50d467`：`lea ecx,[edi+0x1230]; call 0x411320`）。
> 换算：子对象 `+0x5170` = `EnemyInf+0x63A0`（类型旗标）、`+0x563C` = `EnemyInf+0x686C`（记录指针，ctor 里与 `+0x68E0` 同值）、
> `+0x48/0x4c` = `+0x1278/0x127C`（坐标）。**跨函数读偏移前必须先确认 this 是哪个基址。**

### 3.2 送り込み一手链（✅）

| 步 | 谁 | 干什么 | 地址 |
| --- | --- | --- | --- |
| 1 | 敌方 `EnemyInf` 在**你的场地**被打死 | 按自己的 kind 放灵：kind 2/3/4 → 放 `kind=1` 的 ghost，数量取自 `+0x14d4`；kind 5→ghost kind 3；kind 6→ghost kind 4 | `0x50c1f0`（`FUN_0051d4e0(enemy+0x68DC, …)`） |
| 2 | ghost 在场地里游荡 | 有寿命：`+0x28 <= +0x38` 前一直在；位置由 `0x51b6c0` 按 kind 设定 | `0x51afe0`、`0x51b6c0` |
| 3 | **寿命到期** | 取**对手 EnemyCtrl**建 `EnemyInf`，脚本 = `GhostWolf`/`GhostOtterR,L`/`GhostEagle`/`GhostPure`，并置 `+0x710 = 1-owner` | `0x51b480`（`0x51b5a2`/`0x51b621`/`0x51b68f` 三处 call `0x50d410`） |
| 4 | 另外一条路：`ExtraAttack` 发射 | 取对手 EnemyCtrl建 `EnemyInf`，脚本 `ExAttack`（或 `ExAttackW/O/E`），HP 由块给 | `0x423d30`、`0x421dd0`、`0x420140` |

「ExAttackW/O/E」是一张 3 项串表，**索引 = 灵的种类**（W=Wolf/O=Otter/E=Eagle）：

| 表地址 | 项 | 串 |
| --- | --- | --- |

### 3.3 「送进对手场地」改的是**谁**的字段（✅，问题③的正面回答）

## 5. `GhostCtrlInf`（霊/幽灵）：動物霊是不是同一套东西

**结论** ✅：**是同一套**（一手判定，不是类比）：

## 6. 能力卡与这套的接缝

### 6.1 结构（✅）

能力卡对象的 `+0x5c` 在工厂 `0x4deba0` 里被写成 `&DAT_005d1a60 + player*0xf`（记录指针），
而卡的「效果钩子」槽（`AbilityCardInf` vftable 槽 8 = `+0x20`）一律长这样：

```
mov eax,[ecx+0x5c]   ; 卡 -> 记录
mov eax,[eax+0x2c]   ; 记录 -> 每侧「参数/状态」对象（§1.1 表 +0x2c）
mov byte [eax+OFF], 1
```

⇒ **动物灵类能力改的是「自己那一侧的 `[记录+0x2c]` 对象」的字节旗标**。
