### 0.1 共用骨架：per-player 记录表 与 「自场地状态块 S」

后面五节都挂在同一套结构上，先立骨架。

#### 0.1.1 记录表 `DAT_005d1a60`

**发现**：exe 里有一张以玩家序号索引的记录表，**步长 0xf dword（0x3c 字节）**，`&DAT_005d1a78` = `&DAT_005d1a60 + 0x18`。
**验证**：能力卡工厂 `FUN_004deba0` 写 `puVar4[0x17] = &DAT_005d1a60 + iVar7 * 0xf;`（`iVar7 = *(int*)(manager + 0x1000)` = 玩家序号）；
`&DAT_005d1a64`（= +0x4）与 `&DAT_005d1a78`（= +0x18）都按同一 `idx*0xf` 索引。
**结论**：✅（v1.00a）记录表就是「自场地的根」，各系统的对象都往这里登记。

| 记录偏移 | 内容 | 登记点 |
| --- | --- | --- |
| `+0x00` | 该玩家的「场地对象 A」（载 `bullet.anm`，后续管弹） | `FUN_004f6470`（`(&DAT_005d1a60)[p*0xf] = param_1`） |
| `+0x04` | 该玩家的 stage 对象 B（尺寸 `0x14c48`，`B+0x14c44` 回指记录） | `FUN_005478f0`（`(&DAT_005d1a64)[p*0xf] = param_1`） |
| `+0x18` | `AuraCtrlInf*`（除霊オーラ控制器） | `FUN_004e8780`（`(&DAT_005d1a78)[p*0xf] = iVar2`） |
| `+0x2c` | **`S` = 自场地状态块指针**（本文的核心） | 能力卡全部经 `[card+0x5c]+0x2c` 读写 |

> `[card+0x5c]` 就是记录指针：卡工厂 `FUN_004deba0` 里 `puVar4[0x17] = &DAT_005d1a60 + iVar7 * 0xf`（`0x17` ×4 = `+0x5c`）。

#### 0.1.2 自场地状态块 `S` 全字段

## 1. 除霊オーラ

### 1.1 `AuraCtrlInf` 与 19 个 `Aura<角色>Inf` 的关系

**发现**：每 player **一个** `AuraCtrlInf`（尺寸 `0xd0`，Task 派生）；它每帧按角色 id 从 `.rdata` 跳表建**一个**角色专用 `Aura<角色>Inf` 并挂在 `+0x8c`。
**验证**：`FUN_004e8780` 的建场链 —— `FUN_004d6b50(0xd0,4)` → `FUN_0040af20`（vftable `0x5a83c0`）→ `FUN_004ce870(0x3e,"aura.anm")` 存 `+0x10`
→ `+0xc8 = 玩家序号`、`+0xcc = &DAT_005d1a60 + idx*0xf`、`(&DAT_005d1a78)[idx*0xf] = 该控制器`（登记进 `record+0x18`）。
dtor `FUN_0040b110` 里 `(&DAT_005d1a78)[param_1[0x32]*0xf] = 0` 反证 `[0x32]`(=`+0xc8`) 是玩家序号。
**结论**：✅（v1.00a）**1 控制器 : 1 角色オーラ**，控制器是常驻的、角色オーラ是它的产物（不是 20 个并列对象）。

每帧入口 `AuraCtrlInf::vftable[1]` = `FUN_004e9740`：

- `*(int*)(DAT_005d19bc + 0x710) = *(int*)(this+0xc8)` —— 把「当前玩家」写进全局；
- 复位ゲージ组（`+0x90/+0x94/+0x98/+0x9c/+0xa0`）；
- `iVar3 = *(int*)(*(int*)(this+0xcc) + 0x2c) + 0xc` → `clamp(..., 0, 0x13)` → `iVar3 = table[iVar3](this+0xc8)`，
  **`table` = `PTR_FUN_005a0280`（20 项，`[19]=0`）**，结果存 `this+0x8c`；
- 建一发 anm 0 的子弹存 `this+0xb8`（オーラ底座的视觉载体）。

### 1.4 `@AUN2`「オーラの範囲UP」改的是哪个字段

**发现**：`AbilityCardAun2Inf`（vftable `0x5a7ffc`）**只覆写虚表槽 12 与 21**，槽 12 = `0x4085c0`。
**验证**（指令级）：

## 2. 霊撃

### 2.1 「霊撃」在代码里是什么

**发现**：`EX<角色>Inf`（19 槽）的**槽 4（`+0x10`）= 该角色的ゲージアタック**；Reimu 的槽 4 直接构造 `EXReigekiInf`。
**验证**：`vt.py` 反查 `0x53af60` → `EXReimuInf`（vftable `0x5a8a18`）槽 4；函数体 `FUN_004d6b50(0x7b8,4); FUN_00417400(); *_Dst = &EXReigekiInf__vftable;`
（`EXReigekiInf` vftable `0x5a8ab8`，19 槽表里的 `EXMamizouInf` 槽 4 则是 `0x420380`）。
**结论**：✅（v1.00a）`EXReigekiInf` 是 **Reimu 的霊撃/ゲージアタック本体**（尺寸 `0x7b8`），继承自 `ExtraAttackBaseInf`
（dtor `0x417130` 把 vftable 回写成 `ExtraAttackBaseInf__vftable` 并释放 `0x7b8`，基类 dtor `0x4170c0` 释放 `0x77c`）。

| `EXReigekiInf` 槽 | 偏移 | 函数 | 语义 |
| --- | --- | --- | --- |
| 0 | `+0x00` | `0x417130` | deleting dtor（`0x7b8`） |
| 1 | `+0x04` | `0x53b920` | **发动/初始化** |
| 2 | `+0x08` | `0x53b3a0` | **每帧更新（含消弭）** |
| 3/4 | `+0x0c/+0x10` | `0x409900` | `return 0` 占位 |
| 5 | `+0x14` | `0x53b280` | 停止/销毁（释放 3 个玉、摘链） |

### 2.2 次数 / 效果时间 / 发动条件 在哪些字段

**发现**：次数不是 `EXReigekiInf` 的字段，而是 `S+0x68`（残数）与 `S+0x74`（上限）；效果时间由 `S+0x90`（%）缩放。
**验证**：三个独立一手点 ——
1. `FUN_00537c30(S, n, sound)` 的唯一外部调用者是 `AbilityCardNazrin1Inf` 槽 12（`0x4085e0`）：`push 0; push 2; mov ecx,[S]; call 0x537c30` ⇒ `S+0x68 += 2`，然后饱和到 `S+0x74`；
2. `FUN_004ed6d0`（Bomb 族）`S+0x68 = clamp(S+0x68,0,10)` 后 `0 < 残数 && …` 才是「可用」；
3. `FUN_004ed7d0`（ボム发动）里 `iVar6 = S+0x68 - 1; S+0x68 = max(iVar6,0);` ⇒ **消耗一发**。
**结论**：✅（v1.00a）

## 3. チャージ —— **蓄力攻击（5 段ゲージ），不是资源槽**
