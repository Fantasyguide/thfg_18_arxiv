## 0. 一句话结论

1. **三个半径全部钉死**：**进入吸引 96 px**、**脱离（迟滞）128 px**、**收点 20 px**；三者都是**平方距离**、
   圆心都是**自机坐标** `PLAYER_PTR+0x5b8/0x5bc`（= 判定框中心，没有第二个「吸收点」）。
2. **道具（P 点）根本没有「半径」**：它是玩家周围的**方框** —— 非聚焦 ±30 px、聚焦（Shift）±50 px；
   **收点方框只有 ±15 px**。⇒ 用户 ① 成立：**神灵吸附 96 px ≫ 道具吸引 50 px**。
   ⚠ 但反过来说，**神灵的收点（20 px 圆）比道具收点框的角点（15√2≈21.2 px）还小**。
3. **灵界不改吸引半径、不改速度**：`SpiritItem__on_tick` 里**零处**读 `GAME_FLAGS`(`0x4be830`)。
   灵界做的是「进/出灵界时把**场上所有**神灵的 anm 脚本整体换掉」——`0x439280`（换 `type*6+4`）/
   `0x4393a0`（换回 `type*6+1`）。这是 **01 §2.3/§6.3 漏掉的一条**（01 只记了生成时的选择 `0x43907e`）。
4. **「灵界里无条件被吸」只对灵梦成立**：`CHARACTER == 0` 且灵界态（`flags2` bit0）的神灵，
   **距离 ≥ 96 px 也进 state 4 慢吸**（+0.05/帧，上限 4.0），112 px 内转正常快吸
   （`0x4388a1`–`0x4388bb`、`0x438951`）。其余角色灵界里仍只吸 96 px。
5. **打 boss 是按伤害，不是按时间**：引擎侧 `EnemyData+0x3f60`（累计伤害）vs `+0x3ffc`（阈值），
   跨阈值掉 **1 颗 type 1**，阈值按与自机距离加 **200/400/600/1000**（48/96/192 px 分档）。
   死亡瞬间另有一条 **ECL 配置**的爆发通道（`spec1` 窗口帧 / `spec2` 上限颗）。
6. **「所有小怪都掉」只在受伤通道成立**：受伤通道默认对**所有敌人**开，只被 ECL `spec3(1)` 关；
   死亡爆发通道**只有 ECL 显式写了 `spec1/spec2` 的子程序才掉**（21 个 ECL 里 0 处 `spec0`）。
7. **TH18 侧不能照抄 ECL**：TH18 有效 opcode 上限 = **1001**（`th18:0x430dbd`），
   `th18:1000` 落在「万能 no-op」，`th18:1002`+ 直接越界；TH18 的 ECL 数据里 1000–1020 **零使用**。

## 1. 神灵的两个半径与运动

### 1.1 state 机（一手：`SpiritItem__on_tick` `0x438730`，0x6f6 字节）

分派在 `0x43884f`–`0x438861`：`state = [ebx+0x0]`，`dec eax; cmp eax,4; ja` → 表 `0x438e28`（index = state−1）。

| state | 入口 | 行为 | 依据 |
| --- | --- | --- | --- |
| 0 | （无） | 空槽；`SpiritItemManager__on_tick__body` 直接跳过 | `0x438678` |
| 1 | `0x438868` | **漂移**：速度按 `−0.12666667/帧` 衰减（地板 0.13）；出墙翻角 | `0x4387e4`–`0x4387fd` |
| 2 | `0x4388c6` | **被吸**：角度 = 指向自机；速度 = `speed_now`，`+0.3/帧` 上限 12.0 | `0x4388c6`–`0x438949` |
| 3 | `0x438a53` | 直接跳到 switch 之后的公共段 —— 即**不做任何状态转换** | 表 `0x438e28`[2] |
| 4 | `0x438951` | **灵梦专属慢吸**：`+0.05/帧` 上限 4.0；112 px 内转 state 2 | `0x438951`–`0x4389d3` |
| 5 | `0x4389d5` | 引 `ENEMY_MANAGER_PTR->field_1c+0x40`；**本 build 无写点** ⇒ 死代码 🟡 | `0x4389d5` |

### 1.2 三个半径（单位、方向、语义全部钉死）✅

统一量纲：**已经平方过的距离** `dx²+dy²`（float），拿 `fcomp` 与一个**平方后的常量**比。
圆心是 `PLAYER_PTR`（`0x4c22c4`）的 `+0x5b8`(x) / `+0x5bc`(y)。

| 名字 | 值（真实距离） | 常量（一手字节） | 判定指令 | 方向 | 语义 |
| --- | --- | --- | --- | --- | --- |
| **进入吸引** | **96 px** | `0x4aefb8` float `9216.0` = 96² | `0x438887`（state 1） | `dist² ≥ 9216` **不吸**；`<` 才转 state 2 | **吸附半径** ① |
| **脱离（迟滞）** | **128 px** | `0x4aefb4` float `16384.0` = 128² | `0x43891a`（state 2） | `dist² ≥ 16384` 退回 state 1 | 迟滞上界 |
| **收点** | **20 px** | `0x4aee10` **double** `400.0` = 20² | `0x438b17`（普通）/ `0x438cd4`（灵界态） | `dist² < 400` 才收 | **收点半径** |
| 灵梦 慢吸→快吸 | 112 px | `0x4aefb0` float `12544.0` = 112² | `0x4389c2`（state 4） | `dist² < 12544` → state 2 | `CHARACTER==0` 专用 |
| state 5（死代码） | 30 px | `0x4aefa0` **double** `900.0` = 30² | `0x438a37` | `dist² < 900` → state 2 | 无写点 🟡 |

> **`fcomp` 方向怎么读**：`fcomp m; fnstsw ax; test ah,5; jp skip` ⇒ `ST(0) ≥ m` 时跳（C3=1 → PF=1）。
> 所以 `jp` 的那条是「大于等于」，**落下去的那条是「小于」**。收点判定的 `0x438b17`/`0x438cd4` 就是这个形状。

⇒ **01 §4 的两个数（96 / 128）方向是对的，但没写「哪个是进入、哪个是脱离」**。本文钉死：
**96 = 进入吸附，128 = 脱离**。另外 01 的 §4 表头把 20 px 写成「收集半径」是对的。

**「96 是吸引半径」的独立交叉**：这个常量 `0x4aefb8` 在同一函数里**只出现一次**（state 1 分支），
而 state 2 分支用的是 `0x4aefb4`；两者不同 ⇒ 不是同一个数被复用，是**两个独立的迟滞阈值** ✅。

### 1.3 速度 / 加速度 / 目标点

- **目标点 = 自机坐标本身**，不是另一个偏移点 ✅：
  `0x4c22c4` 的 `+0x5b8/+0x5bc` 同时是**判定框** `+0x608..+0x61c` 与**道具框** `+0x146ec..` 的中心
  （`0x4437db`–`0x443871` 用同一对字段建框）。全 exe 没有第二套「吸收点」。
- **加速**（state 2 分支，`0x4388d9`–`0x4388f8`）：
  `speed = speed_now`（`+0x2c = +0x10`），`if (speed_now < 12.0) speed_now += 0.3`。
  常量：`0x4aecdc` float `12.0`、`0x4ae998` double `0.3`。
- **初速**（`spawn_spirit` `0x43919a`–`0x4391bc`）：`speed = 调用参数 + randf()*3.5`（`0x4aef00` = 3.5）。
- **漂移衰减**：`0x4387e4`–`0x4387fd`：`if (0.13 < speed) speed -= 0.12666667`（`0x4aefc8` float `0.13`、
  `0x4aefc0` double `0.12666667`）。
- **位置积分**用引擎通用 `PosVel`：`0x438dd4` 的 `PosVel__update_secondary_fields` +
  `PosVel__step`（`0x4736a0`/`0x473780`），速度/角度写进 `+0x2c/+0x30` 后交给它 ⇒ **没有重力项**（不下落）✅。
- **墙反弹**只对 `flags2` bit1 置位的神灵生效（`0x438773`：`test byte ptr [ebx+0x84], 2`），
  框 = x∈[−192,192]、y∈[0,448]（`FUN_0040bb70` `0x40bb70`：`pos ± 半宽`，参数 `(0,224,384,448)`）。
  480 帧时 bit1 被清（`0x438a6d`）⇒ **寿命到了之后不再反弹**。
- **出界删除**：框 x∈[−224,224]、y∈[−32,480]（`0x438a8a`–`0x438ad4`），出框即 `state=0` + 释放 VM。

### 1.4 对照：TH13 的道具（P 点）**没有半径**，是方框 ✅

这是回答 ① 的关键：TH13 的道具吸引**不是圆形距离判定**，而是**玩家周围的 AABB**。

| 道具用的框 | 玩家字段 | 半宽（Reimu / Marisa / Sanae / Youmu） | 建框指令 | 用途 |
| --- | --- | --- | --- | --- |
| **收点框** | `+0x146ec..+0x14700` | **±15 / ±17.5 / ±15 / ±15** | `0x443877`–`0x44394f` | 道具进框即收 |
| **非聚焦吸引框** | `+0x1471c..+0x14730` | **±30 / ±35 / ±30 / ±30** | `0x4439f1`–`0x443a87` | 进框 → state 4（追踪） |
| **聚焦吸引框** | `+0x14704..+0x14718` | **±50 / ±59 / ±50 / ±50** | `0x443955`–`0x4439eb` | 按住 Shift 时改用这个 |

- 半宽来源：`+0x62c/+0x630 = 0.5 × 表 0x4c0bb8[char]`（表值 **60/70/60/60**，`0x441fe9`–`0x441ffe`）；
  `+0x638/+0x63c = 0.5 × 表 0x4c0bc8[char]`（表值 **100/118/100/100**，`0x44200f`–`0x442026`）。
  两个 FMUL 的**操作码字节已核**（`0x441ff0` = `D8 CA` = `FMUL ST(0),ST(2)`；
  `0x441fc2` = `DC C9` = `FMUL ST(1),ST(0)`），不是猜的。
- **收点框还要再减半一次**：`Player__on_tick` 的 `0x443877` 先算 `0.5×0x62c`，再拿去建 `+0x146ec`
  ⇒ **收点框 = ±15**。吸引框（`0x4439f1`/`0x443955`）用的是**原值** ⇒ ±30 / ±50。
- `Player__initialize`（`0x4420c2`/`0x4421e2`）也写这三个框，但收点框用的是**未减半**的 `0x62c`（=30）
  ⇒ 每帧被 `Player__on_tick` 覆盖成 15。哪个先跑本文未验 🟡，取运行期值 **15**。
- **POC 线**：自机 `y < 128.0`（float `0x4ae9e8`）时，**全屏道具无条件转 state 3（追踪）**
  —— 写入点 `0x42e627`（`ItemManager__on_tick__body`）。这条是全局的，**与道具位置无关**。
  （该浮点常量在函数入口 `0x42e3b0` 被预载进 x87 栈，汇编里判定点不易一眼对应 ⇒ 行为 ✅ / 判定地址 🟡。）
- 道具追踪速度 = 表 `0x4c0bd8[char]`（**5/7/5/6**，写进 `player+0x660` 的 `+8`，`0x441fb0`），
  state 4 时取 `值/3`（`0x42ec59` 附近）；`if (speed < 12.0) speed += 0.2`（`0x42e6xx`）。

**⇒ 回答 ①**：神灵吸附 **96 px（圆）** ＞ 道具吸引 **±50 px（方框，聚焦）** ＞ **±30 px（非聚焦）**
＞ 道具收点 **±15 px**。**用户的直觉成立**，而且差距不小（96 vs 50 的半宽）。
但**收点**是反过来的：神灵 20 px 圆 **小于**道具收点框的角点 15√2 ≈ 21.2 px。

## 2. 灵界中的吸引与外观切换

### 2.1 全 exe 扫 `GAME_FLAGS`(`0x4be830`) 的读者 ⇒ 运动链里零读点 ✅

按函数边界线性反汇编全 exe，含 `0x4be830` 的指令共 **85** 处。其中**读 bit `0x100`** 的只有：

| 函数 | 位置 | 用途 |
| --- | --- | --- |
| `TranceManager__on_tick` / `on_draw` | `0x4057f3` / `0x405d60` | 灵界自身 |
| `Player__on_hit` ×4 角色 | `0x444ca4` 等 | 中弹免伤（01 §7） |
| `Player::die` | `0x444a13` | 免费灵界保命（01 §7） |
| `Spellcard__on_draw` / `BulletManager` 绘制 | `0x4131e2` / `0x40e7c2` 等 | 观感 |
| **`SpiritItemManager__spawn_spirit`** | **`0x438fd0`** | ★ **只在生成时选外观** |

**`SpiritItem__on_tick`(`0x438730`) 一次都没出现** ⇒ **灵界不改变神灵的吸引半径 / 速度 / 收点半径** ✅。

### 2.2 进/出灵界时「全场换脚本」—— 01 漏掉的那条 ✅

| 函数 | 谁调 | 对每个活着的槽做什么 |
| --- | --- | --- |
| `0x439280` | `TranceManager::begin` `0x405b27` | `flags2 bit0 |= 1`；换脚本为 `type*6+4`；重置寿命 zTimer |
| `0x4393a0` | `TranceManager::end` `0x405cd2` | `flags2 bit0 &= ~1`；换脚本回 `type*6+1`；重置寿命 zTimer |

两手都：`for i in 0..255`（stride `0x88`），跳过空槽（`[slot] == 0`），先
`anm_set_interrupt_by_id`/`or [vm+0x1c],0x20` 处理旧 VM，再
`AnmManager__create_vm(TRANCE_MANAGER_PTR+0x10 /*astral.anm*/, script, slot+0x14 /*pos*/, …)`
并把新 VM id 写回 `slot+0x58`。脚本号公式就写在 `0x439323`–`0x439326`（`type*6+4`）与
`0x43941b`–`0x43941e`（`type*6+1`）—— 与 `0x43907e` 的生成期公式**同一条**。

**⇒ 回答 ⑥（外观部分）**：**「灵界时所有神灵变样式」是真的，而且是「进灵界那一下一次性全场换」**，
不是每帧判定，也不是只对新生成的神灵生效。
**01 §2.3 的表头「灵界脚本（生成时处于灵界）」与 §6.3 的「神灵换外观 `0x43907e`」都只写了生成期那半条**，
需订正为「生成期 + 进/出灵界整体换」。

### 2.3 生成时的脚本选择 ✅（复核 01）

`spawn_spirit` `0x43907e`：`test byte ptr [ebx+0x84], 1; jne` → `+4` 分支（`type*6+4`），否则 `type*6+1`。
`flags2` bit0 在 `0x438fd0`–`0x438fe8` 用 `xor` 技巧**按当时 `GAME_FLAGS>>8 & 1` 置位**，
之后**全场换脚本函数只会覆写它、不会清它**；480 帧老化只清 bit1（`0x438a6d`）。

### 2.4 `flags2` bit0 的三重作用（一手汇总）

| 作用 | 读点 |
| --- | --- |
| 选 anm 脚本（生成期） | `0x43907e` |
| **切奖励表**（普通表 `0x438e3c` / 灵界表 `0x438e4c`） | `0x438a53`–`0x438a5b` |
| **使能灵梦 state 4（全屏慢吸）** | `0x4388ae`（`test byte ptr [ebx+0x84], 1`），清位点 `0x43898f` |

⇒ **回答「灵界里神灵是不是无条件被吸」**：**对灵梦是，对其他三个角色不是**。
灵梦 + 灵界态的神灵在 **`dist² ≥ 9216`（即距离 ≥ 96 px）** 时进 **state 4**（`0x4388bb`），
以 **+0.05/帧、上限 4.0** 从**任意距离**飘过来，进入 **112 px** 后转 state 2（快吸）。
非灵梦角色（`CHARACTER != 0`）走的是「远就不吸」的原逻辑。

> `CHARACTER == 0` → **灵梦** 的映射是**推断**（🟡）：依据是判定半径表 `0x4c0ba8` = `[2,3,3,3]`（索引 0 最小，
> 与灵梦的极小判定点相符）＋ 01 已坐实的 `CHARACTER == 2` = 早苗。**索引→角色名的直接证据本文没找到。**

### 2.5 颜色：引擎**不写**神灵的颜色 ✅

`spawn_spirit` 建完 VM 只写：VM id（`0x4390a5`/`0x4390c6`）、`flags2`、位置（`slot+0x14`）；
`SpiritItem__on_tick` 只写 VM 的 `+0x574/0x578/0x57c`（位置，`0x438df6`–`0x438e0d`）；
`0x439280`/`0x4393a0` 同样只写位置。**全链没有一处写 anm VM 的颜色字段。**

`astral.anm` 一手（`thanm -l 13`）核对：**`ins_404`（= `color()`）在全文件只出现 8 次**，
全部落在**普通**脚本里 —— `script2/3`（type 0）、`script8/9`（type 1）、`script14/15`（type 2）、
`script20/21`（type 3）；**灵界脚本 `4/5/6`、`10/11/12`、`16/17/18`、`22/23/24` 一次都没有** ——
灵界版用的是**预先上色的素材** `sprite3..6`（环）+ `sprite7..10`（辉光）。

| 0 | 1 / 2 / 3 | `(0,127,0)` / `(255,32,255)` | 4 / 5 / 6（无 `color()`） |
| 1 | 7 / 8 / 9 | `(63,63,0)` / `(80,80,255)` | 10 / 11 / 12（无） |

但灵界脚本里**没有 `color()` 指令**，那些数值只能来自 `enemy/littlegods.png` 的像素

## 3. 掉落通道 A–F 逐条复核

`call 0x438ec0`（`spawn_spirit`）**全 exe 恰好 6 处** ✅ —— 通道枚举是完备的：

| 通道 | 调用点 | type | speed | sound |
| --- | --- | --- | --- | --- |
| A 受伤阈值 | `0x419de9`（`FUN_00419a90`） | `1` | `2.0` | `1` |
| B 死亡爆发 | `0x419f8e`（`FUN_00419a90`） | `1` | `0.5` | `1` |
| C ECL `spec0` | `0x41f6c1`（opcode 1000） | ECL 参数 0 | `2.0` | `1` |
| D item 10..14 | `0x42f04b`（`ItemManager__spawn_item`） | `item_type − 10` | `0.5` | `1` |
| E 玩家死亡 | `0x4434f3`（`Player__on_tick`） | `3` | `2.0` | `0` |
| F 连锁奖励 | `0x439250`（递归） | `3` | `0.5` | `1` |

**对象基址订正（对 01 的补充）**：A/B 里的 `edi` 是 **`EnemyData` 块**，不是 `Enemy` 本身。
`Enemy__constructor` `0x418f85`/`0x418f9d` 做 `memset(enemy+0x11ec, 0, 0x40f8)`
⇒ `EnemyData = Enemy + 0x11ec`（`0x11ec + 0x40c8 = 0x52b4`，而 `0x418fb9` 正是 `mov [edi+0x52b4], edi`）。
下文所有 `+0x3f60` 这类偏移**都是 `EnemyData` 相对偏移**（01 直接写成 `enemy+0x…`，数值对、基址没交代）。

### 3.1 通道 A：按**累计伤害**掉 ✅（回答「按血量还是按时间」）

`FUN_00419a90`（每帧的敌人伤害结算）里的原文（一手汇编 `0x419d8a`–`0x419e8a`）：

```
edx = [edi+0x3f60]            ; 累计伤害（由 FUN_004179e0 0x4179e0 累加，或 0x419d7a 直接 +=）
cmp edx, [edi+0x3ffc]         ; vs 阈值
jl  0x419e41                  ; 未跨阈值 → 只把冷却计时器重置为 30
cmp dword ptr [edi+0x4004], 0x14   ; 冷却计时器（倒计时）> 19 ?
jl  0x419dee                  ; 不够 → 不生成
... dist² to player ...
test byte ptr [edi+0x4034], 2 ; spec3(1) 关掉掉落 ?

spawn_spirit(mgr, 1, edi+0x44, 2.0, 1)   ; ← 0x419de9：掉 1 颗 type 1
0x419dee: 阈值 += 200/400/600/1000（按 dist² 分档）
0x419e3b: [edi+0x3ffc] += 桶值
0x419e41: [edi+0x4008]=30.0; [edi+0x4004]=30; [edi+0x4000]=29
```

| 项 | 一手值 | 地址 |
| --- | --- | --- |
| 累计伤害字段 | `EnemyData+0x3f60`（int） | `0x419d7a` |
| 阈值字段 | `EnemyData+0x3ffc`（int） | `0x419e3b` |
| 阈值初值 | **0**（`memset(enemy+0x11ec,0,0x40f8)` 覆盖到 `+0x51e8`） | `0x418f9d` |
| 掉几颗 / type | **1 颗 / type 1** | `0x419de7`/`0x419de9` |
| 距离分档（dist²） | `<2304`(48²)→**+200**；`<9216`(96²)→+400；`<36864`(192²)→+600；否则 **+1000** | `0x419dee`–`0x419e3b` |
| 常量 | `0x4af014`=2304.0、`0x4aefb8`=9216.0、`0x4af010`=36864.0 | 一手直读 |
| 冷却 | 计时器 `+0x4004` 倒计时（每帧 `−1.0`，`0x41a3a4`/`0x4732c0`），**>19 才允许掉**；每次受伤都重置为 **30** | `0x419d9c`/`0x419e41` |

**⇒ 回答 B1**：**是「按血量（累计伤害）」，不是「按时间」** ✅。
「时间」只以两种方式间接出现：① 阈值随距离变（越近打掉得越密）；② 冷却倒计时是每帧减的，
所以**持续开火**（每帧都掉血）时冷却恒为 30、判定必过；**停火 >10 帧**后冷却 <20，下一次跨阈值就**不掉**。

> 「越靠近敌人打掉得越密」= 分档桶值 200/400/600/1000 ✅（复核 01 §3.1，数值全对；
> 01 把这句写成「越靠近敌人打，掉得越密」，方向正确）。

### 4.1 与一手**直接冲突**的做法（逐条）

1. ★ **「神灵不下落、不吸引、原地 bob」与一手冲突（①⑥）**。
   一手：神灵有**初速 + 衰减漂移**，进入 **96 px** 就转「加速冲向自机（+0.3/帧，上限 12）」，
   **128 px** 才脱离。这**不是**可选润色，是「神灵」这个对象的**主行为**。
   ⇒ 「我们不做吸引」这个决定是错的；正确做法是把 §1.1–§1.3 的 state 机照搬（state 1/2 + 迟滞 + 加速 + 收点）。
2. ★ **「只有击破一颗 → 1 颗神灵」与一手冲突（⑦）**。
   一手有 6 条通道；最少也要补上**受伤阈值（A）**与**死亡爆发（B）**，
   否则「打 boss 掉灵」这件事在卡里根本不会发生（boss 掉血最多、却永远不死于一次击破）。
3. ⚠ **`TRANCE_SPIRIT_PICK_RADIUS` = 24 px 的「理由」站不住**。
   文件里的理由是「原版会飞向自机，我们不飞 ⇒ 放宽」—— 前半句对（一手确实飞），
   但**结论方向反了**：一手 20 px 是**配合 96 px 吸引**用的终点；一旦吸引也是 96 px，
   自机根本不用走到 24 px 去。**24 px 是在给一个缺失的机制打补丁**，补上 §1 的 state 机后应回到 **20 px**。
   另外 24 px **大于**道具收点框的半宽 15 px，会让神灵比引擎道具更好收 —— 与用户 ① 的直觉反着走。
4. ⚠ **池容量 128 vs 一手 256**：一手 256 槽；且一手**没有「池满就丢」的行为**
   （`spawn_spirit` 线性找第一个空槽，找不到直接 return，`0x438f79`–`0x438f8c`）。
   128 是否够用取决于通道数量，补上 A/B 后单帧可能掉很多颗（BOSS `dropExtra(13,44)`），需重新评估。

### 4.2 与一手**不冲突**、但可以从一手补齐的

- 初速 / 衰减 / 抛向 / 墙反弹 / 出界删（§1.3）；
- 灵界进出时**场上所有**神灵换样式（§2.2）—— 这正是用户 ⑥ 的后半句；
- 灵梦专属 state 4 全屏慢吸（§2.4）—— 若卡要做「灵界 = 全吸」，**这就是一手的依据**，
  但要注意一手把它限定在 `CHARACTER == 0` + 灵界态。
