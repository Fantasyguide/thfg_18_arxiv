## 2. ★★ 分配器：`LaserManager__allocate_new_laser`（`0x448920`，1306 B）

```
undefined4 __stdcall LaserManager__allocate_new_laser(int type, int *spec)   // ret 8
```

| 步骤 | 一手 |
| --- | --- |
| 取 manager | `0x448925  mov edi, ds:0x4cf3f4` ⇒ ★ **LaserManager\* 在 `0x4cf3f4`** |
| 上限 | `0x44892b  cmp [edi+0x798], 0x200` ⇒ ★ **最多 512 条**；满了 `return 0` |
| 序号 | `0x448940  inc [edi+0x79c]`（钳到 ≥`0x10000`）⇒ 返回值就是它 |
| type 分派 | `0x44895f  cmp eax,3 / ja default` ⇒ `0x44896a  jmp [eax*4+0x448e3c]` |
| 建对象 | 每个分支 `push <size>; call 0x48dc71`（`operator new`）→ 调基类 ctor `0x448170`（Line 例外：`0x4482c0`）→ 写 vtable |
| 入链 | `[eax+0x04] = [edi+0x794]`（前一条）、`[ecx+0x08] = eax`、`[edi+0x794] = eax`（★ 链尾）、`inc [edi+0x798]` |
| 初始化 | `push spec` 后 `call [vtable+0xc]`（★ **spec 由各类的 `vtable[3]` 消费**）；Line 分支另有 `[eax+0x80] = 序号` |
| 返回 | ★ **返回序号**（`[edi+0x79c]`），**不是指针** |

## 5. ★ spec 是怎么来的（一手，ECL 侧调用点）

ECL 区 `0x435xxx` 的调用点（`0x435273` 那处）逐字：

```
435251  lea  eax,[ebp-0x548]      ; ★ &spec（栈上）
435268  push eax                  ; param_2 = &spec
435269  push 0x0                  ; param_1 = type = 0（Line）
435273  call 0x448920             ; allocate_new_laser(0, &spec)
```

★ spec **不是** ECL 参数直接传的，而是**从单位/子弹对象拷**：
`[edi+esi+0x5a0]`／`+0x5a4`／`+0x5a8`／`+0x5b4`／`+0x5bc`／`+0x9e0`／`+0xa10`／`+0xa14`
分别落到 spec 的 `+0x10`／`+0x14`／`+0x18`／`+0x1c`／`+0x20`／`+0x2c`／`+0x458`／`+0x45c`（相对 `&spec`）。
⇒ ★ **spec ≈ 0x460 字节**，字段像是 (x, y, z, angle, speed, length, width, …)。

★ 另一条线索（更省事）：`Bullet__run_ex` 里那处调用先用
`rep movs` 从 **`[manager+0x69c]`** 拷 **`0x108` dwords（0x420 字节）** 到栈上 spec，再补几个字段
⇒ ★ **`manager+0x69c` 很可能就是"默认 spec 模板"** —— 卡侧要桥，可以"抄模板 + 改几个字段"，不必从零构造。

## 6. ★★ Curve 的 `vtable+0xc`（`0x44ed70`）—— spec 直接整块拷进对象

```
44ed7c  ecx = 0x118                 ; ★ 0x118 dwords = 0x460 字节
44ed82  esi = [ebp+8]               ; ★ spec 指针
44ed86  edi = ebx+0x788             ; ★ 目标 = 激光对象 +0x788
44ed8c  rep movs                    ; ★ spec 整块拷进 laser+0x788
44ed8e  eax = [ebx+0x7a0]           ; = spec+0x18
44ed9a  [ebx+0x780] = eax           ; （另一个独立字段）
44eda8  [ebx+0x10] = 2 ; [ebx+0x14] = 2
44edbc  call 0x41b430               ; 段/节点数组初始化（esi = laser+0xbe8）
44edcc  cmp [ebx+0x780], 1          ; ★ spec+0x18 == 1 ?
44edd1     ecx=[mgr+0x7b8] ; eax=0x142          → call 0x477d60(esi=laser+0xbe8, eax)
44edee     ecx=[mgr+0x7b8] ; eax=(spec+0x18)+0x8e → call 0x477d60(...)
```

⇒ ★★ **spec 的布局就是 `laser+0x788` 起的那 0x460 字节**（同一份内存）。
⇒ ★ **`spec+0x18` 是"激光外观/类型 id"**：等于 1 时取 sprite `0x142`，否则取 `spec+0x18 + 0x8e`
   ⇒ 与"激光精灵来自 `bullet.anm` 预载表 `[mgr+0x7b8]`"这一条吻合（TH16 是 `mgr+0x604`，TH18 是 **`mgr+0x7b8`**）。
⇒ ★ `0x41b430(laser+0xbe8)` 就是**段/节点数组的初始化** —— 下一轮读它得段结构。

## 9. ★ `0x41b430` = 激光**内置 anm VM** 的初始化（`laser+0xbe8`，0x60c 字节）

`0x44ed70` 里 `call 0x41b430(esi=laser+0xbe8)` 就是它：

```
41b436  movq xmm0,[ecx+0x5f0] ; 41b43f ebx=[ecx+0x5f8] ; 41b446 esi=[ecx+0x548] ; 41b44d edi=[ecx+0x18]   ; 先存
41b450  push 0x60c ; push 0 ; push ecx ; call 0x48f8f0        ; ★ memset(laser+0xbe8, 0, 0x60c)
41b468  eax = 7 ; WORD [ecx+0x534] = 7                        ; ★ 0x534 = 与卡侧 anm VM 的 flags 同一偏移族
41b493  [ecx+0x538] &= ~0x20000 ; |= 0x10000
41b49e  [ecx+0x54] = [ecx+0x58] = [ecx+0x5c] = [ecx+0x60] = [ecx+0x6c] = [ecx+0x70] = 1.0f
```

⇒ ★★ **`laser+0xbe8` 是一个 anm VM（0x60c 字节）** —— 激光的**外观**就是这个 VM；
★ 随后 `0x477d60(laser+0xbe8, sprite)` 给它设 sprite（sprite 由 `spec+0x18` 推出来，见 §6）。
★ 与卡侧的关系：卡侧 `ce_anm_*` 操作的 VM 也是这套字段（`+0x534` flags / `+0x6c` uv_scale）⇒ ★ **同一套 anm VM 结构**。

★ 于是"曲线路径存在哪"的候选缩小为：**spec 拷贝区（`laser+0x788` 起 0x460 B）** 或 laser 对象的其它字段 —— 下一轮定。

## 10. ★★ 曲线不是"存路径点"，而是**逐帧按角速度转的蛇**（`LaserCurve__method_40__curve` `0x451410`）

函数名由 Ghidra 给（`0x451410` = `LaserCurveInf` vtable `+0x40`；与基类槽名 `method_40__curve` 对应）。

```
451412  eax = [edx+0x118] ; cmp eax,[edx+0x148]      ; ★ 已走步数 vs 总步数
45141e  jl 继续 ; 否则 and [edx+0x748], ~0x8 ; return 1     ; ★ bit3 = "还在弯/长"
45142d  xmm1 = [edx+0x12c] * [0x4ccbf0](=1.0f)       ; ★ +0x12c = 每帧角度增量（角速度）
45144f  xmm1 += [edx+0x6c]                            ; ★ +0x6c = 当前角度
451454  把 xmm1 规约到 [−π, +π]（常量 0x4b922c=π、0x4b9260=2π、0x4b9430=−π），循环上限 0x20
45149c  [edx+0x6c] = xmm1                             ; 写回角度
451491  xmm0 = [edx+0x128] ; lea ecx,[edx+0x60]       ; ★ +0x60 = 位置 vec3
```

⇒ ★★ **`LaserCurve` = 每帧把角度 `+0x6c` 加上角速度 `+0x12c`、沿当前角度前进的"蛇"**；
★ `+0x118` / `+0x148` = **已走步数 / 总步数**（到点即清 `+0x748` bit3，停止弯曲）；
★ `+0x60` = 位置 vec3、`+0x748` = 行为位掩码（on_tick 里按 bit 调 vtable `+0x38/+0x3c/+0x40`）。

### 10.1 ★ 这对"可桥性"是好消息

★ 不需要构造"路径点数组" —— ★ **曲线是参数化的**：只要给出
**位置（`+0x60`）、初始角度（`+0x6c`）、角速度（`+0x12c`）、总步数（`+0x148`）** 这几项，引擎自己会把它弯出来。
★ 于是 `spec`（`laser+0x788` 起 0x460 B）里真正要填的是**标量场**，不是数组 ⇒ ★ 卡侧桥的难度**明显低于**上一轮估计。

## 11. ★★ spec → 对象字段的映射（`LaserCurve__initialize` `0x44ef43`–`0x44f001` 一手）

spec 指针 = `laser+0x788`（§6 的 `rep movs` 0x460 B），下面这些是 initialize **从 spec 取出来塞进对象头**的：

| spec 偏移 | 去向 | 语义（据流向与常量） |
| --- | --- | --- |
| `+0x00`／`+0x04` | `[ebx+0x54]`／`[ebx+0x58]` | ★ **位置 x, y** |
| `+0x08` | `[ebx+0x5c]` | ★ 位置 z |
| `+0x0c` | `[ebx+0x6c]` | ★ **初始角度**（§10 的"蛇"就从这个角开始转） |
| `+0x10` | `[ebx+0x74]` | ★ 数量/长度类（整型读入 `mov eax`） |
| `+0x14` | `[ebx+0x78]`；同时与 `+0x24` 一起进 `0x452c90` | ★ 标量（极坐标/偏置计算的一方） |
| `+0x18` | （§6） | ★ **外观/类型 id** ⇒ sprite = `0x142` 或 `id+0x8e` |
| `+0x24` | 参与 `0x452c90`（与 `+0x14` 一起） | ★ 标量（偏置） |

`0x452c90(角度, 半径)` 返回的两个值被**加到位置 x/y 上**（`44ef95`/`44efb5`）⇒ ★ 它是**极坐标 → 偏移**的辅助，用于把出生点沿某角度偏出去。

### 11.1 ★ 于是"最小可行 spec"只要这几项

★ 位置 `+0x00/+0x04/+0x08`、初始角度 `+0x0c`、数量/长度 `+0x10`、标量 `+0x14`、**外观 id `+0x18`**，外加偏置用的 `+0x24`。
★ 其余 ~0x430 字节可以**从模板（`mgr+0x69c`，0x420 B）抄默认值** ⇒ ★ 这就是"卡侧最少要填几个字段"的答案雏形。

## 12. ★ manager 的构造/销毁（前置条件定案）

★ **构造**（`0x442c45` 起，引擎在游戏启动时调）：

```
442c45  push 0x7c4 ; call 0x48dc71        ; ★ operator new(0x7c4)
442c57  lea ecx,[esi+0xc] ; call 0x448170 ; LaserBaseClass__constructor 给 mgr+0xc
442c5f  memset(esi, 0, 0x7c4)
442c6f  [esi+0x79c] = 0x10000             ; ★ 序号初值
442c79  ds:0x4cf3f4 = esi                 ; ★ 存全局
442c7f  push 0x4b636c ; push 7 ; call 0x486880
442c8b  [esi+0x7b8] = …                   ; ★ 精灵表指针（+0x7b8，§6 用）
```

★ **销毁**（`0x448720` 一带）：`call 0x442480`（destroy_all）→ `ds:0x4cf3f4 = 0` → `[esi+0xc] = 0x4b68ec` → `operator delete`（`push 0x7c4`）。

⇒ ★★ **前置条件结论**：
* ★ **卡侧不需要初始化 LaserManager** —— 它是引擎在游戏启动时建的**堆单例**（0x7c4 字节），全局指针 `0x4cf3f4`；
* ★ 卡侧只要**判空**（`*(void**)0x4cf3f4 != 0`）就能安全调用 `allocate_new_laser`；
* ★ 精灵表在 `mgr+0x7b8`，也是引擎灌好的 ⇒ 不用自己预载；
* ★ tick 由 `LaserManager__on_tick 0x4488c4` 每帧跑（`ds:0x4cf2a4 == 0` 时先做死亡清扫 `0x448760`）。

★ `0x448760` 不是初始化函数，★ 是**每帧的死亡清扫**（遍历 `mgr+0x14` 链，读节点 `+0xc` 状态位，`(flags&6)>=4` ⇒ `vtable+0x18` + 解链 + `dec [mgr+0x798]`）。

### 16.1 结构（一手）

```

                      shl eax, 5               ; ★ ×0x20 ⇒ 每段 32 字节
```

### 16.2 ★ 循环体在干什么（一手，`0x4503e1`–`0x4504b0`）

⇒ ★ ★ **段长 = hypot(Δx, Δy)**（就在这两个字段里，不需要另找）✓

**数组 A（`+0x1804`，0x38/段）—— 画法**：
`[+0x0c] = 1.0f`（缩放）、`[+0x10] = −1`、`[+0x14] = 0`、`[+0x18] = [laser+0xf98]`（贴图/颜色 id）。

### 16.7 ★★ 结论：曲线激光 = 「把一条运动轨迹铺成实体」

★ 三个量合起来就是"运动"：
1. ★ **每帧一段**（`+0x118++`，`0x451537`）；
2. ★ **每段的 Δx/Δy**（数组 B `+0x04/+0x08`）—— ★ 即该帧的位移；
3. ★ **角度**（`+0x6c += +0x12c`，段 4 时 `+0x12c = ∓11.25°/帧`）。

⇒ ★★ **曲线激光 = 把"每帧位移"连成一条实体光带** ⇒ ★ **前方有一个"生长头"以该速度前进，身后留下实体**。
★ 这同时解释了：★ 为什么看起来"在动"、为什么"是一条光的实体"、为什么"转弯是连续的"。

1. ★ `+0x12c`（角增量）在**全仓**只有这些写点：`419c8a`、`437066`、`43bd30`、`444e72`、**`449764`（`LaserLine__run_ex`）**、
   `4535aa`、`454cc4`、`456334`… ⇒ ★ ★ **没有任何一处在 `0x450xxx`（`LaserCurve__run_ex`）**
   ⇒ ★ **曲线激光从不写 `+0x12c`**；
2. ★ 曲线对象在创建时被 memset 的范围是 `[0,0x788)`（基类 ctor `0x4481a2`）＋ `[0x788,0xbe8)`（type=2 分支 `0x448c9f`）
   ⇒ ★ `+0x12c`（= 300）落在 `[0,0x788)` ⇒ ★ **初值 = 0**；
3. ★ 而 `method_40__curve`（`0x451410`）的角更新就是 `[+0x6c] += [+0x12c]` ⇒ ★ ★ **增量恒 0 ⇒ 角恒定不转**。

★ 另外：`method_1c` 造子曲线时**不写子 spec 的角度槽**（`[esp+0x64]` 无访问）⇒ ★ 子曲线**继承同一个角**。

### 24.2 ★★ 结论：TH18 的曲线激光是"**直的光带链**"，没有转弯能力

★ 所以 ★ **`609` 那套"8 帧转 90°"的语义不可能在 TH18 的激光代码里实现** —— ★ 与 §19.17 呼应：
★ **TH18 的 `609` 只是 20 字节守卫**，★ 而 **TH19 的 `609` 是真变换 op（`0x5027a3`）**。

★★★ **所以：早苗 C3 的转弯必定由 TH19 自己的引擎实现** ⇒ ★ **必须改读 `th19.exe` 的激光子系统**
（用 RTTI 名 `.?AVLaserCurveInf@@` 在 `th19.exe` 里定位，同 §1 的方法）。

### 24.3 ★ 方法（下一轮直接照做）

1. ★ 在 `local/th19.v1.10c/th19.exe` 里搜 `.?AVLaserCurveInf@@` ⇒ TypeDescriptor → COL → **vtable**；

★ ❗ ★ **这一步是把"读错引擎"纠正过来** —— ★ 前面 §16–§23 关于 TH18 激光对象的结论**仍然是一手**（对象/段/分配器/音效 id/判定尺寸），

## 26. ★★ TH19 的 `609` 落点：`[edi+0x5ac]` → `+0x28` 的段表（一手）

★ 接着读 TH19 的 `609` handler（`0x5027a3`）中段：

```
502808  lea ecx,[edi+0x4e2c]        ; ★ 弹型记录的另一块
50280e  call 0x40eaa0               ; 元素访问
50282a  lea ecx,[edi+0x5ac]         ; ★ ★ **弹型记录基址（与 `602` 同一块）**
502832  call 0x40ebd0               ; 元素访问（按段号取元素）
50283b  lea ecx,[eax+0x28]          ; ★ ★ **该元素的 `+0x28` = 段表**
50283e  call 0x40ee50               ; 再取一层
50284f  [eax+0x24] = esi            ; ★ ★ 写 **段表项 `+0x24`**（= 参数之一）
50285b  … 继续按 opcode 分派写后续项
```

★★ 三条：
1. ★ `609` 的段表**挂在弹型记录 `[edi+0x5ac]` 的元素 `+0x28` 上**（★ 不是激光对象！）；
2. ★ 段表项内的偏移从 **`+0x24`** 开始（与我早先记的 `+0x24/+0x20/+0x10/+0x14` 一致）；
3. ★ 参数取值走 TH19 的两个 helper：★ `0x50c1b0`（**整型**参数）、★ `0x50c1d0`（**浮点**参数）——
   ★ 所以 `609` 的 `r`/`s`（第 7/8 个 float）应由 `0x50c1d0` 取出后写进段表某两个偏移。

★ ❓ 下一步（一步就能定）：★ 在 `0x5028xx` 之后找 **`call 0x50c1d0` 后面的 `movss [eax+0xNN], xmm0`**
★ ⇒ 那两个 `NN` 就是 `r`/`s` 的落点；★ 再找"谁读段表 `+0xNN`"⇒ 消费者 ⇒ 单位。

### 26.1 ★ 浮点参数落 **段表 `+0x04`**（一手，`0x5029b8`）

```
5029b8  call 0x40ebc0           ; 按段号取段表 entry
5029c1  lea ecx,[eax+0x28]
5029c4  call 0x40e030           ; 定位字段
5029d4  movss [eax+0x4], xmm0   ; ★ ★ **浮点参数 → 段表 `+0x04`**
5029d9  movzx eax,WORD [esi+0x4] ; ★ 当前 opcode
5029dd  cmp ax,0x262 ; je …      ; ★ **610**
5029e2  cmp ax,0x264 ; jne 0x502a65  ; ★ **612**
5029f0  再取一个浮点 → 同样写段表（后续偏移）
```

★★ 两条：
1. ★ **浮点参数（`r`/`s` 那一对）写进段表项 `+0x04`（及后续偏移）**；
2. ★ 后面的第二/第三个浮点**只在 opcode 是 `610`/`612` 时才取**（`cmp ax,0x262/0x264`）
   ⇒ ★ 与 THBWiki「★ 大部分 mode 只要 `a b r s`（用 `609`/`611`）；★ 要 8 个参数的用 `610`/`612`」**完全一致** ✓

★ 所以 ★ **`609` 只带 2 个浮点（`r`,`s`）**，★ 它们落在段表的两个偏移（`+0x00`/`+0x04` 一带）；
★ `610`/`612` 才带 4 个浮点。

★ ❓ 还差最后一小步：★ **`r` 与 `s` 分别落 `+0x00` 还是 `+0x04`**（要看第一个 float 的取值点 `0x502967`／`0x5029a3` 各对应第几个参数）。
★ 然后 ★ **找读段表 `+0x00`/`+0x04` 的代码**（应在那套 `et` 变换的应用端）⇒ ★ 单位。

### 26.2 ★★★ `r` → 段表 `+0x00`，`s` → 段表 `+0x04`（一手，`0x502999`／`0x5029d4`）

### 26.3 ★ 消费者不在 handler 区（一手反证）

★ 段表元素访问器 `0x40ebc0` 全仓 **77 个调用点**，★ 全部落在 **`0x502xxx`–`0x503xxx`**（`0x502000` 段 34 处、`0x503000` 段 43 处）
⇒ ★ ★ **那一片是 `et` 族 handler 区**，★ **真正"把 `r`/`s` 用到运动上"的消费者不在这里**。

★ 所以消费者要么 ★ **直接按偏移读段表**（不走 `0x40ebc0`），★ 要么在 ★ **激光/子弹的 update 路径**里。
★ ❓ 下一步：★ 搜 **读 `[reg+0x00]`/`[reg+0x04]` 且 reg 来自 `[e??+0x5ac]` 元素 +0x28** 的代码 ——
★ 或用 Ghidra 对 `0x40e030` 的返回值做数据流（它是"定位字段"的那一步，找到 `[eax]`/`[eax+4]` 的其它读者）。

### 26.4 ★ 段表字段的**全部**访问点都在 `0x502xxx`（一手，否证）

★ 把两个访问器都统计了一遍（一手）：

| 访问器 | 调用点 | 分布 |
| --- | ---: | --- |
| ★ `0x40ebc0`（段表元素） | ★ 77 | ★ **全在 `0x502xxx`–`0x503xxx`**（34 ＋ 43） |
| ★ `0x40e030`（定位字段） | ★ **10** | ★ **全在 `0x502xxx`** |
| ★ `0x40ee50` | ★ 1 | ★ `0x502xxx` |

★★ 结论：★ **段表（`[edi+0x5ac]` → 元素 `+0x28`）的读写全部发生在 `609`–`612` 这几个 handler 里**，
★ **没有任何"运动侧"的代码来读它**。

★ 所以 ★ **`r`/`s` 的作用不是"存起来给运动用"** —— ★ 它们**在 `609` handler 内部就被消费掉了**。
★ 这也解释了为什么前面各条线（激光对象、段链、run_ex）都找不到 `r`/`s` 的痕迹。

### 26.5 ★ 于是唯一剩下的解释（🟡，但已被证据逼到只剩这一条）

★ `609` handler 把 `r`/`s` 写进段表后，★ **同一次调用里**就把它们**转成最终效果**（例如写进子弹的某个"每帧增量"字段），
★ 段表只是**中转/暂存**。
★ 下一步（一步）：★ 把 `0x5027a3` **整个 handler 读完**（它到 `0x502a65` 还有后面的分支），
★ 找出 ★ **最后一次 `movss` 的目标**（写进子弹/激光对象的那一次）—— ★ 那才是 `r`/`s` 的最终落点。
