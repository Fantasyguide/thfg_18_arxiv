## 0. 先说清楚：什么是「VM」、什么是「指令」

本页和 ECL、ANM 页会反复出现「VM」「指令」「opcode」这几个词，先用两段话解释一下。

游戏 exe 里有很多东西是**写死在程序里**的：碰撞怎么判、道具怎么飞。但对话内容、弹幕图案、
动画帧这类每关都不一样的东西，如果也写死在 exe 里，改一句台词就得重新编译整个游戏。
所以 ZUN 的做法是把它们写成**脚本**，编译成一串紧凑的字节，打包进 `thXX.dat`。exe 里只留一个
**解释器**：运行时把这串字节一条一条读出来，看每条是「干什么」的，就去调用对应的引擎功能。
这个「读一条、做一条」的循环，就是**VM**（虚拟机，virtual machine）——它不是模拟一台电脑，
只是「一个按脚本行事的小机器」。ECL、ANM、STD、MSG 各有一台这样的小机器，形状都差不多。

脚本里的每一条叫**指令（instruction）**。指令开头有一个小整数，告诉解释器这条是「显示立绘」
还是「等玩家按键」，这个数叫**指令号**，英文 **opcode**（operation code）。指令号后面跟着
**参数**：显示哪个立绘、等多少帧、显示什么文本。指令号本身没有含义，含义全在解释器里的一张
分支表上——`switch (opcode) { case 11: 等待…; case 17: 写文本… }`。所以「指令表」就是把这张
分支表翻译成人话；社区工具（thmsg、trumsg）给指令起的名字（`pause`、`text-add`）只是为了好读，
文件里存的只有数字。

MSG 的 VM 还有一个特点：它是**按时间驱动**的。每条指令带一个「第几帧执行」的时间戳，解释器
每帧看一眼「到时间的指令有哪些」，把它们全部执行掉，然后等下一帧。所以一段对话的节奏
（立绘先出来、隔几帧文字再出来）完全由脚本里的时间戳决定。§3 讲的就是这台小机器每帧在做什么。

〔依据〕通识段落，不需要证据；「四套 VM 同构」的表述见 `engine/ecl/th16/07-vm-architecture.md`（ECL 取指-门控-派发）与 th16/01 §3。

## 1. 概述

MSG 文件是东方正作里承载**剧情文本**的脚本：关卡里的对话、结局、staff roll 的文字与演出
都由它控制。它和 ECL（弹幕/流程）、ANM（贴图/动画）一样打包在 `thXX.dat` 里，用 thtk 的
`thmsg` 或 ExpHP 的 `trumsg` 可以反编译成文本。

读 MSG 最容易踩的一个坑：**同一个 `.msg` 后缀下面其实有两套互不相干的指令集**。

| 用途 | 文件 | 谁来执行 | 指令集 |
| --- | --- | --- | --- |
| 关卡内对话 | `st01a.msg` … `st07d.msg`（关卡号 + 机体 a/b/c/d） | 关卡 HUD 里的对话 VM | §4，编号 0–36（TH18） |
| 结局 / staff roll | `e01.msg` … `e12.msg`、`staff1.msg` … `staff4.msg` | 结局场景自己的解释器 | §5，编号 0–17 |

两套表的**编号重叠但含义完全不同**：关卡对话里 `3` 是显示文本框（现代作已无效），结局里 `3` 是写一行文本。
thmsg 反编译结局文件要加 `-e`，就是在切这张表。§2、§3 讲的格式和运行方式两边通用，指令表分开列。

自 TH10 起 ZUN 基本没有重写过 MSG 引擎：指令格式、文本编码、执行方式十几年没变，
只是零星加了几条指令、给几条旧指令加了参数。所以本页不按版本分表，只在单条指令后注明
「TH xx 起加入 / 改动」。

〔依据〕th16/01 §0–§1、th16/04 §3、th18/README；两套表并存在 thmsg 源码（`thmsg06.c` 的 `-e` 分支）和 ExpHP thpages 的 MSG/END 两页都能印证。

## 2. 二进制文件怎么组织

### 2.1 文件头：入口表

文件开头是一张**入口表**，每条 8 字节：

```
偏移   大小   含义
0x00   u32    入口条数 N
0x04   u32    入口 0 的脚本偏移（相对文件头）
0x08   u32    入口 0 的 flags
0x0c   u32    入口 1 的脚本偏移
0x10   u32    入口 1 的 flags
…      …      共 N 条
```

**入口号就是 ECL 里起对话时给的那个数**：ECL 执行 `ins_518(x)`（TH10 世代为 `ins_418`）时，
游戏取入口 x 的偏移，从那里开始解释指令。一关的对话文件通常有 2–5 个入口：boss 登场前、
道中 boss、击破后等各占一个。

thmsg 反编译输出里的 `entry 0 (256)`，括号里的 256 就是 flags 字段（`0x100`）。它在 TH10–TH18
的所有文件里恒为 256，**引擎读入口表时只取偏移、不读它**，可以当作编译器留下的常量。TH19 起这 4 个
字节被拆成 4 个 u8 使用，thmsg 会打印成 `(a, b, c, d)`；TH19 的关卡对话文件另外在入口表之前多了一块
0x50 字节的头。

结局和 staff 文件同样有这张表，只是只有 1 个入口。

〔依据〕th18/01 §1（两个读取点 `th18:0x43e360` / `th18:0x42b650` 只读 offset；44 文件 flags 全 256）、th16/04 §1.5；
thmsg `th06_read`（`entry_offset_mul = 2`，TH19 `header_extra = 0x50`）。

### 2.2 指令：4 字节头 + 变长参数

脚本本体是一串连续的指令，每条：

```
偏移   大小   含义
0x00   u16    time    触发时间（帧，相对本入口开始）
0x02   u8     opcode  指令号
0x03   u8     size    参数字节数
0x04   …      参数    按指令号解释，长度 = size
```

下一条指令的位置 = 当前位置 + 4 + size，没有额外对齐（字符串参数自己会补到 4 的倍数）。
入口以 `opcode 0` 结束。参数类型只有 `int32`、`float` 和字符串三种，字符串的规则见 §2.3。

用 thmsg 的输出对照一下（原 wiki 页的例子，按 TH18 的 st01a 还原）：

```
entry 0 (256)          ← 入口 0，flags = 256
@34                    ← 下面几条的 time 都是 34
    10;1               ← opcode 10，参数 1：允许快进
    29;0               ← opcode 29，参数 0：气泡样式 = 圆角矩形
    28;112.0f;240.0f   ← opcode 28，两个 float：气泡位置
    17;よかった         ← opcode 17，一个字符串：追加一行文本
    17;雨が止んで       ← 第二行
@38
    11;600             ← opcode 11，参数 600：等玩家按键，最多 600 帧
```

`@` 行是 thmsg 把相同 time 的指令合并显示，二进制里每条指令各自带自己的 time。

〔依据〕th16/01 §3、th18/01 §1（`run` 按 ushort 读 time）、样本 `st01a.msg` 入口 0。

### 2.3 文本编码

带文本的指令（关卡对话的 15/16/17，结局的 3）参数是一个字符串，规则：

1. **Shift-JIS** 编码，末尾补 `\0`，再用 `\0` 填充到 4 字节倍数；
2. 整段（含填充）逐字节 XOR 一个**递增掩码**：第 1 字节 XOR `0x77`，之后每字节的掩码加一个「速度」，
   速度初值 `0x07`，每字节再加 `0x10`。掩码序列 `0x77, 0x7e, 0x95, 0xbc, …`（8 位溢出截断）。

这套掩码自 TH09 起就没变过。其它字符串参数（结局里的 ANM 文件名、BGM 名）是**明文** ASCII，不加掩码。

**注音（furigana）bug**：TH12 起，文本可以用 `|x偏移,字距,注音文本` 的形式给下一行加注音（§4 的 17）。
ZUN 的编译器有个 bug：含注音的指令之后，**下一条**文本指令解码出来在 `\0` 后面会多出一段
垃圾，内容是上一条注音的密文残留。游戏运行时读到 `\0` 就停，所以不影响显示；但自己写解析器
时不能按 size 整段解码后当字符串用，要按 `\0` 截断。

〔依据〕th16/02 §1（thpages `getMsgTableText`）、th16/04 §1.5、th18/01 §7（40 个文件全部解出）；
thmsg `util_xor(…, 0x77, 7, 16)`；truth `m(bs=4;mask=0x77,7,16;furibug)`。

## 3. 游戏里怎么跑

### 3.1 关卡内对话

**加载**：进关时按**机体**选文件（`st03a.msg` = 3 面、a 机体），整个文件读进内存，之后不再碰磁盘。
四个机体各一份文件，是因为对话内容按角色不同，不是格式差异。

**触发**：ECL 敌机脚本执行 `518 dialogRead(x)` 时：

- 清场：全部子弹、激光、非 boss 敌机被清掉；
- 建一个对话 VM，指令指针指向入口 x，计时从 0 开始；
- 对话期间关卡的 boss 计时、敌人血条等 UI 被压住，画面只剩背景、立绘和文本。

`x` 为负数时不建 VM，而是走特殊分支：`-1` 切 **boss 曲**并弹出曲名，`-3` 切**道中曲**并弹出曲名，
`-2` 结束关卡（TH18；这几个负数 ECL 里常见，原页没提）。TH18 还有一个硬编码分支：6 面持有空白卡时，
开场对话 `518(0)` 会被换成入口 4——所以 st06 有 5 个入口而别的关只有 2–3 个。

**每帧执行**：VM 挂在 HUD 的每帧更新里。每帧它从当前指令往下走，只要下一条指令的 `time`
不大于当前计时就执行它，直到撞上一条还没到时间的，或者一条**阻塞**指令：

- `11 pause(max)`：等玩家按射击键，最多 `max` 帧。等待期间**脚本计时冻结**，所以脚本作者不需要把
  等待时间算进后面的 `@time`。
- `0 end`：VM 销毁，对话结束，关卡 UI 恢复。

**快进**：只有脚本先执行过 `10 skippable(1)`，快进才生效。玩家按下射击键或 Ctrl 后，
把射击键或 Ctrl **按住 20 帧以上**，VM 每帧都把脚本计时直接拨到当前指令的时间，于是所有等待瞬间过完。
`10 skippable(0)` 用来保护「不许跳过」的段落。

**和 ECL 的握手**：对话往往穿插在 boss 战里（boss 说两句、飞进来、再说两句）。这靠三条指令配合：

```
ECL:  518 dialogRead(x)    起对话，ECL 继续往下跑
ECL:  519 dialogWait       卡在这里，等对话放行
MSG:  … 台词 …
MSG:  12 ecl-resume        放行：让卡在 519 的 ECL 越过去（boss 此时飞进来）
ECL:  … boss 移动 / 出弹 …
MSG:  … 台词 … 0 end       对话结束
```

`12` 是**一帧脉冲**：它置一个标志，`519` 当帧看到标志就放行，下一帧标志自动清掉。
所以一条 `12` 恰好放行一条 `519`，多条 `519` 要配多条 `12`。对话整体结束（`0`）后，`519` 也会放行。

**渲染**：立绘、文本行、注音、气泡都是 ANM 精灵，MSG 指令只是在往 ANM 系统里塞脚本和字符串。
文本不走 Windows 字体绘制那条路，所以换字体、改排版的接口在 ANM 侧，不在 MSG 里。

**立绘是怎么控制的**：MSG 不画立绘，它只给立绘的 ANM 脚本发**中断（interrupt）**，
立绘 anm 自己决定「隐藏」「高亮」长什么样：

| 中断号 | 含义 | 发送它的指令 |
| --- | --- | --- |
| 1 | 隐藏 | 4 / 5 / 6 |
| 2 | 高亮（正在说话） | 7 / 8 / 34 |
| 3 | 变暗（未说话） | 7 / 8 / 9 / 33 |
| 7 | 抖动 | 23 / 24 |
| 17 + n | 换到第 n 号表情 | 13 / 14 |

敌方立绘用哪个 anm、从哪个脚本号开始，写在每关的**关卡数据表**里（每个 boss 一条：立绘 anm 槽、
立绘脚本号、名牌 anm 槽、名牌脚本号），`2 show-enemy(who)` 的 `who` 就是这张表的下标——这就是
原页「号码 a 与立绘的对应关系储存位置未知」的答案。自机立绘来自自机自己的 anm，脚本号按机体查一张小表。

**文本框与气泡**：文本每 **2 行**一页：第 1 条 `17` 写上行，第 2 条写下行，第 3 条会先清框再写。
`11 pause` 放行后也会开新框。`29 callout-type(t)` 选气泡样式、`7/8/9/32` 决定气泡朝向（自机侧 / 敌方侧 / 无人），
两者合成一个脚本号（`t × 3 + 朝向`）去气泡 anm 里取外观。

〔依据〕th18/01 §2–§6（全部一手）；th16/03 §2（握手三读写点）。「Ctrl」是按 ZUN 输入位惯例认的（输入位 0x200），未从按键映射一手核。

### 3.2 结局与 staff roll

结局场景不经过关卡 HUD，自己读 `eXX.msg`。TH18 的编号规则：没用过 continue 时
`编号 = 角色 × 2 + (持有空白卡 ? 0 : 1)`（e01–e08），用过 continue 时 `编号 = 角色 + 8`（e09–e12）。
结局 VM 的取指方式和 §3.1 完全一样（同样的 4 字节头、同样的 time 门控），只是指令表换成结局那套：

- 文本是**滚动的 5 行**：`3 text-add` 写一行并把行号 +1，写满 5 行后下一次 `3` 先清屏再从第 0 行写；
- `5 wait` / `6 wait-clear` 等玩家按射击键（负数参数 = 999 帧），后者同时把行号归零；
  **第一次看某个结局时不能快进**，看过之后按住射击键或 Ctrl 会每 6 帧自动翻页；
- `8 anm-set-slot(slot, src, script)` 在某个图片槽里显示一张 CG，`15/16/17` 是它的难度专属版
  （只在 Normal / Hard / Lunatic 下执行）；
- `12 switch-to-staff` 结局播完后**换载 staff 文件并重置 VM**，staff roll 就在同一个解释器里接着跑。
  指令带一个文件名参数，但 TH10–TH18 引擎忽略它，按难度硬选 `staff1–4.msg`（Easy/Extra→1，
  Normal→2，Hard→3，Lunatic→4）；这四个文件只差最后一张 CG 的脚本号。从音乐室 / 结局回想进入时不接 staff roll；
  用过 continue 的结局文件里也没有这条指令。

staff roll 本身就是「图片幻灯 + 音乐」：staff 名字烤在 `staff.anm` 的精灵里，文件里没有文本指令。
按住射击键或 Ctrl 时 staff roll 以 6 倍速播放。

〔依据〕th18/02 §1–§3、th16/04 §1、§1.5–§1.6、§2；难度映射 Easy/Extra→1 按 ZUN 惯例（`DIFFICULTY` 1/2/3 硬编码）推定。
