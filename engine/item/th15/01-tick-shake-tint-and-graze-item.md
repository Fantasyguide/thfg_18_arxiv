> **版本**：TH15 v1.00b（`th15.exe`，md5 `bddd41a586e09e4447f795a14009d68a`，imagebase `0x400000`）。
> 本文裸地址默认属该版本；引用 TH18 一律写成 `th18:0x…`。
> **方法**：objdump 逐指令 + ExpHP `th-re-data`（`zItem` / `zAnmVmPrefix` / `zItemManagerInner` 字段名）
> + `thanm` 解包（`local/th15.v1.00b/anm/bullet/bullet.anm.txt`）+ `anm/bullet/bullet/item.png` 像素直读。
> **可信度**：抖动 / 变色 ✅（逐指令 + 常量一手）；擦弹道具 type 13 的生成链与外观 ✅（指令 + anm 脚本 + 贴图一手）；
> 「45 帧」的计时语义 ✅（`zCounter` 语义一手，§4.2）；⚠ 该分支**实机可见性**未验（🟡，§6）。

## 0. 一句话结论

擦弹把 `lolk_item_slowdown_factor` 打成 0.3（链路见
[`player/th15/01-graze-and-item-slowdown.md`](../../player/th15/01-graze-and-item-slowdown.md)）。
本文补的是**玩家看得见的另外两件事** —— 它们此前都漏记：

1. **满屏道具一起抖**：因子 < 1.0 且道具「年龄 ≥ 32 帧」时，道具 tick 每帧把道具**贴图 VM 的 pos**
   改成 `(rand(−1,1), rand(−1,1), 0)`（±1 px 抖），并把 `color_1` 改成 `0xFFFFA0FF`
   （B=255 G=160 R=255 A=255：整颗压暗、白色部分偏品红）；因子回到 1.0 的那一帧还原成白。
   ⇒ 观感 =「一擦弹，场上所有道具同时抖一下、暗一下」。**不是**屏幕后处理（§5 的旧结论要订正，见 §2.4）。
2. **擦弹弹出的黄点**：一颗弹**连续 45 帧**待在擦弹圈里，第 45 帧会在擦弹点弹出
   一颗 item **type 13**（`script123`：橄榄黄 additive 小方块，淡入 + `3.0→1.0` 缩放 + `45°/帧`自转），
   初速 **2.2**、角度 **−90°±10°**。收下它 = **擦弹计数 +5、分数 +1**。
   ⇒「擦弹时冒出来的黄点」= 这颗道具 + 同帧的弹幕染色（`th15:0x419d3d`）。

## 2. 抖动与变色：`ItemManager::on_tick__body` `0x43f830` ✅

### 2.1 两道闸

| 闸 | 地址 | 指令 | 语义 |
| --- | --- | --- | --- |
| 年纪 | `0x43f9c3` | `cmp DWORD [edi+0xc40],0x20` / `jl 0x43fa9a` | 道具出生 **< 32 帧** ⇒ 跳过整段（刚出生的道具不抖） |
| 减速中 | `0x43f9fc` | `comiss xmm0(1.0), [ebx+0xe5def0]` / `jbe 0x43fa71` | 因子 **≥ 1.0**（没在减速）⇒ 走「还原」分支 |

两条都过 ⇒ 落进 **抖动 + 变色** 分支（`0x43fa05`）。注意位移乘数在更早处已按因子算完（`0x43f97b`/`0x43f9d6`）。

### 2.2 减速分支 `0x43fa05`–`0x43fa6f`（每帧重写）

| 动作 | 地址 | 一手 |
| --- | --- | --- |
| 两次 `Rng__randf_neg_1_to_1`（RNG 实例 `ds:0x4e9a40`） | `0x43fa05` / `0x43fa18` | `0x403840`：`u32 × 2⁻³¹ − 1.0` ⇒ **∈ [−1, 1]**（常量 `th15:0x4cfd8c` = 2⁻³¹） |
| `VM1.pos.xy = (r2, r1)` | `0x43fa44` | `movq [edi+0x48], xmm0`（VM1.pos = VM `+0x38`） |
| `VM1.pos.z = 0` | `0x43fa55` | `mov [edi+0x50], eax`（`eax = 0`） |
| `VM1.color_1 = 0xFFFFA0FF`（B=255 G=160 R=255 A=255） | `0x43fa58`–`0x43fa68` | 三条写：`+0x549` 字 `0xffa0`、`+0x548`/`+0x54b` 各 `0xff`（D3DCOLOR 内存序 **BGRA**） |

> ⇒ 抖动量 = **±1 px**（对 16/32 px 的贴图很明显），颜色 = 白 × (1, 0.63, 1)：
> 白处变**品红偏暗**、红/蓝/绿贴图整体压暗（`item.png` 里红 P、蓝点、品红、绿四族都吃这一下）。

### 2.3 「还原」分支 `0x43fa71`–`0x43fa93`

| 动作 | 地址 | 一手 |
| --- | --- | --- |
| `VM1.color_1 = 0xFFFFFFFF` | `0x43fa71`–`0x43fa81` | 与 §2.2 对称的三条写（`0xffff` + 两个 `0xff`） |
| `flags_lo &= 0xC1FFFFFF`、`flags_lo \|= 4` | `0x43fa88` / `0x43fa8f` | `[edi+0x28]` = VM1 `flags_lo`（VM `+0x18`）；清掉 `0x3E000000` 这 5 位、置 bit2 |
| `VM1.rotation.z = 0` | `0x43fa93` | `mov [edi+0x5c], 0`（VM1 `rotation` = VM `+0x44`，`.z` = `+0x4c`） |

⇒ 减速分支**不**动这三样：rot/flags 保留脚本自己写下的值，颜色由引擎按帧覆盖。

### 2.4 这一段就是「因子的画面消费者」★（订正旧结论）

`player/th15/01 §5` 原写「全库读 `ITEM_MANAGER+0xe5def0` 的地方只有道具 tick 与它自己的恢复，
**没有任何渲染代码读它**」。前半句没错（读因子确实只有 `0x43f97b`/`0x43f9d6`/`0x43f9fc`/`0x440161` 四处），
但结论错了：**渲染不读因子，因子改的是「被渲染的那些字段」** —— 位置（`VM1.pos`）与颜色（`VM1.color_1`）
就是渲染器每帧要吃的东西（draw `0x440760` 把 `item+0xc20` 拷进 VM 的 `entity_pos` 再 `AnmManager__draw_vm`）。
所以「擦弹 → 满屏道具抖一下」是**引擎原生行为**，不是玩家幻觉、也不需要全屏滤镜。

## 3. 副 VM（压暗变体）与擦弹无关 ✅

`bullet.anm` 里 type 1..8 的贴图是**成对**的（`sprite500/501`、`502/503`、`504/505` … 差值恒为 14），
第一颗是亮版（`script112..119`：`type(1)` + `angleVel` 自转 + `scaleTime(16,…)` 冒头），
第二颗是**压暗版**（`script126..133`：`type(0)` + `static()`）。像素直读（`item.png`）：
`sprite500` 主色 `RGB(255,0,0)` 而 `sprite501` 是 `RGB(160,2,2)`、不透明像素也从 144/256 掉到 66/256。

引擎只在这些条件同时满足时才画 **VM2**：draw 闸 `0x440770`（状态 ≠ 0、VM1 可见、`item+0xc74 ≤ 0`）之后
`0x4407bd` `comiss -8.0(0x4d0108), [esi+0x24]` —— `[esi+0x24]` = `item+0x4c` = **VM1.pos.y**，
`jbe 0x44083c`（`pos.y ≥ −8`）画 VM1，否则画 VM2（`0x440824`）并顺手按 VM2 自己的 `pos.y` 当计时器
把 VM2 `color_1` 的 alpha 淡进来（`0x4407fb`/`0x440818`）。

⇒ 擦弹抖动把 VM1.pos.y 写成 `[−1,1]`（恒 `> −8`）⇒ 擦弹路径**永远画 VM1**，副 VM 是别的状态用的
（🟡 具体用途未查，本文只需要「擦弹不换贴图」这一条）。

## 4. 擦弹 45 帧 ⇒ 弹出擦弹道具（item type 13）✅

### 4.1 弹侧：`Bullet::sub_419a50` `0x419a50`（每弹每帧）

| 动作 | 地址 | 一手 |
| --- | --- | --- |

| 擦弹几何（圆/矩形两种，与 §1b 同）算出「在圈里」 | `0x419a77` 起 | `ebx == 2` = 本帧在擦弹圈内；否则 `0x419d8e` 直接返回 |
| 冷却计数 `zCounter` @`+0x143c`：`current != previous` 且 `current % [bullet+0x1464] == 0` 才擦 | `0x419cb5`–`0x419cce` | `zCounter::tick` `0x408ba0` / `zCounter::set` `0x409040` |
| `Player::do_graze`（计数 + PIV + 火花） | `0x419cd1` | 见 [`player/th15/01 §1`](../../player/th15/01-graze-and-item-slowdown.md) |

| **连续擦弹帧数** `zCounter` @`+0x1450`（`current` 在 `+0x1454`）每帧 +1 | `0x419cf0`–`0x419cf6` | 与冷却计数同一对函数 |
| 自机擦弹光圈计时器 | `0x419cfb` | `0x4581d0`（玩家 `+0x1622c` = 9、`+0x16230` = 10、`+0x16234` = 10.0） |
| **因子 = 0.3** | `0x419d05` | `mov DWORD [eax+0xe5def0], 0x3e99999a` |

### 4.2 `[bullet+0x1454]` 到底是什么 ✅

它**只**在 `0x419d0f` 被读，只在两个初始化函数里被写 0（`0x419f3f`、`0x41adcd` 等），
而在本函数里每帧被 `zCounter::tick(&bullet+0x1450)` 推一格（`0x408ba0`）。

`zCounter` 语义（`0x408ba0` 一手）：`previous = current; current += rate`，`rate = *(float*)[0x4ca620 + idx*4]`，
而 `th15:0x4ca620` 的第 0 项 = **`&GAME_SPEED`（`th15:0x4e73e8` = 1.0）** ⇒ **速率 = 1 帧/帧**。

⇒ `[bullet+0x1454]` = **这颗弹连续待在擦弹圈里的帧数**（不擦则本函数整段不执行、不计数；被弹幕擦的冷却
`[bullet+0x1464]` = 30/60 帧只影响 `do_graze` 的结算频率，**不影响**这个计数）。

### 4.3 第 45 帧那一帧干三件事

`0x419d0f`：`eax = [edi+0x1454]` → `cmp eax,0x2d` → 两条岔路：

| 岔路 | 条件 | 动作 | 地址 |
| --- | --- | --- | --- |
| 染色 + 抖 | `frame < 45` | `B=0x80`（`+0x564`）、`G=min((0x68−frame)×2, 0xF0)`（`+0x565`）、`R=A=0xFFFF`（`+0x566` 字）、`flags \|= 0x20000` 且 `&= ~0x40000`、**弹幕绘制偏移** `bullet+0x60..0x68 = (rand, rand, 0)` | `0x419d1a`–`0x419d8b` |
| **弹道具** | `frame == 45`（`0x419d99` 的 `jne` 只放行等号） | 见下 | `0x419d99`–`0x419de6` |

第 45 帧那一支（一手逐条）：

```
0x419d9b  xmm2 = [擦弹点].x
0x419da1  [bullet+0x1464] = 0x1e         ; 擦弹冷却重设 30 帧
0x419dab  SoundManager__play_sound_at_position(0x4c, …)   ; SE 76
0x419db5  角度 = Rng__randf_neg_1_to_1(ds:0x4e9a48) × 0.174533(10°，0x4cfe00) − 1.5708(90°，0x4cfef4)
0x419dcd  速度 = 2.2f (0x400ccccd)
0x419de6  ItemManager::spawn_item(type = 0xd, pos = 擦弹点, angle, speed)      ; 0x4408d0
```

⇒ 角度 **−90°±10°**（屏幕上朝上、带随机散角），初速 **2.2**（`spawn_item` 内部 `0x440f30` = `fsincos` 化成
`vel = (cos, sin) × speed`）。

> ⚠ 一次性：只有 `== 45` 那一帧生成，第 46 帧起 `> 45` 不再生成 ⇒ **一颗弹最多掉一颗擦弹道具**。
> 冷却是「擦弹结算」的，不是这个计数的：弹在圈里待满 45 帧这一条与 `[bullet+0x1464]` 无关。

### 4.4 道具侧：type 13 长什么样、值多少

| 项 | 一手 |
| --- | --- |
| VM1 脚本 | `0x4cb058[13] = 123` → `bullet.anm` `script123` |
| 贴图 | `sprite516` = `item.png` `(192,32,16,16)`；像素直读主色 **`RGB(114,150,39)` 橄榄黄** |

| 收下它 | 跳表 `0x440194 + (type−1)×4` → type 13 = `0x43ff6d`：`push 5; call 0x440eb0`（**擦弹计数 +5**，封顶 `0x5f5e0ff`）→ `push 0xa; call 0x420f50`（**分数 +1**，内部 `+= 实参/10`） |

⇒ 玩家视角：**擦弹擦到第 45 帧，弹幕一路变黄 + 抖**（§4.3 左栏），**该帧弹幕位置冒出一颗会转圈的橄榄黄小方块**
（加算混合、先放大再收小），这就是「擦弹时冒出来的黄点」；同一帧道具整体在抖（§2）。

### 4.5 §4d 的方向订正（`player/th15/01`）

旧文写「`G` 从 0 涨到 240，计时器归零后恢复原色」。按一手：写入只在 `frame < 0x2d` 发生，`G = min((0x68−frame)×2, 0xF0)`，
`frame` 从 0 涨到 45 ⇒ **`G` 只落在 208 → 118**（`0xF0` 的夹永远够不着），即
**「刚擦上：亮黄 `RGB(255,208,128)` ⇒ 快满 45 帧：偏品红 `RGB(255,118,128)`」**，第 45 帧之后不再写。
结论「被擦的弹幕变黄」不变，方向相反且区间要改。

## 5. TH18 对位：**引擎自带同一套三件套**（2026-09-19 二查，订正本文初稿的「TH18 没有」）

TH18 的**道具 tick 里逐指令保留了 TH15 这三件套**（不是残骸，是活代码），落点是 state==1（飘落）那一支：

| 项 | TH18 一手 | TH15 对应 |
| --- | --- | --- |
| 位移 / 重力增量 ×factor | `th18:0x445c0d` / `th18:0x445c6d` | `th15:0x43f97b` / `th15:0x43f9d6` |
| 门①：**必须 state == 1** | `th18:0x445b6f` `cmp eax,1` / `jne …`（跳表 case 1 = 飘落） | 同段（TH15 也是 state 分支内） |
| 门②：**年纪 ≥ 32 帧** | `th18:0x445be6` `cmp DWORD [edi+0xc50],0x20` → `th18:0x445c85` `jl 0x445de6` | `th15:0x43f9c3`（`item+0xc40`） |
| 门③：**factor < 1.0** | `th18:0x445c8b` `comiss 1.0(0x4b9178),[ecx+0xe6bb14]` / `jbe 0x445d50` | `th15:0x43f9fc` |
| 抖动（主 VM） | `th18:0x445c98`/`0x445cab` 两次 RNG（`ds:0x4cf280`）→ `th18:0x445d34`/`0x445d39` 写 `VM1.pos`（`item+0x40`，TH18 的 VM `pos` = `+0x30`） | `th15:0x43fa44`（`item+0x48`） |
| 抖动（另一个 VM） | 按 id 查 VM（`th18:0x445cd4` `AnmManager::get_vm_with_id`，id 在 `item+0xc28`）→ `th18:0x445ce7` 写它的 `entity_pos` | — |
| 染色 | 主 VM `color_1`（`item+0x534`）的 G=0xa0、R=0xff（`th18:0x445d42`）⇒ 与 TH15 **同色** `RGB(255,160,255)`；另一个 VM `color_1 = 0xFFA0FFFF`（`th18:0x445d12`） | `th15:0x43fa58` |
| 还原 | `th18:0x445ebe` 写回 `0xFFFFFFFF` + 还原位置 | `th15:0x43fa71` |

**结论（对卡侧最重要的一条）**：TH18 的原生道具**不需要**任何卡去实现「抖动 / 变黄」——
绀珠传卡（115）只要在擦弹时把 `mgr+0xe6bb14` 写成 0.3（它一直在做：`slow_apply()`，
`LOLK_SLOW_START = 30`），引擎就会把**变慢 + 变黄 + 抖动**一起带出来。**三条门是同一组**：
任意一条不成立 ⇒ 三样**一起**消失（不是只有颜色丢）。⇒ 若实跑只丢「黄 + 抖」而「慢」还在，
那问题不在门上，而在**写进去之后被谁覆盖**（颜色/位置的写者要往 `on_item_frame`（在池 body **之后**）
与各卡的既有写点里找）。⇒ 反过来，若「慢」也一起没了，就是门①（state 被我们推进 3 = 真空飞行：
`ce_item_collect_all()`、POC 闸 `ce_poc_gate_a/b` → `th18:0x445f63` 那条 state=3、114 的批链路）
或门②（道具活不到 32 帧 / 计数被清）被打掉了。

### 7.1 引擎那支染色的**颜色**：是"压绿"（偏品红），**不是黄** ✅

| 项 | 地址 | 一手 |
| --- | --- | --- |
| 道具出生把 VM1 `color_1` 写**白** | `th18:0x447115` | `mov DWORD PTR [esi+0x534],0xffffffff`（四个字节全 `0xff`）|
| 减速期染色**只写两个字节** | `th18:0x445d42` | `mov WORD PTR [edi+0x535],0xffa0` ⇒ `+0x535 = G = 0xa0`、`+0x536 = R = 0xff`，**B(`+0x534`) 与 A(`+0x537`) 保持出生值 `0xff`** |
| ⇒ 最终色 | — | `RGB(255,160,255)`：**只有 G 被压到 63%** ⇒ 白处偏品红、彩图整体压暗 |

**判据（领域常识 + 同一引擎的旁证）**：TH15/TH18 的 `zAnmVm.color_1` 是 D3DCOLOR（内存序 **BGRA**，即
字节 0 = B）。同一作里"**弹幕**被擦到发黄"那支写的正是 `B = 0x80`、`G = min((0x68−frame)×2,0xF0)`、`R = 0xff`
（§4.3 左栏）⇒ **压 B 才是黄**。本条压的是 **G** ⇒ 出来是品红/压暗。
（这条也就是"owner 说的黄不是道具的引擎染色"的一手依据；115 侧另有**弹幕**染色 `LOLK_GRAZED_COLOR`
= `0xffffd080`，那支压的才是 B，观感是黄 —— 与本条不是同一件事。）

### 7.2 这一格（`th18:0x445bb9`）在**寄存器活跃区间**里：接管/回放都会踩到它 🟡

逐指令读 `ItemManager__on_tick__body`（`th18:0x445a80` 起，池循环 `0x445ae0`…`0x4467fc`）：

| 事实 | 地址 | 一手 |
| --- | --- | --- |
| `1.0f`（常量 `0x4b9178`）**一次载入 xmm5** | `0x445a94`（函数序言）、`0x445b5e`（state 5→2 那条路，紧跟 `call 0x4472b0` 之后**重载**）| 编译器只在**它自己知道的调用之后**重载它 ⇒ 引擎自己把 xmm5 当 caller-saved |
| 池循环尾重载 xmm7/xmm4/xmm3/xmm2/xmm6，**但不重载 xmm5**（两条路 `0x44678b`/`0x44679d` 各自写回 `1.0f`）| `0x4467ca`–`0x4467ef` | 下一只道具靠的就是上一个尾巴留下的 xmm5 |
| **"因子 < 1 ⇒ 抖 + 压暗"那道闸消费的正是 xmm5** | `0x445c8b` | `comiss xmm5, [ecx+0xe6bb14]` / `jbe 0x445d50`（≥1 ⇒ 走还原支）|
| 而"×因子"的位移/重力两条乘式**在站点之后重载了自己的操作数** | `0x445bed`（GAME_SPEED）、`0x445bf5`/`0x445bfd`/`0x445c05`（item+0xc38/c3c/c40）、`0x445c0d`（因子）| ⇒ **减速那一段与 xmm5 无关** |

⇒ **结构结论**：站点 `0x445bb9`（那条 `ja`）**正落在「xmm5 = 1.0f 活着、且下游要拿它做"抖/压暗"判据」**的位置，
而引擎只在**自己的调用之后**补重载。任何在这一格**注入一次外来调用**的做法（接管、或让 handler 跑到会
clobber xmm 的代码）都能**精确打掉"压暗 + 抖"而留下"减速"** —— 与 2026-09-19 实跑的现象同形。
⚠ **可信度 🟡（机制候选，不是定案）**：没有逐寄存器坐实"当班那份 handler 一定碰了 xmm5"
（`ce_poc_gate_common` 自己直用 xmm0–xmm4，`ce_log` 那条路才走 `__mingw_vfprintf`）。
**定案的判据是 owner 的 A/B**：只 park 掉 `ce_poc_gate_a/b` 两条站点 ⇒ 一测就正常；放回并真接管 ⇒
"只剩减速"＋崩 —— 见 [`AUDIT.md`](../../../mods/th18.v1.00a/card-expand/AUDIT.md) §BE-EQ（两次最小差分二分）
与 §BE-ER（崩点 `Eip` 与池格算术逐字节对上）。本节的价值是给这条站点补一条**"为什么不该接管"的一手结构理由**：
接管一个"窗口 = 一条 `ja`、且位于活跃 SSE 区间内"的站点，风险不止"落点算错"，还包括**寄存器现场**。
