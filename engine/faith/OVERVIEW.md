# faith/ — 点道具身价（PIV / 最大得点 / 信仰）及其倍率

> **版本**：跨版本。本文出现的地址一律带版本前缀（如 `th10:0x474c4c`）。

**本子系统的主题只有一句**：**点道具（蓝点 / 金钱道具）被收时值多少分，那个「值」在原生里是什么、怎么涨、怎么算。**

- **PIV**（ExpHP 符号，Point Item Value）与 HUD 上的**「最大得点」**是**同一个量的两个名字**：
  它就是**点道具的身价本身**，**不是**「在别的基准之上再加一份」的额外项。
- 各作的差别只在三处：**载体在哪 / 涨入口是谁 / 身价怎么参与那一作的分数公式**（有的直接等于、
  有的乘 (交信度 + 擦弹倍率)、有的乘 (1 + 资金力) 再被难度表夹住）。
- 量纲**逐作不同**（显示 = 存储 ×10 / ÷100 / 1 显示点 = 100 定点 / 点 = `ecx/1000`）⇒ **一个数字都不能跨作搬**。
- 「**额外得点**」这个词在本仓是**卡 mod 侧计分层**的说法（`G = G_0 + Σ uncoupled + coupling×Σ coupled/1000`，
  见 `mods/th18.v1.00a/card-expand/SCORE-LAYER-REWORK.md`）：它指「在 **TH18 原生身价** `G_0` 之外，
  我们的卡再声明多少」，**不是**原作里存在一个叫「额外最大得点」的字段。

「信仰」是 TH10 才出现的**第二条计分行**：它独立于 `CURRENT_SCORE`，由**道具**供养、
按 miss / 灵击 / 阶段超时**回落**，并且**直接充当点道具（蓝点）的身价**——不是分数的一部分，
而是「分数的基准量」。TH11 把它改名成 HUD 上那个**最大得点**，改了量纲（显示 = 存储 ÷ 100），
并给它乘上 **(交信度 + 擦弹倍率)** 这个两位小数倍率。所以两作的数字**一个都不能对搬**。

另外两条容易误传的说法在这一层被否定：**TH10 既没有擦弹倍率、也没有任何擦弹计数器**
（判定、火花、音效都有，就是没有计数变量）；TH10 也没有「连击槽空 ⇒ 逐帧扣信仰」这种衰减。

一手文档按版本放在 `<版本>/`；道具**实体/类型号/掉落**那一层在 [`item/`](../item/OVERVIEW.md)（两层的分界：
本层只管「值多少钱」，`item/` 管「怎么产生、什么类型、长什么样」）。本文件只做跨版本索引 + 断言矩阵。

## 口径（用户 2026-09-18 定，跨作通用）

0. ★★ **总公式（用户 2026-09-18 定，取代早先的 `G = G_0 + ΣΔG_i` 单系数写法）**：

   ```
   G = G_0 × coeff_0  +  Σ_i ΔG_i × coeff_i
   ```

   | 符号 | 是什么 | 一手出处 |
   | --- | --- | --- |
   | `G_0` | **`= G_18`**：TH18 原生身价换成的**点值**（引擎自己给这一颗点/金钱道具的 SCORE 增量 = `ecx/1000`）。**基线只有一个**，不搬别作的基础值 | `th18:0x446b30` / `th18:0x446b86` |
   | `coeff_0` | **TH18 自己的收分高度系数**（= 一手 `coeff_06`：线上 `1.0`、线下 `0.9×(1−d/450)`），落笔 `th18:0x446bf9` 之后由引擎施加 | `th18:0x446bf9`–`th18:0x446cf3` |
   | `ΔG_i` | 第 `i` 作的「**额外机制**」项（单位 = 点）；没有该项的作取 0（th06 / th09） | 见下表 |
   | `coeff_i` | ★ **该作原生里这一项实际经历的收分系数**（不是 TH18 的）—— 逐作见下面的系数表 | 各作一手 |

   ⇒ **每一项走它自己原作的折扣曲线**：原作里「不吃折扣」的项 `coeff_i ≡ 1`（TH07 的樱点、TH11 的最大得点），
   「就是基础值本身」的项 `coeff_i` = 那一作自己的高度式（TH08 / TH10 的 0.5 族…），
   而 `G_0` 走 TH18 的 `coeff_0`。**`coeff_i = 1` 的项在线下会被「反归一」放大**（见下节实现说明）。

1. **难度只关注 E / N / H / L / EX 五档（表索引 `0..4`）。** 第 6 档**只存在于 TH07**：**PH（Phantasm）**
   —— TH07 的难度表因此是 6 行，本仓一手在 107（妖妖梦）卡的 `senro_core.h`：
   `th07:0x42eb7a`–`th07:0x42ec57` 的最大樱点初值 E/N `200000`、H `250000`、L `300000`、EX `400000`（樱点初值 200000）、
   **PH `400000`（樱点初值 300000）**；同一段的樱点初值表 E–L `0`、EX `200000`、PH `300000`。
2. **TH18（本卡的目标平台）没有第 6 档**（E/N/H/L/EX 五档）。TH13 / TH14 / TH15 / TH16 / TH17 的一手难度表里
   物理上仍留着**第 6 行**（例如 TH13 初值表 `th13:0x4c0ab0` = `5000/10000/15000/20000/20000/100000`），
   但那些作的难度名表只有 5 项 ⇒ **该行的含义未解、不属于目标范围**：读表时可以照抄它的值，
   **不要在公式里引用它**，也不要因为「它不可达」去怀疑整张表。
3. **最大得点/身价跨关（面）不清零**（用户口径 2026-09-18；TH15 明确定为「不清零」，TH13 的「灵界槽与最大得点跨面不归零」是同一口径）。
   一手旁证：各作的初始化块只在**新局 / 读档 / 快照恢复**这类时机跑，不是每关跑
   （TH15 的 `th15:0x43c1f0` 块被 `[th15:0x4e7ed8] != 0` 门住，而该全局全 exe 无 `mov` 写点 ⇒ 正是「不是每关」的形状；
   TH13 的 `th13:0x42bb70` 块顺带清零擦弹计数，而擦弹在一局内明显跨关累计 ⇒ 同结论）。⇒ **「一局总最大得点」按累加口径算。**
4. **「基础」= 「初值」（同一个东西的两个说法）。** 各作难度表那一行初值（本文记作 `A[difficulty]`）就是
   各作公式里出现的「基准 / 基础」：th07 的樱点「基准」、th10 的「下限 50000 = 初值」、th11 的「上限 = 初值 ×2」、
   th13 的 `MINIMUM_PIV`、th16 / th17 的 `INITIAL_PIV`、th18 的 `th18:0x4ccd24`（= 下限 = 收道具身价的起点）
   —— **全是同一个量**，别在文档里当成两个。

## ★★ `coeff_i` 到底有几种？（用户 2026-09-18 追问；锚与 `d` 已统一到实际 POC）

**不是「各作一个」，也不是「全都一样」——只有 5 种，而其中六作完全相同**：

| 种 | 谁 | 线上 | 线下（`d` = 各作原生 `y_src` − 实际 POC） | 相对 `coeff_0` |
| --- | --- | --- | --- | --- |
| ① `coeff_0` | th18（就是 `G_0`） | `1` | `0.9×(1 − d/450)` | `1` |
| ② **0.75 族** | ★ **th12 / th13 / th14 / th15 / th16 / th17 —— 六作逐指令同形 ⇒ 完全相同** | `1` | `0.75×(1 − d/450)` | **`5/6`** |
| ③ 无折扣 | th07（樱点项）、th11（最大得点项） | `1` | **`1`** | `1/coeff_0`（反归一放大） |
| ④ th08 | 时点项 | `1` | `0.5×(1 − d/500)`（除数 **500**） | 随 `d` 变 |
| ⑤ th10 | 信仰项 | `1` | `0.5×(1 − d×(F−100000)/(3040·F))` | 随 `d`、`F` 变 |

（th06 = 无项；th09 = 无项。）

⇒ `Σ_i ΔG_i × coeff_i` 因此可以**按族先合并**（线性）：

```
G = G_0·coeff_0
  + coeff_0.75 · Σ_{i ∈ th12..th17} ΔG_i      ← 六作一个系数，且 = (5/6)·coeff_0
  + 1 · (ΔG_07 + ΔG_11)                       ← 不吃折扣的那两项
  + coeff_08 · ΔG_08
  + coeff_10 · ΔG_10
```

⚠ **唯一会让「5/6 恒等式」失效的地方 = 下限**，两边都要照抄：
0.75 族六作的线下支全都带 `if (v ≤ 0) v = 10`（**显示 10 分**：`th12:0x426d7d`、`th13:0x42ea8b`，th14 / th15 / th16 / th17 同位置各一处）；
而 TH18 引擎那边是 `d ≥ 450 ⇒ 下限 +1 分` —— **两个 floor 不是同一个数**，`d` 大时不能互相代。

## ★★ 结论：th12–th17 可以**共用一个 PIV**，且**乘同一个系数**（用户 2026-09-18 认可）

```

## ★ 110 / 111 的「半耦合」口径（用户 2026-09-18 定案）

```

ΔG_11 = (信仰_11 + 信仰_10) × (交信度 + 擦弹倍率)            （地灵殿那一份 = 两份之和 × 本作原生倍率）

| --- | --- |

### 实现说明（mod 侧，**现状与差距**）

- **现状**：落笔只有一个站点（`th18:0x446bf9` 写 `ecx`），层合成 `G = G_0 + Σ未耦合 + coupling‰×Σ耦合/1000`
  ⇒ 引擎的 `coeff_0` 乘在**整笔**上 ⇒ **等价于 `coeff_i ≡ coeff_0`**，与本公式不符（111/107 会被多打折）。
- **落地路线 A（单点归一）**：仍只写 `ecx`，改成 `ecx = 1000 × (G_0 + Σ ΔG_i × coeff_i / coeff_0)`。
  代价：要做除法；`coeff_0 ≤ 0`（线下 `d ≥ 450`，引擎那边只剩「下限 +1 分」）时退化，需要阈值钳位。
- **落地路线 B（两点落笔，推荐）**：前点照旧写 `G_0 + Σ ΔG_i`（全体先吃 `coeff_0`），
  **再在引擎折扣之后**补一笔 `SCORE += Σ ΔG_i × (coeff_i − coeff_0)`（那两段之后本来就有老落笔点 `th18:0x446cf6` / `th18:0x446caa`）。
  好处：**整数、无除法**，`coeff_0 ≤ 0` 也良定义（此时补的正是 `Σ ΔG_i × coeff_i`）。
- **细节**：路线 A/B 里的 `coeff_0` 都要取**引擎实际施加的那个值**（含线下 `d ≥ 450` 时它自己只剩「下限 +1 分」的那种行为），
  否则补的那一笔会偏。
- ★ **路线已定（用户 2026-09-18：「引擎显示不能照着 G 写吗？」）⇒ 走 A**。一手依据（th18）：
  `th18:0x446cfc` 把 `esi` 交给显示 `call th18:0x4645f0`，紧接着 `th18:0x446d0d` 的魔数除法拿**同一个 `esi`** 做 `SCORE += esi/10`
  ⇒ **显示与分数同源**＝引擎对我们 `ecx` 乘完 `coeff_0` 的结果。所以「写值时就归一」＝显示和分数**都**照 G 走；
  路线 B 只修分数、显示仍是引擎自己那个数。
- ★ **中间过程全程整数、不用浮点**（用户 2026-09-18 追问「中间的过程支持浮点吗？」）：
  · `make dllx87` 只禁 **x87**（编 `-mfpmath=sse -msse2` ⇒ `float` 会走 SSE，技术上不违规，
    既有先例：`reverse.c` 的 `bc_atan2f`/`sqrtss`）；但**断点路径尽量别用** —— thcrap 只保证 GPR 上下文，
    `xmm0–7` 是 caller-saved 且可能装着引擎活着的值（本仓既有做法是把它们列进 clobber 约定，AUDIT 里有先例）。
  · **我们这一刀不需要浮点**：`d` 用既有 `ce_q16_from_bits()` 把 float 位型搬成 **Q16 定点**；
    各作曲线**本来就是整数魔数除法**（`0.9×(1−d/450)` = `900·(450−d)/450` 千分点、0.75 族 = `675·(450−d)/450`、
    比值 `5/6` 就是一次 64 位乘除）⇒ **取整顺序照抄原作**才能逐位一致（原作是整数截断，用浮点反而会不一致）。
  · ⚠ 层里原来**没有 `coeff_0` 的真值**（`ce_score_coeff_permille()` 只是「线上/线下」的 1000/0 标记）
    ⇒ **已改为按 `d` 自己算**（整数、与引擎同骨架，`d ≥ 450` 那一档也给 0‰）。**实装状态：已落地**（见 `AUDIT.md` §BE 详录 #46/#47）。
  · ★ **两处实装细节（2026-09-18 补，§BE #47）**：① **族的 y 源不同** —— `coeff_0` 与 0.75 族吃**自机 y**，
    th06/th07/th08/th10 那几族吃**道具 y** ⇒ 几何桥同时带两个 y（`item+0xc2c`）；
    ② **`FAMILY_10` 已实装**（`F` 由 110 桥进来：`500 − d_道具×(F−100000)×1000/(6080·F)`）。

- **共同注意**：`coeff_i > coeff_0` 的项（TH07 / TH11 这类 `= 1` 的）在线下会被**放得很大**
  （例如 `d = 400` 时 `coeff_0 = 0.1` ⇒ 补偿系数 ×10）；接近线底要设**饱和/阈值**，否则数值会失控。

## ★★ 2026-09-23 订正块 ③ ｜ th07「擦弹 **樱点不进**」作废 —— 擦弹是**会**进樱点的

> 订正人 / 日期：**2026-09-23**（DSH 工单「按两份新清册订正既有文档误读」，逐指令复核）。
> 原始清册：[`th06-th09.md`](../_shared/rosters/th06-th09.md) §2.2(b) 与 §5 第 3 / 第 4 条。
> 规矩：本文上表（§「跨作擦弹 ⇒ ？」与上一节「不合并的」）的**旧字一字未删**，只加 ⚠ 标注；判据写在这里。

### 原文说了什么

- 「跨作擦弹 ⇒ ？」表 th07 行：「**500 分/次**（HUD 覆盖层 `th07:0x42803a` 把擦弹计数 `×0x1f4`=500 打印）；**樱点不进** —— 樱点的直接写点 6 处 + 加法器（`th07:0x42f5a2`/`th07:0x42f69f`）9 个调用点里**没有**擦弹站点」。
- 上一节「不合并的」表 th07 行：「樱点（来源是道具/消弹，🟡 原始擦弹计数进不进樱点未核）」。

### 为什么错（一手，逐指令）

- **枚举漏了一族**：那次只数了 `th07:0x42f5a2` / `th07:0x42f69f` 两个加法器的调用点，**漏了同族的另两个加法器 `th07:0x42f736` / `th07:0x42f789`**。
- **`Player::ScoreGraze` `th07:0x43eb90` 自己就调它俩**（`th07:0x43eb90`–`th07:0x43edb2` 是擦弹奖励全函数，入口：`th07:0x43e3b0` 命中 → `th07:0x43e4c5 call 0x43eb90`）：

```
th07:0x43ed5f  movsx ecx,BYTE PTR [eax+0x240d] ; cmp ecx,0x1 ; jne 0x43edae   ; ★ 门 = 结界态（player+0x240d == 1）
th07:0x43ed71  movsx eax,BYTE PTR [edx+0x240b] ; test eax,eax ; je 0x43ed96
th07:0x43ed7c  push 0x1e(30) → ecx=0x626270 ; call 0x42f789    ; player+0x240b != 0 ⇒ 最大樱点 +30
th07:0x43ed88  push 0x1e(30) → ecx=0x626270 ; call 0x42f736    ;                    樱点   +30
th07:0x43ed96  push 0x50(80) → ecx=0x626270 ; call 0x42f789    ; player+0x240b == 0 ⇒ 最大樱点 +80
th07:0x43eda2  push 0x50(80) → ecx=0x626270 ; call 0x42f736    ;                    樱点   +80
```

- **两个加法器的语义（一手，直读函数体）**：`th07:0x42f736` = **樱点**加法器（`[ecx+0x961c] += arg`，随后夹到 `[ecx+0x9618]`）；`th07:0x42f789` = **最大樱点**加法器（`[ecx+0x9618] += arg`，随后夹到 `[[ecx+0x8]+0x88] + 0x989676` ≈ **初值 + 9,999,990**）。**先调最大樱点、再调樱点**（顺序有意义：樱点被夹到最大樱点）。
- 同函数里还有一条**擦弹 → 樱点相关的累加**：`th07:0x43ed12` `(ds:0x62f88c − [globals+0x88]) / 1500 × 20` 累加进 `ds:0x12fe0d0 + 0x9c4`（`0x5dc` = 1500、`imul 0x14` = ×20）🟡 该累加器的消费者未追。
- 所以「樱点不进」只对**非结界态**成立（`player+0x240d != 0x1` 时直接跳 `th07:0x43edae` 返回）。

### 正确的说法（以指令为准，含对清册措辞的订正）

- **th07 擦弹在结界态（`player+0x240d == 1`）时给「樱点」与「最大樱点」各加一个值**：`player+0x240b == 0` ⇒ **各 +80**（`push 0x50`）；`player+0x240b != 0` ⇒ **各 +30**（`push 0x1e`）。
- ⚠ **与清册 / 工单原话的差别（照实记）**：清册 `th06-th09.md` §2.2(b) 的伪代码把「`240b == 0` ⇒ +30 / else +80」配对，工单转述成「+30（低速）= `240b == 0` / +80（高速）」——**两处都把 30 / 80 配反了**；`0x43ed7a: je 0x43ed96` 的跳转目标是 `push 0x50`(80)，**指令说 `240b == 0` ⇒ +80**。本节以指令为准。
- `player+0x240b` 的**写点只有两处**：`th07:0x43efa4`（写 1）/ `th07:0x43f0ba`（写 0），门是输入位 `ds:0x4b9e50 & 0x4`（`th07:0x43ef93`–`th07:0x43ef9e`）；它同帧被用来在**两套速度/贴图档**之间选（`th07:0x43d16f`：非 0 取 `[player+0xb7e74]`、为 0 取 `[player+0xb7e70]`）⇒ 语义 = **低速 / 高速档位**，但**哪一档对应 0 尚未钉死**（🟡；清册注「`240b == 0` = 高速」，与本节读到的「+80」配对方向相反，需实跑或读速度表定案）。
- **「500 分/次」降格为 ❓（两套单位并存）**：内部**每擦一颗弹**走 `th07:0x43ed40` `mov eax,0x7d0; idiv 10` ⇒ `globals+4 += 200`；`×0x1f4`(500) 出现在**结算屏**那一行（`th07:0x42803a` 读擦弹计数 → `th07:0x428040 imul eax,eax,0x1f4` → 格式串 `th07:0x4984dc` = **`Graze  = %8d`**，直读 `.rdata`）。**「内部 200 / 结算 500」的换算关系本轮未钉死**。
  - **待核方式**：① 实跑擦一颗弹看 HUD 分数增量（记 `graze` 前后的显示分差；本作 `globals+0` 是否 = `globals+4`/10 要一并读）；② 读 HUD 分数绘制链里 `[0x626278+0]` 的更新点是否有 `/10`。
