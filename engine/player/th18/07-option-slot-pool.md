# TH18 子机槽 / option 池 —— 它在哪、谁在动它、扩它要花什么代价

> **版本**：TH18 v1.00a（`th18.exe`，imagebase `0x400000`）。本文裸地址默认属该版本。
> **可信度**：结构（内联数组 / 基址 / 步长 / 计数立即数）= ✅ 一手字节；站点清单 = 🟡 **首轮扫描**（见 §5 未查项）。
> **缘起**：owner 2026-10-15 问「其他槽诸如卡组数量都可以扩，这是为什么呢」——
> 本文只回答"子机槽这一侧的真实形态与代价"，不动任何代码。

## 0. 结论先行

1. **子机槽不是一张独立的表**，而是 **内联在玩家对象里的一块定长区**：
   - `player+0x720` = **原生装备 4 格**（`0x45d2c5` `lea esi,[edi+0x720]` + `0x45d2cb` `mov edi,4`）；
   - `player+0xae0` = **能力卡池 12 格**（`0x45d305` `lea esi,[edi+0xae0]` + `0x45d30b` `mov edi,0xc`）；
   - **每格 `0xf0` = 240 字节**（`0x45d2ed` / `0x45d32d` 的 `lea esi,[esi+0xf0]`）；
   - ⇒ 两块连成 **16 格 × 0xf0 = 0x960 字节**，占 `player+0x720 … +0x1080`。
2. **"能不能扩"的真正门槛不是"有没有访问点"，而是"改动的性质"**：
   - 卡表那一侧之所以能扩，是因为数据是**一张可搬走的表** + 访问点被**枚举干净**（25 处内联查表，`native/shape.py` 的骨架匹配钉住）+ 结构体字段可以**搬家**（`zAbilityManager` 长到 `0x116c`）。
   - 子机槽这一侧：**数组本身就在玩家对象里** ⇒ 16 → N 会让**其后所有玩家字段的偏移整体位移** ⇒ 要么"整块搬进 codecave 并改掉每一个访问点"，要么"给玩家对象扩容"；而它的消费者除了分配器/重建，还散在**原生卡自己的 tick** 与**商店**里（§4）。
3. 所以准确的说法是：**「没做 / 代价明显更高」，不是「不可能」** ✗✅ —— 只要访问点枚举干净，理论上同样可扩（对照：卡表那侧当初也被 12 处硬编码挡着）。

## 1. 一手证据（字节）

`Player__commit_death_and_enter_state2+0x240` 起（`0x45d2c5`–`0x45d336`）：

```
0045d2c5  8d b7 20 07 00 00        lea esi, [edi + 0x720]      ; 原生装备 4 格
0045d2cb  bf 04 00 00 00           mov edi, 4
0045d2d0  6a 01                    push 1
0045d2d2  ff 36                    push dword ptr [esi]        ; 第 1 支 VM
0045d2d4  c7 86 50 ff ff ff 00…    mov dword ptr [esi-0xb0], 0 ; 清一格的状态位
0045d2de  e8 fd b8 02 00           call 0x488be0               ; = 给该 VM 发中断标签 1
0045d2e3  6a 01 / ff 76 04 / call  ; 第 2 支 VM（每格两支 VM）
0045d2ed  8d b6 f0 00 00 00        lea esi, [esi + 0xf0]       ; ★ 格大小
0045d2f3  83 ef 01                 sub edi, 1
0045d2f6  75 d8                    jne 0x45d2d0
0045d305  8d b7 e0 0a 00 00        lea esi, [edi + 0xae0]      ; 能力卡池 12 格
0045d30b  bf 0c 00 00 00           mov edi, 0xc
0045d310  … 同一形态的循环 …        jne 0x45d310
```

⇒ 三点直接读出：**① 数组在玩家对象内联**（`lea` 的基址是 `edi` = 玩家指针）；
**② 计数是立即数**（`4` / `0xc`）；**③ 每格 0xf0 且每格带两支 VM 句柄**（`[esi]`、`[esi+4]`）与一个状态位（`[esi-0xb0]`）。

> `[esi-0xb0]` 与 `[esi]`/`[esi+4]` 的具体语义未逐字段核（🟡），但"一格两支 VM"与"清格发标签 1"与 `AUDIT.md` 记的「TH18 清子机槽时发的是**标签 1**」一致 ✅。

## 2. 谁在**跨格遍历**它（首轮扫描 ✓）

扫 `.text` 的两种步长形态：`lea reg,[reg+0xf0]` **13 处**、`add reg,0xf0` **9 处** ⇒ **22 处**（0xf0 也可能是无关位移，未逐处排除 🟡）。落在其中的已命名站点：

| 站点 | 所在函数 | 角色（🟡 由函数名/位置推断）|
| --- | --- | --- |
| `0x40a7b6` | `Player__allocate_option+0x26` | 分配 / 初始化一格 |
| `0x45a6b3` `0x45a6e3` | `PlayerInner__constructor+0x23/+0x53` | **构造期**建 16 格 |
| `0x45ab56` | `Player__initialize+0x3b6` | 玩家初始化 |
| `0x45d2ed` | `Player__commit_death_and_enter_state2+0x25d` | 死亡清槽（§1）|

## 3. 以玩家全局为基址的精确扫描（🟡 首轮）

玩家指针全局 = `0x4cf410`（`native/engine.h:71`，`zPlayer*`）。做法：**取该全局的函数** ∩ **访存位移落在 `0xae0..0x1080` 的函数**：

- 取玩家指针的函数 **48** 个；位移落在区间的函数 **30** 个；**交集 17 个**。
- 交集里的位移主要是 `0xc44` / `0xd1c` / `0xc58` / `0xc60` / `0xf68`（都落在**某几格内部**，不是格首 🟡）。
- 交集的成员（按出现次数）：
  `CardAya__on_tick`(4) · `Player__allocate_option`(2) · `CardSuwako__create_explosion`(2) · `CardTenshi____on_tick_2`(2) · `CardMegumu____on_tick_2`(2) · `AbilityManager__on_tick`(1) · 以及 `*__c_press` 一族（Clownpiece / Miko / Tenshi / Shinmyoumaru / Remilia / Utusho / Raiko / Sumireko / Megumu / Tsukasa）。

⇒ 值得注意：**消费者里有大量"原生装备卡自己的 tick/c_press"**（它们各自管自己那几格的形态/发弹）⇒ 扩槽不是改一个分配器就完，**这些卡也要跟着认新格**。

## 4. 扩到 N 格需要动什么（代价清单，🟡 估算）

| # | 要动的点 | 性质 | 风险 / 失败模式 |
| --- | --- | --- | --- |
| 1 | 玩家对象里那 16 格区的**存放位置**（搬 codecave 或给对象扩容）| 结构位移 | **最危险**：玩家对象后被位移的字段极多；漏改 ⇒ 静默读错字段（不崩、行为怪）|
| 2 | 每格的**分配/初始化/回收**（`Player__allocate_option`、`PlayerInner__constructor`、`Player__initialize`、`AbilityManager__on_tick`）| 代码 | 少改一处 ⇒ 新格没有 VM / 不回收 |
| 3 | **重建 + 通知**（`Player__repopulate_options_and_notify_cards`）| 代码 | 火力档切档时新格不同步 |
| 4 | **死亡/商店清槽**（`Player__commit_death_and_enter_state2`、`AbilityShop__initialize`、两个"发标签 2/3"的函数）| 代码 | 新格漏清 ⇒ **跨局残留 VM**（本仓最怕的一类）|
| 5 | **原生装备卡自己的 tick/c_press**（§3 那 17 个交集函数）| 代码 | 卡不认新格 ⇒ 有格但无行为 |
| 6 | **sht 的子机位置块**（高速/低速各 **10 对**，`sht_base+0x40 + idx*8`，块长 `0xa0`）| 数据布局 | 新格**没有几何** ⇒ 子机叠在一起/无处可站 |
| 7 | **发弹分组按槽号索引**（一手行字段 `+0x02` = 使魔槽号；位域/分组键）| 数据 + 代码 | 新格发不出弹，或串到别格 |
| 8 | 认领判据与 HUD/anm 索引（`option+0x00`、`option+0xd0 == card+0x08`）| 代码 | 认领串格、HUD 错位 |

⇒ **净判断**：第 1 项（结构位移）与第 6/7 项（几何 + 分组）是**两个独立的硬骨头**，其余是体力活。
若只想要"更多格但几何不变"，会先撞上第 6 项（位置块只有 10 对）⇒ **槽数上限不是 12，而是 `min(12, 10)` 这一侧的更小者**（🟡 待核：TH18 的 sht 位置块与"卡池 12"如何对齐，见 §5）。

## 5. 未查 / 待办（**别拿本文当结论**）

1. **完整访问点枚举**：本文 §3 只做了"位移落在区间 + 函数取玩家指针"的**启发式交集**；
   要像卡表那样钉死，需要**按玩家指针做函数内数据流**（`mov reg,[0x4cf410]` → `[reg+disp]`），
   并把「格首 / 格内 / 区间尾」三类分别列出。**这是可否扩的第一决定因素**。
2. **`0xae0..0x1080` 里哪些位移属于"格"、哪些属于"玩家其它字段"**（当前只知格大小 `0xf0`、格数 `4+12`）。
3. **每格 0xf0 的字段图**（已知 `+0x00`/`+0x04` = 两支 VM、`-0xb0` = 状态位、`+0x5c/+0x60` 另见 `AUDIT` §U5 的定点坐标）—— 待逐字段核。
4. **sht 侧**：`pl0X.sht` 的 option 位置块（10 对 / `0xa0`）与"卡池 12 格"的对齐关系；
   超出的格发弹时用哪一组位置。
5. **发弹分组**：一手行字段 `+0x02`（使魔槽号）在 TH18 的上界与位域宽度。
6. **兼容性**：扩槽对**既有卡**（108 / 111 / 116 那些按格认领的）与**存档**的影响面。

## 7. 与卡表那侧的对照（回答 owner 的"为什么"）

| | 卡表 / 卡组那一侧 | 子机槽这一侧 |
| --- | --- | --- |
| 数据形态 | **一张表**（`zTableCardData[]`，stride `0x34`）| **内联在玩家对象里的定长区**（16 × `0xf0`）|
| 上限写死处 | ≥12 处（4 立即数 + 8 结构尺寸）✅ | 计数立即数（4 / 12）+ 结构位移 + 几何数据 ✅/🟡 |
| 访问点 | **25 处**内联查表，骨架匹配可枚举 ✅ | 首轮：22 处跨格遍历 + 17 个取玩家指针的函数（🟡 未穷尽）|
| 可搬性 | 搬到 codecave + 改 25 处 ✅ | 数组在对象内 ⇒ 要么整体搬、要么扩对象（**位移面极大**）|
| 额外硬骨头 | 图鉴 ≤127、anm entry 8 位 ✅（见 `10-extensibility-limits.md`）| **sht 位置块仅 10 对** + 发弹按槽号分组 |
| 结论 | **已实现扩容**（255 行）| **未实现；代价高但不是不可能** |
