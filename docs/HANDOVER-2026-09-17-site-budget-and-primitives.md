## 1. 一句话结论

**thcrap 的断点入场时刻（"站点"）预算 = 全进程共享的硬上限**（分片实验已证伪 per-patch 假设）：
TH18 实测**安全 ≈22 条、≥24 必崩**。因此「新机制能不能做」的第一问不是"能不能写代码"，
而是**"要几条站点、能不能并进已有站点"**。八个跨作系统原语里 **7 个是 0 站点**（走函数调用 /
声明层 / 数据层），只有「收点(12)」复用一条既有站点。

## 2. ★ 屎山为何爆炸 —— 完整因果链

这一节是这份交接的重点：**"崩"看起来像某个玩法 bug，其实是资源记账问题**。

### 2.1 用户视角的现象（最误导的地方）

不是"一开游戏就崩"，而是：**不打就没事；打枪也没事；一上线（过收点线）那一刻爆**。
于是第一反应必然是"是不是收点逻辑 / 上线那个机制写坏了"。**这个方向是错的。**

### 2.2 真相：执行跳进了 thcrap 跳板池的未写区

thcrap 每采纳一条**声明的断点**，就在一块**可执行内存池**里给它一格跳板：
`pool_base + index*0x10`，格内容 = 站点原始字节 + `e9` 跳回（池页如 `th18:0x03c20000` / `th18:0x03d20000`，
`prot = PAGE_EXECUTE`）。这块池子是**按进程分配的固定大小**。

**声明条数超过池子能容纳的格数** ⇒ 取到一格**从没写过**的槽 ⇒ CPU 执行的是 `00 00`
（= `add byte ptr [eax], al`）；此刻 `Eax = 1` ⇒ 正好产生那个看起来莫名其妙的签名：
**`C0000005h`（访问违例）「写」`0x1`**（那天五份 dump 全是这一个签名）。

### 2.3 三条实据（为什么敢说就是它）

| 证据 | 内容 | 说明 |
| --- | --- | --- |
| ① 偏移随条数平移 | 25 条声明时崩点偏移 `+0x65a`；减到 22 条 ⇒ `+0x62a`（Δ = `0x30` = 3 × `0x10`）| 坏指针是「**池布局相对**」的 ⇒ 变量就是**声明条数**，一格 = `0x10` |
| ② `ebp` 链 | `ebp = th18:0x1ade74`（`esp = th18:0x1ade40`，上层 `WinMain+0x8e8`）往上两级，现场夹在 `ItemManager::on_tick` 内部 | ⇒ 是「**收点路径上执行到了那条坏跳板**」，不是收点逻辑本身有 bug |
| ③ 分片实验 | 35 条声明切进**两个**归档（A 18 + B 17，两档都挂）⇒ **照样崩** | ⇒ 预算**不是按 patch 算**，是**按进程**；「多开归档」这条捷径不成立 |

第二条还有一层含义：**「触发者」是被冤枉的**。被写坏的只是**某一条**站点的槽（取决于声明顺序与条数），
谁最先踩到它，谁就成了「触发者」。那天最先被怀疑的是每敌每帧的 `ce_enemy_damage`（`th18:0x42f2cb`，当晚新加）
—— 它确实是最先踩到的人，但**它不是原因**。用户看到的「上线收点那一刻爆」同理：那是**收点路径**最早用到了坏槽。

### 2.4 为什么会走到这一步（根因）

在 ZUN 引擎里，「加新机制」最自然的写法就是**在引擎某处拦一条**（每次射击、每个敌人、每次收点…）。
卡一张张加，站点一条条线性增长 —— **没有任何人在记账**。直到某天总数越过池子容量，
而崩法还长得像玩法 bug（见 2.1）。⇒ 真正的修法不是「把触发的那条删掉」，
而是把**「入场时刻」当稀缺资源统一记账**（见 §5 硬约束）。

### 2.5 诚实记录：安全线数字对不上，别当常量用

同一个池子在三次实测里给出的「安全线」并不一致（`enabled.json` 当时挂哪些归档、别的 mod
（base_tsa / mouse / probe）自己声明多少断点、诊断版是否带观察者站点，**都在吃同一个池子**）：

| 出处 | 记的数字 |
| --- | --- |
| 定责轮（`996624c`）| 声明 ≤12 不崩；14 / 16 / 22 必崩（当次配置 + 诊断版观察者站点）|
| 护栏 round1（`6515c84`）| **24 安全 / 26 必崩** |
| 护栏 round5（`5927201`）| **单档 22 安全 / 24 崩** |
| 当前（2026-09-17 实测）| **22 / 24（余量 2）** = 正式 patch 20 条 + 测试归档 2 条 |

⇒ **把数字当「当前配置下的余量」读**，用 `sites.py check` **现算**，别把任何阈值当常量记。
稳定的只有三件事：崩法与池有关、**按进程共享**、**声明条数是唯一变量**。

### 2.6 现在怎么防（已入库的机制）

| 机制 | 作用 |
| --- | --- |
| `native/sites.py` 的 `SITE_BUDGET`（= 24）| 口径 = **本 patch 实际声明条数**（不是脚本里的列表长度，第一版就误用过）⇒ 超线**构建失败** |
| `native/tools/gen_def.py --check` | 「声明 ↔ 导出」双向对账：一边缺 = 游戏里**静默不生效**，另一边多 = **僵尸导出**（启动器会报）|
| `native/tools/deploy.py` | **唯一发布路径**：构建 → 预算 → 对账 → 复制 → 回读 md5（patch 与 DLL 必须同一次构建）|
| `ce_site_trail()`（`native/sdk.c`）| 每个 handler 入口打一行、**逐行 flush** ⇒ **崩前最后一行就是现场**。⚠ 新加的 handler 必须调它（同僚的 `BP_ce_enemy_damage` 因没打，差点被排除掉）|
| `ce_mem_map_dump()`（`native/sdk.c`）| 把 `th18:0x03c00000..th18:0x03e00000` 里 `PAGE_EXECUTE` 的页整段打 hex ⇒ 离线看出「池里哪些格写过、零尾巴从哪开始」|
| `tooling/crashdump/dmp.py` | 版本无关 dump 解析：异常码 / 访问地址 / `Eip` 属哪个模块 / **崩点那页的原始字节** / `ebp` 链 / 模块表 |

  `esi = 0x1a0af298` 且 `[esi] == 0`。

  调用者（`th18:0x443033`）⇒ **Bomb 是开局单例** ⇒ 崩因是**运行期虚表被零写**，不是"构造函数没跑"。
- 下一步取证：每帧窥视 `[BOMB_PTR]` 首 dword，变 0 就当场打行（帧号 + 站点轨迹）。

## 9. ★ 站点预算：**按进程算**，且 `base_tsa` 也在吃（2026-09-18 补，对所有人都成立）

**这条不只影响我们**：thcrap 的断点池是**进程级**的（分片实验已证 per-patch 是错的）——
凡是在同一进程里声明断点的 mod 都在抢同一排跳板格。本机实测：

| 消费者 | 条数 | 出处 |
| --- | --- | --- |
| 我们的正式 patch | 20 | `patch/th18.v1.00a.js` |
| 我们的测试归档 | 2 | `patch-test/th18.v1.00a.js`（不需要观察者时关掉 ⇒ 免费腾 2）|
| **外部：`base_tsa`（随 thcrap 分发）** | **18** | `repos/nmlgc/base_tsa/th18.v1.00a.js`，handler 在 `thcrap_tsa.dll` |
| **合计（进程级）** | **40** | 2026-09-17 实测：**此配置崩过两次**（池崩，`Eip` 落在 `RESERVE` 未提交区）|

**由此定下的三条（`sites.py` 已实现，`GATES.md` 是台账）**
1. `sites.py check` 现在按**进程级**逐行打印：我们 / 测试归档 / 外部 / **合计**，并给安全线
   （`SITE_BUDGET=24` 我们自己的硬线；`SITE_TOTAL_BUDGET=38` 进程级告警，依据 = 已知 40 崩过）；
2. **闸可观测**：DLL 开机自检打一行 `pool: 可执行页 N、跳板格 M、首个全零格 @…`
   （判据与离线工具 `tooling/poolmap.py` 一致）⇒ **每次运行都能读出实际占用**，不再靠数声明；
3. **配额**：还没真做的卡默认 **0 条新站点**（能调用 / 数据层 / 并进既有站点就不加）；确需则 ≤1 条并写明理由。

**给同僚的操作建议**：加站点前先跑 `python3 native/sites.py check`，确认"合计"没涨过安全线；
如果 `base_tsa` 也升级了断点（它的 18 条可能变），你会从那一行立刻看出来。
