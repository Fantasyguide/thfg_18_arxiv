# Collect-2X Implementation Plan（收点系统卡，双被动）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
> **版本**：TH18 v1.00a（`th18.exe`，imagebase `0x400000`）。本计划裸地址默认属该版本。
> 日期：2026-09-08。状态：计划待审（断点字节已一手核对；未实跑，AUDIT 前一律 🟡）。

**Goal:** 在 card-expand 里落一张双被动卡：被动一 = TH14 辉针城收点系统 1:1（批结算档位表 → 碎片 + 分数补差），被动二 = 非聚焦射击命中掉【金钱】道具（频率随火力）。

**Architecture:** 沿用「引擎断点 → SDK 沿卡链表分派 → 卡 hooks」既有模式。新增 4 个 SDK 断点与 4 个可选 hooks 槽（`ce_hooks_t` 尾部追加，designated-init 增量，既有卡不受影响）；批次状态机与掉钱策略 = 纯逻辑 core（主机单测惯例），卡文件只做接线。**不用引擎 RNG**（掉钱判定纯确定性 → replay 安全）。

**Tech Stack:** C11, i686 MinGW GCC, GNU Make, Python 3（sites 字节校验），thcrap JSON/codecaves，既有主机测试。

**Spec:** `docs/superpowers/specs/2026-09-08-collect-2x-design.md`

### spawn ABI（已核对，`ItemManager__spawn_item 0x446f40`）

- 调用惯例（2026-09-08 objdump PE 对齐复核 `0x430473-0x430493`，**修正本行初稿**）：`ECX = *(void**)0x4cf2ec`（ITEM_MANAGER，从全局装载，`0x430473` `mov ecx,[0x4cf2ec]`）；**8 个栈参、callee `ret 0x20` 清栈**（`0x446f56` 无效型退出与 `0x447137` 正常退出都是 `c2 20 00`——初稿记的 `RET 0x1c` 是错的）：callee 侧 `[ebp+0x8]=type`、`[ebp+0xc]=pos(float* x,y,z 三字段都读)`、`[ebp+0x10]=junk`（原生从没写过，**我方调用传 0**）、`[ebp+0x14]=angle`、`[ebp+0x18]=speed`、`[ebp+0x1c]=计时/种参`（原生撒落传 0 → spawn 置 `item+0xc84`=0 并立即调 `0x4472b0` 一次；**我方照传 0**）、`[ebp+0x20]`/`[ebp+0x24]` 两参**从不读取**但调用方必须压足 8 个（原生 = `0x430479` `sub esp,8` 留的未初始化区，我方传 0）。原生 main-drop 调用点实参 = (type, 敌pos, 垃圾, `−1.5707964f`(`0xbfc90fdb`), `2.2f`(`0x400ccccd`), 0)。type ≥ `0x14` → 返回 0（eax）不撒。返回 eax = 新槽指针。
- spawn 出生写入（`0x446f40` 本体，2026-09-08 一手）：`item+0xc74`(state) = **1**（`0x446fac` `movl $1,0xc74(esi)`）；pos → `+0xc2c`；x 钳 ±192.0；angle/speed → `0x447430` 化成速度存 `+0xc38/+0xc3c/+0xc40`；`+0xc80`(磁力速度)=0、`+0xc84`=计时参、`+0xc78`(type)=入参、`+0xc90`=−1。
- 道具 type：1=P、2=金钱（`collect_money_item 0x446b00`，**每枚固定 +1 钱**：尾 `MONEY=MONEY+1`；身价只喂弹字/分）、4=命碎道具（collect → 命碎链 `0x457570` 口径）、6=符卡碎道具、9–0xe=小分。磁力判定对 type 9–0xe 除外（`0x4465da+` 段），其余含 2/4/6 全被吸。

### 分数补差与批次口径（引擎事实）

- 每枚道具分值在**各自 case 内即时入 `SCORE`**（钱道具 `uVar3/10`、小分/P 各自公式）→ 批次结算只能做「补差」：`SCORE += batch_score × (倍率−1)`（spec §3.2 原文）。
- 每道具分值捕获 = **collect/commit 双断点增量法**：collect 时 `stash = SCORE`（仅批集 type∈{1,2,9–0xe} 才 stash），commit 时 `delta = SCORE − stash`（串行单线程、commit 紧邻其 case 之后、早于下一道具的 collect → 精确一对）。自动包含其它分数卡的 `on_item_score` 改写（batch = 实际所得，1:1）。碎片/其它 type 不 stash → 不误计（即便其 case 加了分）。
- 收点批集 = type∈{1,2,9–0xe}（spec 用户拍板）。碎片（4/6）收集走同一 collect/commit 断点但不入批。
- 引擎收尾 `0x44658a` 后 `[EDI+0xc74]=0`（槽清空、摘链）——「已收集」与「在飞」天然分层。**state 机（2026-09-08 spawn/body 一手补订初稿）**：0=空；**1=出生/飞行中**（spawn `0x446fac` 置 1；抛物/待吸附期）；**3/4=磁力吸附中**（`0x445f6f` 置 3、`0x446647` 置 4，速度存 `+0xc80`；到达自机半径 → `0x44625f` 起 type 分派）；2=分派处理中（瞬态）；5=收集完成后的延迟段（`+0xc84` 倒计时；语义细节点 🟡 不挡本卡路径）。**修正后的批未闭谓词：`type ∈ {1,2,9–0xe}` 且 `state ∈ {1,3,4}` 的槽存在 → 不结算**（初稿漏了 state 1 = 出生即飞行中的整段）。🟡 实跑验「收集路径全覆盖」：line/半径两路是否都过 `0x44625f` 分派（AUDIT §Z，若 line 路直通 case 则其入批点在 commit BP 补）。

### 数值/限速（建议值 → 用户确认，见 §待确认）

- 掉钱间隔（帧）：`96 − power×16`（power=0.00 → 96 帧 ≈0.6 枚/s；4.00 → 32 帧 ≈1.9 枚/s；线性）。每触发 1 枚 type 2，掉在命中敌 pos。上限：全局每帧 ≤1 枚（间隔 ≥32 帧已隐含）。全确定性。
- 批分数补差定点：`delta = batch_score × (mult_permille − 1000) / 1000`（int64，截断向零；倍率 ×0.5/×0.8 档 delta 为负 → 应用时钳 `SCORE ∈ [0, 999999999]`，原版「分数不可减」约束）。
- ×0.5/×0.8 档负补差 = 1:1 原义（该批收点分净得减半/八折）；与 DDC 实机的对照复核进 AUDIT（若实跑显示 DDC 为入账即乘/延迟入账，只需改结算一行 + 测试，AUDIT 定案）。
