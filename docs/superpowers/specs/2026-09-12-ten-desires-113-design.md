## 0.5 ★ 用户 2026-09-12 裁决 + 网络资料核对

### 0.5.1 神灵实体（spec §9 #3 已定）

> **用户原话**：「113 神灵实体 ≈ P 点、蓝点等**下落道具**，但是：**1、不会下落；2、不会被全屏收集收集，必须跟过去吃；3、会随着时间不断变小而消失；它不是敌人。**」

⇒ 实体层 = **自建 VM 池的道具样实体**（不是敌人、不进引擎道具池）：原地不动 / 靠近才吃 / 生命期内**逐渐缩小**到消失。
「不会被全屏收集」是天然的：`ce_item_collect_all()` 只动**引擎道具池**的 state，我们的池不在其中 ⇒ 必须自己走过去。

### 0.5.2 网络资料（2026-09-12 检索，供 §9 #5「计分载体」参考）

- THBWiki「游戏攻略/东方神灵庙/系统」：**满 P 时红点一个 10000 分，没满 P 红点没分数**；结算分 = `100万 × 面数`（EX 记 7 面）再按难度加 `残机×N + 雷×M`（E 100万/25万、N 300万/100万、H 500万/150万、L 1000万/200万、EX 4000万/400万）；**碎片不计入分数**。
- 百度百科（游戏系统概述）：**灵界槽 = 吸收青/白/红/绿四种小神灵激活特殊状态**（与 THBWiki、日文 wiki 口径一致）；神灵**出现方法 = 速破敌人 / 贴近攻击 Boss**（远距离打 Boss 也会出，但频率极低）。
- ⚠ **仍然没有查到**「神灵/灵界 → 最大得点」的直接关系 ⇒ `spec §9 #5` 的计分载体**继续搁置**（卡侧保持「只声明不落笔」，等一手或你拍板）。

### 2.2 「蓝灵 / 白灵」的逐条订正（骨架那一行要重写）

一手四类型（`SPIRIT:73-87`）：**type 0** = 生命碎片 +1（灵界 +2）· **type 1** = 最大得点 +10（灵界 **+100**）·
**type 2** = 符卡碎片 +1（灵界 +2）· **type 3** = 灵界槽 +1 且加分（灵界中只加分）。
一手六条生成通道（`SPIRIT:118-134`）：A 累计伤害阈值（type 1）· B 死亡计时 `spec1/spec2`（type 1）·
C ECL `spec0`（type 任意）· D item 10–14 · E 玩家死亡（type 3）· F 连锁（type 3）。

⇒ 骨架那一行有**三处错**：

1. **「连击产白灵」没有这条通道** —— 连锁通道 F 产的是 **type 3**（灵界槽 + 分），而且它的判据是
   「**60 帧窗口内连掉 10 颗 ⇒ 第 11 颗额外送 type 3**」的**掉落计数**，不是连击数（`SPIRIT:209-222`）。
2. **「击破 / Boss 伤害产」把通道说错** —— 「按累计伤害掉」是通道 A（`SPIRIT:136-151`，越靠近敌人打掉得越密）；
   **击破**走的是通道 B 的 `spec1(N)` / `spec2(N)` **计时窗口**（`SPIRIT:153-167`）。
3. **「红 / 绿 → 残 / 雷碎片」的颜色命名与一手配色不符** —— `astral.anm` 的 `color()` 一手值是
   type0 绿环+品红芯、type1 橄榄环+**蓝**芯、type2 紫环+绿芯、type3 灰环+灰芯（`SPIRIT:99-104`），
   而且**「颜色 ↔ 玩家观感」未做社区对账**（`SPIRIT:89-90,403` 🟡）。

⇒ **以一手为准：按 type 0–3 重建**。「蓝灵 / 白灵」这个二分要么废掉，要么在钉死映射表之后才用 —— ⏳ 待定（`audit` §113① 第 5 条）。

### 3.5 灵界窗口与 `on_delete`

- 时长 = **进入时的槽值帧数**（满 600 帧 = 10 s），灵界中 **−1/帧**（`th13:0x43d4f0`）；
  非死亡触发的结束再 **−200**（夹到 0，`th13:0x405cdd`）—— ✅ 照抄（§4）。
- 原作死亡触发的结束时**会再调一次 `Player::die`**（`th13:0x405c3e`）—— 我们**不做延时**（定案 ②）。
- **删卡路径（METHOD 铁律）**：灵界进行中被倒吊人 / 原版空白卡删掉 ⇒ `on_delete`（`+0x50`）必须收干净：
  灵界背景 VM、HUD VM、无伤闸的闩锁、槽值缓存。商店里 AbilityManager 冻住、tick 全停 ⇒ **只靠 tick 的清理等于没有清理**。
- ⚠ `+0x14` 的现场事实：117 的先例注释写明它是「respawn 之后的钩子，那时 `ce_player_pos()` 已经是复活点」
  （`animal.c:1777`）⇒ 113 若需要「中弹点坐标」，`+0x14` **拿不到**（117 是靠 `+0x10` 存下来的）。

## 7. AUDIT 要点

- **分层不许越界**：`+0x14`（事后层）里**禁止**调 `cancel_impending_death` —— 那是救援层（`+0x10`）的动作；
  113 与 117 的分离正是靠这条（`EC` §4.2、`REVIEW` §5.8）。
- **`+0x14` 拿不到中弹点**（现场是 respawn 之后，`animal.c:1777`）⇒ 不要在里面读自机坐标当「中弹位置」。
- **无敌若走 `player+0x47774`**：必须走声明层（`ce_invuln_request` + `ce_invuln_apply`，`EC` §4.1、`sdk.h:687`），
  否则会**把 107/117 给的长无敌截短**（`EC:145` 的实测风险）。
- **删卡（METHOD 铁律）**：灵界进行中被删 ⇒ `on_delete` 必须收干净（背景 VM / HUD VM / 无伤闩锁 / 槽值）；
  清理**不能依赖 tick**（商店里 tick 停摆），且要能**连续多张**执行（原版空白卡一次删光整副牌）。
- **计分仲裁**：若用 `on_item_score`（`0x446cf6`），必须按 `EC` §3 的「声明 + id 最小者落笔」写，
  **不许直写 `esi`**（否则与 110/111 互相覆盖，`EC:80` 一手现状）。
- **replay 安全**：随机走 `ce_rand()`（`sdk.h:346`）；**禁止 CRT `rand()`**（`SDKMD:217` 的教训）。
- **一次中弹只消耗一次**：113 的「强制灵界」是事后动作、不参与救援消耗 ⇒ 但要确认它**不会**在中弹当帧之外重复触发
  （`EC` §4.1 ②：三张卡共享「一次中弹」这个事件）。
- **自建实体不入原生池的代价**（若走 VM 池）：原生磁吸 / 回收线 / 114 的批集计数都看不到它（`REVIEW:980`）。
