## 4. 根问题最终答案（R1–R10）

### 4.1 R1｜引擎面：要不要「生成真敌人」——**要**

- **原推荐 B（伪实体起步）已被推翻**。两条依据：
  1. **假敌人不可行**（§6.2）：寻的弹每帧按 `enemy_id` 回链表重解析 ⇒ 只写缓存无效；
     塞假块要伪造完整 `zEnemy`（`0x683c` 字节）+ vtable。
  2. **惰性真敌机干净可用**（§6.1）：ECL 名字查不到就得到一个「完全不跑 ECL、不崩」的真敌机身体。
- **落地**：108 使魔 = `EnemyManager__allocate_new_enemy` `0x42d7d0` + 名字传 `NoEnemyDebug`；
  112 也走**真敌人**（§3.2）。

### 4.2 R2｜「击破 / 敌人死亡」信号 —— **开死亡断点**

- **原推荐 B（存活差集代理）被否**。§3.1 第 2 条拍板：**开断点**，109 / 110 / 112 / 113 共用。
- **★ 选址已定（2026-09-11 一手普查 + 主线复核）**：主断点 = **`0x430240`（`Enemy__die` 入口）**，
  `cavesize 6` / `expected 558bec83ec14`（`push ebp; mov ebp,esp; sub esp,0x14` ✓），**thiscall，`ecx` = zEnemy**。
  - 体内顺序（一手）：死亡特效 → **撒主掉落 `0x430469` 读 `enemy+0x623c` → `0x430493 call 0x446f40`（引擎自己撒）**
    → `0x43049f call 0x430510`（既有 `BP_ce_enemy_drop_pre`）→ `0x4304aa` **清空 `enemy+0x623c`**
    → `0x4304c8 call 0x48d920`（死亡 ECL，名字在 `enemy+0x67d4`）。恒定 `mov eax,1` 返回 ⇒ 一敌一生**正好一次**。
  - **7 个调用点**（一手 grep 全集）覆盖四类死亡：被打死 `0x42ee8b` / `0x42f3b2` / `0x42f3d8`、
    ECL 跑完、ECL `die` opcode `0x430f54`、killAll 三兄弟 `0x4307ec` / `0x4309fb` / `0x430c03`。
  - ★ **它在「撒主掉落之前」** ⇒ 是唯一能在**主掉落生成前**改掉落表（`enemy+0x623c`）的位置
    —— 比 `on_enemy_drop_pre`（`0x430510`，在撒之后）强，**直接改 R9 的落地方式**（见 §4.6）。
- **❌ 主断点漏三类「静默消失」**（对四张卡**不该算击破**，漏掉是对的）：

### 6.1 ★ 惰性真敌机干净可用（108 / 112 的载体）

`EclRunContext::ecl_run` `0x48b3a0` 开头两行就是哨兵守门：

48b3b3: mov edx,[edi+8] ; cmp edx,-1 ; je 0x48b4d8   ; 指令偏移 = -1 → 收工
48b3bf: mov ecx,[edi+4] ; cmp ecx,-1 ; je 0x48b4d8   ; sub 索引 = -1 → 干净退出

而 `Enemy__sub_48d920` `0x48d920` 查名失配时写 `[enemy+0xc]+4 = -1`（`0x48d9a7`）
⇒ **给 `allocate_new_enemy` 传一个当前 ECL 里不存在的名字，就得到一个「完全不跑 ECL、不崩」的真敌机身体**。

**★ `NoEnemyDebug` = 原作自带的完美惰性空壳**（一手反汇编）：

```
void NoEnemyDebug() {            /* 一手反汇编 */
    goto L80 @ 0;
L60: wait(1000);
L80: if (1) goto L60 @ 0;
}
```

= **`wait(1000)` 死循环**：不移动、不开火、不设 hurtbox / hitbox、不掉道具、不自删、**永不返回**。

- 反例（都**不能**当空壳）：`DebugSkipFunc` / `DebugSkipStopFunc` = `debug901()/902()` 后**立即 return**

**连带结论**：

- ⚠ **订正（2026-09-12 一手）**：**「不设 hurtbox 就天然打不到」是错的** —— `allocate_new_enemy` `0x42d7d0` →

### 6.2 R1 支证：假敌人塞不进目标链表

- **唯一目标选取入口** = `0x438cb0`（stdcall `(out_id, pos)`，半径走 XMM3）。全 EXE 只有 3 个调用者：
  灵梦高速寻的弹 tick `0x45f7c0`（半径 `0x4b9354` = 256.0）、`CardAlice__on_shoot` `0x40b4e0`（512.0）、
  子机目标选择 `0x421e21`（512.0，结果写 `obj+0xc4`）。
- **判据**：遍历链表 → 跳过 `flags_lo(+0x635c) & 0xc000021` → 取平方距离最小且 `< radius²`；
  结果写 `*out_id = enemy+0x6830`。**不看 boss / owner / 屏幕内 / hurtbox**。
- **决定性**：寻的弹把结果缓存在 `bullet+0x90`，之后**每帧按 id 回链表重解析**，找不到就清缓存
  ⇒ **只写缓存无效，必须真在链表里**。且**没有共享的「当前目标」全局**。
- **数据源**：`ENEMY_MANAGER_PTR` `0x4cf2d0`，链表头 `+0x18c` / 尾 `+0x190` / 计数 `+0x198`；
  节点内嵌在 `enemy+0x1514`（`[+0x1514]` 自指针 / `+0x1518` next / `+0x151c` prev）。
- **塞假块不安全**：`+0x18c` 被约 50 处遍历，至少 3 处会接管假块
  （`0x42ab65` 调 vtable `[eax+0x14]`；`0x430720` / `0x430920` / `0x430b30` `memset(enemy+0x6240,0,0xc0)`；
  `0x42df99` 调 `0x42fe80`）⇒ 必须伪造完整 `zEnemy`（`0x683c` 字节）+ vtable，不如用真敌人。
- **两条有用的 flag（一手）**：`flags_lo & 0xc000021 != 0` = **锁定黑名单**（位 30 由 spawn 参数 `+0x14 >= 1000` 置）；
  `flags_lo & 0x31` **置位 = 被排除在「真敌人」之外**（⚠ **2026-09-12 订正：原文「算作真敌人」极性写反了**；
  铁证 = 计数函数收尾 `0x42d472 test ecx,ecx` / `0x42d477 cmovne eax,edx` ⇒ 置位**不计数**；`0x43c12a` 同向）。
  ⇒ 「打不到但可锁定」理论上可共存（只要不碰位 30），但 TH18 现成的「可锁定且绝对打不到」原型 ❓ 未找到
  （`no_hitbox_timer` `+0x6330` 全程序只有 2 处写、都是失效值，读点未定位）。
  ★ 另一条独立的「排除」杠杆：**`enemy+0x6320 > 0`**（两处判定都带上它，且不碰伤害可及位 `& 0x21`）。
  ✅ **语义已定（2026-09-12，108 实装期一手）**：`enemy+0x6320` = **`invuln_timer.current`** ⇒ 设正值 = 使魔**无敌**，与 108「使魔必须能被打」直接冲突 ⇒ **已否决**，108 注释里备查。
- ⚠ **伤害可及面（新一手）**：伤害源只打 `flags_lo & 0x21 == 0`（`0x42f101`）+ hurtbox > 0（`0x42f10a`）
  + `invuln_timer ≤ 0` + `flags_lo` bit4 = 0 的敌人 ⇒ **`& 0x31` 一旦置位，敌人立刻伤害免疫**（它含 bit0/bit5）。
- **结论**：108 走 `EnemyManager__allocate_new_enemy` `0x42d7d0` 造**真敌人** + 三件无害化
  （卡侧每帧钉 `+0x1270` / `+0x1274`、用无敌字段而非位 30、不给 ECL 行为不掉落）。
  **代价**：真敌人会被敌人 tick / 碰撞 / 掉落 / `enemy_count_real` 一并接管。

### 6.3 发射口（108 使魔）

**★ 实测：敌人几乎没有「离体发射口」** ⇒ **「使魔 = 远发射口实体化」站不住，改判 1:1**。

- **枚举活跃发射口的唯一可靠判据 = `props[i].type`（`+0x00`, u16）≠ 0**
  （`etNew` 先 `memset(props[i],0,0x488)` `0x433e05`，只有 `etSprite` `0x434032` 写它）。
- ⚠ **`offset_final`（`+0x08`）不能当「已配置」标记、也不能直接拿来算距离**：`etNew` 清 0，
  只有 `etOn`（`0x433f8a` / `0x433fec`）那一帧才写 ⇒ 两次 `etOn` 之间它是**过期的世界坐标快照**。
  算距离要用**相对偏移** `offsets[i]`（`enemy+0x4e58+i*0xc`）或 `origins[i]`（`enemy+0x4f18+i*0xc`）。
- ⚠ `etNew` 写的不是「占位」而是**可用默认值**：`+0x1c = 2.0f`、**`+0x46c = 1` / `+0x46e = 1`**、
  `+0x474 = 0x23`、`+0x478 = 0x15`、`+0x47c = 0x26`（`0x433e16`–`0x433e54`）。

**★ 22 个 ECL、838 个子程序逐条统计**：

| 配置的发射口数 | 子程序数 | 占比 |
| --- | --- | --- |
| 0 个 | 632 | 75% |
| **1 个** | **197** | **23%** |
| 2 个 | 8 | 1% |
| 4 个 | 1 | 0.1% |

- 用 ≥2 的**全游戏只有 9 个**（最多的是 `st04bs BossCard3_at` 用满 4 槽；其余 8 个都是槽 0/1）。
- 带 `etOffset` 的只有 11 个子程序，且偏移都是小量或运行期变量；**`etOffsetAbs` 全游戏 0 处**。

**★ 1:1 落地（108）**：

- 使魔数量 = 该敌当前 `type != 0` 的槽数（实测以 1 为主、boss 最多 4）—— 密度天然合理。
- 打死使魔 → 关掉**那个槽**（hook `0x434019`，此处 `esi = enemy + i*0x488` 可反推 `i`）。
- **「下一波要重开」的问题自动消失**：ECL 下一波会重新 `etNew(i)` + `etOn(i)`，
  只要每帧做**状态差分**（活跃且无使魔 → 建；不活跃且有使魔 → 撤）⇒ 除关闭那一个 hook 外**不再需要别的断点**。

**★ 发射口「能不能关」的一手（回答 R7）**：

- `etOn` `0x433f34` **不查 `type`**（全程只读 `origins[i].z` / `offsets[i].xy` / `enemy.pos`；
  `0x433f8a` / `0x433fec` 写完 `offset_final` 直接 `call 0x427810`）。
- `0x427810` 也**不查 `type`**。`props+0` 其实是**弹种 id**（`0x4256b2` 拷进 `bullet+0xf98`；
  `0x425770` 用 `props.type × 0x118` 索引弹种表 `0x4c5f90`）⇒ **写 0 只是变成 0 号弹种，不是关闭**。
- **真闸**：`cmp ax,[edi+0x46e]`（`0x42789e`，外层）+ `cmp ax,[edi+0x46c]`（`0x4278b4`，内层）——
  **≤ 0 整段跳过**；另有「弹池空 → 提前跳出」（`0x424fe0` 返回 1，`0x4278d2`）。
- ⇒ 把 `+0x46c` / `+0x46e` 清 0 **机制上有效**，但 ECL 通常**同帧**先设 count 再 `etOn`，
  `on_draw`（帧末）清 0 挡不住同一帧 ⇒ **不挂断点不可靠**。
- **最省**：hook **`0x434019`**（`etOn` 里 `push eax` 前，`esi = enemy + i*0x488` ⇒ `i` 可反推），
  被禁则跳到 opcode 收尾 `0x43402d`。次省：hook `0x427810` 入口反推 `i` 后直接 `ret`。

### 6.4 消弹接口（109 / 110 / 111）

- 全 EXE 的消弹入口只有四个：`0x4297a0`（全屏）、`0x429370`（半径 + 转道具）、

## 7. 绿点 / 最大得点系统（110 + 111 共用）

### 7.1 一套系统 + 信仰分槽

> 用户原话：「111 的绿点和 110 的绿点**完完全全就是同一个东西**！它们加的都是分，只是加的数量不一样」
> 「110 绿点加的是，**会消失的**最大的分；111 绿点加的是，**最大得分，不会消失**。所以数值尺度才会差。
> ……**信仰分槽**：有 110 的时候，绿点 = 5000 会消失的风神录最大得点；有 111 的时候，绿点 = 100 …的
> 地灵殿最大得点；都有的时候，绿点 = 上面两个之和。然后最终按照最大得点公式算一个出来」

**⇒ 就按这个做：一套系统、分槽记账。**

| 装备 | 绿点落进哪个槽 | 单颗值 | 衰减 |
| --- | --- | --- | --- |
| 只装 **110** | 风神录槽 | **+5000**（E/N）/ +8000 / +10000 | **会消失**（MoF 信仰会掉）|
| 只装 **111** | 地灵殿槽 | **+100**（大绿点）| **不会消失** |
| **两个都装** | **两槽都进** | 上面两个**之和** | 各自按自己的规则 |
| 最终 | **`最大得点 = f(两槽之和)`** | | |

- 这解释了「数值尺度差两个数量级」：**MoF 的最大得点会掉，所以单颗给得多；SA 的不会掉，所以单颗给得少**。
- **不是跨卡耦合**：一套实现 + 两个记账槽，卡只往自己那个槽写。

| | 大 | 中 | 小 | 微 |
| --- | --- | --- | --- | --- |
| **MoF（110）** | **+5000 / +8000 / +10000**（E/N · H · L，一手核实）| — | **+100** | **+10**（消弹）|
| **SA（111）** | **+100** | **+10** | 每 100 个 **+10** | — |

- 实现共识：**VM 池 + spawn + 收集判定 + 加值**；两张卡各自传自己的**数值表**。
- 「**随机把妖精变绿**」也**共用同一套**。
- ⏳ 若两张卡同时装备：**「各有一个池，还是共用一个池」待定**（不阻塞公式）。

### 7.2 记账口径（基础 / Δ / 上限）

**★ 信仰基础两者不一致**：

| | 基础值 | 上限 |
| --- | --- | --- |
| **MoF（110）** | **固定 50000**（所有难度），**下限也是 50000**（不会被扣穿）| — |
| **SA（111）** | **按难度**：E **25000** / N **50000** / H **100000** / L **200000** / EX **200000** | **2× 基础** |

⇒ 只有 **NORMAL** 撞巧同为 50000。

> 用户定案原话（2026-09-11）：「**下限 50000 扣不穿 = 基础 50000 + 从 0 开始计数的"额外信仰"**，
> 我上面的式子都是**额外信仰**」「**按照地灵殿收这么多绿点的时候触及最大得点上限，也就是给额外部分加上限**」

| 量 | 口径 |
| --- | --- |
| `基础_110` | **恒 50000**（常数）|
| `基础_111` | **25000 / 50000 / 100000 / 200000 / 200000**（按难度，常数）|
| `Δ_110` | **从 0 起算**，**下限 0** ← 这就是「50000 扣不穿」的实现方式（不是对总和设下限）|
| `Δ_111` | **从 0 起算**，**上限 = 原版 `基础_111`** ← 原版「上限 = 初值 ×2」的等价写法 |

**由此解掉两个问题**：

1. ✅ **不需要归一化**。「尺度差」不是设计缺陷：**MoF 侧会衰减 ⇒ 稳态本来就低；SA 侧会累积 ⇒ 稳态本来就高**，
   两者直接相加是合理的。
2. ✅ **SA 的上限照旧管**，但作用在 `Δ_111` 上。
3. ⚠ **基础绝不能再相加**（会凭空多出一个底）：**基础只取一份**，只有绿点的**增量**分槽记账。

### 7.8 PV → TH18 计分的接法（一手闭环）

**TH18 原生「吃一颗金钱」的得分式**（`collect_money_item` `0x446b00`）：

```
446d03: mov eax,0xcccccccd ; mul esi（esi = 身价）; shr edx,3   ; edx = 身价 / 10
446d17: add eax,edx        ; SCORE(0x4cccfc) += 身价/10 ; 钳 999999999
```

⇒ **一颗金钱 = `SCORE += 身价/10`**（所以弹窗显示 `value`、实际得分是 `value/10`）。
⚠ 这条路径**不直接读 `0x4ccd24`** —— 它读的是 `esi`（身价），身价在 `0x446b00` 里由 MONEY / 最大得分算出后**钳 ≥10**。

| 项 | 内容 |
| --- | --- |
| 断点 | **`0x446cf6`**（在 `collect_money_item` 内，**弹窗与计分之前**）|

| 双计分 | ✅ **天然不会** —— 改的是**被除数**，不是外加一笔；**不需要关掉原生计分** |
| ⚠ 注意 | ① 弹窗数字会跟着变成 `PV×10`；② `0x4ccd24` / `MONEY` / `MONEY_TOTAL` **不受影响**；③ `int32` 防溢出；④ 频率 = 金钱道具数，性能无虞 |

- ⇒ **卡的写不会被抹掉，但会被叠加**。必须在**帧初**（`on_item_frame` `0x446ee3` 在池 body **之前**）
  改 `pos` 并**同时把 `vel` 清零**。

### 8.3 「改道」三条路线

| 路线 | 判定 | 副作用 |
| --- | --- | --- |
| **a) 卡侧每帧写 `pos`**（`on_item_frame`）| ✅ **推荐** | ⚠ ① 移出界（`|x| >= 200.0` `0x4b9340` 或 `y > 472.0` `0x4b93a4`）→ 引擎**当帧就删**（`0x445e38`）② 移到自机 **30px** 内 → 收点检查（`0x44620a`）**把道具收掉**。⇒ 围栏：目标点**留在屏内、离自机 > 30px** |
| b) patch 两处目标读点（`0x445f79` / `0x446030`）| 🟡 默认**全场生效** | 这两处没有 per-item 目标字段 ⇒ 改成读全局点会把**全场所有** state 3/4 道具都吸过去；要按 type 过滤就得挂**每道具每帧**的热断点，不划算 |
| c) 复用玩家位置 | ❌ 不需要 | 直接走 (a) |

### 8.4 「吸收 = 道具消失」的最小写法

**不要走 `0x44658a`（collect 尾）**，直接置空槽：

```c
slot->state = 0;              /* +0xc74  */
ce_anm_delete(slot->[0xc28]);
slot->[0xc28] = 0;
```

- 池循环头对 `state == 0` **直接跳下一槽** ⇒ 当帧起不运动、不参与收点检查。
- ✅ **与 114 零冲突**：不执行引擎的 `0x44658a` ⇒ `ce_item_commit` **不触发** ⇒ 114 的 SCORE stash/commit
  看不到假提交；`ce_item_collect`（`0x44625f`）同理不触发 —— **「吸收」不计分，正是要的**。
- 唯一代价：**不走空闲链表** ⇒ 该槽本局不复用（**4696 槽**，够用）。要严谨就把 `0x445e38` 尾的 6 条链操作
  照抄进 SDK（顺带做成 `ce_item_despawn`）。

### 8.5 结论：112 最省实现

**在 `on_item_frame` 里自己当「伪磁场」** —— 不改引擎、不挂新断点、不碰 collect / commit。

1. **扫池**：`mgr = CE_ADDR_ITEM_MANAGER_PTR` **`0x4cf2ec`**（⚠ 不是 `0x4cf2bc` —— 那是**弹幕**管理器），
   槽 0 = `mgr+0x14`、**4696 槽**（`0x1258`）、stride **`0xc94`**、活 = `state != 0`。
   这些常量仓里 `engine.h` 早有（`CE_ITEM_POOL_OFF` / `CE_ITEM_SLOTS` / `CE_ITEM_STRIDE` / `CE_ITEM_POS` /
   `CE_ITEM_STATE` / `CE_ITEM_TYPE` / `CE_ITEM_MAG_SPEED`），**直接用宏，别写裸数**。
2. **吸**：`type ∈ {1,2}` 的活道具每帧把 `pos` 朝 UFO 推进一步（**同时清 `vel`**）；进 18px → `state=0` + 删 anm，
   **计数 +1**（= 击破奖励的 `cntA` / `cntB` 来源）。
3. **奖励**：照 th12 公式（`S = floor10(V × cntB × mult)`，红 UFO 另加 `cntA × V × mult`，下限 10）。

### 9.3 樱点计数器 = `th07:0x62f88c` + 6 个写点

**铁证**：`th07:0x4048ec`–`th07:0x4048fd` 取出 `[th07:0x626278]`，读 **`ds:th07:0x62f88c`**，
`sub ecx,[eax+0x88]`，再拿去 `cmp …,0xc350`(50000) 决定颜色
⇒ **`th07:0x62f88c` = 与 50000 比较的那个值 = 樱点（最大得点）**。

**★ 樱点有基准值** `[th07:0x626278 + 0x88]`：

- HUD 显示的是 **`樱点 − 基准`**（`th07:0x4048f1`–`th07:0x4048fd`）；
- 重置时 **`樱点 = 基准`**（`th07:0x4043b9` → `th07:0x4043bf`），同处还写 `[+0x2c]=0`、`[+0x30]=0x32`(50)；
- 扣减**不会低于基准**（`th07:0x440acc` `cmp edx,[ebp-0x8]` / `jl` → `th07:0x440aec` 夹回基准）。
- ⇒ **50000 是相对「樱点 − 基准」算的**（`th07:0x4049a4` `cmp [ebp-0x2c],0xc350`）。

**全部写点（只有 6 处 —— 增减点就在这里）**：

| 地址 | 语义 | 证据 |
| --- | --- | --- |
| `th07:0x4043bf` | **重置**：`樱点 = 基准` | `th07:0x4043b9` `mov ecx,[eax+0x88]` |
