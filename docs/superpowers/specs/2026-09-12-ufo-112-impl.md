### 2.1 为什么 `fill` 不用 `float`（两道独立理由）

1. **x87 硬门**：i686 Windows ABI 下 `float`/`double` ↔ `int` 的转换会生成 x87 指令
   （`fldl` / `fistpll` / `fldcw`），而 `make dllx87` 断言我们的 object 里 **0 条 x87**。
   先按 `float fill` + 一次 `(double)` 写的版本，`ufo_absorb_item` 里当场出现 **6 条**。
   ⇒ 本层的 `.c` **零浮点**；凡返回 `float` 的函数一律 `static inline` 定义在头文件里。
2. **精度**：`float` 只有 24 位尾数，而这一族增量在 `1e-5` 量级、阈值在 `1e0`
   ⇒ 用 `float` 累加会偏（单测当场抓到：stage 1 该 34 颗却算成 32）。
   ⇒ 增量与阈值全走整数（`ufo_inc_millionths`），spec §4 那张关卡表成了**可复算的单测断言**。

### 2.2 为什么「不丢最旧」会死锁（★ spec §9 #2 的取法必须知道这条）

用户只拍了「三同色 / 三互不相同」两种 ⇒ 常规路径取**信息量最少**的一支：先攒满 3 格，不成组就不召唤。
但「**槽满 + 不成组 ⇒ 什么都不做**」会死锁：`{红,蓝,红}` 这类「两同一异」占满 3 格之后，
后续令牌**全被拒**，而这个组**又永远不成组** ⇒ 这张卡**再也召唤不出 UFO**（6 种排列里 3 种会踩）。

⇒ 本实装保留「丢最旧」**只作脱困**：槽满且不成组时丢掉最旧的一格、整条左移、再放新的，
并且**脱困后要判合成**（否则 2 格是 `{A,A}` 时新来 B 还是不成组，永远回不到能合成的状态）。
决策收在纯逻辑 `ufo_group_put()`（单测覆盖：连续喂同色必须在**有限步**内重新成组）。
⏳ 用户对 §9 #2 拍板后，**只改这一个函数**。

### 2.4 坑 #1 的实测记录（为什么它一眼看不出来）

`ufo_hash_unit()` 返回的是 `[0,1]` 的小数；`(int32_t)` 截断 ⇒ **几乎恒为 0**（= `UFO_COLOR_NONE`）。
实测 100000 个 serial 里只有 **1** 个截出非 0（首个在 serial 65533）：

```
serial 0 -> hash 0.4430 -> (int)0
serial 1 -> hash 0.5144 -> (int)0
serial 2 -> hash 0.8719 -> (int)0
serial 3 -> hash 0.4455 -> (int)0
serial 4 -> hash 0.9950 -> (int)0
cast-to-int nonzero count over 100000 serials = 1
```

它之所以没被主机单测抓到：颜色那一格当时写在**卡侧** `ufo.c`，而主机单测只覆盖 `ufo_core.c`（纯逻辑）。
⇒ 修法与教训：**把颜色轮转表搬进纯逻辑层**（`k_ufo_token_color_rotation` + `ufo_token_color_for_serial`），
并把它钉成断言 —— 「表里每个值都合法」「前 8 个 serial 四色齐」「周期 = 4」「大 serial 不越界」
「返回值永不为 `UFO_COLOR_NONE`」（就是这一条当年会红）。


### 2.5 坑 #11 的穷举记录（为什么表长必须 ≥ 7）

把「令牌颜色轮转表」当设计问题穷举：要求**连续 3 个 serial** 的每个滑动窗口里，
两条凑组规则（三同色 / 三互不相同）**都至少出得来一次**（否则那一种的奖励是死代码）。
脚本对 4^P（P = 4..8）张表全跑：

| 表长 P | 有没有能全覆盖的表 |
| --- | --- |
| 4（= 按原作顺序 `红 蓝 绿 彩虹`）| ❌ 无（每个窗口都「三互不相同」⇒ 全是彩虹 UFO）|
| 5 | ❌ 无 |
| 6 | ❌ 无 |
| **7** | ✅ **有（168 张）** ⇒ 采用 |
| 8 | ✅ 有 |

取用的那张：`绿 彩虹 彩虹 蓝 红 红 红`，6 个滑动窗口依次产出
`绿 / 蓝 / 彩虹 / —(不成组) / 红 / 红 / 彩虹` ⇒ 三条同色规则 + 彩虹 + 不成组**全都出现**。
🟡 代价：红占 5/7 ⇒ 红 UFO（命碎片）偏多（绿/蓝各 1 次）。比例是 ❓ 自定手感值，待调 ——
改表之前先看单测里「轮转表覆盖」那一段（会红）。


## 3. 槽泄漏与性能的**记账口径**（spec §7 AUDIT 要求的口径）

- **槽泄漏**：吸收 = `state = 0` + 删 anm VM（`item+0xc28` 置 0）+ **freelist LRU 摘挂**，
  与引擎两条清尾路径（`0x446595` 收集 / `0x445e38` 出界）**四步逐条一致**（`ufo_item_relink`）。
  ⚠ 那个「摘挂」是 normal_items freelist 的 **LRU 移动**，**不是「把槽还回空闲表」**：
  槽仍在池链表上，要等整条池轮一遍才被复用（引擎自己清掉的槽也一样）。
  ⇒ 正确读法：**不是永久丢失，但周转周期 = 池长度**。泄漏量 = 本局吸掉的道具数，
  由 `ufo_card_t.items_pulled` 直接数出来（日志在 `on_run_reset` / `on_stage_start` 打）。
  余量：4696 槽（`CE_ITEM_SLOTS`）对上一手填充率 stage 1 = 34 颗 / 个 UFO ⇒ **待实跑**看一关的
  `items_pulled` 与「道具不再生成」的临界点。spec §3.4 的 `ce_item_despawn()` 仍未实装（SDK 侧），
  本卡**自己在卡里实现了这四步**（带 NULL 守卫 —— 引擎那两条指令对「已摘下的槽」会空指针，
  所以我们不能无脑照抄，见 `ufo_item_relink` 的注释）。
- **扫池成本**：三层**逐槽**早停 —— ① 只在 `ufo_can_absorb()` 时扫（UFO 在场且存活 > 59 帧）；
  ② `state == 0` 立刻跳过（空槽是最常见的一格）；③ **先读 type**（一次访存）不是 1/2 立刻跳过，
  之后才算几何。最坏 = 4696 × 2 次访存 / 帧（UFO 存活期）。
  ⚠ **没有循环级早停**（池没有「活道具数」索引可用）⇒ 约束里的「必须早停」只在**逐槽**意义上满足。
  ⚠ **没有 exe 实跑 ⇒ 不编帧耗**：本文只给口径，实测帧耗**待实跑**。
