## 0. 一句话

**被动卡「永夜抄」**：**低速 = 整个人换成妖侧机体**（外观 + 子机 + 弹幕同时切），**高速 = 原机体**；
妖侧身边有**使魔**（= 从敌人发射口实体化出来的真敌人），**使魔可打**，被打死按 **1/2 把伤害转嫁给本体**。
妖侧**不发原机体原生弹**（但**不允许改 Z 输入位**）。

## 3. 引擎面

### 3.1 止射闸（★ 核心，已定路线）

- **闸点**：`Player__tick_shooting_state` `0x45ea00` 的**行选择** `0x45ebfb`（`mov edi,[edi+edx*4+0xe0]`），
  **已被 SDK 装了断点**（`BP_ce_shot_set_index`，`sites.py` / `sdk.c:722`，先例 = 117 咆哮）。
- **做法**：该断点 handler 里，**108 active && 聚焦（`player+0x476cc != 0`）** ⇒ `return 0` +
  `regs->retaddr = 0x45eca0` ⇒ **整段跳过原生行循环**，`0x45eca0` 起的**卡广播照跑**。
- **为什么安全**（一手复核）：`0x45eca0` 本来就是引擎自己「空行」的跳转目标（`0x45ec06 js 0x45eca0`）；
  `0x45ebfb` 唯一入口是 `0x45ebf0 je` ⇒ 每射击帧恰好命中一次；
  卡广播段自会重载 `eax/edi/ebx/esi`，而 `[ebp-0xc]` / `[ebp-0x10]` 在行循环**之前**（`0x45ebbf` / `0x45ebc2`）已写好。
- **顺序（用户定）**：handler 里 **先问 `on_shot_set_index`** —— 有卡返回 set 索引（= **117 咆哮**，它返回
  `CE_SHT_SET_WOLF_0 0x1e` / `EAGLE_0 0x23` + 火力档）就**本帧不抑制**；没有覆盖时才问 108 的新询问。
- **新 SDK 面**（②已拍板）：`ce_hooks_t` 尾部加 `int (*on_native_shot_suppress)(ce_card_t *)`，
  返回非 0 = 请求跳过本帧原生行循环。
- ★ **2026-09-12 用户口径追加（与本节上面的字面判据有一处偏离，读代码时别以为写错了）**：
  **`count == 0` 时放行原生弹**。原因：妖侧弹的膛口**恒取子机**（`0x40a9c0`，见 `AUDIT` §BO-5）
  ⇒ 子机数为 0 时妖侧**一发都发不出来**，若同时压掉原生弹就**完全没有输出**。
  这条只在「**早苗 + 火力 < 100**」出现（`YK_OPTION_BY_CHAR` 第 3 行 = `{0,1,2,3,4}`；另三支恒 1/1/4）。
  ⚠ 这是**用户口径、不是一手复刻**（原版永夜抄妖侧不看 P、一按低速就有子机，原作没有这个档）。
  实现 = 纯函数 `yk_should_suppress_native(present, focused, character, power_level)`，
  数量的事实来源**只有** `YK_OPTION_BY_CHAR` + `yk_option_count(...)`（与子机声明层同表同帧）；
  `yk_suppress_native_shot_spec31_legacy(present, focused)` 是**旧判据的薄包装**，只给单测用，
  **引擎侧不要再用**。详见 `AUDIT` §BO-10。
- **不做什么**：❌ 清 `0x4ca428` bit `0x001`；❌ 动 `player+0x4779c` bit `0x200`；❌ 碰总门 `+0x476ac`（POC 线在用）；
  ❌ 重定向 `sht+0xe0+idx*4` 指针（在飞弹每帧回查行指针 ⇒ 会把野行喂给在飞弹）；
  ❌ hook `0x45e930` / `0x45e320`（卡也走那里）。

| 项 | 做法 | 依据 |
| --- | --- | --- |
| **换位**（低速换阵型）| **原生双偏移**：`+0x64/+0x68`（非聚焦）vs `+0x6c/+0x70`（聚焦）—— **引擎本来就做**，零成本 | review §6.5.2 |

#### 3.3.1 ★ 低速子机声明层（与伤害层同形；2026-09-12 定案）

**问题**：108 与 111 的低速子机最终都要落到**同一批子机对象**上（原生聚焦偏移 `+0x6c/+0x70`、贴图脚本、数量），
两张卡各自每帧写 = **同一帧谁后写谁赢**的竞态 —— 覆盖关系会**隐式依赖帧内 tick 顺序**，后继改动会悄悄破坏它。

**定案：照仓里**现成的伤害层**先例，做一个**单用途声明层**（用户 2026-09-12 拍板，并定性为
「**研究中推翻了旧结论**」，不是给旧政策开例外 —— 旧结论「不另做 SDK 仲裁层」是在还不知道会撞同一个字段时下的）。

| 环节 | 设计 | 与伤害层对照 |
| --- | --- | --- |
| **卡片侧** | 只**声明**自己的低速子机意图（数量 / 聚焦偏移 / 非聚焦偏移 / anm 脚本），**不直接写字段** | 伤害层各卡只声明 `bullet_damage_permille` |
| **共享物** | SDK 维护**本帧的声明集合** | 伤害层：`ce_dmg_aggregate()` |
| **选举** | **id 最小者胜、且由它落笔**（`sdk_core.c:177` 的既有规则：「稳定且与链表顺序无关」）⇒ **108(108) < 111(111) ⇒ 108 胜** | 伤害层：`ce_dmg_applier()` |
| **落笔** | 只有被选举的卡会被调 `on_option_pose_apply`，由它自己 `ce_option_alloc` / 写偏移 / 重申请 | 伤害层：被选举的卡就地乘 `bullet+0x9c` + 抬上限 |
| **门** | ★ **只在 `player+0x476cc != 0`（Shift / 低速）时应用** | — |
| **不做的** | ❌ 不写通用仲裁器、不做优先级表、不让卡片互相查询 | — |

**为什么它优雅且 bug 更少**（对应你的判据）：

1. **单一写者** ⇒ 没有竞态，覆盖关系**不依赖帧内顺序**（正是伤害层那条注释的理由）。
2. **只碰低速** ⇒ 高速时这一层**根本不动手**，108 不参与 ⇒ 「108 只改按 Shift 的、高速互不影响」**自动成立**。
3. **卡片零耦合** ⇒ 符合「不跨卡耦合」：108 不知道 111 存在，反之亦然；顺序由 id 规则决定。
4. **门式而非推式** ⇒ 引擎的 `Player__repopulate_options` `0x45d5e0` 重建整池后，下一帧落笔自然补回（沿用既有
   `on_power_level_change` 重申请的做法），不需要额外钩子。

**接口草案**（落地时定稿）：

```c
typedef struct {
    int   count;        /* 想要几个低速子机（0 = 本帧不参与声明） */
    float fx, fy;       /* 聚焦偏移（= 原生 option +0x6c/+0x70，单位沿用该字段） */
    float ux, uy;       /* 非聚焦偏移（+0x64/+0x68） */
    int   anm_script;   /* 子机贴图脚本号（与 ce_option_alloc 第 4 参同款） */
} ce_option_pose_t;

void ce_option_pose_declare(ce_card_t *c, const ce_option_pose_t *p);   /* 每帧声明 */
/* ce_hooks_t 尾部：int (*on_option_pose_apply)(ce_card_t *); —— 只有被选举者会被调 */
```

⚠ **落地前要核的两处**：① 偏移字段的**单位与类型**（`+0x64/+0x68` / `+0x6c/+0x70` 是否 1/128 定点）；
② 子机槽 `+0xb0` 与 `+0xb4` 的归属（一手研究留了一条 🟡：native repopulate 的 handle 在 `+0xb4`、
`allocate_option` 读/清的是 `+0xb0`）—— 本层**只碰已验证的偏移字段**，不碰这两格。

### 3.4 弹幕（妖侧的弹）

**★ 定案（2026-09-12 用户拍板）：形态一档固定、数值随 P 变。**

- ⚠ **忠实度标注（一手，2026-09-12）**：原作 TH08 里**妖侧（和人侧一样）的「形态」与「每发数值」都随 P 变**，
  人 / 妖是**两张独立的表**但**共用同一组 P 阈值 `8 / 24 / 48 / 80 / 128 / 999`**。
  ⇒ **「形态一档固定」是我们的主动简化，不是复刻 —— 按 [`METHOD.md`](../../../METHOD.md) 标 `❓ 自定`。**
  （「数值随 P 变」这半条 ✅ **与原作一致**。）
- ★★ **反过来有一条极硬的忠实点**：原作**选哪张表用的就是「低速位」** ——
  `th08:0x450f6f movzx ecx,BYTE PTR [eax+0x3]` / `th08:0x450f75 jne`：
  **非低速取人表 `th08:0xe2a74`、低速取妖表 `th08:0xe2a78`**，而那一位由 `Player::move` 的低速状态机写
  （`th08:0x44b1e0 mov BYTE PTR [edx+0x3],0x1`）。
  ⇒ **「低速 = 妖侧弹幕」是原作自己的机制，我们的 §3.1 + §3.4 组合是忠实复刻**（而 `is_youkai` 在 `zPlayer+0x5`，
  比低速位**晚 7 帧**，不是选表依据）。
- **形态**：妖侧弹幕做成**一档固定形态**（用户明确「形态我可以接受不一致」）。
  ⇒ 只需要**一行 shooterset**（§3.4.1 的 `0x16`）—— 这正好绕开「槽位只剩一格」的硬约束。
  💡 若将来要逼近原作的「形态随 P 变」：需要 5 行（`8/24/48/80/128` 五档）⇒ **槽位不够**；
  唯一的替代是**自建弹幕实体**（零槽位，但要伤害原语、且丢掉原生弹的计分/擦弹语义）—— 不建议现在做。
- **数值**：**可以在运行期改**，不需要多行。两条手段：
  | 手段 | 做法 | 适用 |
  | --- | --- | --- |
  | **① 逐弹改（推荐）** | `on_bullet_created`（卡虚表 **`+0x28`**，先例 = 古锭刀 76 `native/cards/guding.c:59`）里判断「这颗弹是不是我们的妖侧弹」，是则就地改 **`bullet+0x9c`（伤害）** 等字段 | 可以「**只让妖侧弹**随 P 变强」|
  | ② 全局倍率 | `ce_set_bullet_damage_permille`（千分比，与其它卡**连乘**，层内就地乘 `bullet+0x9c`，AUDIT §AA）| ❌ **不适合**：它作用于**所有自机弹**，会连带改人侧与别的卡 |
- **怎么认出「我们的弹」**：`bullet+0xac` 存的是打包 id `(set<<8)|row`（`0x45ec69` 打包、`0x45ee10` 回读）
  ⇒ **判 `set == 妖侧组索引`** 即可精确锁定（见 §3.4.1）。
- 卡的 shooterset 也可以走 `ce_tick_shooters_for_card(o, short, long, CE_SHT_SET_*)`，**索引由卡每帧现传**
  ⇒ 「低速切另一套 = 换一个常量」；但它读的是**同一张 `sht_file+0xe0+idx*4` 表** ⇒ **同样要槽位**。
- ⚠ **原生主炮不会被替换**（`0x45ea00` 独立派发，卡的 shooterset 是**额外**的）
  ⇒ 要「妖侧只打妖侧的弹」**必须**用 §3.1 的闸压掉原生弹。

#### 3.4.1 妖侧弹幕的载体：用最后那一格槽 `0x16`（⚠ 槽位已满）

sht 的 40 格**全部有主**（实测）：`0x00–0x16` 原生（其中 `0x0a/0x0b/0x0e–0x15` + 一个动态索引被原生代码**硬编码调用**
⇒ 回收会破坏原版装备卡）、`0x17–0x18` = 77 豌豆射手、`0x19–0x1d` = 116 季节、`0x1e–0x27` = 117 咆哮。

- ⇒ **108 只能用 `0x16` 这一格**（原生唯一无卡映射的槽；它原本 `fire_rate=0`，就是文档里写「别碰它」的那格 ——
  我们改用**合法记录**（`fire_rate ≥ 1`）覆盖它，div-by-zero 的风险随之消失）。
- **记录写法（关键）**：**全部 `opt_slot = 0`（从自机本体出膛）**。
  依据 `engine/sht/th18/02-shooter-record.md` §4：记录的 `+0x22` 是 anm 脚本号，
  **`opt_slot=0` 的弹贴图取 `pl0X.anm`**、**`opt_slot≠0` 的弹贴图取 `ability.anm`**，而且后者会让引擎在开火期间
  把 `player+0x10` 换成 `ability.anm`、之后再还原 —— **那正是 117 修了七次（AUDIT §AL37）的 anm 上下文串位坑**。
  ⇒ 108 走 `opt_slot=0` + 贴图脚本追加进**四个 `pl0X.anm`**（每机体一套），**从机制上躲开那类 bug**，
  也**不跟 117 抢 `ability.anm` 的脚本号空间**。
- ⚠ 由此的取舍：`opt_slot=0` ⇒ 记录**不会**用子机坐标 ⇒ **妖侧子机不打自己的弹**（子机只做视觉/位置，
  由卡侧 `ce_option_alloc` 管，贴图走 `ability.anm` —— 那是它的正规路径）。这是本设计的**有意简化**。

### 3.5 使魔（= 发射口实体化的真敌人）

- **载体**：`EnemyManager__allocate_new_enemy` `0x42d7d0` + 名字传 **`NoEnemyDebug`**
  ⇒ 惰性空壳：`wait(1000)` 死循环、**永不返回**、不移动、不开火、不设 hurtbox / hitbox、不掉落、不自删。
- **1:1 映射**：使魔数量 = 该敌当前 `props[i].type(+0x00) != 0` 的发射口槽数（实测以 1 为主、boss 最多 4）。
  - ⚠ **`offset_final(+0x08)` 不能当「已配置」标记**（两次 `etOn` 之间是过期快照）；算距离用
    `offsets[i]`（`enemy+0x4e58+i*0xc`）或 `origins[i]`（`enemy+0x4f18+i*0xc`）。
- **位置**：卡侧每帧钉 `enemy+0x1270` / `+0x1274`（真敌人路线；anm 基址 `enemy+0x122c`）。
- **可打**：✅ **惰性真敌人天生可打**（⚠ 2026-09-12 订正，一手）—— `allocate_new_enemy` `0x42d7d0` → `0x42d7ed call 0x42e100`，
  后者在 `0x42e261`–`0x42e288` 把 `enemy+0x133c/+0x1340/+0x1344/+0x1348` 各写 **`0x41c00000` = 24.0f**
  ⇒ **默认 hurtbox = 24.0 > 0**，而伤害闸门读的正是该字段（`0x42f10a` → `0x42f11d comiss 0`）。
  ⇒ C 侧写 `enemy+0x133c` 从「开关」降级为「**调大小**」（想要多大自己改）。🟡 仍待实跑确认一次。
- **被打死 → 关掉那个槽**：hook **`0x434019`**（`etOn` 里 `push eax` 前，`esi = enemy + i*0x488` ⇒ `i` 可反推），
  被禁则跳到 opcode 收尾 `0x43402d`。
- **撤销 / 重建**：每帧**状态差分**（发射口活跃且无使魔 → 建；不活跃且有使魔 → 撤）
  ⇒ ECL 下一波 `etNew(i)`+`etOn(i)` 会自然重开，**不需要别的断点**。
- ⚠ **硬约束**：`life` = spawn 参数 `+0x14` **必须 < 1000**，否则 `flags_lo` 位 30 被置 ⇒ 进锁定黑名单 ⇒ 诱导打不到它。
- ⚠ **代价**：真敌人会被敌人 tick / 碰撞 / 掉落 / `enemy_count_real` 一并接管（`flags_lo & 0x31` 不设可减副作用）。

#### 3.5.1 ⏳ 勘误（2026-09-12 实装期，主会话）：`0x434019` **装不了断点**

`0x434019` 是**单条 1 字节指令** `50 push eax`（紧接 `43401a e8 f1 37 ff ff call 0x427810` 是 **rel32 相对调用**）：

```
434013: 8d 86 98 05 00 00   lea  eax,[esi+0x598]     ; bullet_props 基址（esi = 敌人）
434019: 50                  push eax                  ; ← spec 原定的 hook 点，1 字节
43401a: e8 f1 37 ff ff      call 0x427810             ; ★ 相对寻址
43401f: 8b 0d bc f2 4c 00   mov  ecx,ds:0x4cf2bc
434025: 0f 57 c9            xorps xmm1,xmm1
434028: e8 73 8c ff ff      call 0x42cca0
43402d: e9 e5 23 00 00      jmp  0x436417             ; opcode 收尾（原定「被禁则跳到这」）
```

- thcrap 的断点要把窗口内字节**原样搬进 cave**（本仓所有站点都因此要求「无相对寻址」，见 `native/sites.py` 每条
  site 的注释）⇒ 窗口若含 `43401a` 的 `call rel32`，搬进 cave 后目标地址就错；而 1 字节的窗口又放不下跳转。
- **可用的替代窗口**：`0x434013`（`lea eax,[esi+0x598]`，6 字节、无相对寻址）—— handler 能拿到 `esi`（敌人）与
  `ecx`（弹管理器 `0x4cf2bc`），但**拿不到槽号 `i`**（`lea` 的 disp 是常量 0x598，槽号在更早的循环里）。
- **当前处置**：108 走「每帧状态差分」（§3.5 后半段）已经能覆盖建/撤两侧；断点能多给的只有
  「使魔刚死的那一帧立刻关掉发射口」。缺它时的近似 = **不重建 + 转嫁归零**（发射口本身还会打到 ECL 下一波复位）。
  ⇒ 标 ⏳ 低优先级，需要一轮单独研究（先钉死该 opcode handler 的循环结构与 `i` 的存放位置）再决定加不加。

#### 3.5.2 ❓ 勘误（2026-09-12 实装期，主会话）：`enemy+0x1490/0x149c` 的语义**未证实**

`REVIEW` §6.5.4 推的「使魔换皮肤写 `enemy+0x1490`（`selected_anm_index`）/ `enemy+0x149c`（`anm_main`）」这条，
实装期被独立复核**降级为 ❓**：

- 全 `local/_scratch/th18_full.asm` 里 **`0x1490` / `0x149c` 一条引用都没有**（既没有读也没有写）。
- `0x149c` 恰好与引擎文档记的 **ECL 局部变量 `I1`** 撞址（th16 口径 `+0x1498..+0x14a4 = I0..I3`）⇒ 很可能是巧合/误推。
- ⇒ 108 侧这两个常量的值保持占位 `-1`（= **不写**），因此**当前是死代码**（条件恒假，不生效也不出错）。
- 要坐实需要的一条一手证据：**某处读它的指令**（`movzx`/`movss` 之类），或**某个写它的 spawn 参数**。
  在那之前不许把它当成「复刻」写进文档。

### 3.7 伤害转交（1/2）—— ★ 已定路线（一手研究，2026-09-12）

**结论：不要走 `on_shot_damage`，改用「使魔 HP 逐帧差分 → 每帧一条新伤害源打在 boss 坐标」。**

| 项 | 内容 |
| --- | --- |
| ❌ 为什么不能用 `on_shot_damage` | SDK 的 handler 第一行就有 `CE_PLAYER_FOCUSED()` 门（`native/sdk.c:879`），而 **108 妖机体 = 低速 = 聚焦** ⇒ 卡生效期间**这个回调一次都不来**；且它给的 `dmg` 是「钳后、未乘倍率」的值，**≠ 使魔真正掉的血** |
| ✅ 触发器 | **使魔自己的 `life.current`（`enemy+0x6220`，= `zEnemyData+0x4ff4`）逐帧差分**：本帧掉的血 × 1/2 = 要转嫁的量 |
| ✅ 落点 | **每帧新建一条** `ce_damage_rect(center, 0.0f, 2, dmg, w, h)` 打在 **boss 坐标**（`ce_damage_rect` = `0x45dfa0`，在 `player+0x20574` 的 1024 槽 × `0x9c` 伤害源池建源；寿命按帧 −1.0，`0x45c402` 循环） |
| ✅ 上限 | 同帧 `ce_raise_damage_cap(基值 + 转嫁值)` —— 否则会被每帧每敌上限吃掉 |
| ✅ 时机 | `on_tick_2`（AbilityManager tick 优先级 `0x16` **早于**敌人结算 `0x1b`）|
| ✅ 成本 | **不需要新断点、不需要新 SDK 面**；与自机弹**同一条伤害管线**（`ce_damage_rect` 和 `PlayerBullet::create` 都调 `0x45dfa0`）|
| 先例可照抄 | 青眼白龙 `native/cards/blue_eyes.c:106`、炎魔 `firelord.c:208`（注释直接写「每帧一个**新**源」）、真银 `truesilver.c:60`、破损核心 `broken_core.c:84`；原生原型 `CardRemilia__on_tick_2` `0x40f478` |

**⚠ 必须遵守的三条**（都来自一手研究）：

1. **一源一敌一辈子只结算一次**（tag 守卫 `0x45f45a` 存 `enemy_id`）⇒ **必须每帧新建源**，不能复用。
2. **别直接写 `enemy+0x6220`**（那会跳过 12 件事：每帧上限 / 计分 / ECL 伤害回调 / 符卡 ×7 记账 / **死亡判定本身** ——
   自己调 `0x430240` 还会**打乱死亡事件的 retaddr 分类**）。
3. **`ce_damage_rect` 的返回值不能当成功判据**（池满时 `0x45dfea` 会返回**过期下标**）。
   ⚠ 另外：伤害源**不区分 boss / 部件 / 杂鱼**，范围内全打 ⇒ 打在 boss 坐标时要确认范围只覆盖本体。

**❓ 标「自定」**：TH18 的伤害源管线常量 `0x98967f` 在 th18 出现 5 次、在 **th08 出现 0 次** ⇒
**原作没有这条管线，原作使魔也不是 `zEnemy`、打不到也没有转嫁** ⇒ **「1/2」是我们的设计，不是复刻**（🟡 负证据）。

### 3.9 ⚠ 使魔「能不能被打」的两个前提（一手，2026-09-12 订正）

伤害源要落到使魔身上，必须同时满足（`0x42f101` / `0x42f10a` / `0x42f2b9` / `0x42f2c2`）：

1. **`flags_lo & 0x21 == 0`**（bit0 / bit5 都必须是 0）—— 否则**打不到**；
2. **hurtbox > 0**（`enemy+0x133c`，由卡侧写）+ `invuln_timer ≤ 0` + `flags_lo` bit4 = 0。

⇒ **`flags_lo & 0x31` 绝不能设**（`0x31` 含 bit0/bit5 ⇒ 设了使魔当场**伤害免疫**）。
这**加强了**用户「不设」的决定，但**推翻它的理由**：一手复核证明
**置位 = 被排除在「真敌人」之外**（计数函数 `0x42d472 cmovne`：置位 ⇒ 不计数；`0x43c12a` 同向），
所以 **「不设」= 使魔会被算进 `enemy_count_real` / boss 门控**，而不是「不被看见」。

**★ 替代杠杆（🟡 待验，建议实装时试）**：`enemy+0x6320 > 0` 也被两处判定当作「排除」条件，
且**不碰 bit0/bit5** ⇒ 若能把使魔的 `+0x6320` 设成正值，就能「既排除在真敌人之外、又保持可被打」。
字段语义未定（疑似某种「不计数 / 特殊」标记），**实装前先一手确认它是什么、谁写它**。

#### 11.3.1 前提证实（一手反汇编 + 引擎文档）

`ce_anm_set_sprite`（`native/sdk.h:226` 包 `0x477b00`，thiscall(anm; vm, idx) ret 8）里 `anm` 参数的语义 = **「去哪张 sprite 表查」**：

| 环节 | 一手证据 | 说明 |
| --- | --- | --- |
| 查表用**传入的** anm | `477b27 mov eax,[esi+0x11c]`（esi = 传入 anm）、`477b2d movss xmm0,[eax+ecx*4+0x24]`，`ecx = idx*17` | 每项 `0x44` 字节；`477b24 mov [edx+0x24],eax` 顺手写 sprite id |
| 同时把 UV/尺寸**缓存进 VM** | `477b34`–`477d53`：写 `vm+0x3ac/0x3b0/0x3b4/0x3b8/0x3c0/0x3c4/0x3c8`、`+0x74`、`+0x78`、`+0x3d4`、`+0x454`、`+0x468` | 2D 四边形就吃这些：`47e964 mulss xmm0,[eax+0x74]`、`47e994 movss xmm0,[eax+0x78]` |
| 画的时候贴图取 **VM 自己那份 anm** | 贴图绑定函数 `0x4810d0`（arg1 = VM；`AnmManager__draw_vm` `0x481210` 在 `0x481674` 调它）→ `481117`/`481130`/`481136`/`481171` | `vm+0x20` = VM 所属 anm 页（同向：`engine/anm/th18/03-ascii-text.md` §1「页（`vm+0x20`）」）；贴图由**那张表里的条目**决定 ⇒ 号必须在本页表内 |
| **没有越界检查** | `0x477b00` 与 `0x481136` 都不校验 `idx` 与 `anm+0x118` 的关系 | 拿错 anm 的号 ⇒ 读邻接内存当贴图句柄，**静默错图 / 可能崩** |

贴图那条链，逐条写清（都在 `0x4810d0` 里）：`481117 mov eax,[esi+0x20]`（页）→
`481129 [ANM_MGR + eax*4 + 0x312072c]`（`preloaded[页]`）→ `481130 mov eax,[edx+0x11c]`（**该页自己的** sprite 表）→
`481136 mov ecx,[eax + idx*0x44 + 0x8]`（= `(anm 槽 << 8) | 贴图 entry`）→ `481165 [edx+0x124]` → `481171 call [esi+0x104]`（设备 `SetTexture`）。

**⇒ 「写 `vm+0x24` 要求那张 sprite 在自机 VM 自己所属的 anm（TH18 `pl0X.anm`）里能解析」= 前提成立（✅ 证实）。**
准确说法：sprite 号是在**画的那一刻**用 `vm+0x20` 选出的页 + `vm+0x24` 选出的下标、去**那张页自己的** sprite 表里取的；
`ce_anm_set_sprite` 的 `anm` 参数只决定「UV/尺寸从哪张表算」。往本体 VM 传 `ability.anm` ⇒ **UV 来自 `ability.anm`、贴图仍取 `pl0X.anm`** ⇒ 图错（且越界时是静默的，不会报错）。

**★ 由此的两条订正（对现有代码有直接影响；本节只记录，没动 `native/`）**：

1. **只写 `vm+0x24` 不够**：UV/尺寸缓存是 `0x477b00` 填的。`native/cards/youkai.c:543` 现在直接
   `*(int32_t *)(player + CE_PLAYER_VM + CE_ANM_VM_SPRITE_ID) = sprite;` ⇒ **就算资产接进 `pl0X.anm`，这条也会画出上一张 sprite 的 UV 矩形**。

### 12.1 TH08（`local/th08.v1.00d/`）：妖侧数量由一张固定的 12×4 表决定，**与 P 无关**

**发现（一手）**：自机子机是 `zPlayerOption` 数组，**槽上限 4**，`base = zPlayer+0x40c`、`stride 0x2f4`：

```
th08:0x449d71  push 0x449e50          ; PlayerOption::constructor
th08:0x449d76  push 0x4               ; ★ 个数 = 4（槽上限，写死的）
th08:0x449d78  push 0x2f4             ; ★ 步长
th08:0x449d7d  mov  ecx,[ebp-0x4]     ; player
th08:0x449d80  add  ecx,0x40c         ; ★ 数组基址
th08:0x449d87  call 0x406850          ; 按 ctor 循环建 4 格
```

**哪几格「活」（= 数量）**由 `Player::move` `th08:0x44aec0` 在**按下低速的那一帧**设置：

```
th08:0x44b040  movzx ecx,BYTE [eax+0x3]       ; is_focused：已经是 1 ⇒ 跳过（只加延迟计数）
th08:0x44b047  je    0x44b1be
th08:0x44b04d  movzx edx,BYTE ds:0x164d0b1    ; shottype
th08:0x44b054  cmp   edx,0x3
th08:0x44b057  jg    0x44b11f                 ; ★ 只有组队型 0..3 走这条（单人型走注册期那条）
th08:0x44b060  add   eax,0x40c                ; 数组基址
th08:0x44b086  cmp   DWORD [ebp-0x18],0x4     ; i < 4
th08:0x44b09a  rep stosd                      ; 整格清零（0xbd dword = 0x2f4 字节）
th08:0x44b0ac  mov   eax,[eax+edx*4+0x4c7d40] ; ★ 取 表[shottype][i]
th08:0x44b0b3  mov   [ecx+0x2ec],eax          ; option+0x2ec = 这个值
th08:0x44b0d9  cmp   DWORD [edx+0x2ec],0      ; ★ 非 0 才……
th08:0x44b0e5  mov   DWORD [eax+0x2c8],0x1    ;   state 1 = 出场
th08:0x44b110  mov   DWORD [eax+0x2c8],0x0    ; 0 ⇒ 这一格不激活
th08:0x44b105  mov   [ecx+0x2d0],edx          ; option+0x2d0 = 格号 i（逐格行为 jumptable 拿它）
```

- 表值在别处被当**函数指针**用：`th08:0x44bd79 call DWORD [esi+eax*1+0x6f8]`（`esi` = player、`eax` = `i*0x2f4`，
  `0x6f8` = `0x40c + 0x2ec`）—— 4 格 tick 循环（`th08:0x44bd3b cmp [ebp-0x2c],0x4`）**只调非 0 的格**。

**表 `th08:0x4c7d40[shottype][4]`（直读 `th08.exe` 的 `.data`；`th08:0x4c7e10` 是**同形**第二张，逐行非 0 分布
完全相同、存到 `option+0x2f0`，语义未定 🟡）**：

| 行 `shottype` | 队伍（人 / 妖）| **妖侧子机数** | `th08:0x4c7d40` 该行（非 0 项 = 活的格）| `.sht` 子机索引（独立印证）|
| ---: | --- | ---: | --- | --- |
| 0 | 霊夢 / **八雲紫** | **1** | `{0x44e3a0, 0, 0, 0}` | `ply00as` = `{0, 1}` |
| 1 | 魔理沙 / **アリス** | **1** | `{0x44ea40, 0, 0, 0}` | `ply01as` = `{0, 1}` |
| 2 | 咲夜 / **レミリア** | **4** | `{0x44eb70, 0x44eb70, 0x44eb70, 0x44eb70}` | `ply02as` = `{0,1,2,3,4}` |
| 3 | 妖夢 / 幽々子 | **2** | `{0x44f930, 0x44f930, 0, 0}` | `ply03as` = `{0,1,2}` |
| 人侧 | 只有 `shottype == 3` 的人侧留 1 格 | 1 | 另一张人类表 `th08:0x4c7e00` = `{0,0,0x44f2d0,0}` | `ply03a` = `{0, 3}` |

- **人侧 `.sht`（`ply00a` / `ply01a` / `ply02a`）只用子机索引 0（= 本体）⇒ 人侧 0 个子机** ✅（与「人侧只有 st3 留 1 格」互证）。
- **表只有两个引用点**：`th08:0x44b0ac`（进低速那一帧）与 `th08:0x44db9d`（`Player::on_registration`
  `th08:0x44db45 cmp shottype,3; jle 0x44dc10` ⇒ **单人型 4..11 在注册期**用它，行值 = st5 紫 1 / st7 アリス 1 /
  st9 レミリア 4 / st10 1（只第 3 格）/ st11 幽々子 2）⇒ **再没有第三处能改数量**。
- 退低速那一帧（`th08:0x44b1f8` 起）：`shottype < 3` 把 4 格全置 state 3（散场）；`shottype == 3` 只关前 2 格，
  第 3 格（index 2）改用**人类表**重建 —— `th08:0x44b2ed [ecx*4+0x4c7e00]` / `th08:0x44b300 [ecx*4+0x4c7ed0]`
  （两张表的 index 2 都非 0，正是那一格）。🟡 「index 2 那格是妖夢的半霊」是推断，未验。
- 子机索引 → 记录：`th08:0x44fbad movsx ecx,[rec+0x20]` → `th08:0x44fbb1 sub ecx,1` →
  `th08:0x44fbb4 imul ecx,ecx,0x2f4` → `th08:0x44fbbd lea eax,[player+ecx+0x6b0]`（`0x6b0 = 0x40c + 0x2a4`）
  ⇒ **`N = 0` 是本体、`N ≥ 1` 是第 `N-1` 格子机** —— 这就是上面「`.sht` 索引集合」能当数量的独立印证的依据。

**「数量随 P 变」的反证（两条，都一手）**：

1. `GameManager::get_current_power` `th08:0x422480` 全 exe 共 **22 个 `call`**，**没有一个落在子机链**：
   不在 `Player::move` 的子机段、不在激活/撤销两处、不在 4 格 tick 循环、不在 `0x44e3a0`–`0x44fb70` 的
   任何子机处理函数里。
2. 8 张 `ply*.sht` 的**子机索引集合逐档完全不变**（上表右列是整文件并集）；变的只是「几路弹」与
   「**哪几个子机开火**」：`ply02as` 在 thr 8/24 只从子机 2、3 出膛（`{0,2,3}`），thr ≥ 48 起才是 `{0..4}`；
   `ply00as` 全程 `{0,1}`（路数 2→2→3→4→5→7）。

⇒ **结论（✅ 高 / TH08 v1.00d）**：妖侧子机数量 = **每队一个常数**，与火力档无关
（pl00 紫 **1** / pl01 アリス **1** / pl02 レミリア **4**；`shottype 3` 妖侧 2、人侧 1）。

⚠ **同名不同物（必须分清）**：「使い魔」在 TH08 里是**两套东西**：

| 项 | 自机子机（本卡要的）| 敌人放出来的使い魔 |
| --- | --- | --- |
| 载体 | `zPlayerOption`：`zPlayer+0x40c` × 4、`stride 0x2f4`（`th08:0x449d71`）| `zEnemy`：`Enemy::enemy_create_familiar` `th08:0x41f280` |
| 触发 | 进低速那一帧按 `th08:0x4c7d40` 激活 | ECL opcode（派发表 `th08:0x41ecbe`：**90 → `th08:0x41b10b`**、**91 → `th08:0x41b2bb`**）|
| 计数 | 表里非 0 项数（1/1/4/2）| `enemy+0x3380 += 1`（`th08:0x41b0e4`–`0x41b0ea`）|
| 关系 | 可当发弹点（`rec[+0x20]`）| 与自机子机**无共享字段** |

- 反例一条：`AsciiManager::sub_403460_makes_familiar_popup` `th08:0x403460` 的调用点在**敌人链**
  （`th08:0x42af78` / `0x42b122` / `0x42b296`）⇒ 别拿它当「自机子机也叫使い魔」的证据（🟡 ExpHP 命名 + 仓内
  [`engine/item/th08/01`](../../../engine/item/th08/01-time-orbs.md) 的语境）。

### 12.2 TH16（`local/th16.v1.00a/`）：射命丸文 = **随火力变**，`floor(P/100)`，0..4

**算式（一手，`PlayerInner__repopulate_options` `th16:0x4440e0`）**：

```
th16:0x444100  mov  eax,ds:0x4a57e4        ; CURRENT_POWER（存 ×100）
th16:0x444106  idiv DWORD ds:0x4a57ec      ; ★ / POWER_PER_LEVEL（= 100）→ 档
th16:0x44411a  mov  [edi+0x16088],esi      ; 档存进玩家对象
th16:0x444484  inc  edx                    ; i++
th16:0x4444aa  cmp  edx,ecx                ; ★ i 与 档 比：th16:0x4444ac jge 出口、
th16:0x4444bc  jmp  0x444270               ;   否则回循环体建下一格（记录 stride 0xe4）
th16:0x4444c1  cmp  edx,0x4 ; jae          ; 建完（档 ≥ 4 就不清）
th16:0x4444ca  mov  edi,0x4 / sub edi,edx  ; ★ 把剩下的 4 − 档 格清空
th16:0x4440e9  mov  eax,ds:0x4a57a8        ; 阵型索引用行号 = [0x4a57a8] + CHARACTER
th16:0x4440f7  add  eax,0x4a5e50           ; 表 th16:0x4a5e4c（用 +1 项开始）
```

| 火力 `CURRENT_POWER` | 档 `floor(P/100)` | **子机数** |
| --- | ---: | ---: |
| < 100 | 0 | 0 |
| 100–199 | 1 | 1 |
| 200–299 | 2 | 2 |
| 300–399 | 3 | 3 |
| 400（上限，`th16:0x4a57e8`）| 4 | 4 |

- **四角色同表**（直读 `th16:0x4a5e4c`：四行**都是** `[16, 0, 1, 3, 6, 10, 11, 13]`，取址用 +1 项 ⇒ 有效序列
  `{0,1,3,6,10,11,13}` = 三角数）⇒ **文（`pl03`）与其它三人逐档相同**；顺带这也让它成为
  **robustness**：即使把 `pl03` 认错人，本表也不变（`pl03` = 文的身份判据见 §11.1，本节未推翻）。
- 三角序列同时说明「**每档一套独立阵型**」+「档 L 用 L 个子机」，两件事自洽（子机 i 的阵型下标 = `T(L) + i`）。
- `th16:0x444126 cmp ecx,[0x4a57e8]; jl 0x4441f1` 是一条「**非满火力**」分支（先按 4 格整体清一遍）。
  🟡 它为什么要整清本轮没定死；但**两个分支的数量都是这一档**（同一个 `esi`）。
- ⚠ 别和**季节子机**混：TH16 还有第二组（数量 = 季节槽档 0..6、最多 8，见
  [`engine/player/th16/04`](../../../engine/player/th16/04-options-subshot-system.md) §3b）。108 要的是**本体子机**那组。

  而 108 声明的子机是**另外**申请的（`Player__allocate_option` 的 12 槽公共池，
  [`engine/sht/th18/03`](../../../engine/sht/th18/03-func-tables-timers-and-dead-fields.md) §5）⇒
  **「108 的数量」≠「屏幕上子机总数」**；要「妖侧只有 N 个」得连原生那几个一起管（🟡 需实跑确认聚焦期原生子机是否也画）。

### 12.4 「固定 vs 随火力变」的结论 + 给 C 侧的建议形状

**结论（一手）**：**原作两种都有，取决于作品** —— TH08 妖侧是**固定数**（每队一个，与 P 无关，§12.1）；
TH16 / TH18 是**随火力档变**（`floor(P/100)`，0..4，两作算式逐字相同，§12.2 / §12.3）。
而按用户给的机体置换，**四支里三支落在 TH08、只有早苗那一支落在 TH16**（§11.1）
⇒ 一个「统一形状」必然要么给三支套上五档曲线、要么把早苗那一支压成常数。

**建议形状（本节不改代码，只给形状）**：把常数换成 **`[机体][档]` 的 4×5 小表 + 一个纯函数** ——
一张表同时能表达「固定」（该行 5 个数相同）与「随火力变」（该行递增），换口径只改表不改调用点：

```c
/* youkai_core.h —— 表；youkai_core.c —— 纯函数（无引擎依赖、可直接单测） */
static const unsigned char YK_OPTION_BY_CHAR[4][5] = {
    /* 霊夢   → th08 pl00 妖侧 = 八雲紫   */ { 1, 1, 1, 1, 1 },
    /* 魔理沙 → th08 pl01 妖侧 = アリス   */ { 1, 1, 1, 1, 1 },
    /* 咲夜   → th08 pl02 妖侧 = レミリア */ { 4, 4, 4, 4, 4 },
    /* 早苗   → th16 pl03        = 射命丸文 */ { 0, 1, 2, 3, 4 },
};
int yk_option_count(int focused, int character, int power_level);
/* = focused ? YK_OPTION_BY_CHAR[clamp(character,0,3)][clamp(power_level,0,4)] : 0 */
```

- **签名必须收 `power_level`**：现在的 `yk_option_count(int focused)`（`youkai_core.c:22`）没有它 ⇒
  抄 TH16/TH18 口径时**表达不出来**；要么加参数，要么内部读一个 `yk_current_power_level()`。
- **档位从哪读**：`CE_CURRENT_POWER() / CE_POWER_PER_LEVEL()`（`native/engine.h:183`–`184`；与
  `th18:0x45d604` / `0x45d60a` 同款算式）。想和引擎「同一个档」可直接读它缓存的 `player+0x476f8`
  （一手：`th18:0x45d84d`，`esi = [0x4cf410]` = player；🟡 谁写它本轮没追）。
- **落点**：表 + 纯函数放 `native/cards/youkai_core.h` / `youkai_core.c`（沿现在的分工：纯逻辑、可单测）；
  唯一调用点是 `native/cards/youkai.c:558`（`yk_option_refresh` 里的 `int count = yk_option_count(focused);`）——
  那里已有 `focused`，只需再传角色号与档位。
- **时机天然对得上、不需要新钩子**：声明是「每帧比对 + 粘性重发」（`youkai.c` 的 `s->declared != count`），
  而火力档变化时引擎会走 `CE_FN_PLAYER_REPOPULATE_OPTIONS` `0x45d5e0` 的尾部广播 ⇒ 档一变、下一帧数量就变、
  自动重声明 + 重申请（与 §3.3 的「门式而非推式」同一套）。
- ⚠ **一个形状缺口（❓ 留给下一轮）**：`ce_option_pose_t`（`sdk_core.h:141`–`146`）**只有一套** `fx/fy/ux/uy`，
  而 `youkai.c` 的落笔循环把**同一对**偏移写给**每一格** ⇒ **`count ≥ 2` 时几格子机会叠在同一点**。
  原生 TH18 是逐格取 `sht[0x40 + (TRI[档−1]+i)*8]` 的**不同**位置（`th18:0x45d902`）。
  要「レミリア 4 只」或「文 2–4 只」不叠，就得：① 声明层支持**逐格偏移**（数组或回调）；② 或干脆
  **不写偏移**、留引擎的原生阵型；③ 或 count 恒取 1、靠原生双偏移摆左右 —— 三选一是设计选择（见 §12.6 ③）。
