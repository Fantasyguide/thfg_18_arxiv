## 1. ✅ 共用件 `mof_core_pv()` 的「两卡同装」那一支原来重复计入基础（**已由主会话修掉**）

> **订正（主会话，2026-09-12 收口）**：本节初稿写的「前两个条件与分支体错配 / 两支写反了」是**误判** ——
> 三态条件与分支体其实是对上的（只装 110 ⇒ `agg` 无乘数、只装 111 ⇒ `agg × 乘数`）。
> 表中「只装 111」那两行的期望值本身算错了：`(0, 1, 50000, 0, 0)` 里乘数 = `擦弹 0 + 信号 0 = 0`
> ⇒ 契约值就是 **0**，不是 50000；`(0, 1, 50000, 1000, 0)` ⇒ `50000 × 1.0 = 50000`（实现给的正是这个）。
>
> **真正的缺陷只在 `else`（两卡同装）那一支**：它写成 `(基础均值 + aggregate) × 乘数`，而 `aggregate`
> 是两张卡的**完整**声明之和（各已含自己的基础）⇒ **基础被记了三遍**。
> 一手：`mof_core_pv(1,1,100000,1000,0)` 给 `150000`，契约（`(基础均值 + Δ110 + Δ111) × 乘数`）是 `50000`。
> 后果：**两卡同装时 110 落笔与 111 落笔会给出不同的蓝点分**（111 侧 `signal_core_pv_111()` 一直按契约实现）。
>
> **已修**：`cards/mof_core.c` 的该支改成「先从 `aggregate` 里减掉两份基础、再加基础均值」，
> 与 `signal_core_pv_111()` 逐字等价。🟡 遗留：111 的基础随难度变（EASY 25000 … LUNATIC 200000），
> 而 `mof_core_pv()` 拿不到难度 ⇒ 按 NORMAL 反推，EASY/LUNATIC 下会差 `(基础_111_真实 − 50000)`；
> 将来要精确就给该函数加 `difficulty` 参数（调用方 `mof.c` 已有 `0x4ccd00`）。
>
> **回归**：`tests/test_signal_core.c` §12.6 现在直接断言
> 「两卡同装时 `signal_core_pv_111_scaled()` == `mof_core_pv()`」（含擦弹倍率与信号两路），
> 谁改坏一边都会红；`tests/test_mof_core.c` 的 both 分支四条期望值同步改到契约口径。

## 2. ✅ `faith_slot_add_cancel()` 的 `out_111_add` 量纲与头注释不符（**注释已由主会话订正**）

`faith_core.h` 写「返回值写进 `*out_110_add` / `*out_111_add`（**原始单位**）」，但实现
（`faith_core.c`）把 `faith_slot_add()` 的返回值（**定点 ×100**）直接交出去：

```c
out_111_add 拿到 10 × FAITH_FIXED = 1000，不是 10
```

⇒ 实际口径是 **`out_*` 与槽内 `delta` 同量纲（定点 ×100）**。`signal.c` 只把它当「有没有进位」用
（`if (add111 > 0)`），所以不受影响；单测里按**实测口径**断言，并额外钉住
「返回值 = Δ 的增量」这条不变式。
**处置（2026-09-12）**：保留实现（改实现会动 110 的取值口径），**订正头注释**
（`cards/faith_core.h` 现在写明「定点 ×100，不是原始单位；要原始单位 `/ FAITH_FIXED`」）。

## 3. HUD 槽位的实作要点（一手，踩点用）

1. **`ce_hud_slot_claim()` 填出来的坐标是「认领那一刻」的** —— 同一开场批次里后来的认领会按 id 升序重排
   ⇒ 卡必须**每帧**用 `ce_hud_slot_get()` 取最新值再摆 VM（`sdk_core.h` 的注释这么要求，本卡照做）。
2. **`ce_hud_slot_get()` 的 `x640/y640`**：实装期这里是返回未初始化栈值的隐患（只有 `claim` 写那两格）
   ⇒ **2026-09-12 已由主会话修**：`claim` 与 `get` 都填 `x640/y640`（= 表面 px × `CE_HUD_640_SCALE`）。
   卡侧现在两种写法都安全；自己乘 `CE_HUD_SURFACE_TO_640` 也仍然对。
3. **两套坐标的入口泾渭分明**：`ce_anm_set_pos`（UI 列表 VM）吃**表面 px**；
   `ce_hud_vm_text_set` / `ce_hud_number_*` 吃 **640×480 字面量空间** ⇒ 各取所需，
   **别自己乘 0.5 `/` 别把表面值喂给文字接口**。
4. `drawRect` 的锚点在**图心**（season.c 的一手教训）⇒「从格底往上长的填充」要把中心上移
   `(格高 − 填充高)/2`；`fill == 0` 时给 0 尺寸（不画）。
5. 贴图 VM 的 `tag` 只是日志前缀（`sdk.c` 只在 spawn 失败时用）⇒ 本卡用 `"signal111"`，
   与 110 的 `"mof"` 不混。

## 5. 实现的解释权 / 与 spec 的字面差异（都记下来，别当成「复刻」）

| 项 | spec 说法 | 本卡实现 | 依据 |
| --- | --- | --- | --- |
| 信号强度进公式的**上限** | §2.3「信号强度 **0.00–1.00**」 | `min(signal, 100)/100` ⇒ **100 点与 130 点都是 1.00**；130 只体现在 HUD 格数 | §2.1「显示上 ≥100 一律显示 1.00」 |
| 擦弹倍率进公式 | §2.3「擦弹倍率 **8.99**」 | 用共用件 `mof_core_graze_mult()`，返回值直接当**千分点**加进乘数（8990 = 8.99）| `mof_core.h` 的一手说明（1 graze = 1 千分点）|
| 满槽全收 | §2.1「像上线回收一样自动收道具」 | 每帧 `signal ≥ 100` ⇒ `ce_item_collect_all()`（共享件，107 森罗结界同一件；把活道具 `state` 置 3）| §5.6 订正：`0x445ffc` 是 `comiss` 指令、不是函数入口 |
| 信号槽的**显示** | §2.5「手机信号样式的格子（3–5 格）」+ 信仰 / 蓝点分读数 | 5 个 `drawRect` 格（脚本 104 的 1×1 模板）+ 2 行贴图 VM 数字（信号强度 `0.00` / 信仰 / **本卡**蓝点分预览）| §2.5；**❓ 自定**：没有 TH11 信号槽的原版切图，用矩形拼、不冒充复刻。⚠ 蓝点分读数只是**预览**（用本卡自己那份信仰算），落笔用的完整聚合值只在 `on_item_score` 里算 |
| 小绿点（每 100 个 +10）| §7.5 表 | 走 `faith_cancel_account()` → `faith_slot_add_cancel()`，余数 `small_rem` 跨关保留 | 共用件已实现，本卡只是第一个用户 |
| 大 / 中绿点 | §3.2.1「大 = 击破通道 / 中 = 满 P 后吃 P 点」| **挂 111 自己的 `on_pickup`**，按 `1 << FAITH_SLOT_111` 认领 | 用户定案：「一套实现 + 两个记账槽」，实体层零改动 |
| 灵击 | §2.4 / §3.2.1 | 门槛 ≥2.00 档、扣 1 档、下限 1.05，**调共用件** `mof_core_power_spend()`；库存 > 0 时交给原生 `do_bomb` | 共用件（110 已交付，111 只借）|
| 删卡清理 | `METHOD.md` 铁律二 | `on_delete` → `signal_clear()`：退声明 + 退注册 + **收共用池** + 收 6 个 UI VM + 释放 HUD 槽 | ⚠ `faith_clear_entities()` 会连 110 的绿点一起收（`mof.c` 的既有口径），已登记 |

## 6. 待实跑（**一条都没在游戏里跑过**）

1. 信号槽四段的**手感**（两帧顶满是否太快 —— 这是 SA 原版的节奏，但 TH18 的擦弹密度不同）；

3. 蓝点分的**数值落点**（`on_item_score` 断点的**第一个真用户**，review §7.8 要求按「首用」验：
   单装 111 / 两卡同装，各吃一颗金钱，核对得分正好 = PV）；
4. HUD 块的**位置 / 尺寸 / 配色**（块尺寸 96×20、格 12px、间距 16px 全是初版占位）；
5. 灵击的伤害 / 震屏参数（❓ 占位常量，见 `signal.c` 文件头的 `SIGNAL_BOMB_*`）。
