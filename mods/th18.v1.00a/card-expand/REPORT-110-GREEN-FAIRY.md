## 1.6 ★★ 候选路线 D（用户 2026-09-18 提的「**给循环 +1**」）：**我们自己多刷一只绿的**

用户原话：「**有没有可能你给循环 +1？**」⇒ 目的是「一波只多一两只纯信仰点」，而不是把现有那 24 只改成绿的。
拆成两件事回答：

**(D-a) 直接改 ECL 的循环计数（`$A = 8` → `9`）—— 能做，但多刷出来的是*原色*妖精**：
- 机制上可行：ECL 被载入内存（逐关），循环计数的立即数在字节码里 ⇒ 「卡在场时改、删卡还原」这套
  「运行期改内存 + 备份还原」我们刚在 sprite 表上做过；但要先**逐关逐波定位**那条立即数的偏移
  （dump 里有 `(+0x…)` 字节偏移 ✅ 可查），比 sprite 表脆。
- **致命点**：循环体只有**一处** `enmCreate("GirlBlueA01", …)`，所有迭代共用同一调用点 ⇒
  多出来的那只与其它 24 只**逐字节同源**（引擎里也没有任何字段能区分"我是多出来的那只"）
  ⇒ 想让它变绿只能再叠一层「按个体改色」（路线 B/C，1 格站点预算），而且选择规则只能靠
  「第 k 只 / 最后一只」这种猜法。⇒ **单靠 +1 拿不到"一只绿的"**。

**(D-b) 我们自己「多刷一只绿的」—— 推荐，且基础设施已经在跑**：
- 工具：SDK 已有 `ce_spawn_enemy(ecl_name, spawn)`（`sdk.h:980`；一手 ABI = `CE_FN_ALLOCATE_NEW_ENEMY 0x42d7d0`，
  `spawn` 字段表 = `CE_SPAWN_*`：`+0x00` pos / `+0x0c` score / `+0x10` main_drop / `+0x14` life（**必须 < 1000**）…）。
  `ecl_name` = **加载中的 `default.ecl` 的子程序名**（不是 C 名）。
- **先例三处**：108 使魔壳（`"NoEnemyDebug"`）、112 四个 UFO 令牌、116 —— 而发布链已经通了：
  `assets/ecl/*.ecl.txt`（可读 ECL 源 + 注释）→ `python3 ../assets/ecl/make_ufo_ecl.py`（`make ecl-ufo`，
  把我们的子程序**合进原生 `default.ecl`**、二进制往返回验）→ `native/release.py:33` 把它映射进 thcrap 常开的 patch-step3。
- 我们那支子程序要做的事（三行就能画对）：`anmSelect(2); anmSetMain(0, 10);` ⇒ **天生就是绿的**
  （`S=10` = `enemy.anm` 绿色变体）。★ 附带好处：`(2,10)` **已经是宿主表里的键** ⇒ 它死亡时
  自动撒大信仰点，**不需要任何新逻辑**；把 `main_drop` 填 0 就是「纯信仰点掉落」。
- 好处：**原版妖精一个都不动**（不换色、不改掉落，用户口径里的"额外"）；密度我们说了算
  （每波 1 只 / 每 N 只配 1 只）⇒ 正好落在一波 1–2 只；删卡即停（只在卡在场时刷）。
- 代价 / 待裁决：① 它的**行为**（移动 / 血量 / 是否发弹）是 `❓ 自定` —— 可照 TH18 最朴素的小妖精写；
  ② **计数影响面**：多一只敌人 ⇒ 章节击破数 / 117 的波次普查（`animal_wave_group_totals`）/ 我们的
  「非 boss 击破 +10f 连击」都会看到它，要一并裁决定；③ 位置 / 时机（触发规则）要定一条。
- 与 §1.2/§1.5 的关系：这条路**不需要** sprite 表重映射（那只天生就是绿的）⇒ 现有「外观级变绿」
  机制可以**保持关闭**（`enabled = 0`）留作另一种口味，也可以只用来补 st03 那种缺口。

## 2. 引擎侧：改精灵的三条路线

### 路线 A（**推荐**）：图像层 —— 拷贝 sprite 表项

**一手依据**（`AnmLoaded__set_sprite` `0x477b00` 逐条读出来）：

| 事实 | 地址 |
| --- | --- |
| `anm = [ENEMY_MANAGER + 0x170]`（`N=2` ⇒ `enemy.anm`；`ENEMY_MANAGER = [0x4cf2d0]`） | `0x436c49`–`0x436c4e`（`mov eax,ds:0x4cf2d0` / `mov ecx,[eax+ecx*4+0x168]`，`ecx = N = 2`） |
| sprite 表指针 = `[anm + 0x11c]`（**每文件一张，全局**） | `0x477b27 mov eax,[esi+0x11c]` |
| 表项步长 **0x44** 字节（`id*0x11` 个 dword） | `0x477b1d`–`0x477b22 shl ecx,4 / add ecx,eax` ⇒ `ecx*4 = id*0x44` |
| 表项里被 `set_sprite` 读走的字段 = `+0x24 / +0x28 / +0x2c / +0x30 / +0x34 / +0x38`（UV 矩形 + 尺寸） | `0x477b2e`–`0x477bc7`（6 条 `movss xmm,[eax+ecx*4+…]`） |
| 脚本每条 `ins_300(spriteN)` 都会重写 `vm+0x24 = spriteN` 并重取 UV ⇒ **换表项在下一次执行到 `ins_300` 时生效** | `0x477b24 mov [edx+0x24],eax`（`edx = vm`） |

**做法**（`on_load` / 每帧 `on_tick_2` 幂等）：
1. `anm = *(void**)((uint8_t*)*(void**)0x4cf2d0 + 0x170)`；为 0（关卡未加载）直接返回。
2. `tbl = *(uint8_t**)((uint8_t*)anm + 0x11c)`。
3. 对 §1.2 的每个（源基址 `sb` → 绿基址 `gb`）对：若 `memcmp(tbl+sb*0x44, tbl+gb*0x44, 12*0x44)` 不等，则
   先备份 `tbl+sb*0x44` 的 12 项（每卡一份静态副本），再 `memcpy` 覆盖。
   ⇒ 三组共 **72 项 × 0x44 = 3,168 B**，一次拷贝，之后每帧只做一次 `memcmp`（更省：只比首项 4 字节当闩锁）。
4. `on_delete` / `on_run_reset`：把备份写回（还原）。

**优点**：零新增断点（站点预算不动）、零 VM 重建、与 ECL 的行为完全无交互（不碰 `zEnemyData` 任何字段）、
**新生妖精从第一帧起就是绿的**（卡只在商店增减 ⇒ 那一刻没有在场妖精；妖精出生时第一条 `ins_300` 就在建 VM 那一刻跑）、
可精确还原、离线可单测（表是常量）。
**风险 / 边界**：
- 是**全局换图**（同一外观的所有实例一起变）——正好符合「改某些**种**妖精」，但**做不到「同一波里只变一只」**。
- 妖精脚本是「一条 `ins_300` + 等 4–5 帧」的节奏（`thanm -l` 实测 `+5:`），所以**若**将来要在「有在场妖精」时热切换，
  最坏延迟 = 一条 pose 的帧数（4–8 帧）；用户当前口径下这条不成立。
- `enemy.anm` 若被重新载入（换关 / `preload_anm` 重跑）补丁会没 ⇒ 每帧幂等重放即可（成本可忽略）。
- 未知字段（表项 `+0x00..+0x23`）**整项一起拷**，不去解释它 ⇒ 不依赖对字段语义的猜测。
- 同一批 sprite 还被别的脚本引用？**已穷举核对：没有**（P3）。

### 路线 B（若要求「脚本号也真变绿」）：断点层 —— 改 `anmSetMain` 的实参

妖精的原生写法是 `anmSelect(2)` + **`anmSetMain(0,S)`**（一手：`anmSetMain(0,0)`×58 / `(0,5)`×17 / `(0,15)`×3 / `(0,10)`×2 / `(0,184)`×14 / `(0,189)`×14，
全 ECL 穷举；`anmSetSprite(0,*)` 只有 1 处且不在本表内）。`anmSetMain` 的 handler 是 `0x431592`：

| 事实 | 地址 |
| --- | --- |
| 第 2 实参 `S` 存进栈局部 `[ebp-0x588]` | `0x4315af mov [ebp-0x588],eax` |
| **该局部同时喂给「解析器/建 VM」与「身份记录」两处** | `0x4315d1 push DWORD PTR [ebp-0x588]`（建 VM）＋ `0x431649 mov eax,[ebp-0x588]` → `0x431659 [edi+0x270]=eax`、`0x43165f [edi+0x26c]=eax`（记录） |
| 槽号 `K` 在 `[ebp-0x58c]`，只有 **K==0** 才写记录（原生 153/153 全 K=0） | `0x43163c cmp [ebp-0x58c],0` / `0x431643 jne` |
| `anmReset`（op 318）**从记录重建**：`S = [edi+0x270]`、`N = [edi+0x264]` | `0x431680`–`0x4316f0` |

⇒ 在 **`0x4315d1`（`push [ebp-0x588]` 之前）** 下断点，把 `[ebp-0x588]` 改写成绿色脚本号，
**建 VM 用的脚本**与**记录字段 `+0x26c/+0x270`** 一起变绿 ⇒ `anmReset` 跟随、死亡时读到的 `(N,S)` 就是绿色键
（宿主表判据自然命中，见 §3）。站点窗口已过机器体检（`sitecheck`：`✓ W1 6≥5 / ✓ W2 整指令 / ✓ W3 窗内无分支 / ✓ W4 零重叠`）。

**代价**：**+1 条断点声明**（站点预算现状 **24/24 已满** ⇒ 必须先 park 掉一条别的，或把它并进已有站点）；
**风险**：多了一条热路径上每敌每帧都要过的断点（`anmSetMain` 只在 ECL 设置 anm 时执行，频率低），
且改动会**改变敌人的身份记录**（别人若也用 `(N,S)` 做判据，会看到绿号 —— 目前只有我们 110 用）。

### 路线 C（兜底）：卡侧重建 VM

每帧扫敌人，发现「记录 S 仍是原色」就销毁槽 0 的 VM 并按绿脚本重建（`AnmLoaded__instantiate_vm_to_world_list_back` `0x405bf0`，
thiscall(`AnmLoaded*`; `int* out_id`, `script`, `layer`, `void** out_vm`) ret 0x10；旧 VM 用 `0x488cf0` 标删），
顺带改写记录字段。**不花站点**，但要把位置/层/`+0x4fd8/+0x4fdc` 尺寸复刻对（`layer = [zEnemyData+0x27c] + 7`、
尺寸 = `vm[0x78]*vm[0x58]` / `vm[0x74]*vm[0x54]`，一手 `0x436c55`–`0x436cca`），并且会丢 ECL 对该槽 VM 的 per-VM 设置 ⇒ **只在 A 走不通时用**。

## 3. 掉落侧：怎么「改其掉落物」

**一手前提**：死亡断点 `0x430240` 是 `FUN_00430240` 的**函数入口**，而引擎撒主掉落在同一函数体内的
`0x430469`（读表 `[edi+0x623c]`）→ `0x430493`（`ItemManager__spawn_item`）⇒ **断点里写字段，引擎就会按新值撒**
（`cards/mof.c` 的 `on_enemy_death` 已经挂在这个断点上并实跑过）。附加表 `ex_drop` 在更后面才被
`Enemy__drop_items_and_notify_cards` `0x430510` 消费（`0x43049f` 才进它）。

| 想做的 | 落笔 |
| --- | --- |
| 追加一颗大信仰点（现有行为） | 已实现：`faith_spawn(ev->x, ev->y, …)`（不动原生字段） |
| **清掉原生主掉落** | 死亡断点里 `*(int32_t *)(enemy + 0x623c) = 0` |
| **清掉附加掉落**（P/金钱的 `dropExtra`、限时奖励） | 清 `enemy+0x6240` 起 20 项 + 把限时窗口 `enemy+0x6290`（`zEnemyDrop+0xa4`）置 0（限时表在 `0x430544`–`0x430573` 才并入） |
| 「掉落物整体替换」一条更省事的写法 | 进断点时 `memset(enemy + 0x623c, 0, 0xa8)`（主掉落 + ex_drop + 限时表一次性清零），再撒我们自己的点 |

**判据（跟卡走 + 只对变绿的妖精生效）**：`110 在场` ∩ `该敌的 (N,S) ∈ 变绿表`。
- 走**路线 A** 时 `(N,S)` **保持原色号**（我们没动记录）⇒ 表要用**源键**（`(2,0)/(2,5)/(2,15)/(2,184)/(2,189)` 及其同变体脚本）；
- 走**路线 B** 时记录已变成绿色号 ⇒ 表用**绿键**（`(2,10)/(2,194)`）—— 与现有宿主表 `(2,10)` 天然重合。

**两条硬纪律**（照 `cards/mof.c` 的既有禁令）：死亡回调里**禁止析构敌人**、**禁止缓存 `ev->enemy`**；
本方案只写它自己的两个字段 + 撒自建 VM ⇒ 合规。
