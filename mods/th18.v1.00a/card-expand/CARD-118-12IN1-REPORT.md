### B1 机制诊断（2026-09-18，一手代码定位）

**现象**（用户口径）：TH10/TH11 转化的**绿点**触发了"由 **POC 线**决定的那条**收点**"；每正常吃到一个，
"收点是 `1,0`"，而**应该是 no focus**。（同源后果：114 的 bonus 在 boss 战对着 TH14 掉的 P 点触发。）

**机制（代码一手）**
- 114（`cards/collect2x.c:277` `on_item_collect`）有一道**成员门**：
  ```c
  if (type != 1 && type != 2) return;                       /* 只认 P 点 / 点道具 */
  uint32_t st = *(const uint32_t *)(item + CE_ITEM_STATE);
  if (st != CE_ITEM_STATE_VACUUM) return;                    /* ★ 只有真空态才入批 */
  ```
  注释写明：`type {1,2} 进入 state 3（真空）的唯一入口 = V 门翻 0x445f63`（**上线 / 放 B 前 60 帧 / 对话管理器**）；
  **触收（state 1）与 70px 环收（state 4）不开批、不计数**。
- TH10/TH11 的绿点（`cards/faith.c` 的信仰道具池）**会被转化成 TH18 的 P/点道具**（`type 1/2`）
  ⇒ 只要它们**以真空态被收**（或它们替身走的是 state 3），就会**开批** ⇒ 触发那条"收点"bonus
  ⇒ 这正是用户看到的 `1,0`，也是当年花很久调出来的 **no focus** 口径被破坏的入口。

**候选修法（两处，二选一或都做）**
1. **不让绿点走真空态**（`faith.c` / `mof.c` / `signal.c` 的转化与收集路径）：转化出来的道具按
   **触收/环收**（state 1 / 4）计，而不是 V 门那条；
2. **给 114 的成员门加排除**：把"由 110/111 转化来的道具"排除在批次之外（需要 114 能识别来源 —— 例如
   转化时打一个标记位/用专用 type）。

**判定口径待确认（用户）**：所谓"应该是 no focus"，是①**完全不进 114 的批**（既不计分也不开批），
还是②**进批但不触发 bonus**？两者改的地方不同。

**另记（颜色）**：用户报"目前收点的这个 bonus 颜色似乎也有点奇怪" ⇒ 属 114 的 bonus 显示配色，**单独一条待查**
（先确认是 `collect2x` 的 HUD 颜色还是引擎透传；本目标偏"机制"，UI 颜色排在后面）。

### B1 根因（2026-09-18 二次定位，交点已找到）

**用户口径**：转化出来的**信仰点等价于 P 点与金钱**（所以 type 1/2 是对的，问题不在类型）。

**根因 = "过 POC 线" 与 "真空（收点）" 被我们共用成了同一个 state 值 `3`：**

| 位置 | 代码 | 含义 |
| --- | --- | --- |
| `cards/faith.c:440` | `p->state = 3;  /* ★ 与「过回收线 / 放 B / 对话」同一条 */` | **我们**用 3 表示"信仰点过了回收线（POC）⇒ 朝自机飞" |
| `cards/faith.c:789` | `if (p->state == 3)  /* 3 = 过回收线 / 放 B / 对话 ⇒ 朝自机飞（= 原生 state 3 的对位）*/` | 同上（把我们的 3 对齐到引擎道具的 3）|
| `cards/collect2x.c:283` | `if (st != CE_ITEM_STATE_VACUUM) return;` | **114** 把引擎 `state 3` 当"真空收点" ⇒ 开批（bonus）|

⇒ 正常吃一个**转化信仰点**（它过了 POC 线）被 114 记成一次**上线收点** ⇒ 用户看到的 `1,0`；
⇒ 也正是当年在 114 上花很久调出的 **no focus** 口径被破坏的入口。

**修法（推荐：给转化道具打"来源标记"，让 114 排除）**
1. **转化时打标记**：`faith.c` 把信仰点交给引擎道具槽时，置一个"来源 = 信仰点"的标志位
   （可用道具结构里我方未用的字段/专用 type 侧表；具体字段待核 `CE_ITEM_*` 的可用位）；
2. **114 的成员门加排除**：`collect2x.c` 的 `on_item_collect` 在 `st == VACUUM` 命中后，再查该标记
   ⇒ 命中"信仰点来源"就 **不入批**（但分值照常，因为它等价于 P/金钱）。
   ⇒ 这样既不动引擎的"过线飞向自机 / 全额"语义，也不影响正常的上线收点。

**替代修法**：让转化道具**从不进入 state 3**（走触收/环收）—— 但那会改掉"过线飞向自机 + 全额"这条
一手行为，**不推荐**（与 `collect2x.c` 注释里"引擎 handler 也读 state==3 给全额 —— 同一谓词"冲突）。

**待确认**：标记位放哪（我会先核 `engine.h` 的 `CE_ITEM_*` 字段，挑一个我方未用、且引擎不读的位）。

### B1 规格（用户 2026-09-18 定，**这是验收判据**）

**信仰点本身必须做到**（与 **P 点 / 金钱完全一致**）：
1. **开批**（进入 114 的收点批次）；
2. **计数 +1**；
3. **飞行中的信仰点会组织批次结算**（在飞向自机的过程中参与批次结算，而不是被当成"外来的、不参与结算的"）。

⇒ 所以之前"应该 no focus"那句**不是**说信仰点不该开批 —— 而是说**它得像 P/金钱那样走完整条批次语义**；
真正的偏差要按"与 P/金钱逐面一致"来找。**对齐检查清单**（逐面比对 P/金钱 vs 我们的转化信仰点）：

| 面 | 要查什么 | 现状线索 |
| --- | --- | --- |
| ① 出生 state | 转化时给引擎道具的 state 是否与 P/金钱出生时相同（P/金钱出生即 state 1？过线才翻 3？）| `faith.c:440` 我们用 `state = 3` 表示"过回收线" —— 要核对这**是否就是 P/金钱过线时的同一个值**（若是，则一致；若我们提前置 3，就是偏差）|
| ② 开批 | 收集时 `on_item_collect` 是否命中 114 的成员门（`type 1/2` + `VACUUM`）| 用户报"触发收点是 `1,0`" ⇒ 开批**发生了**，但 **+1 之后的值/分是 0** ⇒ 疑在"值/分"这一面不一致 |
| ③ 计数 +1 | 批次计数是否 +1（与 P/金钱同路径 `c2x_collect_batch`）| 待核：是否走了同一个调用（而不是只"开了批"）|
| ④ 飞行中结算 | "飞行中（已过线、朝自机飞）"的道具是否参与批次**结算**（批闭时结算到分数/加值）| 待核：我们的转化道具在飞行段是否已被移出引擎 item 槽（`faith.c:940` 出生即参与收点判定 / `:654` 置 state 0 = 空槽）|
| ⑤ bonus 触发 | 该批是否触发 TH14 的 bonus（以及 boss 战期间是否应当触发）| 用户原始抱怨：boss 战对着 TH14 掉的 P 点触发 ⇒ 这条要单独判"该不该在这个时机触发"|

**下一步（我来做，不需你）**：按①–⑤ 逐面读代码（`faith.c` 转化/收集、`collect2x.c` 成员门与批结算、`engine.h` 的 `CE_ITEM_STATE/TYPE` 语义），
把"与 P/金钱不一致的面"找出来并逐条修 ⇒ 目标是**四处完全一致**，而不是让信仰点不进批。

### B1 逐面对照结果与修法（2026-09-18 第三轮，**已改并过门**）

**逐面比对**（P 点 / 金钱 = 引擎原生道具；信仰点 = 110/111 共用池的自建 VM，经 SDK 的
「虚拟收集 / 虚拟在飞」两条通道喂 114）：

| 面 | P 点 / 金钱（引擎）| 信仰点（我们，改动前）| 判定 |
| --- | --- | --- | --- |
| ① 出生 state | 出生 `state 1`（抛物）⇒ 过回收线 / 放 B / 对话翻 `3`（V 门 `0x445f63`），出生帧即参与收点判定 | 出生 `state 2`（飞散）⇒ `1`（飘落）⇒ 同一道 V 门翻 `3`；判定同帧即跑（无出生保护）| ✅ **语义对位**（两套编号不可逐值对照，映射表见下）|
| ② 开批 | 只有**真空飞行中被收**（`type{1,2}` ∩ `state 3`）才开批 | **任何状态**被收都开批（`FAITH_VITEM_NOTE_VACUUM_ONLY = 0`）| ❌ **偏差 → 已修** |
| ③ 计数 +1 | 同一条 `c2x_collect_batch()`（只在 state 3 命中）| `c2x_collect_virtual()`（**同一批计数器**，但任何状态都 +1）| ❌ **同上 → 已修** |
| ④ 飞行中组织批次结算 | presence 谓词 `ce_item_pool_any_attracting()` = `type{1,2}` ∩ **`state 3`** | `ce_vitem_declare_flying(…, s_n_big + s_n_small)` =「活着的都算在飞」（含飘落 / 飞散）| ❌ **偏差 → 已修** |
| ⑤ 批分 / bonus 值 | stash 差量 = 该道具的引擎小分 ⇒ 批分非零 | 绿点**不进批分**（`batch_score` 恒不含绿点）⇒ 纯绿点批补差 0 | ⚠ **刻意保留**（用户 2026-09-15 口径「只 +1」；本轮规格的三条里没有它）|

**⇒ 偏差就两条，而且是同一个根**：两条通道都**没加状态门**（旧注释自称「用户口径的字面」）。
引擎侧对 P / 钱的谓词**只有一条** —— `item+0xc74 == 3`（`AUDIT.md` §Z22 成员门 + `sdk.c` 的
`ce_item_pool_any_attracting`），坠落中（state 1）与环吸中（state 4）**既不计数也不续批**
（「普通游玩顺手捡一颗」在引擎那边同样不开批）。

**修法（已落笔）**：判据收敛到**一处**（`cards/faith_core.h` 的 `faith_state_t` + `faith_core_state_is_vacuum_flight()`），
两条通道都过它：
- **成员**：`faith.c` 的 `dot_collect()` 只在 `state == 3` 时报 `ce_vitem_note_collect()`；
- **presence**：`faith_pool_tick()` 尾部只声明**本帧 state 3** 的点数（旧 `s_n_big + s_n_small` 已删）；
- 兜底开关 `FAITH_VITEM_NOTE_VACUUM_ONLY` **删除**（只剩一条路）；`faith:` 汇总行加 `vitem member M skip S` 两列做对账。
- **两套 state 编号的对照**（判据表原文在 `faith_core.h`）：本池 `0 待发射 / 2 飞散 / 1 飘落 / **3 朝自机飞（过线）** / 4 环吸`
  ↔ 引擎 `0 空槽 / 1 抛物坠落 / — / **3 真空飞行** / 4 环吸`。

**为什么这一条能同时解释你报的两个症状**：
- 「**绿点一直触发收点**」← 成员门不看状态 ⇒ **普通游玩顺手捡**的每一颗都在开批 / 计数，批被绿点持续喂大；
- 「boss 战期间对着（114 自己掉的）P 点触发 bonus」← presence 不看状态 ⇒ 一批绿点**飘着就把批吊住**，
  期间收到的原生 P（含 114 被动掉的那些）全并进同一批 ⇒ 批闭时自然落在那批的档位上。
修完两条通道都只认「真空飞行」，普通捡点**不进批**，批只在真的收点（上线 / 放 B / 对话）时开与续。

**改动前的日志证据**（十二合一那一跑 14:33 的 `th18_card_expand.log`，同一份日志里的三行连读，
