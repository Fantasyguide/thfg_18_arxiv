## 0. 一句话

**每个事件都属于下面六类合成语义之一；多卡同装时按其类别的规则合成，绝不依赖帧内顺序或卡链顺序。**

| 类别 | 规则 | 例子 |
| --- | --- | --- |
| **累加型** | SDK 持一个局部累加器，各卡 `+=`，**最后一次性应用** | `on_item_money` |
| **声明族 + 一次合成** | 各卡**声明自己那一族的加数**；SDK 按公式合成并**一次**写终值（无「落笔者」） | `on_item_score`（★ 2026-09-13 重做，见 §3）|
| **先加后乘（作用在最终总数）** | 各卡声明加法；倍率卡声明乘数；层算 `final = (base + Σ加) × Π乘` | `on_enemy_drop_pre` |
| **选举覆盖** | 各卡声明自己的形态；**id 最小者落笔** | 低速子机声明层 |
| **OR** | 任一卡要求即生效（布尔可叠加） | `on_native_shot_suppress` |
| **广播（只读）** | 全卡收同一份只读 payload，各自按字段过滤 | `on_enemy_death` |

## 2. 掉落层：先加后乘，乘作用在**最终总数**（用户 2026-09-12 拍板）

**原则：按卡的意图，不按实现。** 加倍（69）的意图是 **×2**；它现在写成 `+ (倍率−1)`，只是因为
**主掉落那一颗在事件触发之前就已经被引擎撒出去了**（一手：`0x430469` 读表 → `0x430493 call 0x446f40` 撒主掉落 →
`0x43049f call 0x430510` **事件在这里触发** → 体内 `0x430539 lea eax,[ecx+0x54]` 循环撒 `ex_drop` → `0x4304aa` 清表）。

### 2.1 层要算的式子

```
base[main] = 1（引擎已撒） ; base[t] = ex_drop[t]（引擎随后要撒的）
final[t]   = ( base[t] + Σ additions[t] ) × Π multipliers        ← 乘作用在最终总数上
ex_final[main-1] = final[main] − 1        ← 层替卡片扣掉「已经撒出去的那一颗」
ex_final[t]      = final[t]               ← 其余类型原样交给引擎的循环
```

⇒ 效果（一手算例，某类原有 1 颗、倍率 2）：
**110 加的那颗也会被翻倍** ⇒ `(1+1)×2 = 4`，**而不是** `1×2+1 = 3`。
⇒ 且**与卡链顺序完全无关**（现在只是「按卡链顺序」的既成事实，谁都没写下来）。

### 2.2 落地与边界

- ✅ **69 已改成声明式**（2026-09-12）：从「直接改 `counts`」改成 `on_load` 里一句
  `ce_drop_mult_set(69, 2000)`，`dbl_apply` 里那句 `+ DBL_MULT - 1` 补偿搬进了层（`ce_drop_apply`）
  ⇒ 卡的代码反而更简单（少了「主掉落已撒」这个洞的补偿），`cards/double_core.c/h` 退役（纯逻辑单测并入
  `tests/test_sdk_core.c` 的掉层用例）。
- ⚠ **回归面**：69 是 **✅ 实跑过的卡**（AUDIT §S10；且 **S10 的修复本身未复验**）⇒ 层改完必须重跑它的验收：
  主掉落 ×2、非 0 附加 ×2、**第 20 格不撒**。
- ⚠ **层收的是 `zEnemyDrop` 基址**（不是 `counts`）：传 `counts`（= 基址 +0x04）会整体错开一个 type 格（2026-09-12 审计抓到并修）。
- ⚠ **两张表一起乘**：`+0x04 ex_drop[20]` 与 `+0x54 timed_ex_drop[20]`（引擎撒 `ex[i] + timed[i]×(T−timer)/T`，一手 `0x43053f`–`0x430570`）—— 只乘 ex 表会漏掉计时加成那些颗。
- ⚠ **边界沿用一手**：`ex_drop[20]` 但引擎的循环只撒 type `1..0x13`（`0x12 < i` 退出），
  第 20 格永远不撒、主掉落补格也只认到 19 ⇒ 层用同一个上界（`native/sdk_core.h` 的 `CE_DROP_MAX_MAIN 19`）。
- ⚠ `timed` 表**不做**「已撒一颗」补偿（那一颗只补进 `ex` 表）；`T = +0xa4`、计时器 `+0xa8`/`cur +0xac`。
- ⚠ 注意 `base[main] = 1` 只在该类型确实有主掉落时成立（`main_drop == 0` = 无主掉落）。

## 4. ★ 玩家保护层（第四层）：咆哮 / 灵界 / 森罗结界三开怎么办

**问题**（用户 2026-09-12 提问）：同时有 117 咆哮 + 113 灵界 + 107 森罗结界会怎么样？
答案是：**它们全都想在同一批引擎资源上做决定**，所以必须像前三层一样**先分层、再定合成规则**，不能各写各的。

### 4.1 三张卡各自想要什么（语义分层）

| 卡 | 效果 | 会碰的引擎资源 |
| --- | --- | --- |
| **117 咆哮** | 中弹**抵消死亡**（消耗咆哮 + `cancel_impending_death` `0x45d590` 救命；霊撃 40 帧）| 虚表 `+0x10` 钩子、`+0x14`（真死掉落）、**无敌计时器** |
| **113 灵界** | ① 灵界中**中弹无伤** ② ★ **中弹 = 取消这次死亡 + 进灵界，窗口结束时再死一次**（用户 2026-09-12 第二版：**延时不是免死**）③ 神灵奖励翻倍 | 无敌计时器、**救援层（卡虚表 `+0x0c`）**、自建灵界槽 |
| **107 森罗结界** | ★ 用户 2026-09-12：「**在免伤意义上几乎和咆哮一致**」⇒ **救援型**（中弹**消耗结界**、不是免伤）| 虚表 `+0x10` 钩子、无敌计时器、消弹、樱点槽 |

**三个共享资源 = 三个冲突面**（一手字段）：

1. **`player+0x47774` = 无敌计时器**（`CE_PLAYER_INVULN_TIMER`，zTimer；复活置 `{0x117,0x118,280.0}`、决死救回 60、炸弹各自置 —— 见 `native/engine.h:277`）
   ⇒ 三张卡都会想写它 ⇒ **现在是谁后写谁赢（还会把别人给的长无敌覆盖成短的）**。**必须改成声明式**：
   `ce_invuln_request(card, frames)` 各卡只声明，SDK 每帧**取最大值**应用（同「选举落笔」形状，但聚合函数是 `max`）。
2. **一次中弹只能被消费一次**：117 消耗咆哮、113 可能消耗灵界槽、107 可能消耗结界
   ⇒ 需要明确的**层内顺序与代价归属**（见 §4.1 的四层）。
3. **`player+0x476ac` 玩家状态机（0–4）+ `CE_ADDR_BOMB_MGR+0x30`（「正在放炸弹」标志，`0x445bc4` 用它决定道具吸不吸）**
   ⇒ 任何「伪装成 bomb / 对话状态」的做法都会**连带改道具吸附**，属于已知雷区（111 的全收方案已因此否掉 (C)）。

### 4.2 推荐的四层规则（从早到晚）

| 层 | 谁在里面 | 合成规则 |

> ② 自建实体由**它自己的收集判定**决定什么时候算被收 ⇒ 报给虚拟收集通道（`faith.c` 的 `dot_collect()`）。
> ⇒ 同一屏上「原生道具 + 自建绿点」会**同时**喂到 114 的同一个批（成员相加、presence 取或），这正是用户要的。

⚠ **反例**：谁要是「自己把道具删掉再补分」，114 的批就永远开不起来（分差与碎片都没了），
而且绕过引擎的收集链 ⇒ HUD 计数 / 磁吸 / 音效全丢。**改这条前先读本节。**

## 7. ★ 前提：**110 与 111 是同一套信仰点系统**（用户 2026-09-15 口径）

用户原话：「**110 和 111 的卡间耦合很多，因为认为是同一套信仰点系统**」。
⇒ 这不是「两张卡恰好都用到点」，而是**一套系统、两套数值表**。凡是改共用件的活，都要按「**同时影响两张卡**」评估。

| 耦合面 | 载体 | 说明 |
| --- | --- | --- |
| **一套实体池** | `cards/faith.{h,c}` | 撒点 / 飘落 / 吸引 / 回收线 / 收集判定 / 出界**只有一份**；两卡各自注册（`slot_mask`） |
| **档位 ↔ 来源一致** | `faith_core_tier_for_source()` | 大 = 击破、中/小 = **满 P 转换**、微 = **消弹** —— 两作**同一套**（见 `NEXT.md` §1x 的 E-1）|
| **数值表分家** | `faith_core.h` | 同一档在两作**值不同、量纲也不同**（TH10 显示 = 存储×10 / TH11 显示 = 存储÷100）⇒ **常量不许互搬** |
| **满 P 转换写进同一个池** | `faith.c` + 两张卡的卡侧 | 我们**没有** TH18 的信仰点 type ⇒ 转换只能在自建池里落地（删原生 P 道具 + 原位撒自建点）|
| **消弹记账** | `faith_cancel_account()` | 微档**不建实体**（半道具、实体只为动画）；颗数来自 `ce_cancel_radius()` 的返回值 |
| **飘字合计** | 建议搬到 `faith.c` | 同装时显示**两卡合计**（§1x.6）；含义不同、只是显示口径 |
| **计分层耦合** | `sdk_core.c` | `PV = (擦弹倍率 + 信号强度) × …`：擦弹倍率（TH11 的式子）与信号强度**只在两卡同装**时参与 |
| **114 批结算** | `cards/collect2x.c` | 大/中绿点要入批（**成员 + presence 两个通道**，§1x.2）；微档不入批（§1x.3）|
| **115 擦弹减速** | `CE_ITEM_SLOWDOWN` | 大/中绿点要跟着**变黄 / 变慢 / 抖动**（§1x.4）|

**规矩**：改 `faith.*` / `faith_core.*` / 两卡任一处的档位或数值 ⇒ **必须在报告里单开「对另一张卡的影响面」**，
并跑两张卡的单测（`test_faith_core` / `test_mof_core` / `test_signal_core`）。
