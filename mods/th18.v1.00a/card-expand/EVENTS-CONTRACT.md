# 事件合成契约 —— 多卡同装时谁说了算

> **版本**：TH18 v1.00a（`th18.exe`，imagebase `0x400000`）。本文裸地址默认属该版本；引用其他作品须写成 `th08:0x…`。
> **日期**：2026-09-12（起草）。**状态**：规则定稿，代码待实装。
> **归属**：SDK 面（`native/sdk_core.{c,h}` / `native/sdk.c` / `native/sdk/public.h`）；本文是**卡片作者与大改 SDK 的人**共同的口径来源。
> **起因**（三处真实冲突）：① 110 与 111 抢 `on_item_score` 传出来的同一个 `esi`（**谁后写谁赢**）；
> ② 108 与 111 抢同一批子机对象；③ 69 的 ×2 与 110/111 的 +1 谁先谁后结果不同，而**全仓没有一处写下来**。
> **先例**：伤害层 `bullet_damage_permille`（`ce_dmg_set` / `ce_dmg_aggregate` / `ce_dmg_applier`，AUDIT §AA）——
> 「卡片只声明 → SDK 聚合 → **单一落笔者**」这套形状就是从这里来的。
> **相关**：交接体检 [`docs/superpowers/specs/2026-09-11-system-card-spec-review.md`](../../../docs/superpowers/specs/2026-09-11-system-card-spec-review.md) §3.1.1；
> 108 的子机声明层 [`2026-09-12-youkai-108-design.md`](../../../docs/superpowers/specs/2026-09-12-youkai-108-design.md) §3.3.1。

## 0. 一句话

**每个事件都属于下面六类合成语义之一；多卡同装时按其类别的规则合成，绝不依赖帧内顺序或卡链顺序。**

| 类别 | 规则 | 例子 |
| --- | --- | --- |
| **累加型** | SDK 持一个局部累加器，各卡 `+=`，**最后一次性应用** | `on_item_money` |
| **聚合公式 + 单一落笔** | 各卡**声明**贡献；SDK 聚合；**id 最小者**按公式算并一次写值 | `on_item_score` |
| **先加后乘（作用在最终总数）** | 各卡声明加法；倍率卡声明乘数；层算 `final = (base + Σ加) × Π乘` | `on_enemy_drop_pre` |
| **选举覆盖** | 各卡声明自己的形态；**id 最小者落笔** | 低速子机声明层 |
| **OR** | 任一卡要求即生效（布尔可叠加） | `on_native_shot_suppress` |
| **广播（只读）** | 全卡收同一份只读 payload，各自按字段过滤 | `on_enemy_death` |

## 2. 掉落层：先加后乘，乘作用在**最终总数**（用户 2026-09-12 拍板）

**原则：按卡的意图，不按实现。** 加倍（69）的意图是 **×2**；它现在写成 `+ (倍率−1)`，只是因为
**主掉落那一颗在事件触发之前就已经被引擎撒出去了**（一手：`0x430469` 读表 → `0x430493 call 0x446f40` 撒主掉落 →
`0x43049f call 0x430510` **事件在这里触发** → 体内 `0x430539 lea eax,[ecx+0x54]` 循环撒 `ex_drop` → `0x4304aa` 清表）。

### 2.1 层要算的式子

```
base[main] = 1（引擎已撒） ; base[t] = ex_drop[t]（引擎随后要撒的）
final[t]   = ( base[t] + Σ additions[t] ) × Π multipliers        ← 乘作用在最终总数上
ex_final[main-1] = final[main] − 1        ← 层替卡片扣掉「已经撒出去的那一颗」
ex_final[t]      = final[t]               ← 其余类型原样交给引擎的循环
```

⇒ 效果（一手算例，某类原有 1 颗、倍率 2）：
**110 加的那颗也会被翻倍** ⇒ `(1+1)×2 = 4`，**而不是** `1×2+1 = 3`。
⇒ 且**与卡链顺序完全无关**（现在只是「按卡链顺序」的既成事实，谁都没写下来）。

### 2.2 落地与边界

- ✅ **69 已改成声明式**（2026-09-12）：从「直接改 `counts`」改成 `on_load` 里一句
  `ce_drop_mult_set(69, 2000)`，`dbl_apply` 里那句 `+ DBL_MULT - 1` 补偿搬进了层（`ce_drop_apply`）
  ⇒ 卡的代码反而更简单（少了「主掉落已撒」这个洞的补偿），`cards/double_core.c/h` 退役（纯逻辑单测并入
  `tests/test_sdk_core.c` 的掉层用例）。
- ⚠ **回归面**：69 是 **✅ 实跑过的卡**（AUDIT §S10；且 **S10 的修复本身未复验**）⇒ 层改完必须重跑它的验收：
  主掉落 ×2、非 0 附加 ×2、**第 20 格不撒**。
- ⚠ **层收的是 `zEnemyDrop` 基址**（不是 `counts`）：传 `counts`（= 基址 +0x04）会整体错开一个 type 格（2026-09-12 审计抓到并修）。
- ⚠ **两张表一起乘**：`+0x04 ex_drop[20]` 与 `+0x54 timed_ex_drop[20]`（引擎撒 `ex[i] + timed[i]×(T−timer)/T`，一手 `0x43053f`–`0x430570`）—— 只乘 ex 表会漏掉计时加成那些颗。
- ⚠ **边界沿用一手**：`ex_drop[20]` 但引擎的循环只撒 type `1..0x13`（`0x12 < i` 退出），
  第 20 格永远不撒、主掉落补格也只认到 19 ⇒ 层用同一个上界（`native/sdk_core.h` 的 `CE_DROP_MAX_MAIN 19`）。
- ⚠ `timed` 表**不做**「已撒一颗」补偿（那一颗只补进 `ex` 表）；`T = +0xa4`、计时器 `+0xa8`/`cur +0xac`。
- ⚠ 注意 `base[main] = 1` 只在该类型确实有主掉落时成立（`main_drop == 0` = 无主掉落）。

## 3. 计分层（#2）：把 `on_item_score` 从「覆盖型」拉回同族

**现状**（`native/sdk.c:633`–`648`，一手）：

```c
int32_t value = (int32_t)regs->esi;                                  /* 身价（已钳 ≥10） */
for (…沿卡链… ) if (h->on_item_score) h->on_item_score(card, &value); /* 逐张传同一个指针 */
regs->esi = (uint32_t)value;                                         /* 后写者胜 */
```

⇒ 110 / 111 / 113 同装会**互相覆盖**；而且「后写的卡读到的 `*value` 是前一张卡的产物」= 隐性跨卡耦合。

**改成**（形状照伤害层）：

```c
void ce_score_declare(ce_card_t *c, int32_t delta);   /* 卡片只声明自己的贡献 */
int32_t ce_score_aggregate(void);                      /* SDK 聚合（= Σ delta 等）*/
int    ce_score_applier(void);                          /* 落笔者 = 声明者里 id 最小的那张 */
```

- **落笔者**按 110 / 111 既定的 PV 公式算：
  `PV = (基础均值 + Δ_110 + Δ_111) × (擦弹倍率 + 信号强度)`，然后写 `*value = PV × 10`
  （引擎随后 `SCORE += value / 10` ⇒ **精确得到 PV 分**，天然不双计分）。
- **声明者不必是落笔者**：111 只声明 `Δ_111`；110（id 更小）落笔并读**聚合值** ⇒
  **卡片之间互不读对方状态**（不违反「不跨卡耦合」）。
- ⚠ 断点本身**不动**（`0x446cf6` 已装）；114 不使用该事件。

| 1 | `native/sdk_core.c` / `.h` | 照 `ce_dmg_*` 加 `ce_score_declare` / `ce_score_aggregate` / `ce_score_applier`（选举 = **id 最小者**，与链表顺序无关）|
| 2 | `native/sdk.c` | `BP_ce_item_score` 改为「收集声明 → 交给落笔者 → **一次**写 `regs->esi`」 |

| 5 | `AUDIT.md` | 新开一节 + 实跑验收三态（110 单装 / 111 单装 / 都装，各吃一颗金钱，核对得分正好 = PV）|

## 4. ★ 玩家保护层（第四层）：咆哮 / 灵界 / 森罗结界三开怎么办

**问题**（用户 2026-09-12 提问）：同时有 117 咆哮 + 113 灵界 + 107 森罗结界会怎么样？
答案是：**它们全都想在同一批引擎资源上做决定**，所以必须像前三层一样**先分层、再定合成规则**，不能各写各的。

### 4.1 三张卡各自想要什么（语义分层）

| 卡 | 效果 | 会碰的引擎资源 |
| --- | --- | --- |
| **117 咆哮** | 中弹**抵消死亡**（消耗咆哮 + `cancel_impending_death` `0x45d590` 救命；霊撃 40 帧）| 虚表 `+0x10` 钩子、`+0x14`（真死掉落）、**无敌计时器** |
| **113 灵界** | ① 灵界中**中弹无伤** ② ★ **中弹 = 取消这次死亡 + 进灵界，窗口结束时再死一次**（用户 2026-09-12 第二版：**延时不是免死**）③ 神灵奖励翻倍 | 无敌计时器、**救援层（卡虚表 `+0x0c`）**、自建灵界槽 |
| **107 森罗结界** | ★ 用户 2026-09-12：「**在免伤意义上几乎和咆哮一致**」⇒ **救援型**（中弹**消耗结界**、不是免伤）| 虚表 `+0x10` 钩子、无敌计时器、消弹、樱点槽 |

**三个共享资源 = 三个冲突面**（一手字段）：

1. **`player+0x47774` = 无敌计时器**（`CE_PLAYER_INVULN_TIMER`，zTimer；复活置 `{0x117,0x118,280.0}`、决死救回 60、炸弹各自置 —— 见 `native/engine.h:277`）
   ⇒ 三张卡都会想写它 ⇒ **现在是谁后写谁赢（还会把别人给的长无敌覆盖成短的）**。**必须改成声明式**：
   `ce_invuln_request(card, frames)` 各卡只声明，SDK 每帧**取最大值**应用（同「选举落笔」形状，但聚合函数是 `max`）。
2. **一次中弹只能被消费一次**：117 消耗咆哮、113 可能消耗灵界槽、107 可能消耗结界
   ⇒ 需要明确的**层内顺序与代价归属**（见 §4.1 的四层）。
3. **`player+0x476ac` 玩家状态机（0–4）+ `CE_ADDR_BOMB_MGR+0x30`（「正在放炸弹」标志，`0x445bc4` 用它决定道具吸不吸）**
   ⇒ 任何「伪装成 bomb / 对话状态」的做法都会**连带改道具吸附**，属于已知雷区（111 的全收方案已因此否掉 (C)）。

### 4.2 推荐的四层规则（从早到晚）

| 层 | 谁在里面 | 合成规则 |
| --- | --- | --- |
| **① 免伤层**（中弹那一刻就不算撞弹）| **只有 113「灵界中」**（用户 2026-09-12 定；107 与 117 都**不**在这一层）| **布尔 OR**；**只有最先生效的那张付代价** |
| **② 救援层**（死亡已发起、可取消）| **117 咆哮 + 107 森罗结界 + 决死 B + ★ 113 灵界**（用户 2026-09-12 第二版：113「**一定在救援层的最后出发，甚至比决死 B 还靠后**」）| **全部同时爆发**（§5.2）：107/117 各自烧一次、各付代价，顺序 **107 → 117**；只有「全屏消弹」全层一次（107 拿账）+ 无敌取 max。★ 113 排在这三家**之后**：它挂在**卡虚表 `+0x0c`**（决死窗口与 B 键那条路都走完之后才广播）⇒ **结构性**排在最后，靠 `ce_rescue_note_owner()` 让位（见 §5.4）|
| **③ 事后层**（死亡**已经结算**）| 117 的 `+0x14` 真死掉落、**113 的 `+0x14` 只记一行日志** | **全部执行**。⚠ 113 的「强制灵界 → biu」（第一版口径）**已作废**：中弹那条路改在 ② 层做（延时），`+0x14` 只剩收尾 |
| **④ 状态层**（与死亡无关）| 三家的计时 / 收益 / 消弹 / HUD | **各自独立跑**；⚠ 真正的冲突只剩 **HUD 槽位**（三套都要占，`ce_hud_slot_claim` 仍只是草案）|

### 4.3 「三开」的实际表现（按上述规则）

- 咆哮 ready + 灵界槽满 + 结界已开时**撞弹第一次**：先试 ①（**只有 113 的「灵界中」在这一层**）⇒ 灵界中就不死、② 整层不跑；
  ① 不生效才走 ② ⇒ 顺序 **107 → 117 → 决死 B → 113**（用户 2026-09-12 第二版）：
  107/117 在同一帧的 `+0x10` 里各自烧掉（结界结束 + 全屏消弹转小樱点（107 拿消弹账）+ 咆哮结束 + 霊撃，无敌取 max(40,40)=40）
  并各自 `ce_rescue_note_claim()` 报到 ⇒ **113 在 `+0x0c` 里问 `ce_rescue_note_owner()` 看到有人认领 ⇒ 它什么都不做**（不烧槽、不排补死）。
  只有 107/117 都不在场/不满足时，才轮到决死 B（8 帧窗口），再之后才轮到 113。
- 结界 / 灵界各自**计时到点独立结算**（不参与 ①③）。
- 唯一的观感问题：**HUD 三套指示抢角落** ⇒ 依赖槽位分配器。
- ⚠ 若不走「无敌取最大值」而各卡直写 `+0x47774`：后写者会**把别人给的长无敌截短**，这就是必须加这一层的原因。

### 5.2 救援层（②）✅ 定案（用户 2026-09-12）：**一次中弹把救援者全部烧掉**；顺序钉死 **107 → 117 → 决死 B → 113**

**规则**：中弹（死亡已发起、虚表 `+0x10`）⇒ **当前所有「救援型」提供者一起被消耗** ——
**107 森罗结界结束 + 117 咆哮结束**（用户 2026-09-12：「**就撞了同时消耗吧，具体动作的先后就 107 → 117**」）。
★ **第二版追加**（同日晚些时候的用户定案）：「113 这条机制能够确定说，它一定在**救援层的最后**出发，
**甚至比决死 B 还靠后**」⇒ 层内顺序 **107 → 117 → 决死 B → 113**，113 的语义是**延时**（取消死亡 → 进灵界 →
出灵界**再死一次**）。
⇒ 设计意图 = **不允许靠叠卡白赚多次救命**：两张都装，一次中弹两份代价都付。

**⚠ 两者的形态是一样的（都别当成「待命资源」）**：用户 2026-09-12 指出 ——
**117 咆哮不是待命，它是「收集 5 个动物灵自动触发」的状态**（「相当于某种程度上自动按 C」，
甚至躲弹幕时碰到动物灵就自己开了）；**107 森罗结界同样是「开着」的状态**（7 秒）。
⇒ 所以「一次中弹」的语义是：**把当前所有正在生效的救援状态，各自转成一次「救援爆发」** ——
不是「从资源池里挑一个花掉」。

**配套的四条细则**（都从「都烧掉」直接推出来）：

| # | 细则 | 原因 |

### 5.4 ★ 113 的「中弹救援」（2026-09-12 第二版：**延时**不是免死；落点 = 卡虚表 `+0x0c`）

**用户原话（唯一权威）**：「灵界有两个触发方式，一个是手动触发；一个是**在确定中弹后，取消掉死亡，
进入灵界状态；灵界状态退出后，重新死亡**。」＋「113 …一定在**救援层的最后**出发，**甚至比决死 B 还靠后**」。

⇒ 落点 = **卡虚表 `+0x0c` `on_death_after_deathbomb`**（一手：引擎只在
**决死窗口走完 + B 键那条路没救成**之后才广播它，`th18:0x45c114`）。

| 时刻 | 113 做什么 | 依据 |
| --- | --- | --- |
| `Player__die` `0x45d3a0` 广播 `+0x10`（`0x45d574`）| **不做任何事**（这里没有 113 的槽）| 107/117 在这一刻当场取消死亡 ⇒ 排在 113 之前；卡表顺序不可控，所以 113 干脆不参与 |
| 决死窗口内（`state4_timer < 8`）| **什么都不做**（把机会留给决死 B）| `0x45c100` `jl 0x45c2a9`：B 键 → `can_bomb` → `do_bomb` → `cancel_impending_death` |
| ★ 窗口走完的**同一帧**（`0x45c114`）| ① 别人已认领 ⇒ `return 0` ② 槽 < 200 ⇒ `return 0`（照常死）③ 成功 ⇒ claim + **`cancel_impending_death`** `0x45d590` + ★ **`return 1`** | 引擎拿返回值决定扣不扣命：`0x45c12d` `jne` 跳过 `0x45c135` 的 `commit`。**不返回 1 就等于没救** |
| 窗口结束（`trance_tick` 报 `re_die`）| **补一次 `Player__die`**（只在自机 `state 1` 时调）| 一手 `th13:0x405c3e`：`TranceManager::end` 里 `if (this+0x14 & 2) … FUN_00444a10()` = **再死一次** ⇒ 原作就是**延时** |

**★★ 为什么不能用「帧点（`on_item_frame`）等 9 帧」**（第一版实现错在这里，`AUDIT` §BN7）：
窗口关掉的那一帧**没有**「窗口已关但命还没扣」的中间态 —— `0x45c100` 的 `jl` 不跳时，
同一条分支里要么被某个 `+0x0c` 挡住、要么**当场** `0x45c135 call 0x45d090`（扣命）。
而 `+0x0c` 广播在 Player 线 `0x17`、`on_item_frame` 在 ItemManager 线 `0x1e`
⇒ 后者跑到时 `state` 早已不是 4 ⇒ 帧点救援**永远不会触发**。

**一手原生先例（`return 1` 是实质动作）**：`CardEirin__on_player_death_after_deathbomb` `0x40a4f0`
尾段 `0x40a53f call 0x45d590` → **`0x40a544 mov eax,1`** → `0x40a54a ret 4`（stdcall，1 个 dword）。
⇒ 原生自己的「取消这次死亡」就是**两件一起做**：取消 + 返回 1。

**链式是允许的（用户同日定案）**：补死是一次**普通死亡** ⇒ 107/117/**113 自己**都还能再救
（113 的前提是没人认领 + 槽又攒到 ≥ 200）。113 侧**没有任何**「禁止再救」的状态位；
唯一的天然上限就是 `槽 >= 200` 那道门（窗口 = 进入时的槽值帧、槽 −1/帧 ⇒ 自然结束时槽必然已扣光）。
