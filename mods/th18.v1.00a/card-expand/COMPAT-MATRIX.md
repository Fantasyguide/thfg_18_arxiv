### 1.3 `do_bomb` 那条崩（另一类 bug）的锚点（一手，Round 13）

- `th18:0x4cf2b8` = **`BOMB_PTR`**（社区 `statics.json`，`int32_t`）—— 炸弹/能力载体单例。
  读者一手：`Player::get_damage_source_by_index`、`CardEirin` / `CardByakuren` / `CardShikiEiki` /
  `CardUtusho` / `CardTsukasa` 的多个方法、`Bomb::operator new`
  ⇒ 它的字段：`+0x30` 状态（与 `1` 比较）、`+0x44` flags、`+0x34`/`+0x38`/`+0x3c`/`+0x40`/`+0xa0`。
- 崩溃形态（`128152.dmp` 崩点页字节**一手**）：`… 8b 06 | 8b ce | ff 50 04 …`
  = `mov eax,[esi]; mov ecx,esi; call dword [eax+4]`，`esi = [BOMB_PTR] = 0x1a0af298`，
  **`[0x1a0af298] == 0`（虚表为空）** ⇒ 读 `0x4` 违例（`params=['0x0','0x4']`）。
- **镜像里唯一的写点**：`th18:0x443661`（`GameThread::thread_start__stub` 区）`c7 05 b8 f2 4c 00 00 00 00 00`
  ⇒ 它把 `BOMB_PTR` **清 0**，**不是**赋对象 ⇒ 对象是运行期经**间接寻址**写进去的（或堆上对象），
  所以"谁把虚表写没了"要另找（下一步：扫 `lea reg,[0x4cf2b8]` 之后的 store）。
- 与池子越界**不是**同一回事；但有一个待验的**关联假说**：断点被静默跳过 ⇒ 本该初始化/赋值的路径没跑
  ⇒ 单例停在半初始化状态（这条假说要么被证伪、要么就是"静默失效"的第二个实例）。
- **否定证据（Round 14 扫过，把范围缩小）**：
  ① `lea r32,[0x4cf2b8]`（`8d /r` 全 modrm）**0 处** ⇒ 没有经 lea 取址的间接写；
  ② `mov [0x4cf2b8],eax`（`a3` / `89 05`）**0 处**、`mov [abs],al`（`a2`）**0 处**；
  ③ 我们的 patch（211 binhack + 20 断点）与 `base_tsa` 的 patch 都**没有条目**引用 `0x4cf2b8`/`0x443661`
     ⇒ **补丁没改这个全局**。
  ⇒ 剩下的写法只可能是「**基址寄存器 + 位移**」（例 `mov ecx,0x4cf2a0; mov [ecx+0x18],eax`）
  或运行期由别的管理器赋值 —— 下一步按这个形态扫。
- **写点已定（Round 15）**：`mov dword [0x4cf2b8], edi`（`89 3d b8 f2 4c 00`）**全镜像仅 1 处**，
  地址 `th18:0x41ff73`（社区符号 `Bomb::operator new` 区内，紧邻 `th18:0x41ff75` 的 `ret`）
  ⇒ **BOMB_PTR 是在「造炸弹」这条路上被赋值的**（`a3`/`89 05`/`89 0d`/`89 15`/`89 1d`/`89 35` 全为 0 处）。
  ⇒ 结合崩溃形态可推出**缺口在哪**：崩溃时 `BOMB_PTR` **有值**（堆对象 `0x1a0af298`）而**虚表为 0**
  ⇒ 赋值那一步发生过、**虚表写入那一步没有**（构造被跳过 / 半途返回）。下一步看 `th18:0x41ff73`
  之前的构造序列里虚表是在哪条指令写的、以及它前面有哪个分支能提前跳出。
- **写点前没有虚表写（Round 16 一手）**：`th18:0x41ff73` 之前那段只初始化数据域，
  然后就直接返回：`mov [edi+0x84],0` / `[edi+0x7c]=-1` / `[edi+0x78]=0xbf800000` /
  `[edi+0x74]=0` / `[edi+0xa0]=0` / `[edi+0xa4]=0` → `mov [0x4cf2b8],edi` → `pop edi; mov esp,ebp; pop ebp; ret`
  ⇒ **这段里没有任何虚表写入** ⇒ 虚表是**调用方随后调用的构造函数**负责的。
  崩溃时「指针有值、虚表为 0」正好等于**这段跑完了、构造函数那一步没跑**（或半途跳出）。
  下一步：找 `th18:0x41ff73` 所在函数的调用者，看它调用构造函数的那条指令前面有什么分支。

**因此**：① 任何"加站点"的评估要按 **40 → 上限** 来算，不是 22/24；
② 不需要观察者时**把测试归档取消勾选**（免费腾 2 条）；③ 想验证池子余量，最干净的做法是
**临时取消 `base_tsa`** 再跑——那等于一次性腾出 18 条。

### 1.2 ★ 池页实测（离线，2026-09-17）：**1 条断点 = 1 格 `0x10`，一页 256 格**

`sdk.c` 的 `ce_mem_map_dump()`（2026-09-16zg 加的取证）会把 `0x03c00000..0x03e00000` 里
`PAGE_EXECUTE` 的页**整页打 hex**（前 `0x800` 字节）⇒ 日志里就有池子的原始字节，**不需要再实跑**。

对 02:10 那次（装配 = 我们 20 + 测试 2 + `base_tsa` 18 + 分片 17 = **57 条**）的日志离线解析：

| 观测 | 数值 |
| --- | --- |
| 池页 | `0x03d20000`（`prot = PAGE_EXECUTE`）；另一页 `0x03d30000` 只有 1 个条目（不是断点池）|
| 含 `e9` 的格（宽松判据）| 57 个 —— 与该次运行的**声明条数 57 相等** |
| 跳板（严格判据：`e9` 且**回跳目标落在 `.text`**）| **54 个**（宽松数多出的 3 个，是被偷字节里恰好有 `e9`）|
| 复现 | `python3 tooling/poolmap.py <日志> --declared 57`（离线，本项的工具）|
| 格大小 / 页容量 | **`0x10` 字节 / 256 格**（格 = 被偷的原始字节 + `e9 rel32` 回跳 + `cc` 填充）|
| 回跳目标抽样 | `0x43ea04` / `0x43f0c0` / `0x46ee50` / `0x46b3f5` ⇒ 全部落在 `th18.exe` 的 `.text` ✓ |

⇒ **「上限 ≈24 条」这条信念需要更正**：它**不是"池子的格数用完"**（40 条和 57 条都远没填满一页）。
真正可疑的是**提交/布局**层面：boot 时的 memmap 显示 `0x03c00000..0x03cdb000` 是
**`RESERVE`（已保留、未提交）**，而 01:34 / 01:35 两次池崩的 `Eip`（`0x03c1064a` / `0x03c2064a`）
**正落在这段未提交区里** ⇒ 是**跳进了一块没写过的池区**（CPU 在那里执行到 `00 00`），
而**条数本身不足以解释**它——所以「条数 → 上限」的模型要重新验（可能与**归档集合变化**、
thcrap 的 arena 提交粒度、或同一站点被两档重复声明有关；下次实跑配 `ce_mem_map_dump` 即可对照）。

## 5. 全装验收判据（可一键跑）

```bash
# ① 发布 + 构建门（唯一发布路径）
MODKIT_DIR=<modkit> python3 native/tools/deploy.py
# ② 构建期门（缺一不可）
cd native && make check && python3 sites.py check && python3 tools/gen_def.py --check
# ③ 游戏里：组一副**含 106–117 全部 12 张**的卡组，进一关
# ④ 判读（用户实跑之后）
python3 native/tools/verify.py all --check
```

必须同时成立：

1. **卡在场**（防假绿）：日志里 `integrity[stage N]: card[i] id=… ` 逐条列出 12 个 id（106…117），
   少一个 ⇒ 后面所有绿灯都不算数（少一张卡的判据全绿 = **假绿**）。
2. **站点账本**：`sites.py check` 报的声明数 ≤ 24（当前 22），且 `gen_def --check` 双向一致。
3. **八原语**：`verify.py all --check` 的 8 组必需判据**全中**，且反例（`blast queue full` 等）能被解释。
4. **无静默失效**：日志里没有 `youkai: … NOT installed`、`ufo: … could NOT be spawned`、
   `senro: 结界环 VM 起不来` 这类"机制没装上"的行（出现即记为待修，不是通过）。

## 6. 已知冲突 / 挂账

- 「我们的召唤物被别家算成击破」：三张卡（109 / 110 / 113）同源，已登记在资源交互审计 §1.8；
  修法是统一判据（例如引擎侧给自建载体打标记位），**属于跨卡契约改动**，要按 §BE 登记后统一改。
- 站点余量只有 **2**：任何"顺手加一条站点"的做法都要先在这里记账，否则可能直接进崩溃区（实测 ≥24 崩）。
- `dllverify` 的 ordinal 循环在 `Makefile:262` 报假阳性（手工复现通过：38 导出 = 38 def 符号、零不匹配），
  与兼容性无关，仅记录避免误判。
