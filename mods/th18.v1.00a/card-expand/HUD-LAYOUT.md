# HUD-LAYOUT —— 左下角系统卡 UI 的全局槽位分配（研究 + 方案）

> **版本**：TH18 v1.00a（`th18.exe`，imagebase `0x400000`）。本文裸地址默认属该版本；引用其他版本须写成 `th16:0x…`。
> **缘起（用户 2026-09-10）**：要加一堆**系统卡**（复刻原作整块系统的那种）。原作里这些系统的 UI 都在**左下角**
> （TH16 季节槽、TH15 章节面板…），但多张卡不能都堆在左下角 ⇒ 需要**全局**的「我这块 UI 相对左下角偏移多少」。
> 后续 UI 基本不会超出季节指示的范畴，也**都写在同一层**（不需要往别层铺）。
> **结论**：见 §0；实测坐标见 §1；算法 §2；API 草案 §3；约束 §4；迁移 §5。

## 0. 一句话结论

**锚点固定、块自己报尺寸、全局按「货架」算法从左往右再往上摆**：

- 锚点 = **左下角内缩**：表面坐标 `(257, 924)`（= 640×480 空间的 `(128.5, 462)`；两张现有系统卡独立推出的同一条线）；
- 每张卡声明「我的块多大」（`w × h`，表面 px）与「优先左下还是右下」；
- 分配器把块**沿底部从锚点向右排**（间隙 8 px），排不下就**整体上抬一行**（行高 = 该行最高块 + 8）；
- 分配**只依赖卡 id 排序**（不看注册顺序、不看时间）⇒ 完全确定性、replay 安全、跨关不跳；
- 卡被删（倒吊人 / 原版空白卡）时释放，但**在本关内保留占位**（不重排 = 不跳），下关开场重算。

按这个算法，现有两张卡立刻不再重叠（季节 104 宽 + 动物灵 193 宽，同一行放得下），
底边那一行（y 876..924，高 48）还能再放约 2–3 张，再往上还有第 2、3 行。

## 1. 坐标与占用（实测）

### 1.1 两套坐标空间（必须同时给出）

| 空间 | 谁在用 | 换算 |
| --- | --- | --- |
| **表面 px**（= 2× 空间）| UI 列表的 VM：`ce_anm_spawn_ui` + `ce_anm_set_pos` | 我们的 HUD VM 常量都按它写（`resolutionMode(2)`）|
| **640×480 字面量空间** | `ce_hud_text*`（ASCII）、`ce_hud_vm_text_*`、`ce_hud_number_*` | 内部 × `DAT_0056aca0`（分辨率倍率）换成表面 px；640×480 下是 **×2** |

⇒ 分配器**一次返回两套坐标**（`x/y` 表面 + `x640/y640`），卡不用自己换算、也就不会换算错。
（先例：AUDIT §AF7 / AC6；季节卡的数字就踩过这个坑 —— 框按 2× 写、数字按 640 写。）

### 1.2 锚点为什么是 (257, 924)

两张已落地的系统卡**各自独立**推到了同一组数：

| 卡 | 常量 | 名义框 | 实际像素 |
| --- | --- | --- | --- |
| 季节 116 | `SEASON_GAUGE_BX 308 / BY 916`，`k_season_frame[]` 四条边 (dx,dy) | `BX ± 51 = 257..359` | 外沿 **x 263..365 / y 910..920**（调坐标时整体 +6.5 x，所以比名义框右 6 px）|
| 动物灵 117 | `ANIMAL_HUD_X0 281 / Y 900`，5 格 48×48、间距 36 | 首格左 257、底 924 | **x 257..449 / y 876..924**（与名义一致）|

⇒ 两张卡**独立**把「左下角原点」推到了同一条线：**左 257**（季节卡名义框 257、动物灵首格 257）、
**底 924**（游玩区底边 928 再上 4 px）。把它固化进 SDK 常量（`CE_HUD_ANCHOR_X / CE_HUD_ANCHOR_Y`）即可，
不需要新的一手反汇编。⚠️ 但**名义框 ≠ 实际像素**：季节卡调坐标时外沿被推到了 263（+6）——
所以分配器只发**锚点**，块内部怎么摆仍归卡自己；报块宽高时按**实际像素**报（季节 104、动物灵 193）。

## 2. 排布算法：底部货架（shelf packing）

```
输入：所有「已认领」的块，按 card_id 升序（⇒ 与注册顺序/时间无关）
常量：ANCHOR_X 257, ANCHOR_Y 924, GAP 8, X_MAX 1000（右边界，避开卡组图标行的 1056）

cursor_x = ANCHOR_X; row_bottom = ANCHOR_Y; row_h = 0
for blk in blocks:                      # 同一侧（side）分别算
    if cursor_x + blk.w > X_MAX:        # 这一行放不下 → 上抬一行
        row_bottom -= row_h + GAP
        cursor_x = ANCHOR_X
        row_h = 0
    blk.anchor = (cursor_x, row_bottom) # 「块左下角」
    cursor_x += blk.w + GAP
    row_h = max(row_h, blk.h)
```

**演算**（现有 2 张 + 假设 3 张未来卡）：

| 顺序 | 卡 | w×h | 结果锚点（块左下角）| 占位 |
| --- | --- | --- | --- | --- |
| 1 | 季节 116 | 104×36 | (257, 924) | x 257..361（内部元素自己 +6，落在 263..365）|
| 2 | 动物灵 117 | 193×48 | (369, 924) | x 369..562 |
| 3 | 假设：灵界 116 | 150×40 | (570, 924) | x 570..720 |
| 4 | 假设：信仰 117 | 150×40 | (728, 924) | x 728..878 |
| 5 | 假设：信号 121 | 180×44 | (886, 924)→放不下 ⇒ 上抬 | 行 2：底边 `924−48−8 = 868`，锚点 (257, 868) |

⇒ 底边一行（高 48）能放 **4 张**，把 `X_MAX` 放宽到 1040 还能再塞一张；
再往上每行都是「上一行最高 + 8」，第 2 行底边 868、第 3 行 812……
**每张卡自己决定 h**（h = 它的最高元素到最低元素，例如季节卡的圆环/字挂得比框高，就报 36 而不是 10）。

## 3. API 草案（`sdk.c` / `sdk.h`，与 §17 的 `ce_hud_slot_*` 对齐）

```c
/* 声明块尺寸（表面 px）与优先侧；h 进行高，w 进横向游标 */
typedef struct { float w, h; int side; } ce_hud_block_t;   /* side: 0 = 左下（默认），1 = 右下 */

typedef struct {
    float x, y;         /* 表面 px：块**左下角** —— 直接喂 ce_anm_set_pos（UI VM）*/
    float x640, y640;   /* 640×480 空间：同样的点，直接喂 ce_hud_vm_text_* / ce_hud_number_* */
    float w, h;         /* 回显声明值，卡自己按它算内部布局 */
} ce_hud_slot_t;

/* 认领（幂等：同一张卡重复调只返回同一个槽）。首次认领会触发一次重排（见 §4.4）*/
int  ce_hud_slot_claim(uint32_t card_id, const ce_hud_block_t *blk, ce_hud_slot_t *out);
/* 释放（on_delete / on_run_reset 里调；本关内占位保留，下关开场重算）*/
void ce_hud_slot_release(uint32_t card_id);

/* 统一「玩家贴近左下角 → 整摞一起淡出」（TH16 的季节槽触发区 + 迟滞）*/
int  ce_hud_player_near_corner(void);      /* x < −64 && y > 400；恢复 y < 384 || x > −64 */
```

**卡里的用法**（季节卡改造后长这样）：

```c
static ce_hud_slot_t s_slot;                      /* 或放卡状态里 */

static int on_load(ce_card_t *c) {
    ce_hud_block_t blk = { .w = 108.0f, .h = 36.0f, .side = 0 };
    if (!ce_hud_slot_claim(CE_CARD_ID(c), &blk, &s_slot)) return 0;
    /* 框：块左下角起算 */
    ce_anm_set_pos(vm, s_slot.x + 51.0f, s_slot.y - 5.0f, 0.0f);
    /* 数字：640 空间，同一个点 */
    ce_hud_vm_text_set(&s_digit, s_slot.x640 + 25.5f, s_slot.y640 - 2.5f, ...);
    return 0;
}
```

## 4. 约束（写进 API 的注释与 SDK 文档）

### 4.1 层与暂停模糊（★ 2026-09-12 一手复核后的**硬规则**）

`AnmManager__render_layer` `0x4882b8` 的 **UI 列表那一段**（`0x4882f1`）逐条：

```asm
mov  ecx,[vm+0x18]        ; VM 的 layer 字段
lea  eax,[ecx-0x18]       ; layer - 24
cmp  eax,8 ; jbe → ecx += 0x0d        ; layer 24..32 ⇒ 绘制组 = layer + 13  (24→37, 25→38, 26→39 …)
         ; 否则若 ecx ∈ [0x25,0x2d]（37..45）不变（已是组号）
         ; 否则 ⇒ ecx = 0x27 (=39)      ; ★ 其它任何层都折到组 39
if (ecx != 本趟组号) skip; else draw
```

暂停模糊罩 = `text.anm` script59 的 UI VM，**层 38 ⇒ 组 38**（[`engine/anm/th18/03-ascii-text.md`](../../../engine/anm/th18/03-ascii-text.md) §2f 一手）。
UI 列表**尾插**、渲染从表头到表尾（§2b.4）⇒ 组内**后生成的画在上面**。于是：

| 我们的 layer | 折到组 | 暂停时 |
| --- | --- | --- |
| **24** | 37 | ✅ **被罩住**（在罩子之前画）|
| **25** | 38 | ✅ **被罩住**（与罩子同组，罩子是**暂停那一刻才生成**的 ⇒ 组内后画 ⇒ 盖在我们上面）|
| 26 … 32 | 39 … 45 | ❌ **不被罩住**（在罩子之后画）|
| 20–23（以及任何非 24–32 的层）| 39（兜底）| ❌ **不被罩住** |
| 世界层 3–19 | —（世界列表）| 在游玩区 surface 上 ⇒ 会被 blur，但**永远全分辨率 + 过相机 3 视口** ⇒ **不许画 HUD** |

⇒ **HUD 一律放 UI 层 24 或 25**（推荐 25：与 `ce_hud_vm_text_*` 一致）。**不许**用 26+、也不许用 20–23。
**ASCII 文字（`ce_hud_text*`）结构上不可能被罩住**（那几趟绘制的时刻渲染目标不是装 UI 的 surface）
⇒ HUD 的文字/数字一律用**贴图 VM**（`ce_hud_vm_text_*` / `ce_hud_digit_*` / `ce_hud_number_*`，或自己起脚本）。

**2026-09-12 的修正**：`99_hud_digit` / `104_stock_rect` / `105_hud_number` 原来写的是 **layer 26**
（= 组 39 ⇒ 暂停时清晰）⇒ 已全部改成 **layer 25**（重建 `build/ability.anm` 并 `--verify-only` 通过）。
现存脚本的层现状：144/145/154/156/157/158（117 的槽/血条）= 25 ✅；123–127（116 的季节槽）= 24 ✅；
136（`ce_hud_vm_text` 的字形）= 25 ✅；117/118（TH16 时代的季节字/条）**layer 20 且全仓无引用**（历史遗留，别照抄）。
**108 的四支人妖槽 HUD + 字形（`pl0X.anm` 的 `YKGAUGE_*`，2026-09-23 补）= 25 ✅** ——
这五支是从 TH08 `ascii.anm` 搬的（script5/6/7/8 + 4），**原文一个 `layer()` 都没有**（TH08 的层由 VM 保留），
直接搬进来会落到兜底组 39 ⇒ 暂停时不被罩住；生成器 `assets/build_player_anm.py` 的 `_inject_hud_layer`
现在给它们注入 `layer(25)` **+ 紧跟一行 `resolutionMode(2)`**（**只给 HUD 那五支**，同批的刻符
`YKORB_*` 走世界列表、不注入）——⚠ 后半句**不能省**：`layer()` 会把坐标空间改成 ×2（§4.1b-订正二）。

### 4.1b ★★ **硬规则（2026-09-23）：HUD 脚本必须显式写 `resolutionMode(2)`** —— 不写就等于把坐标 ×2

**这条吃掉了一整轮的排查（112 星莲船的「槽位 UI 完全看不见」）**，所以单独立在这里：

| 脚本里 | 坐标与尺寸的解释 | 在 1280×960 下的后果 |
| --- | --- | --- |
| **写了 `resolutionMode(2)`** | **1 单位 = 1 表面 px** | 表面 px 常量按字面生效 ✅ |
| **不写**（`flags_hi & 0x1c00000 == 0`）| **640×480 设计空间** | **一切 × `DAT_0056aca0` = ×2** ⇒ 按表面 px 写的值跑出屏幕 |

- **一手/数据证据（两条独立）**：
  ① 原生 `front.anm` **script20..25** = HUD 右列那几条 `drawRectGrad(96,2)`：写 **640 空间**坐标
     `pos(524,58/80/128/166)`、**不写** `resolutionMode` ⇒ 实测画在表面 **(1048,116…)** 的右列 ✓
     （与 §1.3 的右列表同一条线）；
  ② 全库统计：原生 anm 里用**表面 px 字面量**的脚本 **270 支中 266 支**写了 `resolutionMode(2)`；
     不写的 4 支全在 `text.anm`（640 空间的整屏四边形）。
- **先例核对**：本仓已经实跑可见的 HUD 脚本 **144/145/210..214/105/136/306..308 全部写了它**；
  **302..305 是唯一没写的**（= 那一批的唯一一处看不见）。
- ⇒ 新写 HUD 脚本时：`layer(24|25)` + **`resolutionMode(2)`** + 用表面 px 常量。

  但**别混**：两者只能选一套。`make anm-verify` 不会替你查这一条（它是语义、不是结构）。
  ⚠ 112 这一批的修法见 `AUDIT.md` §BE 详录 #54 / `TUNING.md` §2.0y。

#### 4.1b-订正二（2026-09-26，108 收口）：**上面两节合起来才是真相** —— 决定坐标空间的是 `flags_hi`，而 **`layer()` 会写它**

2026-09-22 那条「订正」（下面保留）只读了 `th18:0x4063d0` **一家**，得出的「不写 ⇒ ×1」在
**「脚本里没有 `layer(20..32|37..45)`」**这个前提下成立 —— 而 HUD 脚本**恰恰都要写 `layer(24|25)`**

| 脚本里 | `flags_hi & 0x1c00000` | 坐标/尺寸 | 在 1280×960 下 |
| --- | --- | --- | --- |

- **实跑合证（108）**：注入 `layer(25)` 之前那几版（脚本无层 ⇒ 模式 0 ⇒ ×1），owner 报

#### 4.1b-订正一（2026-09-22，108 复核；**已被下面的「订正二」收口，别单独引用**）：`0x4063d0` 单看时「不写 ⇒ ×1」

上面那张表的第二行（「不写 ⇒ 一切 × `DAT_0056aca0` = ×2」）**已被一手 + 实跑双双推翻**，
但**落笔纪律不变**（新脚本照样写 `resolutionMode(2)` + 表面 px —— 那是最省心的写法）：

```
th18:0x4063d0（VM 位置 → 屏幕；绘制路径调用点 th18:0x481770）：
  4063e8  mov eax,[edi+0x538] / 4063ee and eax,0x1c00000
  4063f3  cmp eax,0x400000  je 406421   ; mode1 → xmm1 = [0x56aca0]        (×2)
  4063fa  cmp eax,0xc00000  je 406421   ; mode3 → 同上
  406401  cmp eax,0x800000  je 40640f   ; mode2 → ×[0x56aca0]×[0x4b9138]   ([0x4b9138]=0.5 ⇒ ×1)
  406408  cmp eax,0x1000000 jne 406451  ; mode4 → ×1；★ 其余（含 mode 0 = 不写）⇒ 跳到 406451（不乘）
```
尺寸那一支逐位同形（`0x4817c6`：mode1 → ×2、mode2 → ×1、**mode 0 → `0x481819` 直通**）。
⇒ 在 1280×960（`[0x56aca0]` = 2.0）下 **mode 0 ≡ mode 2 ≡ ×1** = 1 单位 = 1 表面 px。
**实跑合证**：108 的人妖槽 HUD 按「不写 ⇒ 必须写 640 空间」改了一版（发布 md5 `ea93d66e…`），

   `front.anm script20..25` 那条「实测 (1048,116)」是**按同一张表推的**（表本身是 640×2 的换算），
   不是独立测量 ⇒ 不能当证据。**逐指令复核见 `AUDIT.md` §BE 详录 #56 第 2 节。**


### 4.2 HUD 文字永远画在 UI 图元之前
`Gui__on_draw` 注册在优先级 `0x31`，最早能画的 UI 层图元是 `0x3c`（层 24）⇒
**我们的块只会压在 HUD 文字上面，永远不会被它压住**。所以每块 UI 的占位**不许**越过 `x = 1040`
（右列读数与卡组图标行在 `x ≥ 1056`）。这条是硬约束，不是审美。

### 4.3 与「符卡名/奖励行」的关系
原版那行在 640 空间 `(224, 200)` 起、表面 `(448, 400)` 起；绀珠传面板（640 空间 192..352 × 201..337）
本来就压着它（AUDIT §AI 已经写明「做不到让文字垫在面板下」）。**中左面板类**保持现状，
但要登记进 §5 的表里，别和左下角带的块抢地方。

### 4.4 什么时候重排（replay 与手感）
- **认领集合按 card_id 排序** ⇒ 同样的卡组永远得到同样的排布（replay 安全、读档安全）；
- **重排只发生在「安全时刻」**：关卡开场（`on_load` 那一批）/ 商店关店后。游玩中卡片被删（倒吊人、
  原版空白卡）**不当场重排** —— 保留占位，避免整摞 UI 突然跳动；**下关开场自然收敛**。
  ✅ **落地（2026-09-12）**：卡侧一律调 `ce_hud_slot_claim_card()`（不是裸 `ce_hud_slot_claim()`）——
  它在认领前把 `CE_CURRENT_STAGE()` 推进「关卡纪元」，**关卡号一变就先清空再认领** ⇒ 上一关的占位
  （含被删卡留下的）在本关开场收敛，而同一关内一笔都不重排。
  ⚠ 别拿 `on_run_reset`（虚表 `+0x4c`）当关卡信号：它由 `recount 0x4080e0` 调，**局中删卡后也会跑**。
- 认领是**幂等**的：`on_load` 每关都会再调一次（`notify_cards_on_load` 不是「开局一次」），
  重复认领必须返回同一个槽。

### 4.5 淡出与自机
原作三个系统（TH16 季节槽、TH13 灵界槽、TH17 咆哮槽）都做了「玩家贴近左下角就淡出」+ 迟滞
（`th16:0x427f41`：`x < −64 && y > 400` 淡出；`th16:0x427f6c`：`y < 384 || x > −64` 淡回；
TH13 是同一套触发区，见 `engine/spirit/th13/01` §8）。**整摞一起淡**（共用
`ce_hud_player_near_corner()`），别各淡各的。
