# HUD-LAYOUT —— 左下角系统卡 UI 的全局槽位分配（研究 + 方案）

> **版本**：TH18 v1.00a（`th18.exe`，imagebase `0x400000`）。本文裸地址默认属该版本；引用其他版本须写成 `th16:0x…`。
> **缘起（用户 2026-09-10）**：要加一堆**系统卡**（复刻原作整块系统的那种）。原作里这些系统的 UI 都在**左下角**
> （TH16 季节槽、TH15 章节面板…），但多张卡不能都堆在左下角 ⇒ 需要**全局**的「我这块 UI 相对左下角偏移多少」。
> 后续 UI 基本不会超出季节指示的范畴，也**都写在同一层**（不需要往别层铺）。
> **结论**：见 §0；实测坐标见 §1；算法 §2；API 草案 §3；约束 §4；迁移 §5。

## 0. 一句话结论

**锚点固定、块自己报尺寸、全局按「货架」算法从左往右再往上摆**：

- 锚点 = **左下角内缩**：表面坐标 `(257, 924)`（= 640×480 空间的 `(128.5, 462)`；两张现有系统卡独立推出的同一条线）；
- 每张卡声明「我的块多大」（`w × h`，表面 px）与「优先左下还是右下」；
- 分配器把块**沿底部从锚点向右排**（间隙 8 px），排不下就**整体上抬一行**（行高 = 该行最高块 + 8）；
- 分配**只依赖卡 id 排序**（不看注册顺序、不看时间）⇒ 完全确定性、replay 安全、跨关不跳；
- 卡被删（倒吊人 / 原版空白卡）时释放，但**在本关内保留占位**（不重排 = 不跳），下关开场重算。

按这个算法，现有两张卡立刻不再重叠（季节 104 宽 + 动物灵 193 宽，同一行放得下），
底边那一行（y 876..924，高 48）还能再放约 2–3 张，再往上还有第 2、3 行。

## 1. 坐标与占用（实测）

### 1.1 两套坐标空间（必须同时给出）

| 空间 | 谁在用 | 换算 |
| --- | --- | --- |
| **表面 px**（= 2× 空间）| UI 列表的 VM：`ce_anm_spawn_ui` + `ce_anm_set_pos` | 我们的 HUD VM 常量都按它写（`resolutionMode(2)`）|
| **640×480 字面量空间** | `ce_hud_text*`（ASCII）、`ce_hud_vm_text_*`、`ce_hud_number_*` | 内部 × `DAT_0056aca0`（分辨率倍率）换成表面 px；640×480 下是 **×2** |

⇒ 分配器**一次返回两套坐标**（`x/y` 表面 + `x640/y640`），卡不用自己换算、也就不会换算错。
（先例：AUDIT §AF7 / AC6；季节卡的数字就踩过这个坑 —— 框按 2× 写、数字按 640 写。）

### 1.2 锚点为什么是 (257, 924)

两张已落地的系统卡**各自独立**推到了同一组数：

| 卡 | 常量 | 名义框 | 实际像素 |
| --- | --- | --- | --- |
| 季节 119 | `SEASON_GAUGE_BX 308 / BY 916`，`k_season_frame[]` 四条边 (dx,dy) | `BX ± 51 = 257..359` | 外沿 **x 263..365 / y 910..920**（调坐标时整体 +6.5 x，所以比名义框右 6 px）|
| 动物灵 115 | `ANIMAL_HUD_X0 281 / Y 900`，5 格 48×48、间距 36 | 首格左 257、底 924 | **x 257..449 / y 876..924**（与名义一致）|

⇒ 两张卡**独立**把「左下角原点」推到了同一条线：**左 257**（季节卡名义框 257、动物灵首格 257）、
**底 924**（游玩区底边 928 再上 4 px）。把它固化进 SDK 常量（`CE_HUD_ANCHOR_X / CE_HUD_ANCHOR_Y`）即可，
不需要新的一手反汇编。⚠️ 但**名义框 ≠ 实际像素**：季节卡调坐标时外沿被推到了 263（+6）——
所以分配器只发**锚点**，块内部怎么摆仍归卡自己；报块宽高时按**实际像素**报（季节 104、动物灵 193）。

### 1.3 原版在这块地方有什么（⇒ 左下角其实是空的）

一手：`zGui__on_draw` `0x43cd00` 的字面量坐标表（AUDIT §AI）+ HUD 图标排版（AUDIT §X5）。**全部右对齐在右列**：

| 原版元素 | 640×480 空间 | 表面 px | 备注 |
| --- | --- | --- | --- |
| 总分 / 最高分 | `(620, 42)` / `(620, 64)` 右对齐 | `(1240, 84)` / `(1240, 128)` | font 10 group 3 |
| 残机·炸弹行 | `(569, 120)` scale 0.6 | `(1138, 240)` | `%3d` `/%d` |
| 符卡计时 | `(224, 144)`+`(268, 150)` | `(448, 288)`+`(536, 300)` | 随符卡 VM 染色 |
| 火力 | `(540..606, 182..189)` | `(1080..1212, 364..378)` | |
| 金钱 | `(620, 204)` 右对齐 | `(1240, 408)` | `CE_HUD_MONEY_COLOR` |
| **卡组图标 3 行** | 根 `(528, 268.5)`，x 步进 40；**行 y = 268.5 / 333.5 / 398.5** | 根 `(1056, 537)`，行 y = 537 / 667 / 797 | 40×40 图标，AUDIT §X5 |
| 符卡名/奖励行 | `(224, 200)` 起 | `(448, 400)` 起 | 与绀珠传面板同高（面板压在它上面，见 §4.3）|

⇒ **表面 px 的 x < 1000、y > 850 这一块（除了我们自己的卡）原版什么都不画** ✓
—— 原作之所以把系统槽放这里，正是因为这地方空着、又紧贴游玩区左下角、离自机与弹幕中心远。

### 1.4 现有卡各自占了多大（块尺寸）

| 卡 | 块（表面 px，实测）| 尺寸 | 现状 |
| --- | --- | --- | --- |
| 季节 119 | 框 x 263..365 / y 910..920；季节字 32×32 @ (280, 904)；等级条 @ (328, 908) ⇒ **整块 x 263..365，y 888..920** | **104 × 36** | 与动物灵**横向重叠 100 px**（两张都把左端锚在 257 附近）|
| 动物灵 115 | 5 格 48×48，中心 x = 281+36i（i=0..4），y = 900 ⇒ **x 257..449，y 876..924** | **193 × 48** | 同上 |
| 绀珠传 118 | 640 空间 x 192..352，y 201..337 | 320 × 272（表面）| **中左**，不在左下角带内（不参与本分配器）|
| 股市 80 | 640 空间 428..628 × 22..78 + 右列读数 | — | **右上 + 右列**，不参与 |

⇒ 需要全局分配的只有「左下角带」里的系统卡；中左（面板类）与右列（读数类）各自有自然位置，
但**也应登记进同一张表**（见 §5），免得以后又撞上。

## 2. 排布算法：底部货架（shelf packing）

```
输入：所有「已认领」的块，按 card_id 升序（⇒ 与注册顺序/时间无关）
常量：ANCHOR_X 257, ANCHOR_Y 924, GAP 8, X_MAX 1000（右边界，避开卡组图标行的 1056）

cursor_x = ANCHOR_X; row_bottom = ANCHOR_Y; row_h = 0
for blk in blocks:                      # 同一侧（side）分别算
    if cursor_x + blk.w > X_MAX:        # 这一行放不下 → 上抬一行
        row_bottom -= row_h + GAP
        cursor_x = ANCHOR_X
        row_h = 0
    blk.anchor = (cursor_x, row_bottom) # 「块左下角」
    cursor_x += blk.w + GAP
    row_h = max(row_h, blk.h)
```

**演算**（现有 2 张 + 假设 3 张未来卡）：

| 顺序 | 卡 | w×h | 结果锚点（块左下角）| 占位 |
| --- | --- | --- | --- | --- |
| 1 | 季节 119 | 104×36 | (257, 924) | x 257..361（内部元素自己 +6，落在 263..365）|
| 2 | 动物灵 115 | 193×48 | (369, 924) | x 369..562 |
| 3 | 假设：灵界 116 | 150×40 | (570, 924) | x 570..720 |
| 4 | 假设：信仰 117 | 150×40 | (728, 924) | x 728..878 |
| 5 | 假设：信号 121 | 180×44 | (886, 924)→放不下 ⇒ 上抬 | 行 2：底边 `924−48−8 = 868`，锚点 (257, 868) |

⇒ 底边一行（高 48）能放 **4 张**，把 `X_MAX` 放宽到 1040 还能再塞一张；
再往上每行都是「上一行最高 + 8」，第 2 行底边 868、第 3 行 812……
**每张卡自己决定 h**（h = 它的最高元素到最低元素，例如季节卡的圆环/字挂得比框高，就报 36 而不是 10）。

## 3. API 草案（`sdk.c` / `sdk.h`，与 §17 的 `ce_hud_slot_*` 对齐）

```c
/* 声明块尺寸（表面 px）与优先侧；h 进行高，w 进横向游标 */
typedef struct { float w, h; int side; } ce_hud_block_t;   /* side: 0 = 左下（默认），1 = 右下 */

typedef struct {
    float x, y;         /* 表面 px：块**左下角** —— 直接喂 ce_anm_set_pos（UI VM）*/
    float x640, y640;   /* 640×480 空间：同样的点，直接喂 ce_hud_vm_text_* / ce_hud_number_* */
    float w, h;         /* 回显声明值，卡自己按它算内部布局 */
} ce_hud_slot_t;

/* 认领（幂等：同一张卡重复调只返回同一个槽）。首次认领会触发一次重排（见 §4.4）*/
int  ce_hud_slot_claim(uint32_t card_id, const ce_hud_block_t *blk, ce_hud_slot_t *out);
/* 释放（on_delete / on_run_reset 里调；本关内占位保留，下关开场重算）*/
void ce_hud_slot_release(uint32_t card_id);

/* 统一「玩家贴近左下角 → 整摞一起淡出」（TH16 的季节槽触发区 + 迟滞）*/
int  ce_hud_player_near_corner(void);      /* x < −64 && y > 400；恢复 y < 384 || x > −64 */
```

**卡里的用法**（季节卡改造后长这样）：

```c
static ce_hud_slot_t s_slot;                      /* 或放卡状态里 */

static int on_load(ce_card_t *c) {
    ce_hud_block_t blk = { .w = 108.0f, .h = 36.0f, .side = 0 };
    if (!ce_hud_slot_claim(CE_CARD_ID(c), &blk, &s_slot)) return 0;
    /* 框：块左下角起算 */
    ce_anm_set_pos(vm, s_slot.x + 51.0f, s_slot.y - 5.0f, 0.0f);
    /* 数字：640 空间，同一个点 */
    ce_hud_vm_text_set(&s_digit, s_slot.x640 + 25.5f, s_slot.y640 - 2.5f, ...);
    return 0;
}
```

## 4. 约束（写进 API 的注释与 SDK 文档）

### 4.1 层与模糊
整摞 UI 都放 **UI 列表层 25**（`AnmManager__render_layer` `0x4882b8` 折到 38 ⇒ 与暂停模糊罩
`text.anm` script59 同一个绘制桩，罩子后起 = 盖在上面）；层 24（折到 37，优先级 `0x3c`）同样在罩子之前，
现有季节卡就是这么用的。**不要**往世界层（3–19）写 —— 那些层永远全分辨率、且过相机 3 的视口。

### 4.2 HUD 文字永远画在 UI 图元之前
`Gui__on_draw` 注册在优先级 `0x31`，最早能画的 UI 层图元是 `0x3c`（层 24）⇒
**我们的块只会压在 HUD 文字上面，永远不会被它压住**。所以每块 UI 的占位**不许**越过 `x = 1040`
（右列读数与卡组图标行在 `x ≥ 1056`）。这条是硬约束，不是审美。

### 4.3 与「符卡名/奖励行」的关系
原版那行在 640 空间 `(224, 200)` 起、表面 `(448, 400)` 起；绀珠传面板（640 空间 192..352 × 201..337）
本来就压着它（AUDIT §AI 已经写明「做不到让文字垫在面板下」）。**中左面板类**保持现状，
但要登记进 §5 的表里，别和左下角带的块抢地方。

### 4.4 什么时候重排（replay 与手感）
- **认领集合按 card_id 排序** ⇒ 同样的卡组永远得到同样的排布（replay 安全、读档安全）；
- **重排只发生在「安全时刻」**：关卡开场（`on_load` 那一批）/ 商店关店后。游玩中卡片被删（倒吊人、
  原版空白卡）**不当场重排** —— 保留占位，避免整摞 UI 突然跳动；下关开场自然收敛。
- 认领是**幂等**的：`on_load` 每关都会再调一次（`notify_cards_on_load` 不是「开局一次」），
  重复认领必须返回同一个槽。

### 4.5 淡出与自机
原作三个系统（TH16 季节槽、TH13 灵界槽、TH17 咆哮槽）都做了「玩家贴近左下角就淡出」+ 迟滞
（`th16:0x427f41`：`x < −64 && y > 400` 淡出；`th16:0x427f6c`：`y < 384 || x > −64` 淡回；
TH13 是同一套触发区，见 `engine/spirit/th13/01` §8）。**整摞一起淡**（共用
`ce_hud_player_near_corner()`），别各淡各的。

## 5. 迁移清单

| 卡 | 现状 | 改动 |
| --- | --- | --- |
| 季节 119 | 常量写死 `BX/BY` + 数字另算 640 坐标 | `on_load` 认领 `104×36` 的块，框/字/条/数字全部由槽锚点推导（消除两套坐标；顺带把那 +6.5 的偏移并进块内）|
| 动物灵 115 | 常量写死 `X0/Y` | 认领 `193×48`；`hud_ensure` 里 5 格的 x 从槽锚点 + `36i` 推 |
| 绀珠传 118 | 中左面板（不重叠）| 登记进表（`side = 2`「中左」或自带锚点），暂不改坐标 |
| 股市 80 | 右上 + 右列 | 同上（自带锚点），只登记 |
| 未来系统卡 | — | 一律 `ce_hud_slot_claim()`，块尺寸按「最高元素到最低元素」报，别省 h |

## 6. 待量 / 未定（❓/🟡）

1. 🟡 **`h` 的取法**：块高按「视觉最高元素」报是我定的口径（季节卡圆环 + 字比框高 26 px）。
   等第二张卡落地后回头统一一次 —— 建议 SDK 里给个 `CE_HUD_BLOCK_PAD`（上下各留 4 px）省得各卡各报。
2. ❓ **右下角那侧的锚点**：`side = 1` 的镜像锚点（表面 `x = 1040`？）没有先例卡验证过；
   按 §4.2 的硬约束，右边只能用到底边这一行（往上会撞卡组图标行 3 行）。
3. 🟡 **`X_MAX` 取 1000 还是 1040**：卡组图标行在 1056 起（40×40），留 16 px 余量是我拍的，
   实跑看一眼再定。
4. ❓ **超过 3 行怎么办**：底边 + 上面两行一共能放 ~10 张。真要更多，只能放宽到「中左面板列」
   （640 空间 x 192..352），那是另一套排布，先不做。
5. 🟡 **暂停菜单/对话时的显示**：层 25 的 VM 在对话时照画（绀珠传面板就带淡出）。整摞是否要
   跟绀珠传一样「玩家贴近就淡」，靠 §4.5 的统一谓词解决，但**多块同时淡**的观感要实跑确认。
