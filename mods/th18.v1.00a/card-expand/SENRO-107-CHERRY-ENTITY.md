## 2. 一手事实（决定了实现形状）

### 2.1 TH07 侧：樱点是**引擎道具实体**，三档 + 一个死代码

| 档 | TH07 type | 值 | 来源（一手） |
| --- | --- | --- | --- |
| ★ | 6 | 樱点 / +C 各 **+20** | 每只死敌 1 颗（`th07:0x423144`）、每颗被消的弹 1 颗（`th07:0x4247c9`） |
| 大樱点 | 7 | **1000 + 100×符卡奖励次数** | **满火力（≥128）时 P 类道具（type 0/2）在 `spawn_item` 顶部被改写成 7**（`th07:0x432724`–`0x432730`） |
| 小樱点 | 8 | +100（+30 双加 / +70 只加樱点） | `th07:0x424740(mode ≥ 3)`，唯一入口 = boss 死亡那颗 `mode 0xa`（`th07:0x420131`） |
| （樱点） | 9 | +100 | **无生成点（死代码）** |

- **ECL 掉不出樱点**：三个掉落 opcode（119 / 124 / 154）的立即数里一个都没有（19,919 条指令全扫）⇒ 三档全是引擎侧产物。
- **运动学**（§7）：主路 = 恒定 **−2.2 竖直下落**（水平速度 0）｜进吸附档 ⇒ `fsincos` 朝自机**恒速直飞**
  （速度 = 那个对象的 `+0x14` 磁速）｜`pos += vel × 1.0`｜下边界 `ds:0x62f870 + 16.0` 出界删除。
- **收取**：`th07:0x43e4e0(PLAYER, item.pos, cfg)`，`cfg = {[0x575948]+0x18, 同, 64.0f}`，内部 `scale = 1/2.0`。

### 2.2 TH18 侧：吸附/收集参数都在**自机字段**（用户口径 2 的落点）

| 量 | TH18 出处 | 一手 |
| --- | --- | --- |
| 磁力吸附速度 | `player+0x47988` | `th18:0x445f63` 写 `item+0xc80`；环吸 = 该值 ÷3（`0x44663b`–`0x446651`） |
| 收集半径 | `player+0x4798c` | `faith.c` 头注「运动学」 |
| 吸引半径（x / y） | `player+0x47990` / `+0x47994` | 同上（另有 70 px 的「环吸」档，`faith_core.h` §state 4） |
| 回收线（PoC） | `player+0x47998` | 同上 |
| 吸引加速步长 / 上限 | `0.2`（`th18:0x4b90f0`）/ `12.0`（`th18:0x4b927c`） | 同上 |

⇒ **107 的实体照这一套走，不照 TH07 的磁速/半径。**

### 2.3 我们已有的先例（不许再写第二遍）

- **110（TH10 / 风神录）已经有一套自建 VM 点实体池**：`native/cards/faith.c` 的 `faith_dot_t`
  （state 0 待发射 / 1 飘落 / 2 飞散 / 3 过回收线飞向自机 / 4 吸引半径内飞向自机），
  **运动学、吸附、收集判定都是 TH18 口径**，池是**共享的**（`faith_register()` 注册，按 `slot_mask` 分流。
  111 就是第二个消费者）。
- **满 P 转换通道已经存在**：`faith_convert_full_p_items()`（`native/cards/faith.c`）——满 P 时逐帧扫道具池，
  **删掉每颗 P 类道具**，再给**每个 `conv_value > 0` 的注册者**在该原位撒一颗点。
  ⇒ 「同装时同时转化出来」（口径 3 前半）**就是给这条通道再加一个消费者**，不是新写一条扫描。
- TH18 的 P 类 = **type 1（小 P）+ type 3（大 P）**（`faith_core_is_p_item_type()`）。

## 3. 设计（口径 3 的落法）

### 3.1 实体从哪来

| 来源 | 档 | 谁触发 |
| --- | --- | --- |
| 死敌 | ★ | 107 的 `on_enemy_death`（每只 1 颗，TH07 §3.2 同形） |
| 消弹 / 灵击 | ★（TH07 原版）｜本卡现有口径见 §5 未定项 2 | 107 的 `on_cancel`（`ce_cancel_radius()` 返回值） |
| **满 P 转换** | **大樱点** | **加入共享通道**（`faith_convert_full_p_items()` 的消费者）；与 110 / 111 的产物**同一帧、同一颗源道具** |

### 3.2 「吸附半径统一到 TH18」

107 的实体**直接用共享点池的运动学**（= 读 `player+0x47988/8c/90/94/98`），不再自算半径。
具体走法见 §4 阶段 2 的复用判决（复用 vs 复制，取决于 `kind` 扩展的成本，见 §5 未定项 1）。

### 3.3 「大樱点 ≡ P 点」（口径 3 后半）

- 满 P 通道**删掉**了那颗原生 P 道具（这是 110/111 现成的行为）。TH07 的对应物是「P 道具**变成**大樱点」
  ⇒ 我们的大樱点**就是那颗 P 道具的后继**，所以对**其它卡的 P 逻辑**它必须等价于一颗 P 道具：
  - 玩家**收掉我们的大樱点时**，要按「收到一颗 P 道具（TH18 type 1）」**通告共享层**，
    让 110 的火力层（`mof.c` 的 `s_p_item` 那一层）与 111 的 P 相关账**照常发生** —— 否则 107 等于把它们的那份吃掉了。
  - 实现形状：SDK 侧一个「**合成一次道具收集事件**」的入口（用栈上假 item 跑既有 `on_item_collect` 派发链），
    107 在收掉大樱点时调它；**这不改原生道具池、不改引擎**。
- 反向不成立：**原生 P 道具不会因为场上有大樱点而少转化**（通道只认道具池）。

## 5. 未定项 / 风险（动手前必须落地一条）

1. **复用 vs 复制**：共享点池复用（改 110 的共享件，AUDIT §BE 登记）还是 107 自己写一层（照抄同一套运动学，~150 行）。
   倾向**复用**（`faith.c` 头注自己就写着「实体层共用一个池，写一遍」），代价是动共享件的 `kind`。
2. **★ 的档位归属**：TH07 的 ★（+20）是**每颗被消的弹**都给；本卡现在把「灵击消弹」记成 TH07 **小樱点**（+100/+30）。
   改成实体后**是否保持本卡现有口径**（灵击 → 小樱点档）还是改回 TH07（消弹 → ★）—— 需要用户拍一下（影响手感与分值）。
3. **`[0x575948]+0x18` 与 `ds:0x62f870` 的值**未查（TH07 侧），但我们**不照抄 TH07 半径** ⇒ 只影响 §7 的完备性，不挡实现。
4. **107 的 slot 号**：`faith.h` 现在只有 `FAITH_SLOT_110` / `_111`，要加 `FAITH_SLOT_107`（`FAITH_MAX_USERS 8`，有位置）。
