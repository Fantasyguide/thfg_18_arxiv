## A. ABI / 栈平衡

> checklist 里最易错、历史上唯一出过真 BLOCKER 的一节。

**整节 N/A —— mod 不调用任何引擎函数。**

`RET imm` vs `RET`、caller/callee 清栈这一整类问题。

- [x] 调用的每个引擎函数的 `ret` 出口 —— **N/A**，零个引擎调用。
- [x] 调用约定 —— **N/A**，同上。
- [x] 交叉验引擎自己怎么调 —— **N/A**。
- [x] 多余的 `add esp` —— **N/A**。
- [x] 被调函数破坏哪些寄存器 —— **N/A**（但跳板 `call` 我们自己的 C 函数，见 §B）。

## B. 手写机器码：跳板

唯一的手写机器码。**CONFIRMED**，逐条由 `check.py` 的 capstone 反汇编支撑——
不是复述注释，是把 `hook.c` 里实际写入的字节抠出来交给反汇编器。

反汇编结果（`fn` 是占位标记）：

```
push rcx / push rdx / push r8 / push r9 / push r10 / push r11
sub  rsp, 0x28
movabs rax, <mouse_tick>
call rax
add  rsp, 0x28
pop  r11 / pop r10 / pop r9 / pop r8 / pop rdx / pop rcx
mov  rax, rsp          <- 以下 13 字节是从 0x140068820 原样搬来的
push rdi
push r12
sub  rsp, 0xd8
jmp  qword ptr [rip]   <- 后跟 8 字节绝对地址 = 0x14006882d
```

### B.1 栈对齐 —— CONFIRMED

x64 ABI：`call` **之前** `rsp` 必须 16 字节对齐（于是被调方入口处 `rsp ≡ 8`）。

| 步骤 | `rsp mod 16` |
| --- | --- |
| 进入跳板（被 patch 的 `call` 刚压了返回地址） | 8 |
| 6 × `push`（48 字节） | 8 |
| `sub rsp,0x28`（40 字节） | **0** ✅ |
| `call` 压 8 字节 → `mouse_tick` 入口 | 8 ✅ |

`0x28 = 40 ≥ 32`，shadow space 够 ✅。`push`/`pop` 逐个配平、顺序严格逆序、
`sub`/`add` 同值，净栈位移 0 —— 四条都由 `check.py` 断言。

### B.2 寄存器 —— CONFIRMED

- **非易失**（RBX/RBP/RDI/RSI/R12–R15、XMM6–15）：跳板一个都不碰。
- **易失**（RCX/RDX/R8/R9/R10/R11）：全部保存恢复。
- **RAX 刻意不保存**：搬来的原序言第一条就是 `MOV RAX,RSP`，会把它重设成正确值。
  正因如此，返回跳转用 `jmp qword ptr [rip+0]` 而**不是** `mov rax,imm; jmp rax`——
  后者会覆盖刚刚建立的 RAX。`check.py` 把这条钉住了。
- **XMM0–5 不保存**：`Player__OnUpdate` 只有一个指针参数（`this` 在 RCX），
  没有浮点参数，入口处 XMM0–5 是 scratch。

> **对抗性追问**：`mouse_tick` 自己会不会破坏非易失寄存器？
> 不会——它是编译器生成的 C 函数，编译器负责按 ABI 保存它用到的非易失寄存器。
> 我们只需要保证**跳板**不破坏，以及调用现场合法。

### B.3 被覆盖的 13 字节 —— CONFIRMED

两件事必须成立，否则搬走就崩：

1. **是完整指令，不能从中间劈开**。capstone 解出 4 条指令，字节数合计正好 13 ✅。
2. **位置无关**。`check.py` 遍历这 4 条的 capstone 详情，检查
   `CS_GRP_JUMP` / `CS_GRP_CALL` / `CS_GRP_BRANCH_RELATIVE` 与
   `X86_OP_MEM.base == RIP`，一个都没有 ✅。

### B.4 入口补丁 —— CONFIRMED

`memset(patch, 0x90)` 打底后填 12 字节，反汇编 = `movabs rax,<stub>` / `jmp rax` / `nop`，
长度正好 13，**不多写一字节**到相邻函数 ✅。

### B.5 第二段手写机器码：`__CxxFrameHandler4` 转发 thunk

换投递点带来的唯一新增机器码。**CONFIRMED**，由 `check.py` §F 反汇编核对：

```
ff 25 b2 fa 01 00    jmp qword ptr [rip + 0x1fab2]    -> .data 的函数指针槽
```

四条性质，逐条机器验证：

| 性质 | 为什么要紧 |
| --- | --- |
| 单条 6 字节 `jmp`，不建栈帧 | unwinder 建立的调用现场必须原样传给真身；C 包装函数会插进自己的栈帧 |
| 不碰任何寄存器 | 同上。`jmp [rip+d]` 是唯一不需要暂存器的间接跳转形式 |
| 目标槽在 `.data`（可写） | 运行时才填真身地址 |
| 槽的静态初值为 0 | **不硬编码任何系统 DLL 地址**——换 Windows 版本也不会跳错 |

**NULL 风险已处理**：`DllMain` 取不到真身就返回 `FALSE`，进程在启动期以
`0xc0000142` 失败。这是刻意的——比留一个 NULL 槽、等到某次异常展开时才崩要好得多，
因为那种崩溃现场完全无从追查。

> **对抗性追问**：`DllMain` 里调 `LoadLibrary` 不是被明令劝阻吗？
> 是。风险是加载器锁重入死锁。这里可接受：进程初始化期只有一个线程，
> 加载器锁是临界区（同线程可重入），且 `VCRUNTIME140_1.dll` 是叶子 DLL、
> 依赖已全部加载完毕。所有 DLL 代理都这么做。**仍未实机验证**，见 §E。

## C. 写入点与内存安全

- [x] `expected` 原字节逐字节核对 —— **CONFIRMED**。`check.py` 从真样本
      （MD5 校验过）读 `0x140068820` 的 13 字节，与 `th06nc.h` 的
      `k_expected_prologue` 逐字节相同。运行时 `mouse_install()` 也做同样比对，
      不匹配则 `g_disabled = 1` **永久停用**、不写任何字节。
- [x] 相对 / 绝对表达式 —— **CONFIRMED**。跳板与入口补丁全用 **绝对** 8 字节地址
      （`movabs` / `jmp [rip+0]` 后跟的 imm64），没有任何 rel32，
      因此不依赖跳板被分配到哪里。这正是选 `movabs` 而非 `jmp rel32` 的原因：
      `VirtualAlloc` 给的地址与 exe 的距离可能超过 ±2GB。
- [x] 目标是否落在只读节 —— **CONFIRMED**。`.text` 是只读可执行；
      `VirtualProtect` 改成 `PAGE_EXECUTE_READWRITE`，写完**改回原属性**，
      再 `FlushInstructionCache`。
- [x] 被重指的槽在零售流程中不被用到 —— **N/A**，没有重指任何指针槽。
- [x] 每个结构偏移能回指 `engine/` 一手文档 —— **CONFIRMED**，见
      [`TARGET.md`](TARGET.md) §5；`check.py` 把每个偏移与
      `th06nc_player_spec.py` / `symbols.json` 逐条对账，对不上就失败。
      > 这一条**抓到过一个真问题**：`OFF_CHAR_DATA +0x7860` 原本注释写着
      > 「§2.5 / §2.7」，但那两节根本没写过速度字段——即偏移**没有一手依据**。
      > 回二进制查证后确认了它（以及另外三个速度字段），补进
      > [`engine/player/th06nc/01`](../../../engine/player/th06nc/01-main-loop-and-collision.md) §2.10
      > 和 `th06nc_player_spec.py`。
- [x] 池 / 数组算式 —— **N/A**，不索引任何池。
- [x] 复用引擎对象时对象大小够不够 —— **N/A**，不分配、不复用任何引擎对象。
- [x] 每帧写的量、时序 —— **CONFIRMED**。写在 `Player__OnUpdate` 入口，
      即玩家移动代码读输入位之前的同一帧，时序天然正确，不需要挑优先级。
- [x] 空指针路径 —— **CONFIRMED**。`g_Player` 是**静态全局对象**（不是指针），

- [x] 释放后使用 —— **N/A**，不释放任何东西。

### C.1 一个真实存在的风险：`Player__OnUpdate` 会在对象初始化前跑吗

**REFUTED（不会）**。它是 chain 回调，注册发生在玩家对象构造之后
（`Player__AddedCallback` 里写 `+0x774c` 等字段）。且即使真跑到了，
`playerState` 分支会让我们跳过坐标读取（见下）。

### C.2 出生 / 死亡期间不接管

`playerState == 1 (SPAWNING)` 或 `2 (DEAD)` 时跳过方向合成。
依据：[`engine/player/th06nc/01`](../../../engine/player/th06nc/01-main-loop-and-collision.md) §2.9
——引擎自己在擦弹判定前查的就是 `!= 1 && != 2`。

## D. 量纲 / 常识关

- [x] 「字段 == 常量」的判断查过真实取值分布吗 —— **CONFIRMED**。
      `playerState` 的 `1 / 2` 不是猜的：值域来自 NC 二进制里
      `MOV byte ptr [RDI+0x7898],0x3` 这类写入与引擎自己的比较，
      且与 TH06 的 `ALIVE/SPAWNING/DEAD/INVULNERABLE = 0/1/2/3` 逐值相同。
      > 这一条正是本仓踩过坑的地方：早前把 `+0x773c` 当成 `playerState`，
      > 因为它被写成 **8**——不是合法枚举值。教训见 `player/01` §2.9 的告警框。
- [x] 数值量级合理吗 —— **CONFIRMED**。速度表读出灵梦 4.0 / 2.0、魔理沙 5.0 / 2.5，
      低速正好是常速一半，与 TH06 逐值相同；斜向 `4/√2 ≈ 2.83`。
      关卡区 384×448 在 640×480 虚拟屏里，比例合理。
- [x] 与游戏内可观察行为冲突时先怀疑自己 —— 见 §E，**尚无可观察行为可比对**。

### D.1 一个已知的、可接受的不精确

死区取的是**正交**速度，但斜向移动时真实步长是 `正交/√2`（更小）。
即斜向时死区偏大约 41%。方向是**保守**的：宁可少走一步，也不会在光标附近震荡。
知道了 `+0x7868/+0x786c` 之后这个可以改准，但**不改**——
改了要重新审计，而当前行为没有正确性问题，只有手感问题，
留给实机验证之后一起处理。

### D.2 另一处已知的、可接受的不精确：`isFocused` 慢一帧

我们在 `Player__OnUpdate` **入口**读 `+0x785c`，但那个字段是同一个函数**稍后**
（`th06nc:0x14006912c`）才根据本帧输入写的。所以死区取的是**上一帧**的低速状态。

按下/松开 Shift 的那一帧，死区会用错一档速度；下一帧自动纠正。
中键映射的低速更明显一点——它是在方向算完之后才 OR 进 `INPUT_HELD` 的。

**不改**，理由同 D.1：这是手感层面的一帧误差，不是正确性问题；
现有实现已过审计，末尾塞一个未审计的改动比留一条已知记录更糟。
真要改的话，正确做法是直接读 `*held & 0x04`（本帧输入），
顺带还能少依赖一个结构体偏移。

### E.1 为什么没实跑

开发机是 **Linux**，没有 TH06NC 的运行环境。DLL 是用 clang 交叉编译出来的
（`--target=x86_64-pc-windows-msvc`），产物经 PE 头核验为
`PE32+ DLL x86-64, machine=0x8664, imagebase=0x180000000`，导出 4 个函数——
**但这只证明它编译对了、格式对了，不证明它能跑。**

静态审计通过 ≠ 能跑。首次上机前请按 [`README.md`](README.md) 的验收表逐条看。

### E.1.5 ❌ 第一次实测：`xinput1_4.dll` 投递失败（2026-09-10）

用户在 Windows 上把 `xinput1_4.dll` 放进游戏目录启动，**我们的日志与游戏自带的
`./log.txt` 都是空的**。

诊断：`mouse_install()` 是 `DLL_PROCESS_ATTACH` 里第一件事，且日志有 `%TEMP%` 兜底——
**没有日志 = DllMain 从没跑过 = DLL 从没被加载**。往里加日志不可能有输出。

回二进制查证后定位到原因：XInput 的加载点 `th06nc:0x1400ab7f4` 上方有个闸门
`th06nc:0x1400ab7b4 JNZ`，前置初始化未成功即整段跳过。
详见 [`TARGET.md`](TARGET.md) §3。

**REFUTED 的一条旧结论**：`TARGET.md` 原先写「NC 会加载 XInput，所以代理成立」——
前半句对（字符串与加载点都在），**后半句错**：会引用 ≠ 一定执行到。
教训与 `player/01` §3 同类：**控制流可达性必须单独验，不能从「代码存在」推出**。

已改投 `VCRUNTIME140_1.dll`（静态导入，加载器必须加载）。

### E.1.6 ✅ 第二次实测：`VCRUNTIME140_1.dll` 投递成功（2026-09-10）

hook 装上、鼠标控制生效。同时暴露一个**真实的坐标错误**：
自机稳定落在光标**右侧约 200px**。

排查（没有靠猜）：

1. 先验坐标系本身。`Player__AddedCallback` 的出生坐标是硬编码
   `th06nc:0x14006822e` 写 `192.0` / `384.0`，与 CC0 `Player.cpp:98-100` 的
   `arcadeRegionSize.x/2` 与 `.y-64` 逐值相同 → **`positionCenter` 的坐标系与 TH06 一致，
   这一侧没错**（[`player/01`](../../../engine/player/th06nc/01-main-loop-and-collision.md) §2.11）。
2. 于是错的只可能是「光标屏幕位置 → 该坐标系」的映射，即关卡区在窗口里的原点与缩放。
3. 找 NC 的 `arcadeRegionTopLeftPos` —— **没找到**，写入方是整块 `memcpy`，
   地址不以 RIP 相对形式出现（全 `.text` 暴力扫过，只有读没有写）。

**结论：不猜。** 改成两点实测标定求解仿射映射，把这个未知量从代码里彻底移除。
这比「凑一个 200 的偏移」更可信 —— 后者在换分辨率/宽高比时必然再错，
而且我们并不知道误差是纯平移还是含缩放。

> 顺带删掉了一处硬编码：可动区不再写死 `384×448`，改成每帧读
> `th06nc:0x1404ff0e0` —— 就是 `Player__OnUpdate` 自己钳位用的那四个 f32。

### E.1.7 ✅ 布局已实测解出（2026-09-10）

两个分辨率各做一次角标定，拟合出 NC 的屏幕布局并烤成默认值，**标定不再必需**。
**CONFIRMED**，三重独立验证：

1. `s = 客户区高/480` 在两组上都精确命中（1.5000 / 2.2500）。
2. 用右下角（点得更准的那个）反推左边界，两个分辨率给出虚拟 `235.33` / `235.11`
   —— 一致，且与「水平居中」的 `234.67` 相符。
3. 该模型**预测**旧代码在 1920×1080 下自机偏右 216px ——
   与用户最初报告的「约 200px」吻合。

根因：**TH06 关卡区左边界固定 `x=32`（右侧留 HUD），NC 改成居中了。**

> 🟡 这是**拟合结果**，不是从二进制读出的常量。`arcadeRegionTopLeftPos` 在 NC 里
> 找不到（很可能由 D3D 视口完成定位）。两组样本都是 16:9，非 16:9 未验证。
> `check.py` §G 把两组实测点钉成回归样本（模型误差 ≤7px，旧模型 211px）。
